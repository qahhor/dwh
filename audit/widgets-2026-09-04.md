# SmartupCMS UI quality audit — 2026-09-04

## Executive summary

**Score after remediation: 88/100. Release status for the UI: conditional.**

The 14 routed screens and 11 shared UI components are visually consistent in
light and dark themes. Desktop navigation, semantic surfaces, form labels,
empty states, dialog naming and focus containment are generally sound. The
release-facing defects found in this audit were remediated: administrator
search now uses the backend contract and recovers after request errors, the
audited 390 px layouts keep horizontal scrolling local to dense regions, the
login wordmark is no longer clipped, and the undersized role/shell controls
meet the local 28 px target. No dark content islands were found in the light
theme, and no white content islands were found in the dark theme.

Release status remains conditional because the newly added cross-route browser
regression specification has been type-checked but was not executed in this
local pass. The running Docker application was instead verified directly in
the approved Codex in-app browser at 1440×900 and 390×844. W-05 and W-07 remain
explicit non-blocking quality debt.

Browser evidence was collected from the running Docker application at
`http://localhost:4200` with authenticated administrator data at 1440×900 and
390×844. All observations below are tied to current source or runtime evidence;
no unverified product behavior is presented as fact.

## Findings

### W-01 — Global search is unavailable and never recovers (P1, M) — **Fixed**

- **Observation:** entering `Тест` opens a request, then the palette remains on
  `Поиск...`. The request returned HTTP 403 and the browser logged an error.
- **Risk:** a primary top-bar control is dead for the seeded administrator; the
  RxJS stream also terminates after the first error, so later queries cannot
  recover without recreating the component.
- **Evidence:**
  - `apps/web/src/app/layout/command-palette/command-palette.component.ts:290`
    starts the stream; the subscription at line 301 has no error recovery.
  - `apps/web/src/app/core/services/command-palette.service.ts:23` sends
    `entity_type`, while
    `apps/server/src/main/java/com/greenwhite/dwh/instance/search/controller/SearchController.java:26`
    accepts `entity`.
  - `apps/server/src/main/java/com/greenwhite/dwh/instance/search/service/SearchService.java:62`
    requires a literal `*.*` permission.
  - `apps/server/src/main/resources/db/migration/V003__rbac_role_matrix.sql:27`
    grants the admin every catalog pair rather than `*.*`; lines 45–79 grant
    `platform.search.view` to manager and user roles even though unrestricted
    search rejects them.
- **Recommendation:** keep unrestricted results admin-only until scoped search
  exists, authorize that role explicitly on the server, align the `entity`
  parameter, and convert request failures into a retryable inline state without
  terminating the query stream.
- **Acceptance:** administrator query returns a result or a named empty state;
  403/5xx shows a retryable alert; a second query after an error still runs.
- **Resolution evidence:**
  - `apps/web/src/app/core/services/command-palette.service.ts` now sends
    `entity`; `command-palette.component.ts` catches each request failure and
    exposes a live-region alert with retry.
  - `apps/server/src/main/java/com/greenwhite/dwh/instance/common/security/RoleMembershipAuthorizer.java`
    authorizes persisted active administrator membership without creating a
    `search → md` module dependency.
  - `SearchServiceTest` covers deny/legacy-wildcard/admin-role paths;
    command-palette unit tests cover contract and recovery after an error.
  - Live Docker/browser query returned `Administrator`; Maven verification
    passed 210 tests with no failures.

### W-02 — Important mobile content is clipped (P1, M) — **Fixed**

- **Observation:** at 390×844 the Tasks `Новая задача` button, Analytics
  `Обновить` button, Users toolbar, Tasks create form, Users create form and
  Profile cards extend past the visible content area. Page-level horizontal
  scrollbars are visible.
- **Risk:** primary actions and form values are partially inaccessible on the
  supported mobile width.
- **Evidence:**
  - `apps/web/src/app/layout/app-shell/app-shell.component.ts:647` enables
    page-level `overflow-x: auto` on mobile, contrary to the design-system rule
    that only tables may scroll internally.
  - `apps/web/src/app/features/tasks/tasks.component.ts:1376` and line 1438
    define non-wrapping action/filter rows; lines 2072–2074 keep create-form
    grids at two and three columns without a mobile override.
  - `apps/web/src/app/features/analytics/analytics.component.ts:371` defines a
    non-wrapping header action row.
  - `apps/web/src/app/features/iam/users/users.component.ts:726` and line 1001
    define a non-wrapping toolbar and two-column dialog grid.
  - `apps/web/src/app/features/iam/profile/profile.component.ts:434` changes the
    grid to plain `1fr` at line 444 but does not zero the min-content width of
    cards.
  - `.superdesign/design-system.md:76` requires no horizontal clipping at the
    390 px viewport.
- **Recommendation:** keep tables and tab strips as local scroll regions, make
  page headers/toolbars wrap, collapse dialog form grids to one column, set
  grid tracks/cards to `minmax(0, 1fr)` / `min-width: 0`, and disable global
  page horizontal scrolling after the descendants are fixed.
- **Acceptance:** at 390×844 every primary action and form field is fully
  visible; `#main-content.scrollWidth === #main-content.clientWidth`; table
  wrappers remain horizontally scrollable.
- **Resolution evidence:** responsive rules were corrected in App Shell,
  Tasks, Analytics, Users, Profile and the shared Modal. Direct browser
  measurements at 390×844 showed equal page/client widths on the rechecked
  Tasks/Analytics/Users surfaces and one-column task and user modal grids;
  Profile's final session-action wrap is covered by the production build and
  the new browser assertion. Dense status tabs and tables retain local
  scrolling.

### W-03 — Login branding is visibly broken (P1, S) — **Fixed**

- **Observation:** the text `SmartupCMS` is rendered inside a 44 px square and
  appears as a clipped fragment.
- **Risk:** the first unauthenticated screen looks unfinished and undermines
  product trust.
- **Evidence:** `apps/web/src/app/features/auth/login/login.component.ts:19`
  renders the full wordmark; the same file at lines 262–273 fixes its container
  to `44px × 44px`.
- **Recommendation:** use the existing shell lockup pattern: the square contains
  `S`, and a separate visible wordmark identifies `SmartupCMS`.
- **Acceptance:** no clipped text at 390 or 1440 px; the lockup has one
  accessible product name.
- **Resolution evidence:** `login.component.ts` now renders `S` in the 44 px
  mark and `SmartupCMS` as a separate wordmark. Component coverage asserts the
  accessible product label and separate visible nodes; both browser viewports
  fit the lockup.

### W-04 — Several high-frequency controls are below 24 px (P2, S) — **Fixed**

- **Observation:** locale buttons render at 21 px height; role edit buttons at
  18 px; role matrix text actions range from 13 to 22 px.
- **Risk:** keyboard focus remains visible, but pointer and touch accuracy is
  unnecessarily poor, especially in the permissions matrix.
- **Evidence:**
  - `apps/web/src/app/layout/app-shell/app-shell.component.ts:480` uses only
    `4px 8px` padding with no minimum height.
  - `apps/web/src/app/features/iam/roles/roles.component.ts:608`, line 757,
    line 774 and line 833 define the undersized edit, expand/collapse, module
    and batch controls.
- **Recommendation:** preserve visual density while applying a 24–28 px minimum
  target and transparent hit padding.
- **Acceptance:** every visible `button`, link-like button and tab has at least
  a 24×24 CSS-pixel target or an explicitly documented adjacent-target
  exception.
- **Resolution evidence:** App Shell locale buttons and the audited Roles
  matrix/edit controls now use a 28 px minimum height. Browser measurements at
  390 px confirmed 28 px for edit, link, module and batch controls.

### W-05 — Async quality states are inconsistent (P2, M)

- **Observation:** Announcements and System have explicit loading, error, retry
  and empty states. Tasks, Projects, Users, Files, Audit and Custom Fields
  mostly suppress their empty state while loading and fall back to transient
  toasts on request errors. Notifications has an empty state but no explicit
  loading/error recovery.
- **Risk:** slow or failed requests can look like stale content, and recovery is
  less discoverable than on the newer screens.
- **Evidence:**
  - strong state handling:
    `apps/web/src/app/features/announcements/announcements.component.ts:87` and
    `apps/web/src/app/features/system/system.component.ts:45`;
  - empty-only table handling:
    `apps/web/src/app/features/tasks/tasks.component.ts:342`,
    `apps/web/src/app/features/tasks/projects/projects.component.ts:210`,
    `apps/web/src/app/features/iam/users/users.component.ts:301`,
    `apps/web/src/app/features/files/files.component.ts:280`,
    `apps/web/src/app/features/audit/audit.component.ts:227` and
    `apps/web/src/app/features/iam/custom-fields/custom-fields.component.ts:104`.
- **Recommendation:** after P1 fixes, copy the existing System/Announcements
  state pattern into data-heavy pages incrementally; do not introduce a new
  state framework in this release pass.
- **Acceptance:** each initial data load exposes loading, actionable error,
  empty and success states without stale data ambiguity.

### W-06 — Browser regression coverage misses the failed surfaces (P2, M) — **Partially fixed**

- **Observation:** 27 web test files / 71 tests pass, but unit output contains
  two CDK focusability warnings from Announcements. Browser smoke omits
  Analytics and Profile, mobile overflow is asserted only for System and
  Announcements, and no global-search browser test exists.
- **Risk:** current tests pass while login branding, search failure and mobile
  clipping remain visible.
- **Evidence:**
  - route list: `e2e/tests/browser/instance/auth.spec.ts:38`;
  - mobile checks: `e2e/tests/browser/system/system.spec.ts:44` and
    `e2e/tests/browser/announcements/announcements.spec.ts:11`;
  - command-palette unit coverage:
    `apps/web/src/app/layout/command-palette/command-palette.component.spec.ts:1`.
- **Recommendation:** add focused regression tests for the three P1 findings,
  extend smoke to Analytics/Profile, and make unit output warning-free.
- **Acceptance:** tests fail against the current implementation, pass after the
  fixes, and the web suite finishes without stderr warnings.
- **Resolution evidence:**
  `e2e/tests/browser/instance/ui-release-regressions.spec.ts` now covers the
  login lockup, global-search request/result state, mobile Tasks/Analytics/
  Users/Profile overflow and modal grids, and Roles target sizes. The spec
  passes TypeScript validation; execution remains pending in the configured
  browser CI because this local pass was restricted to the Codex in-app
  browser. The two pre-existing Announcements focus warnings still keep this
  finding open.

### W-07 — Page components are too large for safe iterative UI work (P2, L)

- **Observation:** templates, styles and behavior are colocated in very large
  files: Tasks 3,136 lines, Users 1,579, Roles 1,354, Audit 1,123, Projects
  1,000 and Files 941.
- **Risk:** small visual changes have a wide regression surface, and state/style
  duplication is difficult to review.
- **Evidence:** source line counts under `apps/web/src/app/features` on
  2026-09-04.
- **Recommendation:** do not rewrite the frontend. Extract only a touched,
  independently testable block when a future feature requires changing it;
  keep the current route and API boundaries.
- **Acceptance:** no release gate; track component size and duplicated CSS as a
  maintainability metric.

## Duplication and design-system gaps

| Pattern | Current duplication | Minimal direction |
|---|---|---|
| Page headers and action rows | Feature-local `view-header` / `header-right` CSS | Normalize responsive behavior first; extract only after two confirmed consumers need the same behavior |
| Table states | Six local empty-state implementations | Reuse the visual language, but keep route-specific recovery copy |
| Form grids | Tasks and Users define separate fixed two-column grids | Apply the same 720 px collapse contract from the design system |
| Permission-matrix actions | Four undersized button styles | One local target-size rule inside Roles |
| Async state panels | Strong in System/Announcements, absent elsewhere | Copy the proven pattern incrementally |

No new palette, spacing scale, typography system or component library is
recommended. The canonical semantic tokens in `apps/web/src/styles.css` are
being used correctly in the rendered light/dark surfaces.
