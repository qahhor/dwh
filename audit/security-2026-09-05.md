## S-01. Экспорт задач без области данных

**High / P0 / S–M (2–4 дня вместе с тестами экспорта), риск изменения medium. OWASP A01:2025; CWE-862/863.**

Наблюдение: [ReportController:21](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/report/controller/ReportController.java:21) требует только `@RequiresPermission(form = "tasks.items", action = "view")`. Пользователь не передаётся в сервис. Оба запроса в [ReportService:45](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/report/service/ReportService.java:45) и [ReportService:124](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/report/service/ReportService.java:124) читают `from ms_tasks t ... order by t.id desc` без scope predicate. [Interceptor:46](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/kauth/security/RequiresPermissionInterceptor.java:46) проверяет permission, не строки данных.

Сценарий: вошедший пользователь с `tasks.items:view` и SELF/UNITS scope обращается к `/api/v1/reports/tasks/export`; в выгрузку входят задачи, недоступные его обычному task API. Это внутроорганизационная утечка; межустановочный доступ не доказан.

Минимальный шаг: передавать actor ID и использовать [MdScopeService.filterForTasks](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/md/service/MdScopeService.java:154) в общем scoped export query для CSV/XML. Не дублировать вручную правила. До готовности можно явно запретить export scoped roles, сохранив доступ только unrestricted admin.

Приёмка: две несвязанные группы/пользователя и уникальные маркеры задач; обе выгрузки SELF/UNITS/SUBTREE не содержат чужих IDs, текста и имён. ALL видит разрешённое множество; обычный список и export согласованы. Добавить audit факта экспорта без содержимого.

Дополнительный **P1 / CWE-1236**: [escapeCsv:161](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/report/service/ReportService.java:161) экранирует разделители, но не formula prefixes. Пользовательский title, начинающийся с `=`, `+`, `-`, `@` или управляющих символов, должен экспортироваться как текст. Не утверждается выполнение кода на любой версии Excel; нужен тест безопасного импорта в поддерживаемый spreadsheet client.

## S-02. Приложение работает с привилегированной DB-ролью

**High / P0 / M (3–5 дней), change risk high. OWASP A01/A02:2025; CWE-250.**

В [production Compose:8](D:/Claude/dwh/deploy/compose/docker-compose.prod.yml:8) server/migrate получают `DB_USER`; в [строке 65](D:/Claude/dwh/deploy/compose/docker-compose.prod.yml:65) тот же `DB_USER` становится `POSTGRES_USER`. Разделён только backup user. Read-only проверка локальной БД дала `dwh: rolsuper=t, rolcreatedb=t, rolcreaterole=t`. Production DB не опрашивалась: вывод о её конфигурационном риске основан на Compose, не на удалённом psql.

Риск: получив возможность исполнять SQL от server, атакующий не ограничен бизнес-таблицами. [Audit immutability V014](D:/Claude/dwh/apps/server/src/main/resources/db/migration/V014__audit_log_immutable.sql) защищена триггерами UPDATE/DELETE, но superuser может менять DDL/триггеры и выполнять TRUNCATE. Это не обнаруженная SQL injection, а чрезмерный blast radius.

Минимальная миграция: новые отдельные credentials для bootstrap/migrate/runtime/backup; runtime — NOSUPERUSER/NOCREATEDB/NOCREATEROLE, не owner схемы, grant только необходимого DML/sequence usage. Перенести audit partition DDL в operator job либо строго ограниченную privileged функцию с фиксированным search_path и validated identifiers. Учесть startup bootstrap/form catalogue и Flyway validation reads; простая замена имени роли без grants сломает запуск.

Приёмка: clean install, upgrade и bootstrap проходят; от runtime запрещены schema DDL, TRUNCATE audit, отключение триггеров, изменение чужих ролей. Partition runway и backup read-only tests зелёные. Rollback — заранее проверенная предыдущая app/grants конфигурация, не возврат superuser как постоянное решение.

## S-03. Trusted-proxy boundary и исчерпание bucket map

**High / P0 / M (2–4 дня вместе с mixed-auth тестом), change risk medium. OWASP A02/A07/A10:2025; CWE-346/770.**

[RateLimitFilter.clientIp](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/config/security/RateLimitFilter.java) читает `forwarded.split(",")[0].trim()`; [web NGINX:44](D:/Claude/dwh/apps/web/nginx.conf:44) использует `$proxy_add_x_forwarded_for`. В самом runtime нет allow-list доверенных proxy для этого чтения. Поэтому при отсутствии внешней очистки входящего заголовка клиент управляет ключом anonymous IP bucket. Фактическая Cloudflare policy неизвестна: наличие Cloudflare само по себе не доказательство очистки XFF.

[RateLimitService](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/config/security/RateLimitService.java): `CLEANUP_THRESHOLD=50_000` — не maximum size. Выше порога каждый запрос обходит map через `removeIf`, а недавно созданные записи не удаляются 10 минут. Смена недоверенного IP одновременно обходит лимит и увеличивает CPU/memory cost.

Минимум: один canonical client IP resolver для login/audit/limiter, список trusted proxy hops, очистка заголовка на первом доверенном edge; не доверять CF headers от прямого клиента. Нормализовать IPv4/IPv6. Hard bound/cache expiry + scheduled/amortized cleanup; edge rate-limit до дорогой аутентификации. Для single-server не нужен Redis.

Приёмка: поддельные XFF/CF headers, несколько hops, direct request и валидный proxy; IP не подменяется, лимит выдаёт 429 и корректный Retry-After. Bounded adversarial-key test не увеличивает размер за configured maximum.

Смежный **P1**: [SecurityConfig.isCsrfExempt](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/config/security/SecurityConfig.java) освобождает любой `Authorization: Bearer ...`, но [KauthAuthenticationFilter:77](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/kauth/security/KauthAuthenticationFilter.java:77) при невалидном Bearer пробует cookie. Проверить `invalid Bearer + valid cookie + no CSRF`: mutation должна отклоняться. Это подтверждённая несогласованность классификации auth; полноценный cross-origin exploit не доказан, custom header обычно требует preflight.

## S-04. Generic idempotency сохраняет исходные секреты

**High / P0 / M (часть I-04), change risk medium. OWASP A04/A06:2025; CWE-312.**

[IdempotencyFilter:44](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/config/idempotency/IdempotencyFilter.java:44) применяется ко всем mutating requests с ключом. [Строки 110–112](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/config/idempotency/IdempotencyFilter.java:110) передают весь успешный response body в `complete`; [IdempotencyRepository:63](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/config/idempotency/IdempotencyRepository.java:63) пишет `response_body::jsonb`. [KauthApiTokenService:32](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/kauth/service/KauthApiTokenService.java:32) возвращает `CreatedTokenResult(record, rawToken)`; [DTO:59](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/kauth/service/KauthApiTokenService.java:59) содержит `rawSecretToken`.

Сценарий: легальный token creation POST с Idempotency-Key кладёт открытый токен в `idempotency_keys`, хотя kauth token table хранит hash. Это противоречит FR-AUTH-03. Фактическое наличие таких записей у клиента не проверялось: секретные строки БД не читались и токены для проверки не создавались.

Минимум: allow-list конкретных business mutations, exclude token/password/OTP/login/webhook-secret endpoints и multipart. Не «маскировать поле, но продолжать выдавать неполный replay» без контракта клиента. Проверить другие secret-bearing responses. Если реальные старые записи содержат credentials — отдельная утверждённая очистка/rotation и оценка копий backups, не автоматический массовый delete.

Приёмка: negative integration tests проверяют DB и response cache после credential endpoint, не печатая значение токена; разрешённая task mutation по-прежнему replay-safe. Crash/TTL и body limits описаны в архитектурном/performance отчётах.

## S-05. Остаточная безопасность webhook

**Medium / P1 при включённых webhooks / S–M; change risk medium. OWASP A01/A04:2025; CWE-918/319.**

[WebhookTargetPolicy:43](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/kwh/service/WebhookTargetPolicy.java:43) разрешает и `http`, и `https`, хотя [NFR-SEC-06](D:/Claude/dwh/docs/technical-specification.md) требует HTTPS. DNS проверяется через `InetAddress`, затем [KwhOutboxWorker](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/kwh/worker/KwhOutboxWorker.java) передаёт URI HTTP-клиенту, который соединяется самостоятельно. Проверка DNS отдельно от соединения не доказывает отсутствие TOCTOU/rebinding.

Положительные контроли: default disabled, exact host allow-list, запрет private ranges по умолчанию, redirects NEVER, connect/read timeouts, HMAC и delivery ID. Не утверждается воспроизведённый обход SSRF. Минимум: enforce HTTPS для managed/public profile; validated connection/egress proxy или сетевой deny private destinations; негативный тест реального connection path, не только resolver mock. Smtp/Telegram provider errors и [MsOutboxWorker](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/ms/notify/worker/MsOutboxWorker.java) `e.getMessage()` подвергать redaction до журналов/last_error.

**ISO/IEC 27001: соответствие не подтверждено.** [ISO/IEC 27001:2022](https://www.iso.org/standard/27001) относится к системе управления информационной безопасностью, а не только к безопасности исходников. Threat model и PII inventory в репозитории существуют — требовать написать их с нуля неверно. Но не предоставлены утверждённая область ISMS, Statement of Applicability, formal risk treatment/acceptance, регулярные access reviews, supplier assessments, training evidence, internal audit/management review и подтверждения исполнения incident/retention procedures. Такие документы могут существовать вне Git: «не предоставлено», а не «в организации отсутствует».

Минимальная release работа: заполнить installation annex (владелец данных, регионы, сроки, роли, DSAR/delete/hold, off-host keys), подтвердить восстановление и on-call. Роль продукта в правовой схеме, договоры и обязательность сертификата уточнить с ответственным за безопасность/право. Сертификацию оценивать отдельным проектом только при подтверждённой бизнес-необходимости. Процент «ISO compliance» не рассчитывался.
