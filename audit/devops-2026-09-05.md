## D-01. Pre-migration backup пропускается после удаления контейнера

**P0 / M (2–3 дня внутри I-05), change risk medium.**

[deploy.ps1:29](D:/Claude/dwh/scripts/prod/deploy.ps1:29) и [deploy.sh:29](D:/Claude/dwh/scripts/prod/deploy.sh:29) проверяют `ps -a -q postgres`; если строка пуста — `treating this as an initial deployment`. Но `docker compose down` без `--volumes` сохраняет данные. Следующий deploy может применить новые миграции к существующей БД без резервной копии. Статически подтверждённый сценарий; на постоянной БД не воспроизводился.

Минимум: resolve exact project/volume names и persistent DB state, отдельно различать empty install и retained data; неизвестное состояние блокирует deploy. Поднять существующую БД на совместимом прежнем digest для backup до применения новой версии. Не менять PostgreSQL major image до backup/upgrade plan. Добавить отдельный явный и проверяемый fresh-install mode, а не эвристику «нет контейнера».

Приёмка: disposable populated DB → down без volumes → deploy новой schema; backup присутствует и восстановим до migrate. Negative scenarios: backup failure, volume inaccessible, inconsistent config, migration failure, readiness failure. [Текущий test-deploy-fail-closed](D:/Claude/dwh/scripts/prod/test-deploy-fail-closed.sh) проверяет failed backup при fake existing container; retained-volume case отсутствует в этом тесте.

## D-02. DB/object backup consistency и безопасный rollback

**P0 / M (3–5 дней внутри I-05), change risk high.**

[Managed acceptance guide:171](D:/Claude/dwh/docs/ops/managed-infrastructure-acceptance.md:171) предлагает DB backup, затем отдельный object archive. [backup-objects:86](D:/Claude/dwh/scripts/prod/backup-objects.ps1:86) перечисляет и копирует storage, проверяет размер/hash, но не связывает capture с DB snapshot или запретом mutation. Между DB dump и копированием можно удалить последний physical object: DB snapshot будет ссылаться на уже отсутствующий файл. Новый объект в обратном окне создаёт orphan относительно snapshot.

[restore-combined:164](D:/Claude/dwh/scripts/prod/restore-combined.ps1:164) обнаруживает mismatch множества ключей, что хорошо: плохой backup не объявляется согласованным автоматически. Но эта проверка не создаёт согласованную копию. Скрипт получает DB size/hash в inventory, а сверка ключей сама по себе не сравнивает все значения DB size/hash с manifest; последующие sample downloads проверяют manifest→bytes. Следует добавить полную metadata→manifest проверку и отдельный тест одинакового key с неверным DB hash/size.

Минимум для первого релиза: короткое операторское окно без записей (закрыть ingress mutations, дождаться uploads/outboxes и остановить writers), затем парная DB/object capture с единым capture ID и timestamp. Альтернатива для больших объёмов — content-addressed snapshot manifest + доказанный retention/versioning; не предполагать наличие S3-versioning в R2. Вводить автоматизацию только после проверки RPO/RTO.

Бэкап всех objects также включает transient/quarantine keys, если они остались в bucket. Нужен явный список committed DB keys и безопасная политика GC/retention; не удалять неизвестные objects автоматически. `backup-objects` делает full capture, поэтому его время, temp disk и storage cost зависят от всего накопленного объёма, не только месячного ingress.

Rollback: [runbook](D:/Claude/dwh/docs/ops/rollback.md) уже правильно различает совместимый app rollback и restore данных. Не рекомендовать автоматический downgrade БД после каждой неудачной readiness. Deploy не сохраняет verified previous digest как durable release state и не исполняет recovery decision tree. Сначала сохранить previous/current digests, schema compatibility и backup capture ID; app-only rollback разрешать лишь при проверенной совместимости, иначе closed traffic + controlled restore. Если заданы `SERVER_IMAGE/WEB_IMAGE` digest overrides, простая смена APP_VERSION не заменит их — обновить runbook согласованно.

Приёмка: isolated restore с exact capture; все DB keys/size/hash совпадают, sample downloads доступны приложению; forced failure сохраняет исходные данные и закрытый ingress. Измеренные RPO/RTO и key custodians утверждены. Copy/checksum успех без restore не является DR.

## D-03. Release gate не связан с полной проверкой выпускаемых образов

**P0 / M (3–5 дней I-06), change risk medium.**

[release.yml:15](D:/Claude/dwh/.github/workflows/release.yml:15) verify запускает Maven, frontend и config contracts; [build:78](D:/Claude/dwh/.github/workflows/release.yml:78) зависит только от verify. E2E и Trivy/Gitleaks security jobs находятся в другом workflow [ci.yml](D:/Claude/dwh/.github/workflows/ci.yml), successful conclusion которого release graph не проверяет. Проверка `git merge-base --is-ancestor` означает reachable от default branch, не наличие зелёного CI именно для tag SHA. Remote branch protection не проверена.

Кроме того [Dockerfile:33](D:/Claude/dwh/Dockerfile:33), [web Dockerfile](D:/Claude/dwh/apps/web/Dockerfile) и DB wrapper выполняют apt/apk upgrade: даже pinned base при rebuild может дать иной resolved runtime. Подпись устанавливает происхождение, не отсутствие уязвимостей; test dev images не заменяет scan окончательного digest.

Минимум: единый reusable verify workflow или explicit required checks/tag SHA, затем build → scan всех exact image digests/architectures → release-topology E2E → attest/sign/publish verified bundle. Имеющийся [runtime scanner:9](D:/Claude/dwh/scripts/security/scan-runtime-images.ps1:9) перечисляет 5 images без обязательного ClamAV; включить scanner в production SBOM/scan inventory. CI `ignore-unfixed:true` оставляет unfixed vulnerabilities за пределами blocking gate: полный отчёт и ограниченные formal exceptions обязательны.

Target deployment также должен fail closed на непроверенных digest/signature/provenance. [deploy.ps1](D:/Claude/dwh/scripts/prod/deploy.ps1) сам не вызывает published verifier; операторский manual step должен быть enforced wrapper/gate, а не обещанием. Compose error message про «immutable tag» не делает registry tag неизменяемым — использовать digest overrides из проверенного bundle.

Приёмка: deliberately failing E2E/scan/checksum/identity → publish и deploy запрещены; verified evidence связан с конкретным SHA и каждым deployed digest. Не требуется bit-for-bit rebuild при разных package repository snapshots, если неизменяемый опубликованный artifact сам проверен; это отдельные свойства воспроизводимости и provenance.

Сопутствующее: full-history gitleaks fixture S-07 требует точного исключения. Последние пять commits не имеют Signed-off-by, хотя [CONTRIBUTING](D:/Claude/dwh/CONTRIBUTING.md) требует DCO, а [dco.yml:4](D:/Claude/dwh/.github/workflows/dco.yml:4) запускается только на PR. Не делать подписи за автора и не переписывать опубликованную историю без его участия; владелец определяет remediation/prospective policy. Проверить branch/tag permissions отдельно.

## D-04. Resource limits, observability и target acceptance

**P0 для production acceptance, P1 для реализации / M–L (6–10 дней I-09), change risk medium.**

Наблюдение: production Compose не задаёт CPU/memory/PID limits; `RESOURCE_PROFILE=S` передаётся приложению как metadata, а не cgroup policy. [Dockerfile:61](D:/Claude/dwh/Dockerfile:61) использует `MaxRAMPercentage=75`; без container memory limit бюджет считается от доступной JVM памяти, а не отдельной установки. Это особенно важно при размещении нескольких installations на host. Development `-Xmx1024m` в [docker-compose.yml:4](D:/Claude/dwh/docker-compose.yml:4) не доказывает production cap.

Минимум: measured S profile/override с memory/CPU/PID/tmpfs quotas и headroom для native+scanner+DB; validate Compose config и реальные cgroup values. Не выбирать VM/RAM по 100 пользователям без request mix и file/scanner tests. Базовая поддерживаемая single-host модель допускает outage host; документировать RPO/RTO и объём затронутых colocated установок.

Наблюдаемость: [application.yml](D:/Claude/dwh/apps/server/src/main/resources/application.yml) включает management metrics/Prometheus; [TraceparentFilter](D:/Claude/dwh/apps/server/src/main/java/com/greenwhite/dwh/instance/config/web/TraceparentFilter.java), scanner и S3 timers существуют. Logging pattern добавляет MDC к тексту; это не доказательство JSON logs и не полноценный distributed trace exporter. В production Compose не поставляются collector/dashboard/alert transport. [ТЗ NFR-OBS-02/AC-12](D:/Claude/dwh/docs/technical-specification.md:230) требует operator setup, не встроенный observability cluster.

Минимум: подключить существующую инфраструктуру оператора к внутреннему endpoint, dashboard error/latency/saturation/backup/search/outbox/temp, тестовый alert→on-call ack и log redaction. Не публиковать management наружу. Backup SUCCESS и CURRENT различаются: default freshness `0s` намеренно NOT_CONFIGURED, это не дефект UI; нужно утверждённое значение.

Приёмка: target edge origin lockdown/validated TLS; R2 private roundtrip; scanner EICAR/outage; DB outage; backup failure; 100-user distributed profile + near-limit uploads + 4h soak; combined restore. Scripts [acceptance](D:/Claude/dwh/scripts/acceptance) есть, но target evidence отсутствует в просмотренном наборе. **Нельзя закрыть эти gates только наличием scripts.**

Резервные копии: [backup-loop:103](D:/Claude/dwh/deploy/images/backup/backup-loop.sh:103) удаляет локальные archives по retention; remote bucket lifecycle должен быть отдельно утверждён и проверен. Backups на одном host не защищают от его потери; нужны off-host destination и age identity вне хоста. Не менять retention/удалять данные без operator policy.
