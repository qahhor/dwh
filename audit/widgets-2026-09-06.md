## 1. Executive summary

Экспертная оценка функциональной UX-зрелости модуля: **6/10**. Это не
сертификация a11y и не измеренная продуктовая метрика.

Визуальный фундамент пригоден: светлые поверхности, читаемые статусы,
именованные действия, два представления, связанный фильтр задач. Однако
надёжность редактирования и состояния отказа отстают от исправленного Tasks.

Три главных проблемы:

1. Фильтр не сбрасывает страницу: результат найден, но не отображается.
2. Закрытие теряет черновик; сохранение не изолировано от повторного открытия
   и редактирования формы; editor использует устаревшую строку списка.
3. Ошибки списка и статистики не имеют устойчивого состояния восстановления;
   отсутствующая статистика выдаётся за ноль.

Выявлено 11 пунктов: 8 P1 и 3 P2. P0 и обход серверных прав этим аудитом не
подтверждены. Сохраняем существующий дизайн; новый модуль, микросервис или
библиотека не нужны.

### W-P01 — Фильтрация оставляет недоступную текущую страницу — P1

- **Доказательство:** [Projects:79](D:/Claude/dwh/apps/web/src/app/features/tasks/projects/projects.component.ts:79),

  Пример: `(ngModelChange)="currentPage = 1"`.
- **Приёмка:** 21 запись → страница 2 → поиск одной записи / архив → страница 1,
  нужная запись видна в list и cards; архивирование последней записи страницы.
- **Усилия:** S. **Риск изменения:** Low. Low-risk предложение: W-P01.patch.

## 5. Design system gaps

Полная новая DS не нужна. Tokens, modal, button, pagination уже есть.
Нужны небольшие правила для editor request ownership, dirty dismissal,
unknown/error stats и минимальной hit area icon actions. Сначала локально
применить существующие контракты; общий компонент выделять только при
подтверждённом повторении, а не ради рефакторинга.

## 8. Стратегические рекомендации и неизвестные

Не добавлять Storybook/Chromatic/Percy/новый UI kit в этот пакет: Angular tests,
Playwright и axe dependency уже доступны. Сначала добавить недостающие
behavioral regressions, а не инфраструктуру ради инфраструктуры.

Неизвестные, которые не следует решать скрытым расширением scope:

- Должны ли проекты быть общим справочником установки или иметь собственную
  область доступа? Текущие project list/detail не применяют actor scope;
  ADR-0013 явно задаёт task/file scope, но не полный project visibility contract.
  Участие в проекте само по себе не объявлять достаточным для доступа к задаче.
- Должна ли метрика означать закрытые задачи или только успешно выполненные?
  Для минимального пакета предлагается честная подпись существующего terminal count.
- Какое ожидаемое число проектов в одной установке? Без этого нет основания
  обещать масштабирование либо вводить новый cursor API.

Публикация, deploy и изменение клиентских данных этим отчётом не разрешаются.
