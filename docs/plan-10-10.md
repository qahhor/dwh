## Принципы

- Один путь на задачу. Для списка, формы, ошибки, фонового задания — один способ. До финального релиза старый способ удаляется в той же ветке; после релиза публичная форма сначала устаревает (ADR-0023, §5; для API платформы — ADR-0033).
- Сначала забор, потом уборка. Включаем линтер с baseline (текущие нарушения заморожены), затем уменьшаем baseline до нуля. Новые нарушения с первого дня валят сборку.
- Малые PR, одна фича за раз. Массовые миграции — по модулям, ≤ 400 строк смыслового диффа, чтобы ревью было реальным.
- Эталон раньше тиража. Сначала доводим один экран и один модуль до 10/10, потом переводим остальные по нему.
- Измеряем, а не спорим. Каждый критерий приёмки — число или тест; дашборд метрик качества обновляется в CI.
- Совместимость не ломаем молча. До финального релиза установок у клиентов нет (решение владельца продукта 2026-10-01, `AGENTS.md`, §3): переименования конфигурации и API делаются сразу, без алиасов и переходного периода, с записью в CHANGELOG и трейлером `Api-Breaking:`. После финального релиза — механизм ADR-0023 (§5): старая форма отвечает ещё один релиз с заголовками `Deprecation` и `Sunset`.

## Ревью фаз 0–6 (2026-10-03)

Ревью готового состояния фаз 0–6 нашло дефекты и расхождения документов с кодом. Исправления идут в ветках `claude/rf-*` (безопасность, CI и тесты, веб, ключи ошибок и схема API, документация); отметку «исправлено» ставит интегратор после слияния, подробности — в `CHANGELOG.md`.

- Безопасность. Подпись доставки вебхука не покрывает метку времени (`X-Signature-Timestamp`), поэтому повтор доставки нельзя отличить, а каталога событий нет — решено 2026-10-03 исправить сейчас (ADR-0032, §19, В9). `/api/v1/openapi.json` решено отдавать только вошедшим пользователям.
- Опыт разработчика. Профиль `devtools` объявлен без одобренной зависимости — `make dev` без devtools (6.5).
- Ключи ошибок и схема API — отдельная ветка `claude/rf-*`. Пример найденного: код `task_revision_conflict` остался в `ErrorCode`, хотя задачи сохраняются через общий runtime и отвечают `revision_conflict` (ADR-0024, п. 2).
- Документация. План, `CHANGELOG.md` ([Unreleased]), ADR-0023, ADR-0024, ADR-0027, ADR-0028, ADR-0030, ADR-0031, `docs/api/README.md`, runbook и комментарии `.spectral.yaml` описывали алиасы, `Sunset` и переходный период до 2026-12-31, отменённые 2026-10-01; ADR-0032 и ADR-0033 оставались «Предложено»; ADR-0032 ссылался на несуществующие `EntitySqlSafetyTest`, `EntitySqlBoundariesTest`, `EntityApiSnapshotTest` (теперь — отступления Р20, Ч13, З14) и на удалённые `test-create-module.ps1` и `MsProbeContractTest`. Исправлено в ветке `claude/rf-docs`.

| 5.7 | Связи, статусы, действия записи | `EntityCollection` (дочерняя таблица в форме, сохранение в одной транзакции, ошибки по адресу `lines[3].qty`); `EntityWorkflow` (состояния, переходы, право на переход); действия по записи; вкладки и связанные списки в карточке | Эталон «документ со строками и статусами» собран без своего экрана; недопустимый переход → 422 с кодом; e2e «создать → 3 строки → провести → история» |

Гейт 3: ≥ 5 сущностей на модели, новая сущность — ≤ 2 серверных файла и 0 файлов экрана.

### Порядок реализации фазы 5

Единый дизайн пунктов 5.1–5.8 и 6.2 — [ADR-0032](adr/ADR-0032-low-code-platform-v2.md) (статус «Принято», 2026-10-03): типы, пакеты, REST, порядок обработки записи, тест-кит и критерии каждого шага. Исполнители берут шаг из его раздела 15 и не расходятся с ним; изменение решения — правка ADR в той же ветке.

Решения владельца продукта (2026-10-01):

1. Общий CRUD — runtime-эндпоинт `/api/v1/entities/{code}`, а не генерация кода при сборке.
2. Документы со строками и проведением (5.7) идут раньше импорта, отчётов и поиска (5.8).
3. Клиентских установок до финального релиза нет (AGENTS.md): задачи, проекты и пользователи переходят на модель сразу, старые пути и `Legacy*Filters` удаляются без переходного периода, изменение ответов записывается в CHANGELOG.

Порядок: 5.0 → 5.1 → 5.3 → 5.4 (runtime за флагом) → 6.2 (ядро кита; без него runtime не включается) → 5.4 (заметки на runtime, вебхуки, поиск, OpenAPI) → 5.5 → 5.6 → 5.7 → 5.8 → 6.2 (веб-помощники, кит у 100% сущностей); типы полей 5.2 идут параллельно после 5.1. Открытые вопросы дизайна — ADR-0032, раздел 19.

## Общий Definition of Done

- Все обязательные проверки CI зелёные: `mvn verify`, веб-тесты и аудиты, сборка, e2e, линтеры, CodeQL, контракты документации.
- Baseline линтеров и ArchUnit не вырос; новый код без нарушений.
- Покрытие диффа ≥ 80%; на каждое исправление дефекта — тест, который падал до него.
- Новые ключи переводов — в ru, uz и en, семантические по соглашению.
- Миграции — только новые файлы, с заголовком таймаутов; изменение данных помечено `destructive: approved`.
- Контракт API изменён осознанно: openapi-diff зелёный или метка `api-breaking` с записью в CHANGELOG.
- Документация обновлена в том же PR: CHANGELOG, ADR при смене решения, руководство по модулю при смене точки расширения.
- Ревью одним инженером из CODEOWNERS; смысловой дифф ≤ 400 строк или обоснование в описании.
- Коммиты подписаны (`git commit -s`), в истории нет секретов и персональных данных.
- Ломающее изменение API отмечается меткой `api-breaking` в PR или трейлером `Api-Breaking:` в последнем абзаце коммита (ADR-0022, ADR-0023).
