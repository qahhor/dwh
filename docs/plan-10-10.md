## Принципы

- Один путь на задачу. Для списка, формы, ошибки, фонового задания — один способ; старый помечается `@Deprecated` с сроком удаления.
- Сначала забор, потом уборка. Включаем линтер с baseline (текущие нарушения заморожены), затем уменьшаем baseline до нуля. Новые нарушения с первого дня валят сборку.
- Малые PR, одна фича за раз. Массовые миграции — по модулям, ≤ 400 строк смыслового диффа, чтобы ревью было реальным.
- Эталон раньше тиража. Сначала доводим один экран и один модуль до 10/10, потом переводим остальные по нему.
- Измеряем, а не спорим. Каждый критерий приёмки — число или тест; дашборд метрик качества обновляется в CI.
- Совместимость не ломаем молча. Переименования конфига и API — с алиасами на один релиз, заголовком `Sunset` и записью в CHANGELOG.

## Фаза 4 — имена и структура (недели 5–7)

Имя должно сразу говорить, что это и где лежит. Сейчас «dwh» означает и продукт, и хранилище, `fnd` смешивает четыре области, а около 20% ключей переводов — транслит. Все переименования, затрагивающие установки, идут с алиасами на один релиз.

| # | Задача | DoD | Критерии приёмки (ACC) |
|---|---|---|---|
| 4.1 | Развести два значения «dwh» в конфигурации | `smc``.*` / `SMC``_*` для продукта, `warehouse.*` / `WAREHOUSE_*` для хранилища; старые имена читаются как алиасы с предупреждением; `@Validated` везде; отказ старта с дефолтными секретами вне dev | 0 свойств `dwh.*` вне хранилища; справочник переменных генерируется из configuration metadata и сверяется в CI; старт с дефолтным ключом Typesense в prod падает с понятной ошибкой |
| 4.2 | Разделить `fnd` | `platform/jobs` (общая очередь), `warehouse/{datasource,migration,raw,mart}`, единицы — в предметный модуль; SQL в `*Repository` | 0 `jdbc.sql` в классах `*Service` (ArchUnit); очередь заданий не зависит от хранилища |

## Фаза 7 — эксплуатация и безопасность production (фоном, недели 1–10)

Наблюдаемость обещана в ADR-0009 и CODE_STYLE, но не реализована: логи текстовые, трейсинга и метрик SLO нет. Инцидент сегодня не заметят и не расследуют. Фаза идёт параллельно с остальными силами потока «Безопасность и эксплуатация».

| # | Задача | DoD | Критерии приёмки (ACC) |
|---|---|---|---|
| 7.1 | Структурные логи | Spring Boot structured logging (ECS), маскирование секретов, `trace_id`/`span_id`; `X-Client-Code` убран; `traceparent` проверяется по формату | Каждая строка — валидный JSON с `trace_id`; тест подтверждает маскирование password/token |
| 7.2 | Трейсинг OpenTelemetry | micrometer-tracing + OTLP, выключен по умолчанию; комментарий `traceparent` в SQL | В тестовой трассе видна цепочка HTTP → JDBC |

## Общий Definition of Done

- Все обязательные проверки CI зелёные: `mvn verify`, веб-тесты и аудиты, сборка, e2e, линтеры, CodeQL, контракты документации.
- Baseline линтеров и ArchUnit не вырос; новый код без нарушений.
- Покрытие диффа ≥ 80%; на каждое исправление дефекта — тест, который падал до него.
- Новые ключи переводов — в ru, uz и en, семантические по соглашению.
- Миграции — только новые файлы, с заголовком таймаутов; изменение данных помечено `destructive: approved`.
- Контракт API изменён осознанно: openapi-diff зелёный или метка `api-breaking` с записью в CHANGELOG.
- Документация обновлена в том же PR: CHANGELOG, ADR при смене решения, руководство по модулю при смене точки расширения.
- Ревью одним инженером из CODEOWNERS; смысловой дифф ≤ 400 строк или обоснование в описании.
- Коммиты подписаны (`git commit -s`), в истории нет секретов и персональных данных.
- Ломающее изменение API отмечается меткой `api-breaking` в PR или трейлером `Api-Breaking:` в последнем абзаце коммита (ADR-0022, ADR-0023).
