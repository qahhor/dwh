# ТЗ-03: Пользовательские сценарии (flows) Этапа 1

**Версия:** 2.0
**Дата:** 2026-08-27
**Статус:** **Утверждено к реализации (Этап 1)**
**Назначение:** динамика системы — последовательности шагов с ошибочными ветками. Дополняет
статику ТЗ-01 (требования), ТЗ-02 (экраны) и ТЗ-04 (API). Формат каждого шага: *действие → реакция системы*.
Ссылки: `FR-*` — ТЗ-01, экраны — ТЗ-02 разд. 6, инварианты `I-*` — ADR-0006 разд. 3, эндпоинты — ТЗ-04.

**Правило:** сценарий — источник истины для приёмки вехи; расхождение реализации со сценарием —
дефект, а не «интерпретация».

## F-01. Вход с 2FA (OTP через Telegram)

**Актор:** пользователь. **Предусловия:** учётка активна; 2FA включена; Telegram привязан (иначе — F-02).

| # | Действие | Реакция системы |
|---|---|---|
| 1 | Открывает URL экземпляра | Форма входа (логин/email + пароль). Никаких сведений о клиенте до входа, кроме логотипа/названия |
| 2 | Вводит логин + пароль → «Войти» | Проверка Argon2id. Успех → шаг 3. Ошибка → `401 invalid_credentials` («Неверный логин или пароль», без уточнения детали — FR-AUTH-4); запись в `login_attempts` |
| 3 | — | 2FA-шаг: система отправляет OTP в Telegram через notification-очередь (приоритетная), показывает экран ввода кода + кнопку «Отправить повторно» (таймаут 60 с) |
| 4 | Вводит код | Верно и не истёк → сессия создана (cookie `HttpOnly` + CSRF-токен), запись в `sessions` и security-журнал; редирект на «Мои задачи» или запрошенный URL |
| 5 | — | Меню строится из эффективных прав (FR-PERM-9); колокольчик подключается к SSE (`/api/v1/events`) |

**Ошибочные ветки:**
- **E1. 5 неверных паролей подряд:** экспоненциальная задержка, после N — временная блокировка входа (`423 login_locked`); security-событие; сообщение «Попробуйте через X минут». Учётка НЕ блокируется навсегда (защита от DoS на пользователя).
- **E2. Неверный/истёкший OTP (TTL 5 мин):** до 3 попыток на код, затем код аннулируется (`401 otp_invalid`/`otp_expired`); «Отправить повторно» — с лимитом FR-AUTH-5 (не чаще 1/мин, ≤ 5/час); при исчерпании — `423 otp_attempts_exceeded` + security-событие.
- **E3. Telegram недоступен (провайдер упал):** сообщение «Код не доставлен» + автоматический фолбэк на SMS, если канал включён; если нет каналов — инструкция обратиться к админу. Инцидент виден в Dead-Letter очереди (FR-NOTIF-7).
- **E4. Учётка заблокирована (state P):** `401 user_blocked` («Учётная запись заблокирована, обратитесь к администратору») — отдаётся только после успешной проверки пароля, чтобы не раскрывать статус пользователя по логину.

**Точный результат:** живой пользователь входит ≤ 30 с при рабочем Telegram; все 4 ветки дают внятное сообщение и след в security-журнале. Экран: «Вход» (M1/M3).

## F-02. Привязка Telegram-канала

**Актор:** пользователь. **Предусловие:** вошёл (пароль; если 2FA обязательна тенантом, а канала нет — система пускает в ограниченный режим «только привязка канала»).

1. Профиль → «Каналы уведомлений» → «Привязать Telegram» → система генерирует одноразовый код (TTL 10 мин) и deep-link `t.me/<бот>?start=<код>`.
2. Пользователь открывает ссылку, жмёт Start → бот получает код → бекенд сверяет, сохраняет `chat_id` в `user_channels`, шлёт подтверждение и в бот, и в UI (через SSE).
3. UI показывает канал «Telegram ✓», доступна кнопка «Отправить тестовое сообщение».

**Ветки:** код истёк → «Ссылка устарела, сгенерируйте новую»; чужой код (уже использован) → отказ + security-событие; отвязка — из профиля, с подтверждением; если Telegram был единственным каналом 2FA — отказ `409 last_2fa_channel` («Нельзя отключить единственный канал 2FA»).

**Точный результат:** привязка ≤ 3 действий пользователя (результат экрана из ТЗ-02 разд. 6); `chat_id` нигде не виден другим пользователям.

## F-03. Онбординг нового сотрудника клиента

**Актор:** админ тенанта → новый пользователь.

1. Админ: «Пользователи» → «Создать» → ФИО, email, роли (из списка) → «Пригласить».
2. Система: создаёт пользователя (`state: 'A'`, без пароля), назначает роли, материализует права (FR-PERM-6), шлёт приглашение на email — ссылка с кодом (TTL 72 ч).
3. Новичок открывает ссылку → задаёт пароль (политика FR-USR-2 с индикатором) → при обязательной 2FA — сразу F-02 → попадает в систему с меню по своим правам.
4. Админ видит в списке статус «Приглашён» → «Активен» после первого входа.

**Ветки:** email занят → ошибка на поле `409 email_taken`; ссылка истекла → админ жмёт «Отправить повторно» (старый код аннулируется); email не доставлен → видно в логе доставок (FR-NOTIF-3), админ может скопировать ссылку вручную (право `iam.users.invite` — только админ).

**Точный результат:** от «Создать» до работающего сотрудника — без участия нашей поддержки; результат экрана «создание ≤ 60 с» (ТЗ-02 разд. 6) соблюдён.

## F-04. Управление доступом: выдать, проверить, отозвать

**Актор:** админ тенанта.

1. «Роли» → создать роль «Кладовщик» → в матрице прав (дерево форм × действия) отметить нужные → «Сохранить» → права роли записаны, `effective_permissions` пересчитаны для всех носителей (никого нет — мгновенно).
2. «Пользователи» → выбрать 3 сотрудников → массовое действие «Назначить роль» → пересчёт в той же транзакции; `permissions_version`++ (I-P2).
3. У сотрудников ≤ 60 с (кэш по версии) появляются пункты меню и действия; без перелогина.
4. Проверка: экран «Права глазами пользователя» — каждое право с источником («роль Кладовщик» / «личное»).
5. Отзыв: снять роль у одного → его права схлопываются ≤ 60 с; открытая страница при следующем действии получает `403 permission_denied` с понятным сообщением «Доступ изменён администратором» и редиректом.

**Ветка массового пересчёта:** изменение прав роли, назначенной 10 000 пользователям → объём > порога (FR-PERM-7) → пересчёт уходит в фон (`202 Accepted {operation_id}`); UI роли показывает прогресс «Права пересчитываются (N из M)»; до завершения права считаются на лету — пользователи не видят «дыры».
**Ветка защиты:** попытка отредактировать/удалить системную роль (pcode) → отказ `409 system_role_immutable` (I-P4). Снять у самого себя админскую роль → отказ `409 last_admin`, если админ последний.

**Точный результат:** результат PERM из матрицы ТЗ-01 разд. 8.2 (отзыв ≤ 60 с; фон на 10 000) демонстрируется этим сценарием на приёмке M2.

## F-05. Жизненный цикл задачи

**Акторы:** постановщик (менеджер), исполнитель.

1. Менеджер: «Задачи» → «Создать» → заголовок, описание (markdown), проект, исполнитель, срок → «Создать» → задача в статусе `new`; постановщик и исполнитель записаны в `task_members` (I-T1: ответственный ровно один; I-T2: постановщик неизменяем).
2. Система: доменное событие `TaskAssigned` → notify → исполнителю in-app (SSE, ≤ 5 с) + Telegram/email по его матрице каналов; `source_code`-upsert не плодит дубли при повторном сохранении.
3. Исполнитель открывает из уведомления карточку → «Взять в работу» → статус `in_progress` (I-T4: право менять — у участника с W-доступом к проекту); флаг «просмотрено» снимает счётчик.
4. Работа: комментарий + вложение (drag&drop, SHA-дедуп FR-FILE-1) → постановщику уведомление `TaskCommented`.
5. Закрытие: исполнитель → «Завершить» → статус `done`, `resolved_time` проставлен (I-T3).

**Ветки:**
- Закрытие при открытых подзадачах → отказ `409 task_closed_with_open_subtasks` («Сначала закройте подзадачи (2)») со ссылками (I-T6).
- Просроченный срок → задача подсвечена в списках; напоминание за 24 ч до срока (событие планировщика) исполнителю и ответственному.
- Смена исполнителя → старому «снят», новому «назначен»; история — в аудите задачи.
- Наблюдатель пытается сменить статус → `403 permission_denied` (I-T4), кнопки скрыты изначально (FR-PERM-9 на действиях).

**Точный результат:** сквозной сценарий приёмки M4 (ТЗ-01 разд. 8.2 TASK) — это ровно данный flow, прогоняется двумя живыми пользователями.

## F-06. Объявление платформы → все клиенты

**Акторы:** наш сотрудник (CP), пользователи клиентов.

1. CP: «Объявления» → черновик (ru + uz/en вкладками) → таргетинг «все» или выбранные клиенты → «Опубликовать» (сразу или по дате).
2. Экземпляры забирают pull'ом ≤ 15 мин (FR-INST-5) → баннер над контентом у целевых пользователей + пункт в ленте объявлений.
3. Пользователь читает → «Понятно» → отметка в `announcement_reads`; баннер исчезает на этом устройстве и любых других (серверная отметка).
4. CP (S): статистика прочтения по клиентам (FR-CP-9).

**Ветки:** отзыв опубликованного (архив) → экземпляры скрывают при следующем pull; экземпляр офлайн → получит при первом же pull (объявления идемпотентны по id); правка после публикации → новая версия контента, отметки прочтения сбрасываются с предупреждением автору.

**Точный результат:** «объявление доходит ≤ 15 мин» из матрицы (CP, разд. 8.2) — демонстрируется на двух стендовых экземплярах в приёмке M3.

## F-07. Разбор инцидента: «кто изменил права X?»

**Актор:** админ тенанта (или наш инженер по просьбе клиента — тогда только через экран CP-доступа со своим правом и следом в security-журнале).

1. Жалоба: «у Каримова пропал доступ к складу».
2. Админ: «Аудит» → фильтр: пользователь=Каримов, таблицы=роли/права, период=7 дней → список изменений: `user_roles DELETE`, кто (`changed_by`), когда, из какого источника (UI/API — признак FR-AUTH-6).
3. Клик по записи → diff изменённых полей (JSONB, только изменённые — FR-AUD-2).
4. Параллельно «Права глазами пользователя» подтверждает текущее состояние; админ возвращает роль (F-04), доступ восстановлен ≤ 60 с.

**Ветки:** изменение сделано API-токеном → видно «через API, токен „интеграция-1С“» → админ отзывает токен (FR-AUTH-6) и разбирается с интеграцией; изменений не найдено → проверка security-журнала (вдруг блокировка/сессии) — отдельный экран.

**Точный результат:** ответ найден ≤ 2 мин (матрица разд. 8.2 AUD) — хронометраж на приёмке M5.

## F-08. Блокировка сотрудника при увольнении

**Актор:** админ тенанта. Самый частый «критичный» сценарий B2B.

1. «Пользователи» → карточка → «Заблокировать» → подтверждение с именем.
2. Система в одной транзакции (I-U1): `state='P'`, все сессии закрыты, все API-токены отозваны; security-событие.
3. Открытые вкладки уволенного при следующем действии → `401 user_blocked` → экран входа; вход невозможен (F-01 E4).
4. Система показывает админу «хвосты»: N открытых задач, где он исполнитель/ответственный → предложение переназначить (списком, массово).
5. Данные и история не удаляются; в списках он «(заблокирован)». Полное удаление = анонимизация (FR-USR-8, S) — отдельное действие с отдельным правом.

**Точный результат:** от «Заблокировать» до фактической недоступности всех входов — ≤ 5 с; ни одна задача не потеряла исполнителя молча. Приёмка M1 (+M4 для переназначения).

## F-09. Наш инженер: утро дежурного по флоту

**Актор:** инженер эксплуатации (CP + Grafana).

1. Telegram-канал дежурных: ночной алерт «backup-verify failed: client-042» (ADR-0009 разд. 4).
2. CP флот-дашборд: client-042 — heartbeat живой, версия актуальна, красный только бэкап → не инцидент клиента, инцидент процедуры.
3. По ссылке из алерта — runbook: перезапуск verify-job → зелёный; если повторно красный — эскалация по runbook (диск/WAL).
4. Grafana: логи client-042 за окно провала по `client_code` ≤ 2 мин (FR-OBS-2), причина — в отчёт.
5. Закрытие: пометка в CP «проверка пройдена», алерт погашен; недельный отчёт эксплуатации пополнился автоматически (NFR-13 — учёт времени на клиента).

**Точный результат:** от алерта до диагноза — ≤ 10 мин без SSH; каждый шаг оставил след (кто, когда, что сделал).

## F-10. Восстановление забытого пароля

**Актор:** пользователь. **Предусловие:** аккаунт активен, доступ к email есть.

1. Экран входа → ссылка «Забыли пароль?» → ввод email → «Отправить инструкцию».
2. Система: всегда возвращает `204 No Content` (не раскрывая существование email в БД); генерирует одноразовый криптографический код (TTL 15 минут); отправляет письмо со ссылкой `/auth/reset-password?code=...` через `MailProvider`.
3. Пользователь переходит по ссылке из письма → форма ввода нового пароля с индикатором требований безопасности (FR-USR-2).
4. Вводит новый пароль → «Сохранить»:
   - Пароль хешируется Argon2id;
   - **Все активные сессии пользователя закрываются в той же транзакции**;
   - Код сброса помечается использованным;
   - Запись события в security-журнал;
   - Редирект на экран входа с сообщением «Пароль успешно изменён, выполните вход».

**Ветки:** код истёк (`400 reset_code_expired`) → «Срок действия ссылки истёк, запросите новую»; код недействителен (`400 reset_code_invalid`) → ошибка ссылки; частые запросы → `429 rate_limited` (не чаще 1 запроса в 3 мин на email/IP).

**Точный результат:** полный цикл восстановления пароля ≤ 2 мин; компрометация ссылки не даёт параллельного доступа (все сессии сбрасываются). Приёмка M1.

## F-11. Истечение лицензии и переход экземпляра в Read-Only

**Актор:** пользователи и администратор экземпляра клиента. **Предусловие:** сетевая изоляция от Control Plane > 14 дней (истёк grace-период).

1. Срок действия лицензии и grace-период (14 дней) истекли. Экземпляр автоматически переходит в статус `license_status: 'READ_ONLY'`.
2. Пользователи при входе и на всех открытых экранах видят неудаляемый системный баннер: *«Действие лицензии приостановлено. Экземпляр работает в режиме чтения. Обратитесь к поставщику услуг»*.
3. Пользователи могут: просматривать справочники, читать задачи, скачивать ранее загруженные файлы, строить отчёты.
4. Любая попытка записи/модификации (`POST, PUT, PATCH, DELETE` по любым бизнес-ресурсам):
   - Сервер отклоняет запрос с кодом `423 Locked` (`{code: "license_expired_read_only", detail: "Мутация данных заблокирована"}`);
   - UI отображает системное предупреждение с отказом сохранения.
5. Восстановление: сетевой контур восстанавливается → очередной фоновый pull экземпляра получает обновлённый лицензионный JWT от Control Plane → подпись валидируется через Vault Transit `kid` → статус мгновенно возвращается в `ACTIVE` → баннер исчезает, доступ на запись открывается без рестарта сервиса.

**Точный результат:** данные клиента не блокируются и не повреждаются; мутации надёжно предотвращены; восстановление происходит автоматически за ≤ 5 мин после сетевой связи с CP. Приёмка M3.

## F-12. Разбор и повтор сбойных доставок (Dead-Letter Queue)

**Актор:** администратор экземпляра.

1. Уведомление не доставлено адресату (например, временный сбой внешнего почтового шлюза или блокировка SMS-шлюза). Воркер `notification_outbox` совершил 5 попыток с экспоненциальным backoff (I-N1) и перевёл запись в статус `DEAD_LETTER`.
2. В интерфейсе администратора у раздела «Оповещения» загорается индикатор ошибок; система шлёт предупреждение дежурным.
3. Админ открывает «Настройки» → «Очередь сбоев (Dead-Letter)»:
   - Список сбойных сообщений с указанием канала (Email, Telegram, SMS), адресата, даты, времени и последней ошибки провайдера (`last_error`);
   - Просмотр тела сообщения.
4. Админ устраняет причину (например, связывается с сотрудником или исправляет опечатку в контакте) и нажимает «Повторить отправку» (опционально с новым адресом получателя).
5. Система переводит запись обратно в статус `PENDING`, воркер мгновенно подхватывает её через `FOR UPDATE SKIP LOCKED` и производит успешную доставку.

**Ветки:** сообщение признано неактуальным → админ нажимает «Отклонить» → запись списывается с фиксацией в аудите; повторный сбой → возврат в Dead-Letter с обновлением счётчика ошибок.

**Точный результат:** ни одно уведомление не теряется молча; разбор и ручной перезапуск выполняются из UI без прямого доступа к базе данных. Приёмка M3.

## F-13. Апгрейд профиля ресурсов клиента (S → M → L)

**Актор:** инженер эксплуатации платформы.

1. У клиента выросло число пользователей (переход за лимит профиля S) или подключён модуль DWH (Этап 2).
2. Инженер в реестре Control Plane изменяет целевой профиль клиента с `S` на `M` (или `L`).
3. Nomad job клиента обновляется с новыми параметрами ресурсов (`resources { cpu, memory }`):
   - При переходе на **M**: выделение памяти для JVM расширяется до 4 ГБ, PostgreSQL OLTP до 4 ГБ, PostgreSQL DWH до 12 ГБ;
   - При переходе на **L**: группа `pg-dwh` через констрейнт Nomad (`constraint { attribute = "${node.class}" value = "dwh-storage" }`) бесшовно планируется на отдельный физический сервер.
4. Выполняется канареечное обновление группы `app` с проверкой health-check.
5. Экземпляр в очередном heartbeat сообщает новый `resource_profile: 'M'`, что отражается на центральном дашборде флота.

**Точный результат:** изменение вычислительных ресурсов и топологии размещения DWH производится штатными средствами шаблона Nomad job без изменения кодовой базы приложения. Приёмка M0/M5.
