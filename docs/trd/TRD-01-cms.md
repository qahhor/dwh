# ТЗ-01: CMS — экземпляр клиента + control plane: пользователи, доступ (RBAC), задачник, оповещения

**Версия:** 0.3
**Дата:** 2026-08-27
**Статус:** Решения по рамкам приняты CEO (см. §11), детализация — в работе
**Основание:** ADR-0001 (логика в приложении), ADR-0002 (стек и версии), ADR-0003 §2.2–2.3 (RBAC, аудит), ADR-0004 (экземпляр на клиента + control plane), ADR-0005 (готовность к AI/ML)
**Прототип предметной модели:** платформа Biruni (`d:\DATA\SMARTUP\biruni`), модули `02_md`, `03_kauth`, `05_ms`

---

## 1. Назначение и рамки

### 1.1. Продуктовая модель (ADR-0004)

Два приложения в одном монорепо, один каркас:

- **Экземпляр (instance)** — разворачивается отдельно для каждого клиента (30–100 клиентов
  на горизонте 2–3 лет): пользователи, RBAC, задачник, оповещения, файлы, аудит.
  Без `company_id`, без RLS — изоляция физическая.
- **Control plane** — наш единственный центральный сервис: реестр клиентов и экземпляров,
  версии/heartbeat, лицензии, авторство объявлений, центральный мониторинг.
  Связь только исходящая от экземпляра (pull/report).

### 1.2. Блоки Этапа 1

1. **Авторизация** — вход, сессии, OTP-2FA, API-токены (экземпляр).
2. **Пользователи** — учётные записи, блокировки, профиль (экземпляр).
3. **Доступ (RBAC)** — формы, действия, роли, эффективные права (экземпляр; тот же механизм в control plane для нас).
4. **Мини таск-менеджер** — проекты, задачи, статусы, участники, комментарии (экземпляр).
5. **Оповещения** — in-app / email / SMS / Telegram + объявления из control plane (экземпляр).
6. **Control plane (минимум)** — реестр, версии, лицензии, объявления, флот-мониторинг.

### 1.3. Ключевые упрощения относительно Biruni (приняты CEO, §11)

| Упрощение | Было в Biruni | Стало у нас |
|---|---|---|
| Single-tenant | `company_id` в каждом ключе, «нулевая компания» | без `company_id`; control plane отдельно |
| Без филиалов | роль в разрезе филиала | право = `(user, role)` |
| Одна сущность пользователя | `md_persons` → `md_users` | одна таблица `users` |
| Только API-токены | полный OAuth2-контур | отзываемые opaque-токены через RBAC |

### 1.4. Вне рамок Этапа 1

DWH и ETL (Этап 2, ТЗ-02) · динамические дашборды (Этап 3, ТЗ-03) · AI/ML-сервисы (принципы —
ADR-0005; реализация — после Этапа 2) · конструктор форм · OAuth2/SSO · канбан, чаты ·
мобильное приложение · push (FCM) · биллинг · вебхуки · динамические поля · шаблоны отчётов ·
автоматический автодеплой флота «одной кнопкой» (в Этапе 1 — скриптованный деплой, см. M0).

## 2. Термины

| Термин | Определение |
|---|---|
| Клиент | Компания-заказчик; получает собственный экземпляр |
| Экземпляр (instance) | Полный стек одного клиента: приложение + PostgreSQL + Garage |
| Control plane | Наш центральный сервис управления флотом экземпляров |
| Пользователь | Учётная запись в экземпляре; логин/email уникальны в рамках экземпляра |
| Форма / Действие | Единица UI/API и операция в ней; основа RBAC |
| Роль | Именованный набор прав `(form, action)` |
| Эффективные права | Материализованный результат: права ролей + персональные права |
| Объявление | Публикация из control plane, отображаемая в экземплярах |
| Лицензия | Подписанный токен от control plane, проверяемый экземпляром |

## 3. Архитектура

```
            ЭКЗЕМПЛЯР КЛИЕНТА (× N)                       CONTROL PLANE (× 1, наш)
┌─────────────────────────────────────────────┐    ┌───────────────────────────────┐
│ Angular 22 SPA                              │    │ Angular 22 SPA (наша команда) │
│      │ HTTPS                                │    │      │                        │
│ Spring Boot 4.1 (Java 25 LTS)               │    │ Spring Boot 4.1               │
│  бизнес-логика, RBAC, notification router   │───▶│  реестр, версии, лицензии,    │
│      │                                      │pull│  объявления, флот-метрики     │
│ PostgreSQL 18 (+pgvector)   Garage (S3)     │◀───│      │                        │
│  constraints, аудит, Flyway  файлы          │    │ PostgreSQL 18                 │
└─────────────────────────────────────────────┘    └───────────────────────────────┘
   каналы доставки: SMTP / SMS-шлюз / Telegram Bot API (конфигурация экземпляра)
```

- Версии зафиксированы в ADR-0002 §5; политика обновлений там же.
- Экземпляр: без `company_id`, без RLS (ADR-0004). Логика в приложении, в БД — целостность
  и аудит (ADR-0001, ADR-0003 §2.3).
- Control plane — тот же каркас и RBAC-механизм, второе приложение монорепо.
- Экземпляр работает автономно: недоступность control plane не ломает работу
  (лицензия с grace-периодом, объявления просто не обновляются).
- pgvector включён в образ PostgreSQL с первого дня (ADR-0005 П4).

## 4. Функциональные требования

Формат: `FR-<блок>-<номер>`. Приоритет: **M** (must) / **S** (should) / **L** (later).

### 4.1. Экземпляр: инициализация (INST)

| ID | Требование | Прио |
|---|---|---|
| FR-INST-1 | Экземпляр инициализируется при первом старте: миграции Flyway, `instance_info` (код клиента, название, ключи control plane), системные роли по pcode, системные статусы задач, первый админ (из env/секрета). | M |
| FR-INST-2 | Heartbeat в control plane: версия, время старта, базовые метрики (пользователи, состояние очереди доставки) — период 1–5 мин, исходящее соединение. | M |
| FR-INST-3 | Проверка лицензии: подписанный токен от control plane; grace-период offline (настройка, по умолчанию 14 дней); по истечении — read-only режим, не блокировка данных. | M |
| FR-INST-4 | Получение объявлений из control plane pull'ом (период ~15 мин); локальное хранение и отметки прочтения. | M |

### 4.2. Пользователи (USR)

| ID | Требование | Прио |
|---|---|---|
| FR-USR-1 | Таблица `users`: ФИО, логин, email, телефон, состояние (A/P), язык, часовой пояс, аватар. Логин и email уникальны в рамках экземпляра; телефон — среди активных. | M |
| FR-USR-2 | Пароли: Argon2id; мин. 10 символов, проверка по словарю распространённых паролей. | M |
| FR-USR-3 | Принудительная смена пароля (флаг), дата последней смены. | M |
| FR-USR-4 | Блокировка пользователя с немедленным закрытием сессий и отзывом токенов. | M |
| FR-USR-5 | Менеджер пользователя (`manager_id`) — для задачника. | S |
| FR-USR-6 | Приглашение по email: ссылка с кодом, установка пароля при первом входе. | S |
| FR-USR-7 | Профиль: смена пароля (со старым), языка, часового пояса, аватара. | M |

### 4.3. Авторизация (AUTH)

| ID | Требование | Прио |
|---|---|---|
| FR-AUTH-1 | Вход: логин (или email) + пароль. | M |
| FR-AUTH-2 | Сессии серверные: opaque cookie (HttpOnly, Secure, SameSite=Lax), в БД. Журнал: IP, user-agent, ОС/устройство, created/last_seen/closed (аналог `kauth_sessions`). | M |
| FR-AUTH-3 | Пользователь видит и завершает свои сессии; админ — сессии всех пользователей экземпляра. | M |
| FR-AUTH-4 | Анти-brute-force: экспоненциальная задержка, блокировка после N неудач; журнал попыток. | M |
| FR-AUTH-5 | 2FA — OTP по SMS или Telegram (канал выбирает пользователь из привязанных). Включается на уровне экземпляра или пользователя. Лимиты отправки OTP. | M |
| FR-AUTH-6 | API-токены: выпуск, opaque (в БД — hash), срок, отзыв, last_used. Права = права владельца через RBAC. Вызовы по токену помечаются в аудите признаком «через API» (ADR-0005 П3). | M |
| FR-AUTH-7 | Восстановление пароля: код по email (позже SMS/Telegram), срок и лимит попыток. | M |
| FR-AUTH-8 | Автозакрытие неактивных сессий (настройка, по умолчанию 12 ч). | M |
| FR-AUTH-9 | Ограничение входа по IP-диапазонам. | L |

### 4.4. Доступ / RBAC (PERM)

| ID | Требование | Прио |
|---|---|---|
| FR-PERM-1 | Каталог форм/действий регистрируется из кода при старте (`@RequiresPermission(form, action)`); ручное редактирование запрещено; исчезнувшие формы помечаются устаревшими. | M |
| FR-PERM-2 | Роли: имя (уникально), состояние, порядок; системные по pcode не удаляются/не редактируются. | M |
| FR-PERM-3 | Права роли: `(form, action)`; `action='*'` — вся форма. UI: дерево форм с чекбоксами. | M |
| FR-PERM-4 | Назначение ролей: `(user_id, role_id)`. | M |
| FR-PERM-5 | Персональные права поверх ролей: `(user_id, form, action)`. | M |
| FR-PERM-6 | Эффективные права материализуются (`effective_permissions(user_id, form, action)`) в транзакции изменения; кэш с версией; отзыв права действует ≤ 1 мин без перелогина. | M |
| FR-PERM-7 | Эндпоинт без декларации права не проходит CI (архитектурный тест). | M |
| FR-PERM-8 | Меню фронтенда строится из эффективных прав. | M |
| FR-PERM-9 | Экран «права пользователя»: итог с объяснением, из какой роли пришло. | S |
| FR-PERM-10 | Скрытие колонок гридов по роли; сервер вырезает колонки из ответа. | S |

### 4.5. Мини таск-менеджер (TASK)

| ID | Требование | Прио |
|---|---|---|
| FR-TASK-1 | Проекты задач: имя, состояние, сроки; участники R/W. Задача может быть вне проекта. | M |
| FR-TASK-2 | Статусы настраиваемые: имя, цвет, порядок; системные по pcode (`new`, `in_progress`, `done`, `cancelled`). | M |
| FR-TASK-3 | Задача: заголовок, описание (markdown), проект (опц.), подзадачи (один уровень), приоритет, сроки, resolved_time. | M |
| FR-TASK-4 | Участники по ролям: ответственный/исполнитель/участник/постановщик/наблюдатель; флаг «просмотрено». | M |
| FR-TASK-5 | Комментарии; вложения к комментариям и задаче. | M |
| FR-TASK-6 | «Мои задачи»: фильтры по роли участия/статусу/проекту/сроку; счётчик непросмотренных; просроченные выделяются. | M |
| FR-TASK-7 | События задачника публикуются в систему оповещений. | M |
| FR-TASK-8 | Чек-листы, типы/группы, циклические шаблоны, матрица переходов, реакции — после Этапа 1. | L |

### 4.6. Оповещения (NOTIF)

Единый notification-сервис экземпляра: событие → получатели → каналы. OTP — та же
инфраструктура, приоритетная очередь.

| ID | Требование | Прио |
|---|---|---|
| FR-NOTIF-1 | In-app: тип (info/success/warning/danger), заголовок, текст, ссылка на форму, `source_code`-upsert (как `ms_notifications`); прочтение, «прочитать все». | M |
| FR-NOTIF-2 | Realtime: SSE. | M |
| FR-NOTIF-3 | Email: SMTP, мультиязычные шаблоны, лог отправок. | M |
| FR-NOTIF-4 | Telegram: бот (токен — конфигурация экземпляра); привязка аккаунта deep-link'ом с одноразовым кодом; уведомления и OTP. | M |
| FR-NOTIF-5 | SMS: интерфейс `SmsProvider`, шаблоны, лог запрос/ответ; провайдер по договору, до договора канал выключен. | M |
| FR-NOTIF-6 | Очередь доставки: таблица + воркер (`FOR UPDATE SKIP LOCKED`), ретраи с backoff, dead-letter. Брокер не вводим. | M |
| FR-NOTIF-7 | Матрица получателя «тип события × канал»; OTP и security-события неотключаемы. | S |
| FR-NOTIF-8 | Объявления: получены из control plane (FR-INST-4), баннер/лента в UI, отметка «прочитал»; локальные объявления админа экземпляра. | M |

## 5. Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-1 | **Изоляция клиентов** — физическая (отдельный экземпляр, БД, хранилище). Общих данных между клиентами нет нигде, кроме control plane (реестр, лицензии, объявления). |
| NFR-2 | **Производительность экземпляра:** p95 CRUD < 300 мс при 200 одновременных пользователях; проверка права — из кэша. |
| NFR-3 | **Объёмы на экземпляр:** до 10 000 пользователей, до 1 млн задач, до 10 млн оповещений/мес. Флот: до ~100 экземпляров. Сверх — не оптимизируем. |
| NFR-4 | **Футпринт экземпляра:** целевой минимум — 4 ГБ RAM / 2 vCPU / 50 ГБ диск на весь стек (проверяется в M4 нагрузочным прогоном). |
| NFR-5 | **Автономность:** экземпляр полностью работоспособен при недоступном control plane (grace лицензии — 14 дней). |
| NFR-6 | **Доступность:** 99.5% на экземпляр; окна обслуживания — вне рабочего времени клиента. |
| NFR-7 | **Бэкапы:** на каждый экземпляр — ежесуточный полный + WAL; RPO ≤ 15 мин, RTO ≤ 4 ч; восстановление тестируется ежеквартально на одном экземпляре выборочно. |
| NFR-8 | **Безопасность:** OWASP ASVS L2; секреты вне репо; TLS везде; CSP/HSTS; OTP/токены — только hash в БД. |
| NFR-9 | **Наблюдаемость:** Micrometer → OTLP в центральный коллектор; структурные JSON-логи; сквозной trace-id. |
| NFR-10 | **Миграции:** Flyway, только вперёд, применяются автоматически при старте экземпляра (это и есть механизм обновления флота). |
| NFR-11 | **Тесты:** RBAC — интеграционные на Testcontainers (обязательны); каналы доставки — контрактные с моками. |
| NFR-12 | **Деплой:** Docker Compose; создание нового экземпляра «под ключ» скриптом ≤ 1 часа; обновление экземпляра = замена тега образа + рестарт. |

## 6. Модель данных (ядро экземпляра)

Обычные PK (`bigint generated always as identity`), обычные FK, без `company_id`, без RLS.
Служебные колонки: `created_by/created_at/modified_by/modified_at`.

| Таблица | Прототип Biruni | Отличия |
|---|---|---|
| `instance_info` | `md_companies` | одна строка: код клиента, название, ключи CP |
| `users` | `md_persons`+`md_users` | слиты; Argon2id; уникальность в экземпляре |
| `roles`, `role_permissions` | `md_roles`, `md_role_form_actions` | pcode для системных |
| `user_roles` | `md_user_roles` | `(user_id, role_id)` |
| `user_permissions` | `md_user_form_actions` | `(user_id, form, action)` |
| `effective_permissions` | `md_gen_user_form_actions` | + `permissions_version` |
| `role_hidden_columns` | `md_role_revoked_columns` | (S) |
| `forms`, `form_actions` | `md_forms`, `md_form_actions` | из кода |
| `sessions`, `login_attempts` | `kauth_sessions`, `kauth_log_in_attempts` | |

## 8. План работ (вехи)

| Веха | Содержание | Критерий готовности |
|---|---|---|
| M0. Каркас | Монорепо, два Spring Boot-приложения, Flyway, Testcontainers, CI, compose-шаблоны, скрипт создания экземпляра | новый экземпляр разворачивается скриптом ≤ 1 ч |
| M1. Пользователи и вход | INST-1, USR, AUTH-1..4,7,8; security-журнал | вход/выход/восстановление; блокировка закрывает сессии |
| M2. RBAC | PERM (M) | архитектурный тест прав; отзыв ≤ 1 мин |
| M3. Оповещения + CP | NOTIF-1..6,8; OTP-2FA (AUTH-5); CP-1..6 (реестр, heartbeat, лицензии, объявления) | OTP через Telegram; объявление из CP доходит в экземпляры; флот-дашборд показывает версии |
| M4. Задачник + файлы | TASK (M), FILE | сквозной сценарий с уведомлениями |
| M5. Стабилизация | AUD-экраны, i18n-словари uz/en, нагрузочный прогон (NFR-2, NFR-4), приёмка | чек-лист ниже |

### Приёмочный чек-лист Этапа 1

- [ ] Два экземпляра разных «клиентов» + control plane развёрнуты скриптами.
- [ ] Отзыв права действует ≤ 1 мин без перелогина.
- [ ] Вход с OTP по Telegram (SMS — за флагом при отсутствии договора).
- [ ] Объявление из CP: публикация → баннер в обоих экземплярах → отметка прочтения.
- [ ] Флот-дашборд: версии и heartbeat обоих экземпляров; алерт при остановке одного.
- [ ] Лицензия: отзыв → экземпляр в read-only после grace (проверка с укороченным grace).
- [ ] Задачник: сквозной сценарий, уведомления во всех включённых каналах.
- [ ] Аудит отвечает «кто изменил права и когда»; API-вызовы помечены.
- [ ] Восстановление экземпляра из бэкапа.
- [ ] Экземпляр укладывается в 4 ГБ RAM под нагрузкой NFR-2.

## 9. Этапы 2–3 (рамочно)

- **Этап 2 — DWH (ТЗ-02):** БД DWH в составе экземпляра клиента (отдельный PostgreSQL);

- **AI/ML после Этапа 2:** прогнозы на DWH, LLM-ассистент (pgvector уже в образе), AI-агенты
  через machine-friendly API (ADR-0005).

## 10. Риски

| Риск | Митигция |
|---|---|
| Операционка флота (30–100 экземпляров) | Автоматизация с M0: скрипт создания, миграции при старте, heartbeat, центральные метрики; обновление = смена тега |
| Возврат к SaaS-модели станет практически невозможен | Риск принят CEO осознанно (ADR-0004, вариант B отклонён) |
| SMS-договор задержится | Канал за флагом; OTP через Telegram |
| Очередь на PostgreSQL упрётся в объём | Порог NFR-3; сверх — брокер отдельным решением |
| Разъезд версий экземпляров | Правило: флот не отстаёт больше чем на 2 minor; CP-дашборд подсвечивает отстающих |
| Клиент требует размещения у себя | Архитектура допускает (исходящая связь с CP); процедуру поддержки таких экземпляров описать до первого случая |
