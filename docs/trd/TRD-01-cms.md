## 1. Назначение и рамки

### 1.1. Продуктовая модель (ADR-0004)

Два приложения в одном монорепо, один каркас:

- **Экземпляр (instance)** — разворачивается отдельно для каждого клиента (30–100 клиентов
  на горизонте 2–3 лет): пользователи, RBAC, задачник, оповещения, файлы, аудит, а с Этапа 2 —
  и хранилище данных клиента. Без `company_id`, без RLS: изоляция физическая.
- **Control plane** — наш единственный центральный сервис: реестр клиентов и экземпляров,
  версии/heartbeat, лицензии, авторство объявлений, инвентарь флота. Связь только исходящая
  от экземпляра.

Флот управляется **Nomad + Consul + Vault** (ADR-0007).

### 1.2. Блоки Этапа 1

1. **Авторизация** — вход, сессии, OTP-2FA, API-токены (экземпляр).
2. **Пользователи** — учётные записи, блокировки, профиль (экземпляр).
3. **Доступ (RBAC)** — формы, действия, роли, эффективные права (экземпляр).
4. **Мини таск-менеджер** — проекты, задачи, статусы, участники, комментарии (экземпляр).
5. **Оповещения** — in-app / email / SMS / Telegram + объявления из control plane.
6. **Control plane (минимум)** — реестр, версии, лицензии, объявления, флот-мониторинг.
7. **Безопасность и эксплуатация** — сквозные требования разд. 4.11, разд. 4.13.

### 1.3. Ключевые упрощения относительно Biruni

| Упрощение | Было в Biruni | Стало у нас |
|---|---|---|
| Single-tenant | `company_id` в каждом ключе, «нулевая компания» | без `company_id`; control plane отдельно |
| Без филиалов | роль в разрезе филиала | право = `(user, role)` |
| Одна сущность пользователя | `md_persons` → `md_users` | одна таблица `users` |
| Только API-токены | полный OAuth2-контур | отзываемые opaque-токены через RBAC |

### 1.4. Вне рамок Этапа 1

DWH и ETL (Этап 2, ТЗ-02) · динамические дашборды (Этап 3) · AI/ML-сервисы (ADR-0005) ·
конструктор форм · OAuth2/SSO · канбан, чаты · мобильное приложение (адаптивный web —
в объёме, ТЗ-02) · push (FCM) · биллинг · шаблоны отчётов · **Typesense** (отложен до первого
клиента M/L — решение CEO 2026-08-28; поиск Этапа 1 — `pg_trgm`) · **сертификация ISO 27001
и её организационные артефакты** (решение CEO 2026-08-27; технические меры безопасности
разд. 4.11 принимаются независимо) · автоматический failover БД (Patroni) · выделение модулей
в микросервисы (ADR-0006).

> Примечание v1.1: вебхуки (KWH) и динамические поля (ATTR), исключённые в ранних версиях,
> **включены в объём решением CEO 28.08.2026** — см. разд. 4.16–4.18 и журнал решений.

```
   ┌──────────────────────────────────────────────────────────────────────┐
   │                                                                      │
   │   job "client-<code>"  (× N клиентов)          CONTROL PLANE (× 1)   │
   │  ┌──────────────────────────────────┐        ┌────────────────────┐  │
   │  │ group app   Spring Boot 4.1      │        │ Spring Boot 4.1    │  │
   │  │             (Java 25 LTS)        │───────▶│ реестр, версии,    │  │
   │  │ group pg-oltp  PostgreSQL 18     │  pull  │ лицензии,          │  │
   │  │ group pg-dwh   PostgreSQL 18     │◀───────│ объявления         │  │
   │  │             (+pgvector, Этап 2)  │        │ PostgreSQL 18      │  │
   │  │ group storage  Garage (S3)       │        └────────────────────┘  │
   │  └──────────────────────────────────┘                 ▲              │
   │            ▲                                          │              │
   │            │ Angular 22 SPA (HTTPS)                   │ Nomad API    │
   └────────────┼──────────────────────────────────────────┴──────────────┘
                │
   каналы доставки: SMTP · SMS-шлюз · Telegram Bot API (секреты — из Vault)
```

- Версии зафиксированы в ADR-0002 разд. 5; политика обновлений там же.
- Логика в приложении, в БД — целостность и аудит (ADR-0001, ADR-0003 разд. 2.3).
- Приложение — модульный монолит с границами модулей (ADR-0006), не микросервисы.
- Экземпляр автономен: недоступность control plane не ломает работу (grace лицензии 14 дней).
- Секреты — только из Vault, на диск узла в открытом виде не попадают (ADR-0008 разд. 2.3).

#### 4.4.1. Системные роли экземпляра (pcode)

Создаются при инициализации (FR-INST-1), не удаляются, имена локализуются, права роли `admin`
не могут быть урезаны ниже этой матрицы (инвариант I-P4). Клиент создаёт свои роли поверх —
системные лишь стартовая точка, чтобы новый экземпляр был пригоден сразу.

| Блок форм | `admin` Администратор | `manager` Руководитель | `user` Сотрудник | `auditor` Аудитор |
|---|---|---|---|---|
| Профиль, свои сессии, свои каналы и уведомления | ✔ всё | ✔ всё | ✔ всё | ✔ всё |
| Пользователи | ✔ всё | 👁 просмотр | — | 👁 |
| Роли и назначение прав | ✔ всё | — | — | 👁 |
| Сессии/токены всех пользователей | ✔ всё | — | — | 👁 |
| Задачник: проекты | ✔ всё | ✔ создание и управление | 👁 + участие | 👁 |
| Задачник: задачи | ✔ всё | ✔ всё в своих проектах | ✔ свои и где участник | 👁 |
| Файлы | в рамках задачных прав | в рамках задачных прав | в рамках задачных прав | 👁 |
| Объявления (локальные) | ✔ всё | — | 👁 | 👁 |
| Аудит и security-журнал | ✔ просмотр | — | — | 👁 |
| Настройки экземпляра | ✔ всё | — | — | 👁 |
| Свои API-токены | ✔ | ✔ | ✔ | — |

Правила поверх матрицы:
- **`auditor` не имеет ни одного мутирующего действия** — это его определение; попытка выдать
  мутирующее право этой роли отклоняется. Роль для проверяющих/финконтроля.
- **Последний носитель `admin` защищён** от снятия роли и самоблокировки (сценарий F-04).
- **Сервисные учётки** (интеграции): создаются без роли `user`, получают минимальные
  персональные права под конкретную интеграцию; API-токен выпускается от них (след в аудите
  различим — FR-AUTH-6).

## 5. Нефункциональные требования

### 5.1. Профили ресурсов экземпляра (заменяет прежний NFR-4)

DWH размещается **внутри контура клиента** (решение CEO 2026-08-27). Единый футпринт 4 ГБ,
заявленный в v0.3, признан несостоятельным (AUDIT-01, S-1) и заменён профилями:

| Профиль | Пользователей | Объём DWH | RAM | vCPU | Диск |
|---|---|---|---|---|---|
| **S** | до 50 | до 50 ГБ | 10 ГБ | 4 | 200 ГБ |
| **M** | до 500 | до 300 ГБ | 24 ГБ | 8 | 1 ТБ |
| **L** | до 10 000 | 1 ТБ+ | 64 ГБ | 16 | 4 ТБ+ |

Распределение внутри профиля (пример для M): приложение 4 ГБ · PostgreSQL OLTP 4 ГБ ·
PostgreSQL DWH 12 ГБ · Garage 1 ГБ · резерв ОС 3 ГБ.

- Профиль задаётся в Nomad job клиента и фиксируется в реестре control plane (FR-CP-1).
- Для профиля **L** группа `pg-dwh` планируется на отдельный узел (`constraint`): логически
  внутри контура клиента, физически на своём железе. Архитектура при этом не меняется.
- Профиль тарифицируется в цене клиента — это часть коммерческой модели.
- **Триггер пересмотра:** если у клиента объём DWH превышает профиль L или аналитические
  запросы перестают укладываться в SLO, рассматривается специализированное хранилище
  (отдельное решение Этапа 2, не входит в текущий объём).

## 6. Модель данных и DDL-спецификация ядра

### 6.1. Общие принципы проектирования схемы PostgreSQL 18

1. **Первичные ключи:** Суррогатные `bigint generated always as identity` (или `uuid` для внешних/публичных идентификаторов).
2. **Внешние ключи:** Явные `FOREIGN KEY ... ON DELETE RESTRICT` (защита от случайных каскадных удалений бизнес-данных). Каскадное удаление (`ON DELETE CASCADE`) разрешено только для дочерних таблиц внутри агрегата (например, `task_members` при удалении черновика задачи).
3. **Изоляция:** Без `company_id`, без RLS (физическая изоляция экземпляров, ADR-0004).
4. **Служебные колонки:** Каждая бизнес-таблица содержит:
   - `created_at timestamptz not null default now()`
   - `created_by bigint references users(id)` *(NULL для системных/фоновых операций)*
   - `modified_at timestamptz not null default now()`
   - `modified_by bigint references users(id)`
5. **Временные метки:** Исключительно `timestamptz` (хранение в UTC, отображение в часовом поясе пользователя, FR-I18N-2).

- **`idempotency_keys`** — фиксация идемпотентности мутирующих запросов (FR-API-3):

## 8. План работ (вехи)

### 8.1. MVP-линия и порядок

Чтобы 80+ must-требований не превратились в «полгода без продукта», фиксируются правила:

1. **Спайк-неделя внутри M0 (первые 5–7 дней):** треугольник «Nomad job → batch-миграция →
   canary с авто-откатом» на стенде. Это самая рискованная связка проекта; если она
   сопротивляется — узнаём на неделе 1, а не на клиенте 20.
2. **MVP-линия = M0–M3:** после M3 продукт пригоден для пилота (кольцо R1) — вход, RBAC,
   оповещения, control plane. Задачник (M4) пилоту доставляется обновлением — это заодно
   первая проверка проката релиза по живому клиенту.
3. **WIP-лимит:** веха не начинается, пока предыдущая не принята (кроме организационных задач).
4. Понижены до S: интеграция SMS-провайдера (FR-NOTIF-5), локальные объявления (FR-NOTIF-9).

| Веха | Содержание | Критерий готовности |

### 8.2. Матрица точных результатов Этапа 1

Каждый блок ТЗ имеет **один проверяемый результат** — измеримый, с вехой и методом проверки.
Блок считается сданным только по своему результату; «сделали много всего» результатом не является.

| Блок | Точный результат (проверяемый) | Веха | Метод проверки |
|---|---|---|---|
| **INST** | Экземпляр инициализируется batch-job'ом; приложение отказывается стартовать на несовпадающей схеме; heartbeat в CP каждые ≤ 5 мин; отозванная лицензия переводит экземпляр в read-only после grace | M1/M3 | Учение с ломаной миграцией; тест с укороченным grace |
| **USR** | Админ создаёт/блокирует пользователя из UI; блокировка закрывает все сессии и токены в одной транзакции | M1 | Интеграционный тест I-U1 + ручной сценарий |
| **AUTH** | Вход по паролю + OTP (Telegram); восстановление по email; 10 неверных паролей → временная блокировка с записью в security-журнал; API-токен работает и отзывается | M1/M3 | E2E-сценарии + security-журнал |
| **PERM** | Отзыв права действует ≤ 60 с без перелогина; эндпоинт без `@RequiresPermission` не проходит CI; пересчёт прав роли на 10 000 пользователей не блокирует работу (уходит в фон); системные роли соответствуют матрице разд. 4.4.1 (в т.ч. `auditor` без единой мутации) | M2 | Автотест с секундомером; архитектурный тест; нагрузочный тест пересчёта; автотест матрицы ролей |

Правило сопровождения: новое требование в ТЗ обязано либо попадать под существующий результат,
