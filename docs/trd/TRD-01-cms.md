## 1. Назначение и рамки

### 1.1. Продуктовая модель (ADR-0004)

Два приложения в одном монорепо, один каркас:

- **Экземпляр (instance)** — разворачивается отдельно для каждого клиента (30–100 клиентов
  на горизонте 2–3 лет): пользователи, RBAC, задачник, оповещения, файлы, аудит, а с Этапа 2 —
  и хранилище данных клиента. Без `company_id`, без RLS: изоляция физическая.
- **Control plane** — наш единственный центральный сервис: реестр клиентов и экземпляров,
  версии/heartbeat, лицензии, авторство объявлений, инвентарь флота. Связь только исходящая
  от экземпляра.

Флот управляется **Nomad + Consul + Vault** (ADR-0007).

### 1.2. Блоки Этапа 1

1. **Авторизация** — вход, сессии, OTP-2FA, API-токены (экземпляр).
2. **Пользователи** — учётные записи, блокировки, профиль (экземпляр).
3. **Доступ (RBAC)** — формы, действия, роли, эффективные права (экземпляр).
4. **Мини таск-менеджер** — проекты, задачи, статусы, участники, комментарии (экземпляр).
5. **Оповещения** — in-app / email / SMS / Telegram + объявления из control plane.
6. **Control plane (минимум)** — реестр, версии, лицензии, объявления, флот-мониторинг.
7. **Безопасность и эксплуатация** — сквозные требования §4.11, §4.13.

### 1.3. Ключевые упрощения относительно Biruni

| Упрощение | Было в Biruni | Стало у нас |
|---|---|---|
| Single-tenant | `company_id` в каждом ключе, «нулевая компания» | без `company_id`; control plane отдельно |
| Без филиалов | роль в разрезе филиала | право = `(user, role)` |
| Одна сущность пользователя | `md_persons` → `md_users` | одна таблица `users` |
| Только API-токены | полный OAuth2-контур | отзываемые opaque-токены через RBAC |

### 1.4. Вне рамок Этапа 1

DWH и ETL (Этап 2, ТЗ-02) · динамические дашборды (Этап 3) · AI/ML-сервисы (ADR-0005) ·
конструктор форм · OAuth2/SSO · канбан, чаты · мобильное приложение · push (FCM) · биллинг ·
вебхуки · динамические поля · шаблоны отчётов · **сертификация ISO 27001 и её организационные
артефакты** (решение CEO 2026-08-27; технические меры безопасности §4.11 принимаются
независимо) · автоматический failover БД (Patroni) · выделение модулей в микросервисы (ADR-0006).

## 2. Термины

| Термин | Определение |
|---|---|
| Клиент | Компания-заказчик; получает собственный экземпляр |
| Экземпляр (instance) | Полный контур одного клиента: приложение + PostgreSQL OLTP + PostgreSQL DWH + Garage |
| Профиль ресурсов | Размерность экземпляра (S/M/L), определяющая выделяемые ресурсы (§5.1) |
| Control plane | Наш центральный сервис управления флотом |
| Кольцо развёртывания | Стадия проката релиза по флоту: R0 стенд → R1 пилоты → R2 остальные |
| Модуль | Логическая часть приложения с явной границей и публичным API (ADR-0006) |
| Форма / Действие | Единица UI/API и операция в ней; основа RBAC |
| Эффективные права | Материализованный результат: права ролей + персональные права |

## 3. Архитектура

```
                    NOMAD + CONSUL + VAULT  (наша инфраструктура)
   ┌──────────────────────────────────────────────────────────────────────┐
   │                                                                      │
   │   job "client-<code>"  (× N клиентов)          CONTROL PLANE (× 1)   │
   │  ┌──────────────────────────────────┐        ┌────────────────────┐  │
   │  │ group app   Spring Boot 4.1      │        │ Spring Boot 4.1    │  │
   │  │             (Java 25 LTS)        │───────▶│ реестр, версии,    │  │
   │  │ group pg-oltp  PostgreSQL 18     │  pull  │ лицензии,          │  │
   │  │ group pg-dwh   PostgreSQL 18     │◀───────│ объявления         │  │
   │  │             (+pgvector, Этап 2)  │        │ PostgreSQL 18      │  │
   │  │ group storage  Garage (S3)       │        └────────────────────┘  │
   │  └──────────────────────────────────┘                 ▲              │
   │            ▲                                          │              │
   │            │ Angular 22 SPA (HTTPS)                   │ Nomad API    │
   └────────────┼──────────────────────────────────────────┴──────────────┘
                │
   каналы доставки: SMTP · SMS-шлюз · Telegram Bot API (секреты — из Vault)
```

- Версии зафиксированы в ADR-0002 §5; политика обновлений там же.
- Логика в приложении, в БД — целостность и аудит (ADR-0001, ADR-0003 §2.3).
- Приложение — модульный монолит с границами модулей (ADR-0006), не микросервисы.
- Экземпляр автономен: недоступность control plane не ломает работу (grace лицензии 14 дней).
- Секреты — только из Vault, на диск узла в открытом виде не попадают (ADR-0008 §2.3).

## 4. Функциональные требования

Приоритет: **M** (must) / **S** (should) / **L** (later).

### 4.1. Экземпляр: инициализация (INST)

| ID | Требование | Прио |
|---|---|---|
| FR-INST-1 | Экземпляр инициализируется при первом развёртывании: `instance_info` (код клиента, название, ключи control plane), системные роли по pcode, системные статусы задач, первый админ. Схема создаётся **отдельным batch-job миграций** (NFR-10), не приложением. | M |
| FR-INST-2 | Приложение при старте проверяет версию схемы БД и **отказывается стартовать при несовпадении** с ожидаемой (ADR-0007 §2.3). | M |
| FR-INST-3 | Heartbeat в control plane: версия, время старта, профиль ресурсов, базовые метрики (пользователи, состояние очереди доставки) — период 1–5 мин, исходящее соединение. | M |
| FR-INST-4 | Проверка лицензии: подписанный токен от control plane с идентификатором ключа (`kid`); grace-период offline (по умолчанию 14 дней); по истечении — read-only режим, не блокировка данных. | M |
| FR-INST-5 | Получение объявлений из control plane pull'ом (период ~15 мин); локальное хранение и отметки прочтения. | M |

### 4.3. Авторизация (AUTH)

| ID | Требование | Прио |
|---|---|---|
| FR-AUTH-1 | Вход: логин (или email) + пароль. | M |
| FR-AUTH-2 | Сессии серверные: opaque cookie (HttpOnly, Secure, SameSite=Lax) + **CSRF-токен** (FR-SEC-1). Журнал: IP, user-agent, ОС/устройство, created/last_seen/closed. | M |
| FR-AUTH-3 | Пользователь видит и завершает свои сессии; админ — сессии всех пользователей экземпляра. | M |
| FR-AUTH-4 | Анти-brute-force: экспоненциальная задержка, блокировка после N неудач; журнал попыток. | M |
| FR-AUTH-5 | 2FA — OTP по SMS или Telegram (канал выбирает пользователь). Включается на уровне экземпляра или пользователя. Лимиты отправки OTP. | M |
| FR-AUTH-6 | API-токены: выпуск, opaque (в БД — hash), срок, отзыв, last_used. Права = права владельца через RBAC. Вызовы помечаются в аудите признаком «через API». Освобождены от CSRF-проверки, подчиняются лимитам частоты. | M |
| FR-AUTH-7 | Восстановление пароля: код по email, срок и лимит попыток. | M |
| FR-AUTH-8 | Автозакрытие неактивных сессий (по умолчанию 12 ч). | M |
| FR-AUTH-9 | Ограничение входа по IP-диапазонам. | L |

### 4.4. Доступ / RBAC (PERM)

| ID | Требование | Прио |
|---|---|---|
| FR-PERM-1 | Каталог форм/действий регистрируется из кода при старте (`@RequiresPermission`); ручное редактирование запрещено; исчезнувшие формы помечаются устаревшими. | M |
| FR-PERM-2 | Роли: имя (уникально), состояние, порядок; системные по pcode не удаляются и не лишаются базовых прав (инвариант I-P4). | M |
| FR-PERM-3 | Права роли: `(form, action)`; `action='*'` — вся форма. UI: дерево форм с чекбоксами. | M |
| FR-PERM-4 | Назначение ролей: `(user_id, role_id)`. | M |
| FR-PERM-5 | Персональные права поверх ролей: `(user_id, form, action)`. | M |
| FR-PERM-6 | Эффективные права материализуются в транзакции изменения; `permissions_version` инкрементируется там же (I-P2); кэш с версией; отзыв права действует ≤ 1 мин без перелогина. | M |
| FR-PERM-7 | **Порог фонового пересчёта:** если объём пересчёта превышает настраиваемый порог (по умолчанию 50 000 строк), пересчёт уходит в фоновую задачу; до её завершения права вычисляются «на лету». Экран показывает статус пересчёта. | M |
| FR-PERM-8 | Эндпоинт без декларации права не проходит CI (архитектурный тест). | M |
| FR-PERM-9 | Меню фронтенда строится из эффективных прав. | M |
| FR-PERM-10 | Экран «права пользователя»: итог с объяснением, из какой роли пришло. | S |
| FR-PERM-11 | Скрытие колонок гридов по роли; сервер вырезает колонки из ответа. | S |

|---|---|---|

## 5. Нефункциональные требования

### 5.1. Профили ресурсов экземпляра (заменяет прежний NFR-4)

DWH размещается **внутри контура клиента** (решение CEO 2026-08-27). Единый футпринт 4 ГБ,
заявленный в v0.3, признан несостоятельным (AUDIT-01, S-1) и заменён профилями:

| Профиль | Пользователей | Объём DWH | RAM | vCPU | Диск |
|---|---|---|---|---|---|
| **S** | до 50 | до 50 ГБ | 10 ГБ | 4 | 200 ГБ |
| **M** | до 500 | до 300 ГБ | 24 ГБ | 8 | 1 ТБ |
| **L** | до 10 000 | 1 ТБ+ | 64 ГБ | 16 | 4 ТБ+ |

Распределение внутри профиля (пример для M): приложение 4 ГБ · PostgreSQL OLTP 4 ГБ ·
PostgreSQL DWH 12 ГБ · Garage 1 ГБ · резерв ОС 3 ГБ.

- Профиль задаётся в Nomad job клиента и фиксируется в реестре control plane (FR-CP-1).
- Для профиля **L** группа `pg-dwh` планируется на отдельный узел (`constraint`): логически
  внутри контура клиента, физически на своём железе. Архитектура при этом не меняется.
- Профиль тарифицируется в цене клиента — это часть коммерческой модели.
- **Триггер пересмотра:** если у клиента объём DWH превышает профиль L или аналитические
  запросы перестают укладываться в SLO, рассматривается специализированное хранилище
  (отдельное решение Этапа 2, не входит в текущий объём).

## 8. План работ (вехи)

### 8.1. MVP-линия и порядок

Чтобы 80+ must-требований не превратились в «полгода без продукта», фиксируются правила:

1. **Спайк-неделя внутри M0 (первые 5–7 дней):** треугольник «Nomad job → batch-миграция →
   canary с авто-откатом» на стенде. Это самая рискованная связка проекта; если она
   сопротивляется — узнаём на неделе 1, а не на клиенте 20.
2. **MVP-линия = M0–M3:** после M3 продукт пригоден для пилота (кольцо R1) — вход, RBAC,
   оповещения, control plane. Задачник (M4) пилоту доставляется обновлением — это заодно
   первая проверка проката релиза по живому клиенту.
3. **WIP-лимит:** веха не начинается, пока предыдущая не принята (кроме организационных задач).
4. Понижены до S: интеграция SMS-провайдера (FR-NOTIF-5), локальные объявления (FR-NOTIF-9).

| Веха | Содержание | Критерий готовности |
|---|---|---|
| **M0. Каркас и платформа** | Спайк-неделя (п.1); монорепо, два Spring Boot-приложения, модули + ArchUnit, Flyway с batch-job миграций и линтером, Testcontainers, CI (SCA/SBOM/gitleaks), кластер Nomad+Consul+Vault **на кворуме из трёх узлов + N+1 клиентский**, стек наблюдаемости (FR-OBS-1), restore одной командой, шаблон job'а с профилями, CSRF и лимиты частоты | Новый экземпляр разворачивается из шаблона ≤ 1 ч; restore экземпляра ≤ 1 ч по секундомеру; сборка падает при нарушении границ модулей и при Critical-уязвимости; логи стенда видны в Grafana |

### Приёмочный чек-лист Этапа 1

- [ ] Два экземпляра разных клиентов + control plane развёрнуты через Nomad из шаблона.
- [ ] Прокат релиза по кольцам R0 → R1 → R2 выполнен; canary с намеренной ошибкой откатился автоматически.
- [ ] Учения по миграциям: намеренно ломаная миграция остановлена batch-job'ом, приложение не стартовало, откат выполнен.
- [ ] Автопроверка восстановления прошла для обоих экземпляров; провал даёт алерт.
- [ ] Отзыв права действует ≤ 1 мин без перелогина; пересчёт на 10 000 пользователей уходит в фон.
- [ ] Вход с OTP по Telegram (SMS — за флагом при отсутствии договора).
- [ ] Лицензия: отзыв → read-only после grace; ротация ключа подписи не потребовала остановки.
- [ ] Задачник: сквозной сценарий, уведомления во всех включённых каналах; dead-letter разбирается из UI.
- [ ] Аудит отвечает «кто изменил права и когда»; API-вызовы помечены; retention работает.
- [ ] Ни одного секрета вне Vault (проверено сканером); CSRF и лимиты частоты подтверждены тестами.
- [ ] Нагрузочный прогон по профилю M укладывается в SLO NFR-2.
- [ ] Учение «отказ клиентского узла»: приложение переехало само, restore БД ≤ 1 ч.
- [ ] Учение «отказ узла платформы»: деплой и выпуск лицензий продолжают работать.
- [ ] Учение «CP лежит»: экземпляры работают, vmalert поднял тревогу, CP восстановлен ≤ 2 ч.
- [ ] Логи любого экземпляра находятся в Grafana за минуты; trace_id связывает запрос → лог → SQL.

## 10. Риски

| Риск | Митигция |
|---|---|
| Nomad — новая платформа для команды | Внедрение на M0, пока клиентов нет; обучение на dev-кластере; Nomad проще K8s |
| Операционка флота 30–100 экземпляров | NFR-13 как измеримая цель; кольца, автопроверки, инвентарь версий с M0 |
| Отказ узла = простой клиента (нет failover БД) | Соответствует NFR-6 (99,5%); Patroni — отдельное решение при повышении требований |
| Профиль L упрётся в возможности PostgreSQL под аналитикой | Триггер пересмотра в §5.1; специализированное хранилище — решение Этапа 2 |
| SMS-договор задержится | Канал за флагом; OTP через Telegram |
| Возврат к SaaS-модели практически невозможен | Риск принят CEO осознанно (ADR-0004) |

## 12. Открытые вопросы

1. **SMS-провайдер** (Eskiz / Play Mobile / другой) — блокирует только включение SMS-канала.
2. **SMTP** — свой сервер или внешний сервис.
3. **Имя продукта и домен** — нужно для Telegram-ботов, писем, URL экземпляров.
4. **Telegram-бот:** один общий на всех клиентов или на экземпляр (предварительно — на экземпляр).
5. **Состав системных ролей** экземпляра — предложу при детализации M2.
6. **Размер и состав команды** — нужен для перевода вех в календарные сроки.
7. **Пилотные клиенты для кольца R1** — нужны к M5.
