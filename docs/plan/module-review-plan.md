# План помодульного пересмотра CMS (Этап 1)

**Статус:** рабочий документ, обновляется по мере закрытия модулей
**Создан:** 2026-08-29
**Основание:** решение CEO — пересмотреть каждый модуль по отдельности, довести до
закрытого состояния и только потом двигаться дальше
**Источник требований:** [ТЗ-01](../trd/TRD-01-cms.md) разд. 4 (функциональные требования),
разд. 6 (модель данных), разд. 8.2 (матрица точных результатов)

---

## 1. Зачем этот документ

Реализация Этапа 1 шла блоками, и сейчас между «объявлено в ТЗ», «есть таблица в БД»,
«есть класс в коде» и «работает и проверено» — разные вещи. Этот документ фиксирует
разницу по каждому модулю и задаёт порядок, в котором мы её закрываем.

Правило: **модуль считается закрытым, когда закрыты все его M-требования** и результат
воспроизводится на живом экземпляре, а не только компилируется.

## 2. Протокол пересмотра одного модуля

По каждому модулю проходим шесть шагов в этом порядке. Пропуск шага — не экономия,
а перенос дефекта на потом.

| Шаг | Что смотрим | Чем заканчивается |
|---|---|---|
| 1. Архитектура | Границы модуля, зависимости, публичный фасад, события. Соответствие ADR-0006 | Список нарушений границ |
| 2. Логика | Сценарии из [ТЗ-03](../trd/TRD-03-flows.md), инварианты, ошибочные ветки | Список расхождений с ТЗ |
| 3. Поля БД | Каждая колонка: нужна ли, тип, `not null`, значение по умолчанию, индекс | Diff схемы к ТЗ-01 разд. 6 |
| 4. Ограничения | PK/FK/unique/check, каскады, транзакционные инварианты, что защищает БД, а что приложение | Список недостающих ограничений |
| 5. Права и аудит | Каждый эндпоинт объявляет право; каждое значимое действие оставляет след | Список незакрытых действий |
| 6. Точный результат | Проверяемое утверждение в терминах разд. 8.2 + автотест + живой прогон | Отметка «закрыт» |

## 3. Порядок пересмотра

Порядок — по зависимостям, а не по номерам ТЗ: сначала то, на чём стоит всё остальное.

**Круг 1 — ядро доступа.** Пока не закрыты пользователи, вход и права, любой другой
модуль проверяется на зыбком основании.
M2 Пользователи → M3 Авторизация → M4 RBAC

**Круг 2 — сквозные контракты.** Влияют на все модули сразу; чем позже введём, тем
дороже переделка каждого.
M8 Аудит → M10 API-контракт → M9 Настройки и i18n

**Круг 3 — бизнес-функции.**
M5 Задачник → M6 Оповещения → M7 Файлы → M16 Атрибуты → M17 Поиск → M18 Вебхуки

**Круг 4 — платформа.**
M1 Экземпляр → M15 Control plane → M11 Безопасность → M12 Модульность →
M14 Провайдеры → M13 Наблюдаемость
