# План перестройки серверных модулей

**Актуализировано:** 2026-10-21

**Статус:** предложение, ждёт решения владельца. Ничего из описанного не сделано.

**Область:** `apps/server`, пакеты `com.smartup24.cms.instance.*`. Таблицы, миграции и пути API **не меняются**.

## Зачем

Модуль `md` (мастер-данные) вырос до 117 файлов и около 16,1 тыс. строк и собрал не связанные друг с другом части. Часть из них
используется почти только одним соседом (контракты форм — `studio`, меню — `config`), поэтому границы модулей условны и карту
сложно читать. Почему важно: меньше связности — дешевле изменения, понятнее карта для людей и агентов.

## Что лежит в `md`

Анализ 2026-10-21, подсчёт по именам классов. Числа с пометкой «оценка» не пересчитывались при подготовке документа.

| Часть | Файлов / строк | Кто использует |
|---|---|---|
| IAM: пользователи, роли, права | 29 / 4,1 тыс. (оценка) | 47 файлов вне `md` (оценка) |
| Контракты форм Studio `MdSimpleForm*`, `MdFormStudio*`, `MdFormCatalog*` | 25 / 3 942 (проверено) | только `studio`: 48 файлов, всего 173 импорта `md` в `studio` (проверено) |
| Отчёты, дашборды, списки-представления, виджеты | 22 / 3 209 по именам (анализ: 23 / 3,3 тыс.) | см. шаг 4 |
| Меню (`NavigationItem*`) и реестр модулей (`ModuleRegistry*`, `MdInstalledModules`) | 9 / 1 339 (проверено) | вне `md` только `config` (`DemoData`) (проверено) |
| Динамические поля, языки, оргструктура, настройки | остальное | разные |

## Шаги (от меньшего риска к большему)

Каждый шаг — отдельный коммит. После шага зелёные `ModuleBoundariesTest`, `ModularArchitectureTest`, `ModuleMapTest`,
`PlatformModulesReservedTest`, затем целевые тесты затронутого модуля.

1. **`FormStudio*` и `FormMetaController` из `common.entity` в `studio`** (около 3–5 файлов, оценка). Сейчас общий пакет `common`
   содержит код Studio. Критерий успеха: `common` не ссылается на `studio`, правила границ зелёные.
2. **Меню и реестр модулей — в отдельный модуль** (9 файлов, около 1,3 тыс. строк). Использует только `config`; риск низкий.
   Нужны `package-info.java`, строка в `module-map.md`, запись в `ModuleBoundariesTest.MODULES`; коды областей прав не меняются
   (ADR-0028).
3. **Контракты форм Studio из `md` в `studio`** (25 файлов, 3,9 тыс. строк). Потребитель один — `studio`; импорты правятся в
   48 файлах `studio`; в `ModuleBoundariesTest` обновляются префиксы `ownerOf` (имена таблиц не меняются, ADR-0020). Риск
   средний: много правок импортов, логика не меняется.
4. **Отчёты и дашборды из `md` в `report`** (22–23 файла). `MdPref` и `MdPreferenceSharing` остаются в `md`, иначе появится цикл
   `report` ↔ `kauth`. Перед шагом проверить всех импортёров этих классов (оценка: нужна проверка графом зависимостей).

**Не рекомендуется:** переносить отчётный движок `common.entity.report` и `QueryAggregate*` (на них держится runtime сущностей);
дробить IAM (47 внешних потребителей, выигрыш не окупает риск).

## Защитные тесты

- `ModuleBoundariesTest` — строгий, замороженного хранилища нет. **Замечание:** [ADR-0006](../adr/ADR-0006-modular-monolith.md)
  всё ещё упоминает `archunit_store`; каталога `apps/server/src/test/resources/archunit_store` нет (там только
  `archunit.properties`), текст ADR устарел и требует правки отдельным коммитом.
- `ModularArchitectureTest` — правила зависимостей слоёв; `ModuleMapTest` — карта модулей и `package-info.java`;
  `PlatformModulesReservedTest` — зарезервированные имена модулей платформы.

## Риски — что может пойти не так

- Много механических правок импортов: делать скриптом и сверять `git diff --stat`; не смешивать с логикой.
- Перенос класса затрагивает `ModuleSourceBoundariesTest` и baseline комментариев: прогонять `CommentLanguageTest`.
- Внешние модули зависят от `libs/platform-api`, не от `md`; публичный контракт не затрагивается (проверить japicmp).

## Решение владельца

Нужно решить: делать ли шаги 1–4, в каком порядке и одним ли этапом. Предположение: шаги 1–2 можно сделать без отдельного ADR,
шаги 3–4 стоит зафиксировать ADR об изменении границ модулей.
