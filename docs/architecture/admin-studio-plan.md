# Студия SmartupCMS: план реализации, DoR, DoD и ACC

**Цель:** администратор проектирует формы, отчёты и дашборды через общий интерфейс, а платформа исполняет их через существующие runtime, права и компоненты.

**Архитектура:** модульный монолит, EntityDefinition/EntityRuntime, общий QueryList и UI kit сохраняются. Определение данных, представление формы, запрос отчёта и расположение панели разделены. Первые изменения физической схемы проходят существующие CLI, Flyway и CI; публикация новых сущностей без выпуска приложения — отдельный этап.

**Стек:** Java 25, Spring Boot 4.1, PostgreSQL 18, Angular 22. Новые зависимости для начального этапа не нужны.

**Основание:** поручение владельца от 2026-10-15 улучшить план, определить DoR/DoD/ACC и начать реализацию; техническое задание, ADR-0019, ADR-0032, ADR-0033 и план 10/10. Это рабочий план инициативы; он не заменяет нормативное ТЗ и не объявляет будущие функции реализованными.

**Исполнение:** небольшие проверяемые изменения, тест воспроизводит дефект до исправления; обязательные проверки перед RC/merge. STU-00…06 реализованы и проверены локально в пределах своих этапов; подготовленный пакет STU-02 не активирует рабочие формы. Следующие этапы начинаются по своему DoR. Публикация, merge, закупки и установка новых пакетов в этот объём не входят.

## 1. Что уточнено после изучения практик

| Практика | Применение к SmartupCMS |
|---|---|
| Разделение схемы данных и UI schema — [JSON Forms](https://jsonforms.io/docs/) | Стабильные идентификаторы полей; отдельно версии entity schema, form layout, report definition, dashboard layout. Библиотеку JSON Forms не внедряем: используем свой runtime |
| Явный диалект схемы — [JSON Schema](https://json-schema.org/understanding-json-schema/reference/schema) | Если выбран JSON Schema, фиксируем диалект; версия бизнес-определения хранится отдельно. Сервер принимает ограниченный набор конструкций, без сетевых ссылок и исполняемого кода |
| Источник и артефакт выпуска разделены — [Power Platform ALM](https://learn.microsoft.com/en-us/power-platform/alm/solution-concepts-alm) | Черновик не исполняется как опубликованная форма. Наша рекомендация: пакет версии, зависимостей и контрольных сумм; тот же проверенный пакет проходит между окружениями |
| Изменение схемы учитывает строки, зависимости и блокировки — [PostgreSQL ALTER TABLE](https://www.postgresql.org/docs/18/sql-altertable.html) | Для required/type/delete предварительная проверка данных; план выполнения, lock/statement timeout и восстановление. Возврат старого UI не считается откатом данных |
| Уведомление после commit не заменяет состояние — [NOTIFY](https://www.postgresql.org/docs/18/sql-notify.html), [LISTEN](https://www.postgresql.org/docs/18/sql-listen.html) | В БД хранится активная ревизия. После commit LISTEN узел читает состояние, затем обрабатывает сигналы; startup/reconnect восстанавливает пропущенное |
| Запрет по умолчанию, права на каждом запросе — [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) | Отдельные права авторства/публикации; общий отчёт выполняется с правами читателя. Preview/export/drill-down не обходят scope |
| Агрегаты имеют определённую семантику — [PostgreSQL aggregate functions](https://www.postgresql.org/docs/18/functions-aggregate.html) | NULL не равен нулю; avg/min/max нельзя складывать в «Остальные». Для неподдерживаемого графика показывается точная таблица |
| Drag не единственный способ управления — [WCAG 2.5.7](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html), [сложные изображения](https://www.w3.org/WAI/tutorials/images/complex/) | Перестановка/размер кнопками и кликами, отдельно клавиатура; у графика доступные значения, не только цвет |
| DoD — общий стандарт качества — [Scrum Guide](https://scrumguides.org/scrum-guide.html#commitment-definition-of-done) | DoR — наше соглашение о готовности задачи, ACC — её конкретное поведение; они не подменяют общий DoD |

Источники проверены 2026-10-15. Архитектура пакетов, лимиты и порядок работ ниже — решения/предложения для SmartupCMS, а не требования перечисленных продуктов или заявление о сертификации.

## 2. Границы и принципы

- Текущие статические сущности сохраняют свои hooks, права и scope. Администратор меняет только явно разрешённые части.
- Схема данных отдельно от layout. Перевод/порядок поля не меняет его ID, значения и ссылки отчётов.
- Опубликованная версия неизменяема. Изменение создаёт черновик; ревизия записи, ревизия определения и версия формата декларации различаются.
- Серверная валидация обязательна: allowlist типов/операторов, глубины и размера декларации; неизвестные свойства отклоняются. Произвольные SQL/Java/JavaScript/shell не поддерживаются.
- Публикация использует контрольную сумму проверенного содержимого и compare-and-set активной ревизии; для новой create-only формы STU-05 — уникальность кода и сравнение checksum при повторе (ADR-0038). Повтор запроса идемпотентен; конфликт редакторов видим.
- Создание определения, публикация, назначение доступа и использование данных — разные полномочия. Предпросмотр роли не расширяет доступ автора.
- Поиск, история, импорт/экспорт и вложения включаются в область проверки изоляции, а не добавляются после CRUD.
- Архивирование определения не удаляет данные. Необратимое удаление — отдельная явно подтверждаемая операция.
- Общий dashboard даёт доступ к определению, но не к данным владельца. Кэш результатов вводится только после измерений и с учётом отзыва прав.
- Отключение редактора Студии отдельно от доступности опубликованных приложений.
- API SLO сохраняются: p95 ≤ 300 мс, p99 ≤ 1 с. SQL timeout отчёта 5 с не является SLO. Фоновые вычисления требуют отдельного бюджета завершения.
- ru/uz/en, доступность, mobile, серверные Problem Details, If-Match, неизменяемые миграции и отсутствие роста baseline — действующие правила проекта.
- Мгновенная публикация новых сущностей расширяет границы ADR-0032; её нельзя включить скрыто под видом UI-редактора.

## 3. DoR — готовность отдельной задачи к работе

Задача Ready, когда выполнены все применимые пункты; N/A содержит причину:

| ID | Проверяемое условие | Артефакт / ответственный |
|---|---|---|
| DOR-01 | Указаны пользователь, проблема, наблюдаемый результат и границы задачи | История; product owner + инженер |
| DOR-02 | Есть ACC с happy/error/recovery сценариями и примерами данных | Матрица ниже; инженер + QA |
| DOR-03 | Известны существующие точки расширения, файлы, контракты и зависимости | План задачи; инженер |
| DOR-04 | Описаны права, scope, скрытые поля и доверие входным данным | Матрица доступа; backend/security |
| DOR-05 | Для данных/публикации определены версия, совместимость, повтор, конфликт и восстановление | ADR/план миграции; backend/DevOps; для STU-00 N/A |
| DOR-06 | Есть макет/правила состояний, i18n и управление без drag, если меняется UI | Дизайн поведения; frontend |
| DOR-07 | Известны команды проверки, тестовые данные, текущая база и способ воспроизведения | Test plan; инженер/QA |
| DOR-08 | Нет нерешённого решения, меняющего безопасность или способ хранения; есть роль-владелец и оценка после исследования | Карточка этапа |

DoR не запрещает исследовательские задачи: их результат — ответ на конкретный вопрос и проверенный прототип, не production-функция. Отсутствие staging не мешает локальным задачам, но не превращает локальную проверку в staging-приёмку.

## 4. DoD — общий стандарт завершения

DoD дополняет, не ослабляет общий DoD из [плана 10/10](../plan-10-10.md#общий-definition-of-done).

- DOD-01: все ACC задачи проверены; каждому соответствует тест/протокол. Исправления имеют наблюдавшийся RED, затем GREEN.
- DOD-02: отрицательные сценарии прав и повреждённых входов покрыты там, где меняется серверное поведение. Ожидания тестов заданы независимо от реализации.
- DOD-03: существующие сценарии не сломаны; выполнены обязательные проверки затронутых слоёв. Перед RC/merge — полный локальный CI по AGENTS.md, без снижения coverage/baseline.
- DOD-04: код прошёл ревью; нет проглоченных ошибок, временных обходов, секретов и непроверенных новых зависимостей.
- DOD-05: новые UI-тексты в ru/uz/en; состояния loading/error/empty и retry доступны; клавиатура и мобильный экран проверены.
- DOD-06: при изменении API обновлены OpenAPI/web types, при breaking change — CHANGELOG и соответствующий trailer/label.
- DOD-07: миграции/публикация проверены на повтор, конфликт и прерывание; откат описывает данные, а не только интерфейс. N/A для локальных UI-исправлений.
- DOD-08: документация, cookbook/guide при изменении расширений, CHANGELOG и handoff актуальны; статусы подтверждены фактическими результатами.
- DOD-09: для публикации на целевом контуре проверены его SLO, доступы, backup/restore и эксплуатационные процедуры. Без этого нельзя объявлять production-ready.
- DOD-10: коммит, когда запрошен, содержит DCO и attribution; публикация/merge выполняются только в разрешённом объёме.

Статусы не смешиваются: «реализовано и проверено локально» ≠ «полный DoD релиза выполнен» ≠ «опубликовано».

## 5. ACC — критерии приёмки

ACC здесь означает acceptance criteria, критерии приёмки. Все будущие строки изначально Planned; наличие строки не является результатом теста.

| ID / этап | Given → When → Then | Проверка |
|---|---|---|
| ACC-01 / STU-00 | API списка виджетов отвечает 403/500/сетевая ошибка → загрузка завершена → видна ошибка и retry, отсутствует empty-state | HttpTestingController + DOM |
| ACC-02 / STU-00 | Ошибка списка → повтор успешен → ошибка исчезает, показывается актуальный список; при повторной ошибке старые карточки не показываются как актуальные | Component regression |
| ACC-03 / STU-00 | Запрос ещё выполняется / ответ [] → UI показывает соответственно loading / empty, не смешивая их | Component regression |
| ACC-04 / STU-00 | Более 5 серий или неполная матрица групп avg/min/max → bar → полная таблица и пояснение вместо суммы агрегатов, в том числе в виджете без обычной таблицы | Реальные результаты с вручную заданными значениями |
| ACC-05 / STU-00 | Совместимые count/sum с 7 сериями 1…7 → bar → первые 4 серии и «Остальные» = 18; исходная таблица сохраняется | Component regression |
| ACC-06 / STU-00 | Разные raw-ключи имеют одинаковую подпись либо значение совпадает с внутренним маркером «Остальные» → bar → значения не объединяются ошибочно | Component regression |
| ACC-07 / STU-00 | Более 2 измерений, несколько валют (включая явно выбранную группировку), NULL/отрицательное/нечисловое значение первой меры → bar → точная таблица вместо непредставимого графика; NULL KPI отображается как отсутствие значения | Component regression |
| ACC-08 / STU-01 | Меняется подпись/положение поля → сохранить layout → ID/API/данные/ссылки отчётов неизменны | Contract + UI integration |
| ACC-09 / STU-01 | Неизвестный тип, оператор, свойство, циклическая/сетевая ссылка или превышение лимита → validate → структурированная ошибка, ничего не исполняется | Server negative contract |
| ACC-10 / STU-02 | Два автора одной ревизии → второй сохраняет → конфликт без перезаписи; неподтверждённый draft не виден обычному пользователю | Integration + E2E |
| ACC-11 / STU-02 | Пакет проверен → содержимое изменено/публикация повторена/оборвана → изменённый пакет отклонён, повтор безопасен, активная версия остаётся согласованной | Publication fault injection |
| ACC-12 / STU-03 | Общий отчёт → читатель с меньшими правами / отзыв доступа → данные ограничены его scope/полями при запуске и скачивании | Access matrix integration |
| ACC-13 / STU-03 | Панель с общим фильтром и одним отказавшим источником → загрузка → фильтр применяется явно, ошибка только у своего виджета, остальные не обнуляются | E2E + API |
| ACC-14 / STU-03 | Таблица/график/экспорт на одинаковых параметрах → сравнить → совпадают агрегаты, NULL, валюты, период/часовой пояс и признак усечения | Golden data integration |
| ACC-15 / STU-04 | Required/type/delete несовместимы с данными/зависимостями → preflight → публикация запрещена с объяснением; скрытие не удаляет данные | Migration/integration |
| ACC-16 / STU-04 | Администратор создаёт простой справочник → генерация и CI → форма работает через общий runtime; повтор генерации не перезаписывает ручные правки | CLI smoke + E2E |
| ACC-17 / STU-02…05 | Узел пропустил уведомление, затем startup/reconnect → сверка БД → актуальный согласованный snapshot; один запрос не смешивает версии | Two-node integration |
| ACC-18 / STU-05 | ID записи другой сущности → CRUD/history/search/export/files → нет доступа через подмену кода/ID | Isolation matrix |
| ACC-19 / UI-этапы | Пользователь без drag / с клавиатурой / mobile → собирает форму и панель → все основные действия доступны, нет зависимости только от цвета/hover | A11y + ручной протокол |
| ACC-21 / STU-02,04 | Открыта форма версии N, опубликована N+1 → сохранение старой формы → сервер проверяет schema revision и новые ограничения; UI сохраняет ввод и предлагает повторную проверку; required/read-only/scope не обходятся | API + E2E |
| ACC-20 / RC | Зафиксированы workload, конфигурация и кандидат → нагрузка/операционные drills → утверждённые SLO и release gates выполнены, результаты сохранены | Target acceptance |

ACC-17 применяется уже к layout/отчётам/панелям, если они активируются без deploy в STU-02/03. Динамические реестры новых сущностей дополнительно проверяются в STU-05.

## 6. Этапы, зависимости и ценность

| Этап | Приоритет | Результат / владелец | Зависимость и выход |
|---|---|---|---|
| STU-00 | P0 инициативы | Достоверность текущих виджетов/графиков; frontend + QA | Независим от хранения. ACC-01…07 |
| STU-01 | P1 | Контракт деклараций и вертикальный прототип настройки одной существующей формы; backend + frontend | Зафиксировать точные лимиты/типы, стабильные ID и границы UI/API. ACC-08…09. Прототип без изменения DB schema |
| STU-02 | P1 | Черновик, версии, dependencies, проверка и пакет публикации; backend + frontend | STU-01; отдельное решение ADR для нового жизненного цикла. ACC-10…11 |
| STU-03 | P1 | Общие отчёты, агрегированный экспорт и именованные панели; backend + frontend + QA | STU-00, минимальная основа STU-02; ACC-12…14,19. Первая самостоятельная ценность Студии |
| STU-04 | P1 | Редактор простых новых форм и CLI/Flyway delivery; backend + frontend + DevOps | STU-01…02; данные и миграции проверены. ACC-15…16,19 |
| STU-05 | P2, либо P1 при обязательной мгновенной публикации | Новая сущность без выпуска приложения; backend + DevOps + QA | Отдельный ADR и сравнение физических таблиц с JSONB; ACC-17…18,20 |
| STU-06 | P2 | Дополнительные charts, подготовленные cross-entity datasets, помощник ИИ | По реальным сценариям после устойчивой основы; ИИ только готовит проверяемый draft |

План улучшен: вместо большого общего «сначала построить всю платформу версий» — вертикальные поставки. STU-01 доказывает минимальный контракт на одной форме; STU-03 даёт пользу до сложной динамической схемы. Нельзя выдавать STU-04 за hot publish.

Предварительная оценка STU-00: 2–4 инженерных дня; STU-01: 5–8. Остальные оценки пересчитываются после прототипа и выбора MVP. Ранее 54–92 дня были грубой суммой, не календарным обещанием и без hot publish. До оценки roadmap нужны число полей/форм/записей, команда и сценарии публикации. Финансовый ROI пока не рассчитан: измерять время создания формы/отчёта и долю изменений без разработчика.
