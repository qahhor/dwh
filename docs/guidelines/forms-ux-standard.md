# Стандарт UI/UX форм

**Версия:** 1.4

**Обновлено:** 2026-10-14

**Основание:** ADR-0012 (UI-фундамент: токены, один способ на задачу),
ADR-0015 (перенос UI-кита, Signal Forms — основной путь форм),
ADR-0019 и ADR-0032 (форма сущности из `form-meta`), ADR-0021 (модель
ошибок, problem+json), ADR-0024 (If-Match и конфликт ревизий), ADR-0031
(семантические ключи переводов), [CODE_STYLE](../../CODE_STYLE.md), раздел 6;
каталог компонентов — [`apps/web/src/app/shared/README.md`](../../apps/web/src/app/shared/README.md).

Краткое правило для всех экранов — [стандарт на одной странице](forms-one-page.md).
Маршруты, вложенные редакторы и применимые операции — [реестр форм](forms-catalog.md).

Документ задаёт, как выглядит и ведёт себя любая форма веб-клиента: диалог,
страница редактирования, панель настроек. Эталон — общая форма сущности
(`smt-entity-form` на странице `/e/<код>/new`) и форма источника UPL
(`sources-list.component.html`: Signal Forms, `smt-control`, подсказки,
ошибки сервера под полями). Механические правила проверяет
`npm run forms:audit` (входит в `npm run lint`, раздел 11).

Язык правил: **должно** — обязательно для новой и переписываемой формы;
**следует** — по умолчанию, отступление объясняется в коде ссылкой на этот
документ.

## 1. Из чего строится форма

| Что | Чем | Не так |
|---|---|---|
| Форма объявленной сущности | `smt-entity-form` (поля, правила, права — из `form-meta`) | своя разметка полей сущности |
| Своя форма с правилами | Signal Forms: `form(model, schema)`, `[formField]` на контроле кита | `ngModel`, `FormsModule` (ESLint запрещает вне кита), флаг `submitted` и ручные проверки в шаблоне |
| Подпись, «*», подсказка, ошибка поля | `smt-control` (`[smtLabel]`, `[smtHint]`, `[smtError]`) | свой `<label>`, `<span class="req">*</span>`, `<span class="field-error">` |
| Поле ввода | `smt-input`, `smt-textarea`, `smt-select`, `smt-data-select`, `smt-multi-data-select`, `smt-date-picker`, `smt-time-picker`, `smt-switch`, `smt-checkbox`, `smt-radio-group`, `smt-money-field`, `smt-file-field` | нативные `<input>`, `<select>`, `<textarea>` |
| Ряд кнопок | `ui-form-actions` | свой `<div footer>` с кнопками |
| Сводка ошибок | `ui-form-error-summary` | список ошибок в тосте |
| Фокус на первой ошибке | `uiFocusFirstInvalid` на `<form>`; `focusFirstInvalid()` для ответа сервера | ничего (фокус остаётся на кнопке) |
| Ошибки сервера по полям | `problemFieldErrors()`; для сущности — `serverProblems()` | общий тост с текстом 422 |
| Диалог | `smt-dialog` (`[smtSize]`: `sm`, `md`, `lg`, `xl`) | своё модальное окно |
| Вопрос «вы уверены?» | `SMTModalService.confirm()` (`destructive: true` для удаления) | отдельный `smt-dialog` с текстом и двумя кнопками |
| Вопрос «Отменить изменения?» | `discardChangesQuestion()` (`shared/ui/discard-changes.ts`) для диалога; `leaveQuestion()` (`shared/ui/leave-question.ts`) в `canLeaveRecordPage()` страницы | свой диалог подтверждения и свои ключи модуля |

Фильтр списка, строка поиска и одиночная настройка без кнопки «Сохранить»
не считаются формой: контрол кита привязывается напрямую
(`[(value)]`), но подпись по-прежнему даёт `smt-control` или `aria-label`.

## 2. Раскладка

### 2.1. Сетка

- Подпись **должна** стоять над полем (`smt-control` так и рисует), не слева.
- Общая форма `smt-entity-form` использует шесть долей с зазором 12px:
  короткий текст (до 64 символов), число, дата, время, переключатель и select —
  две; ссылка, email, телефон, URL и дата-время — три; длинный текст и деньги —
  четыре; многострочный текст, markdown, JSON, файлы и множественная ссылка —
  вся строка. Это правило представления по существующим типам и ограничениям
  metadata, без специальных исключений для модулей.
- При ширине контейнера до 600px все поля занимают полную строку, в том числе
  внутри узкого диалога на широком экране. Порядок DOM и обхода Tab следует
  metadata; уплотнение grid с перестановкой полей не применяется.
- Форма в одну колонку (`display: flex; flex-direction: column; gap: 16px`)
  допустима в диалоге `sm` и в форме до четырёх полей.
- Отступы и цвета — только токены (`var(--space-*)`, `var(--radius-*)`),
  CODE_STYLE, раздел 6.

### 2.2. Размеры диалогов

| `[smtSize]` | Ширина | Для чего |
|---|---|---|
| `sm` | 400px | 1–4 поля в одну колонку: имя роли, email для сброса пароля, подтверждение |
| `md` (по умолчанию) | 580px | обычная форма создания/изменения, до двух колонок |
| `lg` | 800px | форма с разделами или строками, три колонки, редактор с вкладками |
| `xl` | 1100px | конструкторы: отчёт, формат UPL, матрица прав |

Форма больше `lg` или с несколькими экранами данных **следует** делать
страницей (`/e/<код>/new`, `/e/<код>/<id>/edit`), а не диалогом. Ширина
страницы формы — до 960px (`smt-entity-edit-page`).

### 2.3. Разделы и порядок полей

- Разделы — `<fieldset>` с `<legend>` (как `smt-entity-form`): заголовок
  13–14px, полужирный; при одном разделе `legend` скрыт визуально (`sr-only`),
  но остаётся для экранного диктора.
- Порядок: сначала то, что идентифицирует запись (код, затем название),
  потом обязательные поля, потом необязательные, в конце служебные (порядок
  сортировки, состояние). Связанные поля стоят рядом (дата начала и окончания).
- Дополнительные параметры разрешено сворачивать, сохраняя значения; важные
  выбранные параметры показываются в краткой сводке. Ошибка внутри блока
  раскрывает его до перехода фокуса. Обязательные динамические поля остаются
  видимыми. Скрытие блока представления не меняет `visibleWhen` и payload.
- Поле, которое пользователь не может изменить, показывается в том же месте
  (раздел 7), а не исчезает.

## 3. Поле

| Элемент | Правило |
|---|---|
| Подпись | **Должна** быть у каждого поля: `[smtLabel]`, ключ `<модуль>.<экран>.<поле>`. Без двоеточия, с заглавной буквы, существительное: «Название», не «Введите название». |
| Обязательность | `smt-control` ставит «*» (`aria-hidden`) и `aria-required` по правилу `required` схемы. Вручную «*» не рисуется. Если обязательных полей меньше половины, помечаются обязательные; признак «необязательно» не используется. |
| Подсказка | `[smtHint]` под полем, всегда видна, связана через `aria-describedby`. Говорит о формате и ограничениях: «Латиница, цифры и `_`, до 50 символов». |
| Плейсхолдер | Только пример значения (`user@company.com`, `0`), никогда не подпись и не подсказка: он исчезает при вводе и плохо контрастен. Ключ `<поле>_placeholder`. |
| Ограничения | Длина — `maxLength` в схеме; `smt-textarea` показывает счётчик. Числа — `[smtMin]`, `[smtMax]`, `[smtStep]` на `smt-input type="number"`; границы и единицы — в подсказке. |
| Ширина | Поле занимает ячейку сетки целиком; короткое значение (код, число) не растягивается на всю строку — ставьте его в ячейку, а не в полную строку. |

Даты, время, числа и деньги:

- ввод — только пикеры кита (`smt-date-picker`, `smt-time-picker`,
  `smt-money-field`): они берут формат языка интерфейса (`datePattern()`),
  принимают ввод с клавиатуры и отдают ISO-значение;
- вывод в форме только для чтения и в сводке — общие функции
  `fieldText()`, `momentText()`, `moneyText()`
  (`apps/web/src/app/shared/entity/entity-values.ts`), а не свой
  `toLocaleString`; отдельных пайпов форматирования пока нет (раздел 12).

Выбор из списка:

- до ~7 фиксированных вариантов — `smt-select` (или `smt-radio-group`, когда
  все варианты должны быть видны);
- справочник с сервера — `smt-data-select` / `smt-multi-data-select` с
  источником `RefLookups` (поиск, подгрузка страницами);
- «Нет значения» у необязательного выбора — через `allowClear`, а не
  отдельный пункт «—».

## 4. Ошибки проверки

1. **Когда показывать.** Ошибка поля появляется после того, как поле
   потеряло фокус (touched), и у всех полей сразу при попытке сохранить:
   перед `submit()` вызывается `markSMTFormFieldsTouched(form)`. Во время
   набора ошибка не появляется; исправленное значение снимает её сразу.
   Ошибка сервера (`[smtError]`) показывается сразу.
2. **Где.** Под полем, в `smt-control` (красная подпись 12px, рамка поля
   `var(--danger)`, `aria-invalid="true"`, текст связан через
   `aria-describedby`). Тост для ошибки поля не используется.
3. **Сводка.** `ui-form-error-summary` над полями, когда после сохранения
   ошибок три и больше или есть ошибка поля, которого форма не показывает
   (`other` из `problemFieldErrors()`). Ошибки остаются и под полями.
4. **Фокус.** После неудачной попытки сохранить фокус переходит на первое
   поле с ошибкой: `<form uiFocusFirstInvalid>` делает это для проверки на
   клиенте; ответ сервера с ошибками полей — `focusFirstInvalid(form, injector)`
   после того, как ошибки показаны.
5. **Текст.** Сообщения правил — из каталога (`ui.control.*` для встроенных
   правил кита; свои — `<модуль>.<экран>.<поле>_<правило>`), говорят, что
   сделать: «Укажите код», «Не больше 366 дней», а не «Ошибка валидации».
6. **Ошибка не поля** (нет прав, сеть, конфликт) — `smt-alert` над полями
   внутри формы или `SaveErrorNotifier` (раздел 5); форма и введённые данные
   остаются.

## 5. Ответ сервера

- Запрос сохранения отправляется с `notifyError: false`; отказ разбирает
  экран.
- **422 с ошибками полей.** `problemFieldErrors(problem, { known, rename })`
  раскладывает `errors[].field` (а также `pointer` и `invalid_params[].name`)
  по полям формы: `fields` → `[smtError]` каждого `smt-control`, `other` →
  сводка. Для сущности то же делает `serverProblems()` из `form-meta`.
- **409 `revision_conflict` / 428** (ADR-0024) — `SaveErrorNotifier.show()`
  с `reload`: тост с кнопкой «Обновить»; форма не закрывается.
- **Прочие отказы** — `SaveErrorNotifier.show()` с ключом
  `<модуль>.<экран>.save_failed` / `create_failed`; текст сервера (`detail`)
  важнее своего.
- **Успех** — тост `<модуль>.<экран>.created` / `updated` (ADR-0031: роль, не
  пересказ), затем закрытие диалога или переход к записи. Тост не дублирует
  то, что пользователь и так видит (новая строка в списке подсвечена).

## 6. Кнопки

- Ряд кнопок — `ui-form-actions`. В диалоге он помечается `footer`, и
  `smt-dialog` держит его внизу, пока тело прокручивается; на странице он
  стоит под формой, выровнен вправо.
- Порядок слева направо: [действие отдельно слева] … «Отмена» (secondary),
  основное действие (primary) — **справа**. Одно основное действие на форму.
- Тексты: «Сохранить» (`common.save`, по умолчанию) для изменения,
  «Создать» (`common.create`) для новой записи, «Отмена» (`common.cancel`),
  «Закрыть» (`common.close`) в окне только для чтения, «Удалить»
  (`common.delete`). Своя формулировка — только когда она точнее
  («Отправить ссылку», «Загрузить»), ключ `<модуль>.<экран>.<действие>`.
  Копии общих текстов в модуле (`upl.common.cancel`, `iam.org_units.save`)
  не заводятся.
- Основная кнопка — `type="submit"` формы (`form="<id формы>"` у
  `ui-form-actions`), поэтому Enter в поле и кнопка вызывают один обработчик.
- **Сохранение идёт:** основная кнопка показывает спиннер кита и недоступна
  (`[submitting]`), «Отмена» тоже недоступна; обработчик дополнительно
  выходит, если сохранение уже идёт (`if (saving()) return`): одна
  отправка на нажатие.
- **Кнопка не блокируется из-за неверных данных.** Нажатие показывает ошибки
  (раздел 4) — так человек узнаёт, что исправить. `submitDisabled` — только
  для состояния, которое форма исправить не может: нет права, ещё нечего
  сохранять в редакторе с явным «Сохранить изменения» (матрица прав, формат
  UPL).
- Разрушительное действие (удалить запись) — отдельно слева
  (`uiFormActionsStart`, `smtVariant="danger"`) и всегда через
  `SMTModalService.confirm({ destructive: true })`. Окно подтверждения
  удаления: основная кнопка «Удалить» (`submitVariant="danger"`).

## 7. Только чтение и недоступность

- **Только чтение** (нет права на поле, поле закрыто состоянием записи,
  ADR-0032 5.2): значение видно и выделяется для копирования; рисуется тем же
  контролом в состоянии disabled кита либо текстом (markdown — просмотром).
  Объяснение — в подсказке поля, если причина неочевидна.
- **Недоступно** (`disabled`): поле временно не участвует (идёт сохранение,
  зависит от другого поля). Отключённое поле не проверяется и не попадает в
  ошибки.
- Скрытое правилом `visibleWhen` поле не показывается вовсе; значение
  скрытого поля не отправляется (как `recordPayload()`).

## 8. Открытие, закрытие и несохранённые изменения

- **Фокус при открытии:** первое редактируемое поле (`[smtFocusInitial]` у
  `smt-input`; у прочих — `cdkFocusInitial` на поле). Не кнопка закрытия.
  Без явного маркера CDK выбирает первый доступный контроль содержимого.
  Крестик остаётся в заголовке, но следует за содержимым в порядке Tab;
  Shift+Tab с первого контрола возвращает к нему внутри ловушки фокуса.
- **Escape**, клик по фону и крестик только просят закрыть (`(closed)` у
  `smt-dialog`); экран решает. Пока идёт сохранение, диалог не закрывается.
- **Enter** в однострочном поле отправляет форму (форма — настоящий
  `<form novalidate (submit)="$event.preventDefault(); save()">`); в
  `smt-textarea` и markdown Enter — перевод строки.
- **Несохранённые изменения:** если форма изменена (значение отличается от
  исходного), закрытие диалога (Escape, фон, крестик, «Отмена») и уход со
  страницы спрашивают `SMTModalService.confirm({ destructive: true })`:
  «Отменить изменения?» — «Изменения будут потеряны». Вопрос один на все
  формы: `discardChangesQuestion()` из `shared/ui/discard-changes.ts`
  (ключи `common.discard.title|message|confirm|keep`); `formChanged()` оттуда
  же сравнивает значения с исходными. Страница — через
  `canDeactivate: [recordNavigationGuard]` и `canLeaveRecordPage()`, который
  возвращает `leaveQuestion()`: вытесненный переход и тот, что его заменил,
  получают один открытый вопрос, а вопрос, который больше никто не ждёт
  (выход по истёкшей сессии), закрывается сам. Нетронутая форма закрывается
  без вопроса.
- Общий вопрос используют также оргструктура, назначения подразделений и
  области доступа. Начальный фокус — «Продолжить редактирование». Отзыв
  прав, уничтожение экрана или отменённая навигация закрывают устаревший
  вопрос без подтверждения действия; `closeWhen` отменяет его подписку.
- После успешного сохранения диалог закрывается, фокус возвращается к
  элементу, который его открыл (это делает `SMTModalService`).

## 9. Состояния формы

- **Загрузка** записи для изменения: вместо формы — состояние загрузки
  (`role="status"`, текст `common.loading`), не пустые поля.
- **Ошибка загрузки:** сообщение и «Повторить» (`smt-entity-page-state`),
  форма не показывается.
- **Нет права** создать или изменить: состояние «нет доступа», а не форма с
  отключённой кнопкой.
- **Пустой справочник** в выборе: текст «Нет вариантов» кита и, если
  есть право, ссылка «Создать» (как выбор источника в загрузке UPL).

## 10. Доступность и тексты

- У каждого поля есть доступное имя (`label for` от `smt-control`, у
  составных контролов — `aria-labelledby`); подсказка и ошибка связаны
  `aria-describedby`; ошибка ставит `aria-invalid="true"`; обязательность —
  `aria-required`. Всё это делает `smt-control`, вручную не дублируется.
- Сводка ошибок — `role="alert"`; ссылки сводки переводят фокус на поле.
- Порядок Tab совпадает с визуальным; ловушку фокуса диалога даёт CDK.
- Цвет — не единственный признак ошибки: всегда есть текст.
- Тексты форм — ключи по ADR-0031: `<модуль>.<экран>.<поле>` (подпись),
  `<поле>_hint`, `<поле>_placeholder`, `<поле>_<правило>` (ошибка),
  `title`, `created`, `updated`, `save_failed`; общие кнопки —
  `common.save|create|cancel|close|delete`; тексты кита — `ui.control.*`,
  сводка — `ui.form.error_summary`. Русский каталог — источник, uz и en
  полные (`npm run i18n:sync-ru`, `npm run i18n:audit`).

## 11. Проверка

`apps/web/scripts/forms-audit.mjs` (`npm run forms:audit`, входит в
`npm run lint`) проверяет шаблоны `features`, `layout`, `shared/entity`,
`shared/ui`:

| Правило | Что находит |
|---|---|
| `raw-control` | нативный `<input>`, `<select>`, `<textarea>` вместо контрола кита |
| `raw-label` | свой `<label>` вместо `smt-control [smtLabel]` |
| `manual-required` | свой знак «*» (`class="req"`, одиночная `*`) |
| `manual-error` | своя ошибка поля (`field-error`, `error-text`, `upl-field-error`) |
| `dialog-footer` | футер диалога не через `ui-form-actions` |
| `disabled-invalid` | кнопка, отключённая из-за неверных данных |
| `module-button-key` | ключ модуля с текстом общей кнопки («Сохранить», «Отмена», …) |
| `literal-label` | статический текст в `[smtLabel]` / `[smtHint]` / `[smtTitle]` |

`apps/web/scripts/forms-audit-baseline.json` пуст: все три волны завершены,
механические исключения отсутствуют. Новый код не должен увеличивать baseline.
Ноль нарушений этого скрипта не доказывает корректность blur, серверных ошибок,
сохранения и отмены: их проверяют поведенческие тесты и браузерная приёмка.
Составные контролы, которые сами
оборачивают нативный элемент (деньги, markdown, командная палитра),
перечислены в скрипте (`OWN_CONTROLS`) с причиной. Остальное проверяют:
`smt-control` (подпись, aria), `npm run i18n:audit` (кириллица в коде,
ключи), `npm run aria:audit` и `e2e` a11y (axe) на собранных экранах.

## 12. Форматирование значений

Общий runtime форматирует значения функциями `entity-values.ts`; специальные
шаблоны используют `DatePipe` с явным числовым форматом. Для полных дат
и времени не использовать `short`/`medium`: их вид зависит от locale Angular
и может расходиться с выбранным языком интерфейса. Заметки, задачи и
операционные журналы следуют тем же правилам; при необходимости журнал
сохраняет секунды. Время показывается в часовом поясе пользователя.

## Приложение B. Общие исправления поведения

- `smt-entity-form` и строки документа отмечают уход с редактируемого поля,
  после отправки проверяют все доступные поля и снимают устаревшие ошибки
  при исправлении. Переход внутри составного контрола не считается уходом.
- Ошибки строк следуют за строками при перемещении и удалении; общая сводка
  формы ведёт к полю нужной строки. Неизвестная серверная ошибка остаётся
  в сводке, без выдуманной подписи поля.
- Общая таблица по умолчанию выводит `dd.MM.yyyy` и `dd.MM.yyyy HH:mm`, как
  карточка сущности. Явный формат колонки остаётся приоритетным; 24-часовой
  формат не содержит AM/PM. Формат ввода задаёт язык пикера.
- Сегментированный переключатель сохраняет читаемые подписи; на узком
  экране допускается перенос вариантов.

Исторические волны миграции: IAM/auth/profile — 86 нарушений, settings/UPL/
notifications/layout — 73, tasks/shared/остальное — 72; все приведены к нулю.

## 12. Уточнения после проверки наполненного стенда

- Заголовок вложенного экрана — h2: `ui-page-header.headingLevel=2`;
  на странице остаётся один h1. Ошибка чтения настроек меню сохраняет старые
  записи и доступный повтор, а пустой поиск предлагает очистку.
- Все мобильные действия до 767 px имеют область не меньше 44×44 px.
  Размер видимого индикатора switch при этом не меняется. Ширина колонки
  включает кнопки, промежутки и padding ячейки.
- Скрытые контролы checkbox ограничены позиционируемой обёрткой; доступная
  таблица диаграммы скрыта обёрткой, а не самой таблицей. Они не расширяют
  страницу за пределы видимой области. Высота меню учитывает его координату.
- В диалоге несохранённых прав `ui-form-actions.cancelFocusInitial` выбирает
  безопасное «Продолжить редактирование». Значения уровней доступа в выборе
  участников совпадают с серверным контрактом R/W, начальное значение — R.
  Повторный поиск после очистки или открытия диалога выполняется снова;
  загрузка, отсутствие результата и ошибка с повтором различаются.
- Общий drawer начинает Tab-порядок с содержимого; крестик закрытия остаётся
  в заголовке визуально, но следует за содержимым в DOM. Фильтр сохраняет
  внутренние отступы и доступное удаление условия на мобильной ширине.
- «Добавить участника» не меняет существующий доступ: дубликат возвращает
  ошибку поля, даже если участник находится за пределами загруженной страницы.
  Явное изменение доступа описано в руководстве модулей.
