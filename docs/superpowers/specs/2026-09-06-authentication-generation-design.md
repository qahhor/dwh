# Версия доступа и конкурентная смена пароля

**Дата:** 2026-09-06

**Статус:** подход согласован пользователем; подробный дизайн ожидает проверки перед планом реализации.

**Область:** серверный контур смены пароля, выдачи и отзыва доступа. Это проект изменения, не свидетельство исправления или production readiness.

## 1. Основание и границы

Нормативная основа — `FR-AUTH-01`–`FR-AUTH-05`, `FR-IAM-01` и
`FR-IAM-05` в [каноническом ТЗ](../../technical-specification.md).
Сохраняются [ADR-0014](../../adr/ADR-0014-unified-open-source-runtime.md),
граница `kauth → md` и [правила миграций](../../guidelines/database-migrations.md).

Пользователь выбрал версию доступа вместо единой длительной блокировки
пользователя на весь вход. Проверяемый исходный commit — `6c80748`; поверх него
уже есть локальное изменение обычной смены пароля и связанного интерфейса.
Оно не считается завершением конкурентной части этого дизайна.

Включено:

- обычная и обязательная смена собственного пароля через оба существующих URL;
- cookie-сессии, API-токены и OTP первого шага входа;
- адаптация общего OTP-хранилища для существующего `channel_verify`;
- сохранение общего механизма отзыва при блокировке и анонимизации пользователя;
- forward migration, PostgreSQL concurrency tests и изолированная приёмка.

Не включено:

- восстановление пароля H01: его UI, доставка, reset-repository и контракт
  подтверждения требуют отдельного дизайна; исправлять только имя таблицы и
  тем самым включать прежний небезопасный сценарий запрещено;
- исправление всех ошибок OTP, включая откат счётчика неудачных попыток и
  привязку подтверждения канала к конкретной редакции адреса;
- изменение RBAC, CSRF, rate limits, формата публичных запросов или вида секретов;
- отмена уже выполняющихся бизнес-запросов и принудительное завершение SSE;
- отзыв всех пользователей только из-за установки новой версии приложения;
- push, изменение рабочей установки, production migration или deploy.

Следовательно, приёмка этого пакета закрывает конкурентную часть **обычной
смены пароля**, но не весь `FR-AUTH-04`, пока отдельно не принят reset-сценарий.

## 2. Подтверждённая причина

В текущем коде `MdUserService.changePassword` читает хеш, проверяет пароль и
выполняет безусловный `MdUserRepository.updatePassword`. Два запроса могут
проверить один старый хеш и последовательно записать разные новые пароли.

`KauthAuthService` создаёт сессию после отдельного чтения пользователя и
проверки пароля/OTP. `KauthApiTokenService` создаёт токен по `userId`, не сохраняя
версию исходного доказательства входа. Массовые UPDATE отзыва не видят строку,
которую другой запрос вставит позднее. Один вызов invalidator этого не исправляет.

Эти выводы основаны на текущих service/repository/filter, а не на статусе
локального audit-черновика. Контрольные точки:

- `MdUserService.changePassword`, `setUserState`, `anonymizeUser`;
- `KauthAuthService.login`, `verifyOtp`;
- `KauthApiTokenService.createToken` и `KauthAuthenticationFilter`;
- `KauthUserSessionInvalidator` и три credential-repository.

## 3. Выбранное решение

У пользователя хранится монотонная `auth_version`. Каждая сессия, API-токен и
OTP хранит **версию доказательства, на основании которого он выдан**.
Credential действителен только при совпадении с текущей версией пользователя.

Сравнение хеша и версии при записи пароля выполняется условным UPDATE
(compare-and-set, CAS). Увеличение версии, запись нового пароля, физический
отзыв существующих сессий/токенов и security audit входят в одну транзакцию.

Альтернатива — общий user-row lock, повторная проверка каждого доказательства
под ним и единый порядок блокировок во всех issuance paths. Она отклонена как
основной подход: добавляет длительные критические секции и требует особенно
осторожного взаимодействия с хешированием и синхронной отправкой OTP.
Обычные короткие row locks самих UPDATE сохраняются и при выбранном решении.

Глобальный `SERIALIZABLE`, Redis, JWT, новый provider и процессный mutex не нужны.
Авторизация не использует Typesense или закэшированную «последнюю версию».

## 4. Инварианты и точная граница гарантии

1. После commit глобального отзыва новый authentication lookup не принимает
   credential предыдущей версии, даже если его строка вставлена после bulk UPDATE.
2. Выдача не может повысить старое доказательство до новой версии: запрещено
   повторно читать текущую `auth_version` и подставлять её вместо исходной.
3. Для двух смен пароля с одинаковыми исходными хешем и версией успешно
   фиксируется не более одной. Проигравший запрос не повторяется автоматически.
4. Ошибка invalidator или audit откатывает пароль, флаг обязательной смены,
   версию и физические признаки отзыва вместе.
5. Разблокировка не уменьшает версию и не оживляет старые credentials.
6. Действия одного пользователя не меняют версию и доступ другого.
7. Уведомление об успехе и HTTP success появляются только после commit сервиса.

Под «новым lookup» понимается запрос проверки с новым PostgreSQL snapshot,
полученным после commit отзыва. Запрос, прошедший проверку раньше, может
завершиться; это не обещание отмены всех in-flight операций. Но выпущенный им
credential несёт старую версию и не становится доступом новой версии.

| Порядок событий | Допустимый результат |
|---|---|
| Прочитана версия 4 → отзыв commit версии 5 → попытка выдачи с 4 | Отказ; либо строка с 4 из перекрывающегося statement snapshot, которая не проходит новую проверку |
| Credential с 4 выдан → отзыв commit версии 5 | Credential больше не принимается |
| Отзыв commit версии 5 → новый успешный вход с новым паролем | Credential выдаётся с 5 и принимается |
| Две смены прочитали один хеш/версию | Один commit; второй получает ошибку устаревших учётных данных |

При перекрывающихся операциях возможен HTTP success со credential, который
успел стать недействительным до следующего запроса. Это допустимо; выдача
**действующего** credential новой версии по старому доказательству — недопустима.

## 5. Схема и совместимость

Следующая свободная миграция на текущей базе —
`V025__authentication_generation.sql`. Перед реализацией номер проверяется
снова; опубликованные V001–V024 не редактируются.

| Таблица | Новое поле | Начальное значение |
|---|---|---|
| `md_users` | `auth_version bigint not null default 0 check (auth_version >= 0)` | 0 |
| `kauth_sessions` | то же поле | 0 |
| `kauth_api_tokens` | то же поле | 0 |
| `kauth_otp_codes` | то же поле | 0 |

Начальное значение 0 сохраняет ранее действовавшие credentials; признаки
`closed_at`, `revoked_at`, `is_used`, expiry и состояние пользователя не
сбрасываются. Миграция не удаляет историю и не создаёт сырые секреты.
Она не доказывает, что до обновления никогда не происходила компрометация.

Все новые production INSERT передают версию явно. Default 0 обеспечивает
совместимость добавления схемы, а не заменяет snapshot при выдаче.
Переполнение bigint завершает транзакцию ошибкой; сброс или повторное
использование старой версии запрещены.

В Java репозиторные записи получают `long authenticationVersion`.
`MdUserView` остаётся без этого поля. Сессионные/token HTTP responses также
не получают новое внутреннее поле: оно исключается из JSON-проекции и
проверяется тестом. Имена и типы существующих публичных полей не меняются.

Необходимые token-hash indexes и PK пользователя уже существуют. Новые
глобальные cache, таблицы и индексы «на всякий случай» не добавляются.

## 6. Владение транзакцией и отзыв

Порт `md.UserSessionInvalidator.invalidateAllAccess(Long userId)` сохраняет
направление зависимости. Его реализация в `kauth`:

1. увеличивает `md_users.auth_version` на 1 через `MdUserRepository`;
2. закрывает существующие открытые сессии пользователя;
3. отзывает существующие API-токены пользователя.

Применяется `@Transactional` с обычным REQUIRED propagation: вызов из MD
участвует в уже открытой транзакции; standalone вызов через Spring proxy тоже
атомарен. `REQUIRES_NEW` здесь запрещён.

OTP предыдущих версий логически недействительны. Массовый UPDATE всех OTP
при отзыве не нужен: отказ определяется версией. Это не добавляет обратной
блокировки OTP → пользователь к существующему порядку отзыва. История
использования OTP не подменяется фиктивным успешным потреблением.

Смена пароля, блокировка и анонимизация вызывают этот порт ровно один раз в
своей успешной транзакции. Разблокировка его не вызывает. Обычный logout,
закрытие отдельной/всех cookie-сессий и удаление отдельного API-токена сохраняют
свою текущую область действия: они не отзывают все виды доступа через bump версии.

## 7. Смена пароля без перезаписи победителя

Контроллер берёт `userId` и `authenticationVersion` только из серверного
principal. Клиент продолжает передавать только `oldPassword` и `newPassword`.
Оба URL используют один сервисный метод:

```java
void changePassword(Long userId, long authenticatedVersion,
                    String oldPassword, String newPassword);
```

Сервис читает пользователя, требует активное состояние и совпадение версии
principal с прочитанной версией. Далее применяет текущую проверку старого
пароля и действующий password validator, вычисляет новый Argon2id hash и
вызывает репозиторий:

```java
boolean compareAndSetPassword(Long userId, long expectedAuthVersion,
                             String expectedPasswordHash, String newPasswordHash);
```

Условие UPDATE включает `id`, `state = 'A'`, `auth_version` и
`password_hash IS NOT DISTINCT FROM :expectedPasswordHash`. Запись меняет
хеш, `password_changed_at`, `force_password_change = false` и `modified_at`.
Этот UPDATE **не** увеличивает версию: единственный владелец bump — invalidator.

Ноль изменённых строк означает `INVALID_CREDENTIALS` / HTTP 401; новый пароль
не записывается, audit успеха не создаётся, invalidator не вызывается.
После одного обновления вызываются invalidator и существующий `PASSWORD_CHANGED`
audit. Row lock UPDATE удерживается до завершения всей транзакции.

При READ COMMITTED PostgreSQL повторно проверяет WHERE после ожидания
конкурентного UPDATE. Это основание для CAS, а не утверждение, что отдельные
SELECT и UPDATE сами по себе атомарны.
Источник: [PostgreSQL 18 — Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED).

Legacy `updatePassword` в незавершённом reset-сценарии не используется для
обычной смены. Его удаление/замена и привязка reset-доказательства к версии
входят в H01; поддерживаемое восстановление пароля пока не заявляется.

## 8. Выдача и проверка credentials

### 8.1. Парольный вход

`KauthAuthService.login` получает хеш, состояние и версию в одном `UserRecord`.
После проверки пароля эта версия передаётся в INSERT сессии либо login OTP.
Репозиторий не подставляет более новую версию пользователя.

INSERT сессии/OTP использует параметр исходной версии и проверяет активного
пользователя с этой версией (`INSERT … SELECT … WHERE`). Отсутствие строки
результата превращается в отказ входа, без успешной cookie или OTP response.
Существующая синхронная доставка OTP не переносится под новый user-row lock.

### 8.2. Второй фактор

OTP lookup проверяет token hash, purpose, expiry, остаток попыток, `is_used`,
активность пользователя и совпадение версий. После корректного кода
conditional consume допускает ровно один успешный claim:
`is_used = false`, `attempts_left > 0`, ещё не истёк и версия совпадает.

Сессия наследует версию OTP, а не пользователя из позднего SELECT.
Claim OTP и INSERT сессии входят в одну транзакцию. При ошибке записи сессии
claim откатывается. Устаревший/повторно использованный OTP возвращает
существующую ошибку `OTP_INVALID`, без выдачи cookie.

Общий repository требует явную версию и для `channel_verify`. В bind она
берётся из authenticated principal, в confirm проверяется принадлежность
пользователю, purpose и версия. Изменение адресной модели канала и бюджетов
неверных попыток не маскируется под эту адаптацию.

### 8.3. API-токены и principal

`SecurityContext.KauthPrincipal` сохраняет существующие поля и добавляет
`long authenticationVersion` и идентификатор исходного API-токена.
Для cookie используется существующий `sessionId`; для Bearer сохраняется
`apiTokenId`, который сейчас теряется при построении principal.

`KauthApiTokenService.createToken` получает серверное доказательство, а не
голый `userId`. Проверяются принадлежность исходной сессии/токена, отсутствие
отзыва/истечения, активность пользователя и исходная версия. Новый токен
получает ровно эту версию. Нет пути «старый principal → прочитать новую
версию → выпустить новый действующий токен».

Повторная проверка отдельного исходного credential не расширяет обещание
глобальной линейности на обычный logout. Уже выполняющиеся запросы и
параллельный отзыв только одной сессии сохраняют границу из раздела 4.

### 8.4. Проверка входящего запроса

Session/token active lookup соединяет credential с `md_users` и требует
равенства версий, активного состояния и прежних условий validity.
При последующем чтении пользователя filter не должен повысить версию
доказательства; если версии расходятся, он не аутентифицирует запрос.

`findActiveByUserId` для сессий использует тот же predicate: запоздалая
строка старой версии не показывается как активная. Обновление last-used/
last-seen не меняет версию и не восстанавливает доступ. Старые token catalog
records остаются историей; наличие строки не означает валидность секрета.

## 9. Ошибки, секреты и существующий UI

- CAS conflict и недействительное authenticated доказательство: существующий
  HTTP 401; новая password-policy ошибка остаётся HTTP 422.
- Не добавлять silent retry при смене пароля или генерации нового секрета.
- Не писать исходные пароли, OTP, cookie, Bearer или hash в сообщения ошибок,
  логи и test artifacts. Версия не является секретом, но не нужна публичному API.
- CSRF и permission interceptor остаются обязательными и не обходятся тестами.
- Успешная смена заканчивает прежний вход, включая текущий; интерфейс уже
  подготовлен к повторному входу. Ошибка сохраняет возможность исправить ввод.
- UI unit tests не заменяют проверки серверной версии и реального HTTP отказа.

## 10. Миграция, запуск и откат

Проверяются пустая БД и upgrade с V024, содержащей активные/закрытые сессии,
действующие/отозванные/истёкшие токены и OTP разных purpose. После upgrade
версии равны 0, прежние признаки validity сохранены, business data и audit
не изменены. Повторный Flyway migrate ничего не меняет.

Для будущего rollout необходимо остановить/дренировать старый server до
включения нового механизма. Старый и новый writer не работают совместно:
старый код не проверяет `auth_version` и не увеличивает её при отзыве.
Это ограничение совместимости безопасности, даже при аддитивной SQL-схеме.

Application-only rollback к старому server не объявляется безопасным после
использования новых версий. Нужен отдельно проверенный совместимый forward
fix либо операторский restore по существующему runbook. Restore также требует
оценки credentials, действовавших на момент backup. Ни миграция, ни этот
документ не разрешают автоматически сбрасывать доступ всех пользователей.

На данном этапе миграции применяются только к disposable PostgreSQL и новому
изолированному candidate. Существующий `localhost:4200`, его данные и образы
не меняются без отдельного разрешения.

## 11. Критерии приёмки

Каждая гонка воспроизводится на PostgreSQL 18 двумя настоящими транзакциями.
Порядок задаётся latch/barrier с ограниченным timeout, а не `sleep`.
Spring transaction proxy используется в тестах use case; мок целиком
`KauthAuthService` не считается доказательством выдачи или повторного входа.

| Проверка | Обязательный результат |
|---|---|
| Две смены одного старого пароля | Один успех, один 401; итоговый hash победителя; один bump и один audit успеха |
| Старый principal после смены, даже с новым правильным паролем | Отказ; невозможно обойти отзыв чтением свежего UserRecord |
| Пароль проверен → пауза → смена commit → продолжение login | Нет credential новой версии; старый credential получает 401 при новой проверке |
| То же для создания login OTP | Старое доказательство не выдаёт сессию после завершения второго фактора |
| Валидный OTP → пауза → смена commit → продолжение verify | Нет действующей сессии; новая проверка прежнего OTP отклоняется |
| Два одновременных правильных подтверждения одного OTP | Не более одной выдачи сессии; атомарный claim |
| Cookie/Bearer principal → пауза → смена commit → create API token | Нет действующего токена новой версии; оба источника проверены отдельно |
| Новая сессия пытается использовать старое channel_verify | Отказ по версии и принадлежности; успешное новое подтверждение не сломано |
| Блокировка → разблокировка | Старые сессии, токены и login OTP не оживают |
| Анонимизация и конкурентный login/OTP | Старые credentials не принимаются; нет неконтролируемого deadlock |
| Ошибка после реальных revocation writes | Hash, forced flag, версия, сессии, токены и audit откатились |
| Другой пользователь | Его hash, версия и доступ не изменены |
| Migration upgrade/repeat/readiness | V024 → новая версия, данные сохранены, повтор безопасен, старая схема не ready |
| HTTP контракт | Оба password URL, Cookie+CSRF, Bearer, forced-change и негативные случаи сохранены |
| Реальный browser E2E | Bootstrap → обязательная смена → второй вход; profile change → выход → новый вход |

Для последнего пункта нужны реальные server и PostgreSQL с синтетическими
учётными записями. Фикстурный frontend с подставленными API-ответами не
засчитывается. Проверяются 401 старого пароля/сессий/API-токенов и успешный
вход с новым паролем; UI не получает скрытого автоматического входа.

После focused RED/GREEN выполняются полный Maven verify, Angular tests,
app/E2E typecheck, i18n audit, production build, relevant architecture/docs
gates, изолированный browser E2E и независимый code review. Известные
несвязанные failures фиксируются отдельно и не скрываются.

## 12. Карта реализации и следующий gate

Реализация затронет:

- новую Flyway migration и migration/upgrade tests;
- `MdUserRepository`, `MdUserService`, порт и `KauthUserSessionInvalidator`;
- session/token/OTP repositories и соответствующие сервисы;
- `SecurityContext`, `KauthAuthenticationFilter`, password/token controllers;
- адаптацию `KauthChannelService` к versioned OTP;
- PostgreSQL regression tests, существующий OTP integration test и HTTP tests;
- постоянный password-change browser regression и проверенный handoff.

Подробный пошаговый implementation plan создаётся **после проверки этого
документа пользователем**. В нём должны быть точные signatures, файлы,
самостоятельные RED/GREEN шаги, migration acceptance и критерии review.
До этого gate новый authentication код и миграция не пишутся.
