# ADR-0003: Модель RBAC и аудита на PostgreSQL (изначально — с мультиарендностью)

**Статус:** Частично заменён ADR-0014 (2026-09-03)
**Дата:** 2026-08-26
**Решают:** CEO/Founder, техлид платформы
**Зависит от:** ADR-0001, ADR-0002

> Историческое решение ниже сохраняется для трассируемости. Положения о
> Control Plane, fleet, лицензировании, Nomad, Consul и обязательном Vault
> больше не описывают поддерживаемый runtime.

> **Примечание 2026-08-27:** решением CEO продуктовая модель изменена на «экземпляр на клиента»
> (ADR-0004). Раздел **разд. 2.1 (изоляция: company_id + RLS) не действует** — изоляция физическая,
> `company_id` удалён из схемы. Разделы **разд. 2.2 (RBAC)** и **разд. 2.3 (аудит)** действуют в рамках
> одного экземпляра: все ключи читать без `company_id`.

---

## 1. Контекст

Система обслуживает многих клиентов (арендаторов). Внутри арендатора — пользователи,
роли, доступ к формам. Модель прав Biruni проверена в проде и её семантику мы сохраняем
(ADR-0001 разд. 6), **за одним упрощением**: филиального разреза прав нет (решение CEO 2026-08-26) —
право выдаётся как `(user, role)` без измерения `filial_id`. Вопросы этого ADR:

1. Как изолировать арендаторов в PostgreSQL.
2. Как устроить RBAC: хранение, вычисление и проверку эффективных прав.

## 2. Решения

### 2.1. Изоляция арендаторов: общая схема + `company_id` во всех таблицах + RLS

Рассмотрены три стандартных варианта:

| Вариант | Изоляция | Стоимость эксплуатации | Миграции | Вердикт |
|---|---|---|---|---|
| A. База на арендатора | Максимальная | Высокая (N баз × бэкапы × миграции) | N прогонов | Нет |
| B. Схема на арендатора | Средняя | Средняя, но каталог растёт с N | N прогонов | Нет |
| C. Общие таблицы, `company_id` в ключах + **Row-Level Security** | Логическая, принудительная на уровне БД | Низкая | 1 прогон | **Да** |

Выбор C повторяет модель Biruni (там — `company_id` в составном PK каждой таблицы) и добавляет
то, чего в Oracle-версии не было: **декларативную защиту RLS**. Политика на каждой таблице:

```sql
alter table t enable row level security;
create policy tenant_isolation on t
  using (company_id = current_setting('app.company_id')::bigint);
```

Приложение при получении соединения из пула выставляет `set_config('app.company_id', :id, false)`
и сбрасывает при возврате. Эффект: даже ошибочный запрос без `where company_id = ?` физически
не увидит чужие строки. Это страховка, а не замена фильтрам — фильтры в запросах остаются
(планировщику так лучше).

Ключи — как в Biruni: PK `(company_id, entity_id)` + уникальный индекс по `entity_id`
(глобальная последовательность). FK всегда составные — `(company_id, ref_id)` — чтобы ссылка
не могла указать на строку другого арендатора.

### 2.2. RBAC: реестр форм/действий + роли + материализованные эффективные права

Семантика Biruni, перенесённая 1:1 на PostgreSQL (соответствие таблиц — в ТЗ разд. 6):

- **Каталог**: `forms` (реестр форм), `form_actions` (действия формы). Заполняются из кода при
  старте приложения (аннотации/регистрация), а не руками — каталог не может разойтись с кодом.
- **Назначение прав**: роль → набор `(form, action)`; `*` — доступ к форме целиком.
  Роль назначается пользователю напрямую: `(company_id, user_id, role_id)` — без филиального
  разреза (упрощение относительно Biruni, см. разд. 1).
- **Персональные права** поверх ролей: `(company_id, user_id, form, action)` — как
  `md_user_form_actions`, но без `filial_id`.
- **Скрытие колонок**: `(role_id, form, grid, column)` — как `md_role_revoked_columns`.

**Материализация.** В Biruni эффективные права пересчитываются в `md_gen_user_form_actions`
(через global temporary «dirty»-таблицы). Нам нужна та же идея, но проще:

| Вариант | Оценка |
|---|---|
| A. Вычислять права на каждый запрос (join ролей) | Просто, но 3–4 join на каждый HTTP-запрос |
| B. Материализованная таблица `effective_permissions`, пересчёт по событию изменения ролей/прав | Как в Biruni; выбранный вариант |
| C. Кэш только в приложении | Инвалидация между инстансами сложнее, чем таблица + версия |

Выбор B: таблица `effective_permissions(company_id, user_id, form, action)`,
пересчитываемая **синхронно в той же транзакции**, где меняются роли/назначения (объёмы прав —
тысячи строк на пользователя, это дёшево). Поверх — кэш в приложении с инвалидацией по
`permissions_version` на пользователя (инкремент при пересчёте; проверка версии — одно чтение
по PK или слушатель `LISTEN/NOTIFY`).

Проверка права в рантайме — одна функция: `has(userId, form, action)` → lookup в кэш →
при промахе один запрос по PK в `effective_permissions`.

### 2.3. Аудит: одна таблица + generic-триггер (вместо X/Y-генерации)

В Biruni аудит — DDL-генерация X-таблицы и Y-триггера на каждую таблицу. В PostgreSQL то же
достигается одним универсальным триггером, пишущим в одну таблицу:

```sql
audit_log(
  audit_id bigint generated always as identity,
  company_id bigint not null,
  table_name text not null,
  row_pk text not null,
  event char(1) not null,          -- I/U/D
  changed_by bigint,
  changed_at timestamptz not null default now(),
  session_id bigint,
  old_row jsonb,
  new_row jsonb,
  changed_columns text[]
) partition by range (changed_at);
```

`old_row`/`new_row` — `to_jsonb(OLD/NEW)`; `changed_columns` вычисляется в триггере. Партиции
по месяцам, старые уходят в архив/детач. Контекст (`changed_by`, `session_id`) передаётся через
`set_config('app.user_id', ...)` — тот же канал, что и для RLS. Включение аудита на таблицу —
`create trigger`, без генерации DDL-объектов. Семантика X-таблиц (кто/что/когда/какие колонки)
сохранена полностью.

## 3. Компромиссы

- **RLS стоит немного производительности** (предикат на каждый запрос). Для B2B-нагрузки CMS
  это копейки; выигрыш в защите несоизмерим. На DWH-этапе для тяжёлых витрин RLS можно осознанно
  не включать (доступ туда только через сервис).
- **Синхронный пересчёт прав** упрощает согласованность, но операция «выдать роль всем 10 000
  пользователям» станет заметной транзакцией. Порог: если объём пересчёта > N строк — уводим
  в фоновую задачу (флаг «права пересчитываются»). Реализуем, когда появится реальный кейс.
- **JSONB-аудит** дороже по месту, чем колоночные X-таблицы. Компенсируется партициями и сжатием;
  зато нулевая стоимость подключения новых таблиц.

## 4. Последствия

- Изоляция арендаторов проверяется автотестом: пользователь арендатора A не видит данные B
  даже при намеренно испорченном запросе (тест на RLS обязателен в CI).
- Любая новая таблица обязана: иметь `company_id`, составные FK, RLS-политику, аудит-триггер
  (если данные бизнес-значимые). Прописать в шаблоне миграции.
- Каталог форм всегда соответствует коду — «мертвые» права чистятся при старте (мягко: помечаются).
