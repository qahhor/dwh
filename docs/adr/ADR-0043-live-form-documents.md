# ADR-0043: документы живых форм — строки, номер, статусы с согласованием

**Статус:** принято 2026-10-18 и реализовано в этапе 2, шаг 2.2 плана универсального конструктора (раздел
«Конструктор форм и отчётов» в [плане 10/10](../plan-10-10.md)); файлы перенесены в следующий шаг (см. «Не сделано»).
Дополняет [ADR-0038](ADR-0038-live-simple-forms.md), [ADR-0041](ADR-0041-live-form-evolution.md) (формат simple-form 6,
правила совместимости — раздел «Реализация», шаг 2.2) и [ADR-0042](ADR-0042-live-form-formulas.md) (формулы над строками).
Гарантии сохраняются: без DDL в runtime, граница `form_id`, права и область данных на сервере, аудит, отказ одной формы
не роняет каталог.

## Контекст

Критерий этапа 2 — документ «заказ со строками и согласованием» без программиста. Платформа уже умеет это для
объявленных в коде сущностей (ADR-0032, 9): строки документа (`EntityCollection` в своей таблице, проверка строк,
аудит изменений строк, блокировка состоянием), процесс (`EntityWorkflow`: состояния, переходы — действия записи со своим
правом и `If-Match`, блокировки полей, конечные состояния), номер по последовательности (`FieldDefault.sequence`). Живая
форма (общая таблица `studio_records` с партицией `form_id`) ничего из этого не получала: правила хранения запрещали
партиционированной сущности строки и процесс, а последовательность — это DDL.

## Строки документа: где хранить

| Вариант | Суть | Почему не выбран / выбран |
|---|---|---|
| A. JSON-массив в `payload` записи | строки — массив объектов в JSONB записи | каждое изменение строки переписывает весь документ (TOAST до сотен КБ при 500 строках); отчёты 2.3 по строкам — `jsonb_array_elements` по каждой записи, индексы по строкам невозможны; id строк и аудит изменений пришлось бы делать заново, вне готового `EntityLines` — **не выбран** |
| B. Одна общая таблица строк с признаком таблицы | `studio_record_lines(record_id, line_table, …)` | `EntityCollection` (STABLE Platform API) не знает фильтра по признаку: нужен новый компонент записи и бинарно-совместимый конструктор, т. е. изменение публичного контракта ради одной реализации — **не выбран** |
| C. Таблица на место таблицы строк | до трёх таблиц строк у формы; строки таблицы с местом k (1…3) любой формы лежат в `studio_record_lines_k` (V227) с `record_id`, `position`, `payload` | готовый runtime коллекций работает без изменений сигнатур: строки читаются и пишутся `EntityCollectionStore` по `record_id`, проверяются `EntityLines`, аудит и блокировки — общие; отчёт 2.3 — обычный `join` по месту таблицы; запись строк — DML — **выбран** |
| D. Таблица на каждую форму | `CREATE TABLE` при активации | DDL в runtime, противоречит ADR-0038 — **не выбран** |

Граница партиции: строка достижима только через запись (`record_id`), запись читается только в своей партиции и области
данных (общий runtime, ADR-0038, решение 5), удаление записи удаляет строки (`on delete cascade`). Строка — объект JSON не
больше 16 КиБ (check), строк в документе — `maxRows` таблицы (1…500, `EntityCollection`), колонок — до 20, таблиц — до 3.
Конкурентность — ревизия записи: изменение строк поднимает ревизию документа и требует `If-Match`, как любое изменение.

Правила Platform API только расширены (сигнатуры прежние, japicmp зелёный): партиционированная сущность может иметь
коллекции в другой таблице и процесс; поле процесса может быть JSON-свойством; строка коллекции может держать
JSON-свойство (только чтение — значение сервера), элемент справочника (`ENUM`) и ссылку на строку другой сущности. Ссылки и
элементы справочника в строках проверяются по базе одним запросом на поле для всех строк сохранения (`EntityLineChecks`):
новое значение должно существовать, быть видимым сохраняющему (право `view` и область цели) и не быть в архиве.

## Номер документа

Шаблон из текста и токенов `{YYYY}`, `{YY}`, `{MM}` и ровно одного счётчика `{N…}` (1–12 цифр), период сброса
(`never`/`year`/`month`; годовой требует года в шаблоне, месячный — года и месяца), необязательный статус выдачи
(`assignOn`). Номер выдаёт сервер (хук живой декларации) из счётчика `studio_form_number_counters(form_id, period)` (V228)
тем же способом, что `studio_form_counters` даёт номер записи (V224): `insert … on conflict do update … returning` в
транзакции сохранения. Блокировка строки счётчика до фиксации сериализует выдачу в форме и периоде, откат возвращает
счётчик вместе с записью, поэтому номер получает ровно одна зафиксированная запись и никогда не выдаётся повторно (в том
числе после удаления записи); пропусков из-за откатов нет. Номер хранится в колонке `studio_records.doc_number`
(уникальна в форме, триггер не даёт изменить выданный номер), ищется строкой поиска и сортируется как текст. Период — по
часовому поясу запроса (`X-Time-Zone`). Шаблон и период выданной нумерации не меняются (см. совместимость).

## Статусы и согласование

Статусы формы компилируются в `EntityWorkflow` общего runtime: поле `docStatus` (JSON-свойство, выбор состояний,
только чтение, начальное — первое состояние), блокировки (`lockAll` — все видимые поля и таблицы строк; конечное
состояние — только чтение), переходы — действия записи `POST …/actions/<code>` с `If-Match`, у каждого — своё право формы
(`studio.<form>` / `<code>`, регистрируется при активации и новой версии, выдаётся административным ролям, остальным —
редактором прав). Условие перехода — формула ADR-0042 (да/нет, пустое не разрешает), правило «автор не выполняет»
(`notAuthor`) — правила перехода (`TransitionGuard`): сервер отказывает 422 (`error.studio.transition_condition`,
`error.studio.transition_author`), а список действий записи не предлагает переход, который правило не пропустит. Права
проверяются общим runtime (403), область данных — чтением записи (404).

Комментарий перехода (`none`/`optional`/`required`, до 1000 символов) приходит в теле действия, хук проверяет
обязательность и пишет его в `docComment` — изменение попадает в аудит вместе со статусом и кодом действия, история
показывает переход с комментарием. Уведомление: переход с `notify` сообщает тем, кто может его выполнить, когда документ
приходит в его исходный статус — активным пользователям с правами `view` и перехода, видящим запись в области формы, без
выполнившего и (если все такие переходы `notAuthor`) без автора; не больше 200. Событие `common.entity.EntityNotice`
публикуется в транзакции, `ms.notify` пишет уведомление в приложении на языке получателя (откат отменяет оба). Модуль
`studio` не зависит от `ms`: общий контракт в `common`. Ответственный пользователь или руководитель подразделения как
согласующие — не сделано: понятия «руководитель подразделения» в платформе нет; поле «пользователь» с правом перехода
решает частный случай.

## Формулы

Язык ADR-0042 расширен без новых операторов: имя с точками читает строки (`lines.<таблица>.<колонка>` — список значений,
`lines.<таблица>` — строки), только агрегаты принимают списки: `sum` (сумма заполненных чисел, ноль без строк — правило
`total > 0` должно отклонять пустой документ) и `count` (число строк или заполненных значений). Формула колонки читает свою
строку и введённые поля шапки (`doc.<поле>`); вычисляемые поля шапки ей недоступны, поэтому порядок без циклов: строки
готовятся после введённых значений и умолчаний шапки и до её вычисляемых полей (`EntityFieldValues.prepareAll`), веб
повторяет порядок. Шапка читает также `docNumber` и `docStatus`. Общий набор `docs/api/formula-conformance.json` дополнен
случаями строк для Java и TypeScript.

## Экспорт, история, вебхуки

XLSX списка пишет строки документа на лист каждой таблицы (запись по первому столбцу списка, № строки, колонки; ссылки и
элементы справочника — по именам в области выгружающего); строки страницы читаются одним запросом на таблицу. История —
изменения строк одной записью аудита (как у объявленных документов). Вебхук несёт запись со строками; подписке с охватом `creator` — только запись, видимую автору подписки (ADR-0041,
решение владельца 2026-10-18).

## Совместимость версий

Разрешено: добавить таблицу (в конец), колонку (необязательную), статус, переход; менять подписи, условия, комментарии,
блокировки, флаги, формулы колонок; увеличить `maxRows`; убрать `assignOn`. Запрещено (`StudioDocumentChangeRules`, те же
правила в редакторе): убрать или переставить таблицу (`lines_moved` — строки лежат по месту), уменьшить `maxRows`
(`max_rows`), изменить колонку как поле (`removed`, `type`, `target`, `option_removed`, `required`, `max_length`, `scale`,
`computed`, адрес `lines.<таблица>.<колонка>`), изменить шаблон или период номера или убрать номер (`numbering` — выданные
номера должны остаться уникальными; новый шаблон — новая форма), убрать статусы (`workflow_removed`), удалить статус
(`state_removed` — в нём могут быть записи) или сменить начальный (`initial` — записи без статуса читают первый).
Добавить нумерацию или статусы существующей форме можно: старые записи без номера (номер получают новые записи или
переход в статус выдачи), их статус читается как начальный.

## Не сделано в шаге 2.2

- **Файлы** (`file` поле живой формы через модуль `mf`). Платформа держит файл колонкой записи (`FILE`), вложения
  `mf_record_files` — по полю; партиционированная сущность JSON-свойства файла не умеет, множественных вложений нет ни у
  одной сущности. Нужны: чтение и вложение файла из JSON-свойства, проверка `EntityFiles.attachable` для живой формы и
  решение о нескольких файлах (таблица строк с колонкой-файлом или новый тип). Перенесено в следующий шаг, путь загрузки —
  только `mf` (проверка, ClamAV, квоты, право чтения записи).
- Согласующий — ответственный пользователь записи или руководитель подразделения; параллельное согласование нескольких лиц.
- Агрегаты `min`/`max`/`avg` по колонкам; фильтр списка «документы, в строках которых …».

## Последствия

- Администратор собирает заказ со строками, номером и согласованием в редакторе Studio; эталон — e2e
  `e2e/tests/browser/instance/studio-order-approval.spec.ts`, серверный — `StudioDocumentHttpTest`.
- Отчёты 2.3 по строкам строятся соединением `studio_record_lines_<k>` с `studio_records` по месту таблицы; статус —
  выбор `docStatus`, номер — колонка `doc_number`.
- Три одинаковые таблицы строк — цена отказа от изменения публичного контракта; четвёртая таблица — новая миграция.
