# ADR-0011: Механизм провайдеров — SPI-адаптеры с выбором конфигурацией

**Статус:** Принято (CEO, 2026-08-27)
**Дата:** 2026-08-27
**Инициатор:** CEO — «поставщиков может быть разных, нужен механизм плагинов»
**Зависит от:** ADR-0006 (модульный монолит), ADR-0008 (секреты в Vault)

---

## 1. Контекст

Внешние поставщики услуг различаются по клиентам и рынкам и будут меняться:

| Возможность | Возможные поставщики |
|---|---|
| SMS | Eskiz, Play Mobile, другой локальный шлюз, международный |
| Email | свой SMTP, внешний сервис |
| Мессенджер | Telegram (сейчас), потенциально другие |
| Объектное хранилище | Garage (сейчас), любой S3-совместимый |
| LLM (Этап 3+) | облачный API, self-hosted (ADR-0005 П6 уже требует `LlmProvider`) |
| Потенциально | ЭСФ/фискальные сервисы, платёжные шлюзы — по мере развития продукта |

Требование CEO: добавление нового поставщика не должно требовать переделки ядра, и у разных
клиентов могут быть разные поставщики одной и той же возможности.

## 2. Решение

**Единый паттерн Provider SPI, адаптеры собираются вместе с приложением («in-tree»),
выбор и настройка — конфигурацией экземпляра.**

### 2.1. Устройство

```
ядро (модуль notify/files/…)          адаптеры (отдельные Maven-модули)
┌───────────────────────────┐         ┌──────────────────────────────┐
│ interface SmsProvider     │◀────────│ sms-eskiz                    │
│ interface MailProvider    │         │ sms-playmobile               │
│ interface MessengerProvider│◀───────│ messenger-telegram           │
│ interface LlmProvider (Э3)│         │ mail-smtp                    │
│                           │         │ …новый = новый модуль        │
│ ProviderRegistry          │         └──────────────────────────────┘
│  выбор по конфигурации ───┼── settings: notify.sms.provider=eskiz
│  секреты ─────────────────┼── Vault: secret/instances/<client>/providers/sms
└───────────────────────────┘
```

- **Контракт на возможность, не на поставщика.** Ядро знает только интерфейс
  (`send(message) → result`, `healthCheck()`, `capabilities()`); всё специфичное поставщику —
  внутри адаптера.
- **Регистрация** — Spring-механизмами (адаптеры объявляют себя, `ProviderRegistry` выбирает
  активного по настройке экземпляра). Разные клиенты → разные поставщики без пересборки:
  меняется конфигурация, не код.
- **Секреты поставщика** — в Vault по пути экземпляра (ADR-0008 разд. 2.3), адаптер получает их
  через конфигурацию, не хранит.
- **Health-check каждого активного провайдера** — в readiness-панель экземпляра и метрики
  (ADR-0009); отказ поставщика виден как деградация канала, а не загадочные ошибки.

### 2.2. Контрактный тест-кит

На каждую возможность — набор контрактных тестов, которые обязан проходить любой адаптер
(отправка, ошибка сети, невалидный получатель, таймаут, идемпотентность повторов).
Новый поставщик считается готовым, когда его адаптер проходит кит + прогон на песочнице
поставщика. Это делает добавление поставщика **процедурой, а не проектом**.

### 2.3. Что сознательно НЕ делаем (и триггер пересмотра)

| Не делаем | Почему |
|---|---|
| Динамическая загрузка jar в рантайме (OSGi/classloader-плагины) | Чужой код в JVM с данными клиента: безопасность, изоляция, совместимость версий, отладка. Ради «разные поставщики у разных клиентов» это не нужно — решается конфигурацией |
| Маркетплейс плагинов, SDK для третьих сторон | Нет ни одного стороннего разработчика; преждевременно |
| Горячая замена провайдера без рестарта | Смена поставщика — редкое событие; рестарт экземпляра по кольцу — штатная операция |

**Триггер пересмотра:** если появятся партнёры, которые должны поставлять адаптеры вне нашего
релизного цикла — отдельный ADR, и решением будет **изоляция процессом** (адаптер как
отдельный сервис/sidecar по gRPC), а не чужой код в нашей JVM.

## 3. Последствия

- Вопрос «какой SMS-провайдер?» перестаёт блокировать что-либо архитектурно: договор —
  бизнес-задача, адаптер — 2–4 дня по тест-киту.
- В M0 добавляется ядро SPI + тест-кит + mock-адаптеры (для тестов и стенда) — ~2 и-д.
- Дисциплина: любая интеграция с внешним поставщиком проходит только через SPI — прямые
  вызовы из бизнес-кода запрещены (ArchUnit-правило).
- LLM-интеграция Этапа 3 получает готовый паттерн.
