# ADR-0037: новые простые формы через CLI и Flyway

**Статус:** принято в рамках утверждённого STU-04, 2026-10-15.

## Контекст

Администратору нужен редактор нового справочника без написания Java. Архитектура ADR-0019/0032/0033 остаётся статической: `EntityDefinition`, общий runtime и экран `/e/:code`. Черновики представления существующей формы ADR-0035 не описывают физическую схему. Мгновенная регистрация сущностей относится к STU-05.

## Решение

1. Отдельный закрытый контракт `simple-form` версии 1: модуль, сущность, три перевода названий, до 20 дополнительных полей. `name`, `code`, `modifiedAt` задаются существующим генератором. Поддержаны text, textarea, number, date, datetime, time, bool, email, phone, url. Ссылки, произвольные выражения, SQL, hooks, файлы, денежные поля и статусы в редактор не входят.
2. `POST /api/v1/form-studio/new-forms/prepare` требует `md.settings.update`, проверяет декларацию и возвращает `simple-form-package`. Операция не хранит состояние, не регистрирует сущность, не исполняет CLI/DDL; ответ `200`, `Cache-Control: no-store`, без replay. Она независима от модуля «Примеры». Черновик можно сохранить локальным JSON-файлом; отдельный `check-draft` проверяет структуру при восстановлении незавершённого ввода и не возвращает пакет; это явно отличается от общей истории версий STU-02.
3. Контрольная сумма SHA-256 считается по UTF-8 JSON декларации: ключи объектов рекурсивно сортируются, порядок массивов сохраняется, пробелы отсутствуют. Это контроль целостности, не подпись доверенного издателя и не разрешение на публикацию. CLI независимо валидирует вход и целевой checkout.
4. `cms form apply <file> --dry-run` показывает план. Без `--dry-run` CLI создаёт статическое объявление, тест, миграции таблицы и прав, переводы и записи реестров через существующие примитивы генератора. Доступ получают только системные административные роли; другие права администратор назначает явно. Выпуск требует CI, резервной копии и штатного шага Flyway до запуска нового приложения.
5. Доставка только новой сущности. Изменённый пакет для уже существующей сущности, совпадение таблицы/кода или несовместимый модуль блокируются до записи. Повтор исходного пакета не перезаписывает ручные правки. Эта консервативная проверка блокирует также required/type/delete; она не заявляет поддержку безопасной эволюции существующих данных. Изменение видимости в списке не означает DROP.
6. Результат генерации проверяется в отдельной копии репозитория на настоящем PostgreSQL/Flyway и общем runtime; при прерывании генерации нельзя продолжать выпуск до проверки целостности исходников и миграций. Детали восстановления и доказательства повторяемости фиксируются в руководстве и тестах CLI.

## Границы приёмки

ACC-15: несовместимые изменения существующей сущности отклоняются целиком; анализ/преобразование старых строк не поддерживается. ACC-16: пакет → CLI → Flyway → общий runtime; повтор сохраняет ручные изменения. ACC-19: редактирование и перестановка кнопками, клавиатура, мобильный экран.

ACC-17 и ACC-21 не применяются к этой поставке: нет активации без deploy и нет перехода схемы существующей формы N→N+1. Перед разрешением эволюции схемы нужны отдельные проверки данных/зависимостей, schema-revision handshake при сохранении старой открытой формы и восстановление; ревизия записи If-Match их не заменяет.

## Последствия

Новая форма требует выпуска приложения, но не отдельного frontend CRUD. Java/SQL остаются проверяемыми артефактами Git/CI; сервер не получает права менять файловую систему и схему по запросу из браузера. Цена границы — отсутствие автоматического обновления ранее созданной схемы и общей истории черновиков новых форм. Эти возможности не маскируются под успешную публикацию.
