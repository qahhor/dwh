# ADR-0004: Модель развёртывания — экземпляр на клиента + control plane

**Статус:** Заменено ADR-0014 (2026-09-03)
**Дата:** 2026-08-27
**Заменяет:** ADR-0003 разд. 2.1 (изоляция через общие таблицы + company_id + RLS)
**Зависит от:** ADR-0001, ADR-0002
**Заменено решением:** [SmartupCMS unified open-source design](../superpowers/specs/2026-09-02-smartupcms-unified-open-source-design.md)

> Историческая запись. Активная модель: одна самостоятельная установка
> SmartupCMS для одной организации и многих пользователей, без центрального
> управляющего сервиса, лицензирования или обязательной внешней связи.

---

## 1. Контекст

Изначально (ADR-0003) была принята классическая SaaS-модель: одна инсталляция, общие таблицы,
`company_id` в составных ключах, RLS. CEO пересмотрел продуктовую модель: **каждый клиент получает
независимый экземпляр системы**. Ожидаемый масштаб — 30–100 клиентов на горизонте 2–3 лет,
клиенты — B2B (дистрибьюторы/производители) с хорошим чеком и высокими требованиями к
изоляции данных. Впереди Этап 2 (DWH — тяжёлая аналитика per-client) и AI/ML-сценарии
(ADR-0005), включая per-client модели.

## 2. Решение

1. **Экземпляр на клиента (single-tenant).** Полный стек на клиента: Spring Boot-приложение +
   PostgreSQL 18 + Garage (S3) + Angular SPA. Развёртывание — Docker Compose на нашей
   инфраструктуре/VPS (допустимо и на площадке клиента — архитектура этого не запрещает).
2. **`company_id` удаляется из схемы полностью.** Обычные суррогатные PK, обычные FK, без RLS.
   Вместо таблицы `companies` — таблица `instance_info` с одной строкой (код клиента, название,
   параметры экземпляра).
3. **Control plane** — отдельный наш центральный сервис (минимум — в Этапе 1): реестр клиентов
   и экземпляров, версии, лицензии, центральный мониторинг (heartbeat), авторская часть
   объявлений.
4. **Связь экземпляр ↔ control plane — только исходящая от экземпляра** (pull/report):
   экземпляр шлёт heartbeat (версия, состояние, базовые метрики), забирает объявления и
   лицензионный статус. Control plane не требует входящего доступа к экземплярам — это
   позволяет ставить экземпляры за файрволами клиентов.

## 3. Рассмотренные варианты

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| A. Multi-tenant SaaS (как ADR-0003) | Одна инсталляция, дешёвая эксплуатация, мгновенные апдейты | Общая БД — сложнее продавать «вашим данным никто не сосед»; DWH-нагрузка клиентов конкурирует; сложнее per-client ML | Нет |
| B. Экземпляр на клиента, `company_id` остаётся колонкой-константой | Путь назад в SaaS открыт | Постоянный налог на код ради опции, которой бизнес не хочет | Нет (обсуждён, отклонён CEO) |
| C. Экземпляр на клиента, без `company_id`, + control plane | Простейший код; физическая изоляция; DWH и per-client ML естественны | Эксплуатация × N; консолидация в SaaS позже — только через большую миграцию | **Да** |

## 4. Последствия

**Упрощается**
- Схема БД и весь код доступа к данным: без составных ключей, без RLS, без tenant-контекста.
- Изоляция данных — физическая; аргумент продажи и комплаенса.
- DWH (Этап 2): хранилище клиента живёт рядом с его экземпляром, не конкурирует с другими.
- AI/ML: per-client модели обучаются на данных экземпляра без риска перемешивания.

**Усложняется (принятая цена)**
- Эксплуатация флота: миграции, бэкапы, мониторинг, обновления × N экземпляров.
  Митигция: автоматизация с первого дня — версионированные образы, скриптованный деплой,
  Flyway-миграции применяются при старте приложения, центральный сбор метрик/логов.
- Обратной дороги в общую SaaS-инсталляцию практически нет (риск принят CEO осознанно).
- Один человек у двух клиентов = два аккаунта (глобального логина больше нет).

**Каскадные изменения принятых решений**
| Было | Стало |
|---|---|
| «Нулевой тенант» внутри системы | Control plane — отдельный сервис |
| Глобально уникальный логин | Логин уникален в рамках экземпляра |
| Объявления «нулевого тенанта» | Авторство в control plane, экземпляры забирают по API |
| RLS-тест изоляции в CI | Не нужен; изоляция физическая |
| NFR «500 тенантов» | Флот до ~100 экземпляров; лимиты — на один экземпляр |

## 5. Минимальный состав control plane (Этап 1)

| Возможность | Описание |
|---|---|
| Реестр клиентов/экземпляров | Код, название, контакты, URL, окружение |
| Версии и heartbeat | Экземпляр периодически сообщает версию/состояние; дашборд флота |
| Лицензии | Подписанный лицензионный токен; экземпляр проверяет с grace-периодом offline |
| Объявления | Создание/публикация/таргетинг; экземпляры забирают pull'ом |
| Центральные метрики | Приём OTLP/метрик с экземпляров в общий мониторинг |

Control plane — то же самое приложение-каркас (Spring Boot + PostgreSQL, тот же RBAC-механизм),
отдельная кодовая база не нужна: это второй модуль в монорепо.
