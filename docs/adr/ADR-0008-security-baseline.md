# ADR-0008: Базовые требования безопасности

**Статус:** Принято (2026-08-27)
**Дата:** 2026-08-27
**Закрывает находки аудита:** SEC-1 (CSRF), SEC-2 (rate limiting), SEC-3 (секреты), SEC-5 (SCA/SBOM), SEC-7…SEC-10, A-5 (ключи лицензий)
**Зависит от:** ADR-0002, ADR-0004, ADR-0007

---

## 1. Контекст

Аудит выявил, что NFR-8 («OWASP ASVS L2; секреты вне репо; TLS; CSP/HSTS») — декларация
намерения, а не набор решений. Две находки признаны критичными: CSRF не адресован нигде,
ограничение частоты запросов отсутствует в требованиях. Продукт продаётся как enterprise,
и его основная ценность — управление доступом; пробелы именно здесь неприемлемы.

Решение по ISO 27001 (CEO, 2026-08-27): **сертификация сейчас не нужна**. Организационные
артефакты (реестр активов, регламент пересмотра доступа, IR-план) выносятся из объёма.
Технические меры ниже принимаются независимо от сертификации — они защищают продукт, а не
проходят аудит.

## 2. Решения

### 2.1. CSRF — double-submit токен (SEC-1)

**Проблема.** Сессия через cookie `HttpOnly, Secure, SameSite=Lax`. `Lax` блокирует
межсайтовые POST, но не покрывает: атаки с поддоменов (а мы планируем `client.product.uz` —
cookie разделяются между поддоменами одного домена), нестандартно реализованные методы,
браузеры без поддержки `SameSite`.

**Решение.** Double-submit CSRF-токен для всех мутирующих запросов (Spring Security,
`CookieCsrfTokenRepository` + заголовок `X-CSRF-TOKEN` из SPA). Cookie сессии остаётся
`HttpOnly` — защита от кражи через XSS сохраняется, CSRF закрывается отдельным токеном.

Запросы с аутентификацией по **API-токену** (заголовок `Authorization`) от CSRF-проверки
освобождаются: они не используют cookie, вектор неприменим по построению.

### 2.2. Ограничение частоты запросов (SEC-2)

Отсутствовало в требованиях. Вводится в Этап 1 как обязательное.

| Уровень | Лимит (значения по умолчанию, настраиваются) |
|---|---|
| По IP, неаутентифицированные | 60 запросов/мин |
| По пользователю (сессия) | 600 запросов/мин |
| По API-токену | 300 запросов/мин |
| Дорогие операции (экспорт, отчёты, массовые выгрузки) | 10 запросов/мин на пользователя |
| Отправка OTP | уже ограничена FR-AUTH-5, сохраняется |

Реализация — Bucket4j, состояние в памяти процесса (при одном инстансе приложения
достаточно; при нескольких — общее хранилище). Превышение: `429 Too Many Requests` с
заголовком `Retry-After`. Все срабатывания — в security-журнал.

**Обоснование.** API-токены выдаются клиентам для интеграций. Без лимитов один некорректный
скрипт клиента способен положить его собственный экземпляр — и для клиента это будет
выглядеть как отказ нашего продукта.

### 2.3. Управление секретами — Vault (SEC-3)

Приходит вместе с Nomad (ADR-0007), отдельного решения не требуется.

- Секреты экземпляра (пароль БД, ключи S3, токен Telegram-бота, SMTP, SMS, ключи control
  plane) хранятся в Vault по пути `secret/instances/<client-code>/*`.
- Nomad получает их через нативную интеграцию и подставляет в задачу как переменные
  окружения или файлы; на диск узла в открытом виде они не ложатся.
- Политика Vault на экземпляр: задача клиента A не может прочитать секреты клиента B.
- Ротация: процедура и периодичность (не реже раза в год, немедленно — при увольнении
  имевшего доступ или подозрении на компрометацию).

**Запрет:** секретов нет в репозитории, в образах, в `.env`-файлах на узлах и в переписке
поддержки. Проверяется сканером секретов в CI (gitleaks).

### 2.4. Ключи подписи лицензий — Vault Transit (A-5)

Control plane подписывает лицензионные токены. Хранить закрытый ключ в конфигурации
приложения нельзя: его компрометация позволяет выпустить лицензию на любой экземпляр.

**Решение:** движок **Vault Transit** — подпись выполняется внутри Vault, закрытый ключ
никогда не покидает хранилище и недоступен приложению даже при его компрометации.

- Токен содержит `kid` (идентификатор ключа) — ротация возможна без остановки флота.
- Экземпляры хранят набор доверенных публичных ключей и принимают подписи любым из них
  в течение переходного периода.
- Процедура экстренной ротации при компрометации — в runbook.

### 2.5. Зависимости: SCA и SBOM (SEC-5)

В CI обязательно:
- **SCA** — Trivy или OWASP Dependency-Check по зависимостям и по собранным образам.
- **SBOM** — генерация CycloneDX для каждого релиза, хранение вместе с артефактом.
- **Блокировка сборки** при уязвимостях Critical/High без зарегистрированного исключения
  с обоснованием и сроком.
- Renovate (ADR-0002) — автоматические PR на обновления.

### 2.6. Прочие меры

| ID | Мера |
|---|---|
| SEC-7 | **Шифрование бэкапов** при записи, ключ в Vault; хранение вне узла экземпляра (ADR-0007 §2.5) |
| SEC-8 | **Хранение и удаление персональных данных:** сроки хранения по типам данных; процедура удаления по запросу субъекта; удаление пользователя = анонимизация (записи аудита сохраняются, персональные поля обезличиваются) |
| SEC-9 | **Защита от SSRF:** исходящие соединения только по allow-list адресов (SMTP, SMS-шлюз, Telegram API, control plane). Пользовательский ввод не может задать адрес назначения |
| SEC-10 | **Безопасный SQL:** только параметризованные запросы; конкатенация пользовательского ввода в SQL запрещена; правило в CODE_STYLE + статический анализ в CI |
| SEC-11 | **Заголовки ответа:** `Content-Security-Policy`, `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY`, `Permissions-Policy` |
| SEC-12 | **Загрузка файлов:** проверка реального типа по содержимому (не по расширению), запрет опасных расширений, выдача с `Content-Disposition: attachment` и отдельного origin |
| SEC-13 | **Тестирование:** внешний пентест перед первой коммерческой поставкой; далее — при существенных изменениях контура аутентификации |

## 3. Что сознательно не делаем

| Не делаем | Причина |
|---|---|
| Сертификация ISO 27001 и её артефакты | Решение CEO 2026-08-27: сейчас не требуется. Пересмотреть при выходе на enterprise-сделки, требующие сертификата |
| WAF | При Nomad+Consul и allow-list избыточен на текущем масштабе |
| Полный OAuth2/OIDC-провайдер | ADR-0002/ТЗ: только API-токены на Этапе 1 |
| Шифрование данных на уровне колонок БД | Физическая изоляция экземпляров + шифрование дисков и бэкапов покрывают модель угроз |

## 4. Действия

1. [ ] CSRF-защита в конфигурации Spring Security + поддержка в SPA.
2. [ ] Rate limiting (Bucket4j) с настраиваемыми лимитами по уровням.
3. [ ] Политики и пути Vault для секретов экземпляров; интеграция с Nomad.
4. [ ] Vault Transit для подписи лицензий, поддержка `kid` и ротации.
5. [ ] SCA, SBOM, gitleaks в CI с блокировкой сборки.
6. [ ] Заголовки безопасности, allow-list исходящих, проверка типов файлов.
7. [ ] Правило параметризованного SQL в CODE_STYLE + статический анализ.
8. [ ] Планирование внешнего пентеста к моменту первой поставки.
