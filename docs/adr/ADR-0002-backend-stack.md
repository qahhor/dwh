# ADR-0002: Бэкенд-стек — Java Spring Boot vs Node.js (+ фиксация версий)

**Статус:** Принято (CEO, 2026-08-26)
**Дата:** 2026-08-26
**Решают:** CEO/Founder, техлид платформы
**Зависит от:** ADR-0001 (логика в приложении)

---

## 1. Контекст

По ADR-0001 бизнес-логика живёт в приложении. Кандидаты, заданные заказчиком: **Java Spring Boot**
или **Node.js**. Система — B2B, долгоживущая (10+ лет), с последующим DWH-этапом
(тяжёлые выгрузки, стриминг больших ответов, интеграция с Oracle-источниками Smartup5x).

Факты о команде и инфраструктуре (из существующей кодовой базы):

- Boot-слой Biruni уже на **Java 21 + Spring Boot 3.4 + Tomcat 10** — команда эксплуатирует это в проде.
- Node.js в экосистеме есть, но только как микросервис (`usersync`: синхронизация в Keycloak через Kafka)
  и как сборочные скрипты. Продуктовой Node.js-разработки нет.
- Фронтенд Biruni — Angular 17 (TypeScript-компетенция в команде есть, но это фронтенд-компетенция).

## 2. Решение

**Java 25 LTS + Spring Boot 4.1.x** (актуальные стабильные линии на 2026-08, см. 5).
Доступ к данным — **SQL-first (Spring JDBC / jOOQ), не JPA** для сложных запросов; JPA допустим
точечно для простых CRUD-справочников, если команда захочет. Node.js остаётся в нише
вспомогательных сервисов, если такие понадобятся.

## 3. Рассмотренные варианты

### Вариант A: Java (LTS) + Spring Boot

| Измерение | Оценка |
|---|---|
| Сложность | Средняя |
| Стоимость | Средняя: команда уже в стеке |
| Масштабируемость | Высокая (virtual threads зрелые в Java 25 — минус блокирующего IO снят) |
| Знакомство команды | **Уже в проде** (шлюз Biruni на Boot 3.4; модель программирования в 4.x та же) |

**Плюсы**
- Zero-cost вход: сборка, деплой (Tomcat/Docker), мониторинг (Micrometer/OTLP) — всё уже отработано
  на Biruni; CI/CD-паттерны переносятся как есть.
- Spring Security — самый зрелый фреймворк авторизации на рынке; RBAC, session/JWT, OAuth2 —
  из коробки, аудировано тысячами внедрений.
- Экосистема данных: JDBC-драйвер PostgreSQL эталонный; jOOQ даёт типобезопасный SQL;
  Flyway — миграции; Testcontainers — интеграционные тесты на реальном PostgreSQL.
- Строгая типизация + null-safety анализ → дешевле сопровождение на горизонте 10 лет.
- Для DWH-этапа: JDBC-стриминг больших результатов, коннекторы к Oracle (уже используем UCP),
  Kafka-клиенты первого класса.

**Минусы**
- Более многословный код, чем Node.js; медленнее прототипирование.
- Потребление памяти JVM выше (частично лечится настройкой, для B2B-нагрузки не критично).

### Вариант B: Node.js (NestJS + TypeScript)

| Измерение | Оценка |
|---|---|
| Сложность | Средняя |
| Стоимость | Высокая скрытая: обучение команды продуктовой Node.js-разработке |
| Масштабируемость | Высокая для IO-bound, слабая для CPU-bound (однопоточная модель) |
| Знакомство команды | Низкое (только utility-сервисы) |

**Плюсы**
- Один язык с фронтендом (TypeScript) — теоретически общие типы DTO.
- Быстрое прототипирование, большая экосистема npm.
- NestJS структурно похож на Spring — вход для Java-разработчиков не с нуля.

**Минусы (решающие)**
- **Команда не эксплуатировала Node.js под продуктовой нагрузкой.** Все прод-компетенции —
  JVM. Менять лошадь на переправе перед 10-летним проектом — неоправданный риск.
- Экосистема авторизации (Passport и др.) — конструктор, который собираешь сам; в Spring Security
  это готовый, проверенный каркас. Для системы, чья главная ценность — управление доступом,
  это прямой аргумент.
- CPU-bound задачи DWH-этапа (генерация тяжёлых Excel, преобразования) блокируют event loop —
  придётся городить worker threads / отдельные процессы.
- Дисциплина типов держится на линтерах; `any` протекает. На горизонте 10 лет дороже.

### Вариант C: Гибрид (ядро на Java, edge-сервисы на Node.js)

Отвергнут как **преждевременный**: два прод-стека = двойные пайплайны, двойной мониторинг,
двойные стандарты кода — при команде, которая пока строит один продукт. Вернуться к этому можно,
когда появится реальная ниша (например, BFF для мобильного клиента).

## 4. Анализ компромиссов

Решающий фактор — не «Java vs Node вообще», а **наша команда и наш горизонт**. Прод-опыт JVM,
готовый CI/CD, требования к безопасности (RBAC — ядро продукта) и DWH-этап впереди — всё
указывает в одну сторону. Единственный сценарий, где Node.js выиграл бы: маленькая команда
фулстек-TS-разработчиков без Java-опыта. Это не наш случай.

Внутри Java-стека фиксируем анти-паттерн, о который спотыкаются мигранты с БД-центричной модели:
**не тащить бизнес-логику в JPA-сущности с ленивыми связями.** Основной инструмент доступа
к данным — явный SQL (Spring JDBC `JdbcClient` или jOOQ). Это сохраняет главный навык команды —
мышление на SQL — и убирает главный источник деградации производительности.

## 5. Фиксация версий (актуальные стабильные на 2026-08-26, проверено по официальным источникам)

Требование бизнеса: самые актуальные **стабильные** версии, пригодные для B2B (длинные окна
поддержки, зрелые patch-линии).

| Слой | Версия | Обоснование / окно поддержки |
|---|---|---|
| Язык / рантайм | **Java 25 LTS** (Temurin) | Текущий LTS (вышел 09.2025, уже год patch-зрелости). Java 26 — не LTS, не берём. Следующий LTS — Java 29 (09.2027). |
| Фреймворк | **Spring Boot 4.1.x** (сейчас 4.1.1) | Последняя GA-линия; OSS-поддержка до 07.2027. Линия 3.5 уже вне OSS-поддержки (кончилась 06.2026) — стартовать на ней нельзя. |
| Доступ к данным | Spring JDBC (`JdbcClient`) + jOOQ по мере роста | JPA — только простые справочники, по решению техлида |
| Миграции БД | Flyway Community (актуальная 11.x) | версионируемые SQL-файлы в репо |
| БД | **PostgreSQL 18** (сейчас 18.6) | Актуальный мажор (09.2025), шесть minor-патчей — зрелый; поддержка до 11.2030. |
| Аутентификация | Spring Security (в составе Boot 4.1) | session-based + opaque token, детали в ТЗ |
| Тесты | JUnit 5 + Testcontainers (PostgreSQL 18-образ) | интеграционные тесты обязательны для слоя прав |
| Сборка | Maven | как в Biruni, привычно команде |
| Наблюдаемость | Micrometer → OTLP | тот же стек, что у Biruni |
| Контейнеризация | Docker + compose | как у Biruni |
| Фронтенд | **Angular 22.x** (сейчас 22.1.3) + Node.js 24 LTS для сборки | Актуальный мажор (05.2026), поддержка до 06.2028. |
| Файловое хранилище | **S3-совместимое: Garage** (альтернатива — SeaweedFS, Apache-2.0) | **MinIO отвергнут:** community-версия с 12.2025 в maintenance mode (только security-фиксы), admin-функции вырезаны в платный AIStor. Код зависит только от S3 API — реализация заменяема. |

Замечание по Spring Boot 4.x: это новый мажор (11.2025, Spring Framework 7), но для greenfield
это преимущество, а не риск — миграционного багажа нет, модель программирования та же, что в 3.x,
а стартовать на линии с истекшей OSS-поддержкой (3.5) для B2B недопустимо.

### Политика обновлений (B2B)

| Что | Правило |
|---|---|
| Patch-версии (Boot, PG, Angular) | Ежемесячно; security-патчи — в течение недели |
| Minor Boot (4.1 → 4.2) | В течение квартала после GA |
| Java | Только LTS; переход на следующий LTS (29) в течение 6–12 мес после выхода |
| PostgreSQL мажор | После выхода минимум .2-патча нового мажора, в плановое окно |
| Angular мажор | Не отставать больше чем на одну поддерживаемую мажорную линию |
| Автоматизация | Renovate/Dependabot: PR на обновления зависимостей в CI |
| Запрет | Ни один компонент прод-контура не живёт на линии с истёкшей поддержкой |

## 6. Последствия

- Новые разработчики бэкенда нанимаются по профилю «Java + Spring + PostgreSQL» — самый ликвидный
  профиль на нашем рынке.
- Каждая фича слоя прав сопровождается интеграционным тестом на Testcontainers — прописать в DoD.
- jOOQ вводим не с первого дня, а когда появятся первые сложные динамические запросы (гриды
  с фильтрами) — до этого хватает `JdbcClient`.
