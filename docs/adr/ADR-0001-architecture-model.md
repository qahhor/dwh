# ADR-0001: Где живёт бизнес-логика — БД-центричная модель (как Biruni) или приложение

**Статус:** Принято (CEO, 2026-08-26)
**Дата:** 2026-08-26
**Решают:** CEO/Founder, техлид платформы
**Контекст проекта:** новая система CMS + DWH для клиентов (репозиторий `dwh`)

---

## 1. Контекст

Мы строим новую систему с нуля. У компании уже есть работающая платформа **Biruni** (v8.20, GreenWhite),
на которой построена вся экосистема Smartup5x (`core`, `anor`, `trade`, `finance`, `wms`, `pharm`,
`telecom`, `billing`). В иерархии Biruni уже зарезервирован узел `smartup5x_dwh`.

Ключевая особенность Biruni — **БД-центричная (metadata-driven) архитектура**:

- Вся бизнес-логика — в Oracle PL/SQL (13 модулей: `kernel`, `md`, `kauth`, `kl`, `ms`, `mt`, `mf`,
  `ker`, `kdyn`, `kset`, `bmb`, `mbi`, `plugin`).
- Java/Spring Boot — **только шлюз**: один wildcard-эндпоинт `@PostMapping("/**")` →
  `BiruniRouteService.dispatch()` → `Biruni_Route.Execute_Route(...)`.
- Маршрутизация — данные, а не код: таблица `biruni_routes(uri, action_name, action_in, action_out,
  access_type, ...)`, вызов процедуры по имени через динамический PL/SQL.
- Под этим лежит собственная библиотека `fazo` (json, hashmap, gmap, array, stream, query) — фактически
  свой стандартный рантайм внутри БД.

Перед тем как решать «Spring Boot или Node.js», нужно ответить на более фундаментальный вопрос:
**повторяем ли мы эту модель на PostgreSQL?** От ответа зависит всё остальное — потому что в
БД-центричной модели выбор бэкенд-языка почти не имеет значения (шлюз можно написать на чём угодно),
а в приложение-центричной — это решение на 10 лет.

---

## 2. Решение

**Не повторяем БД-центричную модель Biruni. Бизнес-логика живёт в приложении.**
PostgreSQL используется как СУБД (включая тяжёлый аналитический SQL, представления, агрегаты),
но не как среда исполнения бизнес-логики.

При этом **сознательно переносим из Biruni проверенные концепции данных** — реестр форм и действий,
материализацию эффективных прав, сквозной аудит.
Мы отказываемся от механизма, а не от модели предметной области.

---

## 3. Рассмотренные варианты

### Вариант A: БД-центричная (порт модели Biruni на PL/pgSQL)

| Измерение | Оценка |
|---|---|
| Сложность | Высокая |
| Стоимость | Очень высокая на старте (нужен свой рантайм) |
| Масштабируемость | Только вертикальная |
| Знакомство команды | Высокое (модель), низкое (PL/pgSQL) |

**Плюсы**
- Команда мыслит в этой парадигме, есть 10+ лет опыта.
- Логика рядом с данными: массовые пересчёты без сетевых round-trip.
- Единая точка изменения — можно править логику без пересборки приложения.

**Минусы (решающие)**
- **PL/pgSQL ≠ Oracle PL/SQL.** Нет пакетов (нет инкапсуляции «спецификация/тело», только схемы и
  функции), нет коллекций уровня `fazo`, нет автономных транзакций (нужен `dblink`/`pg_background` —
  костыль), нет встроенного планировщика (нужен `pg_cron`), заметно слабее отладка и профилирование.
- **`fazo` придётся написать заново.** Это не «пара утилит» — это json/hashmap/gmap/array/stream/query
  плюс покрытие тестами. Годы работы, которые не создают ценности для клиента.
- **Инструментарий.** Нет полноценного рефакторинга, `pgTAP` слабее JUnit, нет статического анализа
  уровня SonarQube/ErrorProne.
- **Найм.** Разработчиков, готовых писать бизнес-систему целиком в PL/pgSQL, на рынке практически нет.
  Каждый новый человек — 3–6 месяцев на вход.
- **Масштабирование.** Логика в БД масштабируется только вертикально. Приложение масштабируется
  горизонтально дешевле.
- **Конфликт с Этапом 2.** DWH создаёт тяжёлую аналитическую нагрузку. Держать в том же экземпляре
  ещё и OLTP-логику CMS — гарантированная деградация. Разделение слоёв нужно с самого начала.

### Вариант B: Приложение-центричная

| Измерение | Оценка |
|---|---|
| Сложность | Средняя |
| Стоимость | Средняя, предсказуемая |
| Масштабируемость | Горизонтальная |
| Знакомство команды | Высокое (Spring Boot уже в проде как шлюз Biruni) |

**Плюсы**
- Стандартная индустриальная модель — легко нанимать, легко передавать.
- Полноценные тесты (JUnit + Testcontainers на реальном PostgreSQL), CI, статический анализ.
- Приложение и БД масштабируются независимо; БД можно вынести в managed-сервис.
- Готовые аудированные библиотеки для аутентификации, валидации, миграций.

**Минусы**
- Массовые операции требуют аккуратности: наивный ORM-код даёт N+1 и round-trip. Лечится
  дисциплиной (см. ADR-0002: SQL-first доступ к данным вместо JPA по умолчанию).
- Логика больше не «в одном месте с данными» — нужна дисциплина, чтобы часть правил не уехала в БД
  явочным порядком.

### Вариант C: Гибрид с явной границей

Логика — в приложении. В БД остаётся только то, что **обязано** быть там:

| Что | Где | Почему |
|---|---|---|
| Ограничения целостности | БД (constraints, FK, check) | Последний рубеж, приложение может ошибиться |
| Изоляция клиентов | Инфраструктура (отдельный экземпляр — ADR-0004) | Физическая изоляция вместо RLS |
| Аудит изменений | БД (generic-триггер) | Нельзя обойти в обход приложения |
| Массовые пересчёты, ETL, витрины | БД (SQL, materialized views) | Данные не должны ходить по сети |
| Бизнес-правила, workflow, валидация | Приложение | Тестируемость, читаемость, найм |
| Маршрутизация, авторизация | Приложение | Статический анализ, типобезопасность |

**Это и есть выбранный вариант.** Формально — B с явно зафиксированной границей.

## 4. Анализ компромиссов

Главный компромисс: **мы меняем «мощь метапрограммирования» на «предсказуемость и найм».**

Biruni-подход выигрывает, когда нужно очень быстро выпускать однотипные CRUD-формы силами
небольшой команды, глубоко знающей платформу. Он проигрывает, когда систему нужно передавать,
масштабировать команду и держать под аналитической нагрузкой.

Второй компромисс: **таблица маршрутов vs код.** Динамический вызов процедуры по имени из
`biruni_routes` даёт гибкость (можно добавить эндпоинт без деплоя), но ломает статический анализ:
IDE не покажет вызывающих, компилятор не поймает опечатку в имени процедуры, невозможно
автоматически проверить, что все маршруты покрыты правами. Мы выбираем **код как источник истины
о маршрутах**, а метаданные (каталог форм и действий) **генерируем из кода при старте** — тогда
каталог физически не может разойтись с реальностью.

## 5. Последствия

**Становится проще**
- Нанимать: обычный Spring Boot + PostgreSQL, а не «наша платформа».
- Тестировать: полноценные интеграционные тесты на реальной БД в CI.
- Разделять нагрузку: OLTP-контур CMS и аналитический контур DWH — разные базы (Этап 2).
- Рефакторить: переименование действия — операция IDE, а не поиск по строковым литералам.

**Становится сложнее**
- Массовые операции: нужен осознанный SQL-first подход, нельзя «просто взять JPA».
- Дисциплина границы: без ревью бизнес-правила начнут расползаться в триггеры. Явный запрет
  в CODE_STYLE: **триггеры только для аудита и целостности, никогда для бизнес-правил.**
- Нет «горячего» изменения логики без деплоя. Компенсируется нормальным CI/CD.

**К чему придётся вернуться**
- Если появится требование «клиент сам настраивает формы без разработки» — понадобится слой
  конфигурации форм. Это отдельное решение, не Этап 1.
- Граница «что считается тяжёлым SQL» будет уточняться на Этапе 2 (DWH).

## 6. Что берём из Biruni, а что нет

**Берём (модель предметной области — проверена в проде):**

| Концепция | Источник в Biruni |
|---|---|
| Реестр форм и действий как основа прав | `md_forms`, `md_form_actions` |
| Право = (форма, действие), `*` = доступ к форме | `md_role_form_actions.action_key` |
| Права роли + персональные права пользователя | `md_role_form_actions` + `md_user_form_actions` |
| Скрытие отдельных колонок грида | `md_role_revoked_columns` |
| Материализация эффективных прав | `md_gen_user_form_actions` |
| Сквозной аудит всех изменений | X-таблицы + Y-триггеры |
| Модуль/проект как лицензионный контур | `md_role_projects`, `project_code` |

**Не берём (механизм):**

| Что | Почему |
|---|---|
| Таблица маршрутов + динамический вызов по имени | Ломает статический анализ и типобезопасность |
| Генерация z-пакетов (обёрток DML) | В приложении это репозитории, генерация не нужна |
| Аудит через DDL-генерацию X/Y-объектов | В PostgreSQL достаточно одной таблицы + generic-триггера на JSONB |
| Двойной фронтенд (legacy JS + Angular) | Начинаем с одного |
| Филиальный разрез прав (`filial_id` в `md_user_roles`) | Решение CEO 2026-08-26: у целевых клиентов филиалы не нужны; право = `(user, role)` |
| Разделение персона/пользователь (`md_persons` → `md_users`) | Решение CEO 2026-08-26: одна таблица `users`; тип «без права входа» добавим при потребности |
| Мультиарендность (`company_id` в составных ключах, «нулевая» компания) | Решение CEO 2026-08-27 (ADR-0004): экземпляр на клиента, без `company_id`; управление платформой — отдельный control plane |
| Вся логика в БД | См. решение выше |

## 7. Действия

1. [ ] Зафиксировать в `CODE_STYLE.md`: триггеры — только аудит и целостность.
2. [ ] Зафиксировать генерацию каталога форм/действий из кода при старте приложения (ADR-0003).
3. [ ] Принять ADR-0002 (стек) и ADR-0003 (мультиарендность и RBAC).
4. [ ] Развести контуры: БД CMS и БД DWH — раздельно с первого дня (детали — Этап 2).
