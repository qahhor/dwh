# ADR-0006: Модульный монолит — границы модулей и инварианты предметной области

**Статус:** Частично заменено ADR-0014 (2026-09-03)
**Дата:** 2026-08-27
**Закрывает находки аудита:** A-1 (стиль не зафиксирован), A-2 (связанность `libs/`), A-3 (границы DDD)
**Зависит от:** ADR-0001, ADR-0004

> Историческое решение ниже сохраняется для трассируемости. Положения о
> Control Plane, fleet, лицензировании, Nomad, Consul и обязательном Vault
> больше не описывают поддерживаемый runtime.

---

## 1. Контекст

Ни один ADR до сих пор не отвечал на вопрос «монолит или микросервисы». ТЗ описывает
монорепо с двумя приложениями, то есть фактически модульный монолит, но это нигде не названо.
Умолчания в архитектуре не живут: первый сильный разработчик предложит «вынести уведомления
в отдельный сервис», и возразить будет нечем.

## 2. Решение

**Модульный монолит.** Каждое из двух приложений (`instance`, `control-plane`) — единый
процесс, внутри разделённый на модули с явными границами. **Выделение любого модуля в
отдельный сервис требует нового ADR.**

### 2.1. Почему микросервисы здесь противопоказаны

Аргумент арифметический, а не вкусовой. При модели «экземпляр на клиента» (ADR-0004) каждый
сервис умножается на число клиентов: 6 сервисов × 100 клиентов = **600 процессов вместо 100**.
Каждый несёт свой JVM-оверхед (~200–400 МБ) и свою сетевую границу. При этом:

- Нет ни одной причины масштабировать модули независимо: нагрузка внутри экземпляра одного
  клиента однородна и невелика.
- Нет разных команд, которым нужны независимые релизные циклы, — команда одна.
- Транзакционная целостность между правами, задачами и аудитом важнее независимости деплоя;
  распределённые транзакции здесь были бы чистым вредом.

Микросервисы решают организационные проблемы больших команд. У нас их нет, а платить за них
пришлось бы ресурсами клиента.

### 2.2. Модули экземпляра

| Модуль | Ответственность |
|---|---|
| `platform` | `instance_info`, настройки, клиент control plane (heartbeat, лицензия, объявления) |
| `iam` | Пользователи, пароли, сессии, OTP, API-токены, восстановление доступа |
| `rbac` | Каталог форм и действий, роли, гранты, эффективные права, проверка доступа |
| `tasks` | Проекты, задачи, статусы, участники, комментарии |
| `notify` | Уведомления, каналы доставки, очередь, шаблоны, объявления |
| `files` | Хранилище файлов, метаданные, выдача |
| `audit` | Журнал изменений, security-события |

### 2.3. Правила зависимостей (проверяются автотестом)

1. **Обращение только через публичный API модуля.** Модуль экспортирует фасад-интерфейс;
   его репозитории, сущности и таблицы — внутренние. Прямой SQL к чужим таблицам запрещён.
2. **Циклов нет.** Направление: `tasks`/`files`/`notify` → `rbac` → `iam` → `platform`;
   `audit` не зависит ни от кого (пишется через триггеры и события).
3. **Связь между бизнес-модулями — через события, а не вызовы.** `tasks` не вызывает
   `notify` напрямую: он публикует доменное событие (`TaskAssigned`, `TaskCommented`),
   `notify` подписывается. Это убирает связанность и заодно даёт готовый источник событий
   для AI/ML (ADR-0005 П5).
4. **Enforcement:** ArchUnit-тест в CI. Нарушение правила ломает сборку — иначе правила
   не соблюдаются.

### 2.4. Решение по общим модулям `libs/` (находка A-2)

Аудит зафиксировал риск: общий изменяемый код между двумя деплоями заставляет обновлять их
синхронно — изменение ради control plane потребовало бы перевыката всего флота.

**Решение: сократить общее до действительно стабильного.** В `libs/` остаются только
утилиты без бизнес-логики (типы, работа со временем, криптопримитивы, клиенты каналов
доставки). **RBAC в control plane реализуется отдельно и проще**: там нет форм клиента,
нет персональных грантов, десяток наших сотрудников и 3–4 роли. Попытка переиспользовать
полноценный RBAC экземпляра ради этого — ложная экономия.

## 3. Инварианты предметной области (закрывает A-3)

DDD применяем точечно: полноценные агрегаты нужны там, где есть нетривиальные правила.
Остальное — CRUD, и навязывать ему агрегаты вредно.

### Агрегат `Task`

Границы: задача + участники + чек-лист. Комментарии — отдельный агрегат (растут независимо).

| Инвариант | Правило |
|---|---|
| I-T1 | У задачи ровно один ответственный (`involve_kind = R`) в любой момент времени |
| I-T2 | Постановщик задаётся при создании и не меняется |
| I-T3 | `resolved_time` заполнен тогда и только тогда, когда статус терминальный (`done`/`cancelled`) |
| I-T4 | Менять статус может только участник задачи с правом записи в её проекте |
| I-T5 | Подзадача принадлежит тому же проекту, что и родитель; вложенность — один уровень |
| I-T6 | Закрытие задачи с незакрытыми подзадачами запрещено |
| I-T7 | `begin_time ≤ end_time`, если оба заданы |

Место обеспечения: методы агрегата `Task`, не контроллеры и не сервисы. Проверяется
юнит-тестами без БД.

### Агрегат `EffectivePermissions`

| Инвариант | Правило |
|---|---|
| I-P1 | `effective_permissions` = объединение прав ролей пользователя и его персональных прав — всегда, без «окон рассогласования» видимых наружу |
| I-P2 | Любое изменение прав инкрементирует `permissions_version` пользователя в той же транзакции |
| I-P3 | Грант ссылается только на существующую пару `(form, action)` из каталога |
| I-P4 | Системная роль (с `pcode`) не может быть удалена или лишена базовых прав |

### Агрегат `User`

| Инвариант | Правило |
|---|---|
| I-U1 | Блокировка пользователя закрывает все его сессии и отзывает токены в той же транзакции |
| I-U2 | Логин и email уникальны в рамках экземпляра |
| I-U3 | Пароль хранится только как Argon2id-хеш; исходное значение не логируется никогда |

### Очередь доставки `notify`

| Инвариант | Правило |
|---|---|
| I-N1 | Сообщение попадает в dead-letter только после исчерпания N попыток |
| I-N2 | Доставка идемпотентна: повторная обработка не порождает второе сообщение получателю |

## 4. Последствия

- Появляется ArchUnit-тест — новая обязательная часть CI.
- Событийная связь между модулями требует дисциплины: события — часть контракта модуля,
  их переименование ломает подписчиков. Именование событий фиксируется в code review.
- Control plane получает собственный простой RBAC вместо переиспользования — небольшое
  дублирование в обмен на независимость деплоя.
- Если когда-нибудь понадобится выделить сервис — модульные границы уже есть, и это будет
  операция извлечения, а не переписывания.

## 5. Действия

1. [ ] Структура пакетов по модулям + фасады.
2. [ ] ArchUnit-тест правил зависимостей в CI.
3. [ ] Реализация инвариантов I-T*, I-P*, I-U*, I-N* в агрегатах + юнит-тесты.
4. [ ] Пересмотр состава `libs/`: только утилиты; RBAC control plane — отдельно.
