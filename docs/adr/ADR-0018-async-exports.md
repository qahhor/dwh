# ADR-0018: Асинхронная выгрузка списков в xlsx и журнал выгрузок

**Статус:** Принято (2026-09-25)
**Дата:** 2026-09-25
**Зависит от:** ADR-0006 (модульный монолит), ADR-0013 (скоуп данных),
ADR-0016 (реестр полей), ADR-0015 (п. 22 роадмапа)

---

## 1. Контекст

Списки на реестре полей (ADR-0016) листаются страницами, но человеку нужен
весь список файлом — отдать, свести, отфильтровать в Excel. Синхронная
выгрузка большого списка держит запрос и соединение минутами; старый CSV
задач (`/reports/tasks/export`) — единственный экспорт и написан под один
список. Идея журнала выгрузок — из Biruni; реализация своя.

## 2. Решение

### 2.1. Источник строк — сам список

Модуль объявляет бин `QueryListExporter` (`instance.common.query`) на свой
список: он отдаёт те же страницы, что экран, — с тем же скоупом данных, теми
же правами на поля (ADR-0016, 2.9) и теми же объектами, что получает клиент.
Значение ячейки читается по ключу поля реестра, который совпадает с именем
свойства в JSON. Отдельного SQL для выгрузки нет, поэтому выгрузка не может
показать больше, чем список. Первые выгрузки: `upl.sources`, `upl.packages`,
`mf.files` (с параметром `scope`, как переключатель «мои/все»).

### 2.2. API и журнал

- `POST /api/v1/exports` — `{list, filter, sort, q, columns, options, lang}`.
  Запрос проверяется сразу: список и право на него (чужой и несуществующий
  неотличимы — 404), фильтр, сортировка и поиск — тем же компилятором, что
  список, колонки — только видимые смотрящему поля, параметры — только
  объявленные экспортёром (422). Больше трёх выгрузок в работе у человека —
  409 `EXPORT_BUSY`. Ответ 202 и строка журнала `queued`.
- `GET /api/v1/exports` — последние 50 выгрузок человека.
- `GET /api/v1/exports/{id}/file` — файл своей выгрузки, пока она `done` и
  не истекла; чужая выгрузка — 404.

Журнал — таблица `report_exports` (V118): состояние `queued → running →
done | failed`, число строк, признак обрезки, код ошибки, срок хранения
(7 дней). Модуль — `report`: он зависит только от `common`, `md` и `fnd`,
граф модулей остаётся без циклов.

### 2.3. Задание

`report.export` — задание очереди основы. Оно берёт выгрузку в работу
(`queued → running` атомарно), выполняется **от имени владельца с его
правами на момент выполнения** (права, отозванные после запроса,
соблюдаются; заблокированному выгрузка не пишется — `EXPORT_FORBIDDEN`),
листает список по 200 строк до конца или до предела
`dwh.reports.export.max-rows` (по умолчанию 50 000; обрезка отмечается),
пишет xlsx во временный файл и кладёт его в хранилище экземпляра. Файлы
выгрузок не входят в квоту пользователя.

В файле — строка заголовков (подписи колонок на языке запроса), затем
строки; числа — числами, даты и моменты — датами Excel (UTC), флаги —
«да/нет», перечисления — словами. Фильтр и закреплённая шапка.

`report.export_cleanup` раз в час удаляет истёкшие выгрузки: файл из
хранилища, затем строку журнала; если файл удалить не удалось, строка
остаётся до следующего раза.

### 2.4. UI

`ui-export-button` в панели `ui-server-table` (вход `exportable`) собирает
состояние экрана: фильтр, сортировку, поиск, показанные колонки в их
порядке и параметры списка. Журнал — страница «Мои выгрузки» (`/exports`,
меню профиля): состояние, строки, срок хранения, скачивание; страница
сама обновляется, пока есть незаконченные выгрузки.

## 3. Последствия

- Любой список реестра получает выгрузку одним бином в своём модуле.
- Выгрузка никогда не шире экрана: одна и та же страница, скоуп и права.
- Упавшее задание очереди не перезапускается (особенность основы) —
  выгрузка остаётся `failed`, человек заказывает её снова.
- Задание держит транзакцию, пока листает список; для предела 50 000
  строк это приемлемо, для больших выгрузок нужен потоковый курсор.
