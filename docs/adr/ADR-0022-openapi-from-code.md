# ADR-0022: Описание API из кода

**Статус:** Принято (2026-09-29)
**Дата:** 2026-09-29
**Зависит от:** ADR-0021 (единая модель ошибок); план 10/10, пункт 3.3

---

## 1. Контекст

`/api/v1/openapi.json` отдавал `OpenApiController`: 400 строк описания,
написанного руками. Он отставал от контроллеров (в нём было меньше операций, чем
обработчиков), не знал формата ошибок и держал единственное, кроме
`UplXlsxParser`, исключение из правила размера классов (пункт 3.10). Веб
описывал ответы сервера своими интерфейсами, и ничто не сверяло их с сервером.
Изменение, ломающее клиентов, ничем не ловилось.

## 2. Решение

1. **Описание генерирует код.** springdoc-openapi (`springdoc-openapi-starter-webmvc-api`,
   без Swagger UI) строит OpenAPI 3.1 по контроллерам и DTO. `ApiDocsConfig`
   добавляет то, чего код не говорит: заголовок, схемы входа (`BearerAuth` —
   персональный токен, `SessionCookie` — cookie веб-приложения) и ответ
   `default` с `application/problem+json` (`ProblemDetailRecord`, ADR-0021) у
   каждой операции. Адрес прежний — `/api/v1/openapi.json`; с 2026-10-03 —
   только для вошедшего пользователя (решение владельца продукта: описание
   называет все сущности и поля установки), без входа — 401.
2. **Копия в репозитории.** `docs/api/openapi.json` — то, что генерирует код,
   в каноническом виде (ключи по алфавиту, отступы). Её читают генератор типов
   веба и проверка совместимости; её diff в pull request показывает изменение
   API глазами клиента.
3. **Типы веба из описания.** `npm run api:types` в `apps/web` генерирует
   `src/app/core/api/openapi.d.ts` (openapi-typescript). Генератор живёт в
   отдельном пакете `tools/api-types`: openapi-typescript 7 требует
   TypeScript 5, веб — на TypeScript 6. Новый код берёт типы через
   `ApiSchema<'Имя'>`; рукописные интерфейсы, которые остаются, сверяются с
   описанием тестом (первый — модель ошибок).
4. **Совместимость.** Pull request, ломающий клиентов базовой ветки (удалена
   операция, поле, сужен тип), не проходит CI. Намеренный слом — метка
   `api-breaking` у pull request или трейлер коммита `Api-Breaking: <что и
   почему>` у прямого пуша (у него нет метки), и в обоих случаях запись в
   `CHANGELOG.md`. Удаление устаревших форм после `Sunset` объявляется так же
   ([ADR-0023](ADR-0023-uniform-rest.md), §4).

## 3. Проверки

- `OpenApiContractTest` (backend, `mvn verify`): каждый обработчик приложения
  есть в описании; `docs/api/openapi.json` совпадает с тем, что генерирует код.
  После намеренного изменения API:
  `mvn test -pl apps/server -Dtest=OpenApiContractTest -Dopenapi.update=true`.
- `scripts/api/test-api-contract.ps1` (job `api contract` в CI):
  1. Spectral (`.spectral.yaml`, правила `spectral:oas`) — ошибки валят сборку;
  2. `openapi.d.ts` сгенерирован из текущего описания байт в байт;
  3. openapi-diff против `docs/api/openapi.json` базовой ветки, `--fail-on-incompatible`.
- `api-schema.spec.ts` (веб, typecheck): поле, которое сервер описал в
  `ProblemDetailRecord` или `FieldErrorItem`, а веб не знает, — ошибка сборки.

## 4. Последствия

- Изменение контроллера или DTO меняет `docs/api/openapi.json`; без
  перегенерации падает `OpenApiContractTest`, без `npm run api:types` —
  проверка типов.
- Описание операций (`summary`, `description`) пока пустое: Spectral выдаёт
  предупреждения `operation-description`. Их снимают по мере работы с
  контроллерами (пункт 3.4 добавляет правила стиля REST).
- Обязательность полей в описании берётся из аннотаций; пока их нет, все поля
  в типах необязательные. Сверка рукописных типов проверяет имена полей, не
  обязательность.
