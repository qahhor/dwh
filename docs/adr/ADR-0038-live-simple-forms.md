# ADR-0038: создание простых форм без выпуска приложения

**Статус:** реализовано и проверено локально по поручению STU-05 от 2026-10-15; целевая приёмка RC остаётся открытой. Результаты — в [плане STU-05](../architecture/admin-studio-plan.md#14-stu-05-новые-формы-без-выпуска-приложения).

## Контекст и сравнение

STU-04 создаёт проверяемый пакет и доставляет статическую форму через CLI/Flyway.
STU-05 разрешает новую простую форму без следующего выпуска приложения.
Сохраняются модульный монолит, EntityDefinition/EntityRuntime, QueryList, права,
аудит и общий экран `/e/:code`. Runtime PostgreSQL не получает DDL-привилегии.

| Вариант | Достоинство | Цена / решение |
|---|---|---|
| Таблица на каждую форму | Нативные типы, индексы, меньше изменений SQL runtime | Нужны привилегированный online DDL, блокировки и отдельное восстановление; не выбран |
| Общая фиксированная таблица JSONB | Flyway создаёт схему заранее, активация только DML, транзакция включает определение и права | Нужны обязательная partition-граница во всех путях и лимиты; выбран |
| Отдельный динамический CRUD | Изоляция новой реализации | Дублирует права/валидацию/историю, расходится с архитектурой; не выбран |

## Решение

1. CLI создаёт каркас модуля `studio`; фиксированные служебные таблицы и таблица
   записей поставляются Flyway. Только namespace `studio.*` разрешён при активации.
   Другие модули сохраняют доставку STU-04. Физические имена и SQL не берутся из браузера.
2. Пакет simple-form-package v1 повторно проверяется сервером. Контрольная сумма
   подтверждает целостность, а не доверие к автору. Право `studio.forms.publish`
   отдельно от `md.settings.update`; авторство не выдаёт права использования.
   Первоначальные CRUD grants только административным ролям. Другим ролям их
   назначают существующим редактором прав.
3. Активация create-only: определение неизменяемо. Точный повтор возвращает то же
   определение; другой пакет с тем же кодом даёт 409. Нет UPDATE/DROP схемы,
   деактивации, конвертации данных, hooks, ссылок, файлов или глобального SEARCH.
   Поддержаны прежние 10 простых типов, до 20 дополнительных полей, ru/uz/en.
4. Определение, каталог прав и аудит создаются одной транзакцией. Ограничение
   количества активных форм — 100 на установку (инженерный лимит первого этапа).
   Конкурентная активация сериализуется внутри БД; rollback не оставляет форму.
5. Общий runtime получает типизированную partition binding и JsonProperty:
   partition записывает только сервер; он входит в каждое чтение и изменение.
   JSON-поля сохраняют обычную валидацию, обязательность и точность типов.
   Системные name/code остаются колонками; уникальность code — внутри формы.
   У каждой формы отдельное логическое имя аудита; ID записей глобален.
6. Источник определений — БД. Один HTTP-запрос использует один immutable snapshot
   во всех реестрах; новые запросы и новый процесс читают актуальное состояние.
   NOTIFY не является условием корректности. Права проверяются существующим
   механизмом на каждом запросе, не входят в snapshot. Фоновые операции получают
   целостный snapshot; неизменяемость существующих форм сохраняет их семантику.
7. Меню, metadata, списки, история и экспорт читают те же определения. Источники
   истории и экспорта сущностей берутся из реестра при каждом вызове, а не
   копируются при старте: форма в карантине, сломанная или с выключенным модулем
   отвечает 404 и не перечисляется в `GET /api/v1/history`. Глобальный поиск берёт
   список при старте, но живые формы SEARCH не получают (охранный тест).
   Рестарт не делает динамические права deprecated. Переводы добавляются ограниченным
   namespace без перезаписи bundled keys; UI обновляет данные после активации.
8. Выключатель модуля закрывает использование созданных форм штатным механизмом.
   Отдельный выключатель активации закрывает создание новых форм, сохраняя чтение
   уже активированных. Значения и эксплуатационные команды фиксируются в cookbook.
   Выключенный модуль `studio` не читает и не компилирует каталог: live-сущностей нет.
9. Изоляция сбоя (уточнение 2026-10-17). Сохранённая форма, которая не загружается
   (декларация не компилируется, код совпал со статической сущностью, ключи переводов
   перекрывают bundled-ключи, строка за пределом 100 форм), пропускается: ERROR в логе
   с кодом и причиной, метрика `smc_studio_forms_broken`, health-компонент
   `studioForms` DOWN с деталями. Компонент не входит в readiness: остальные формы и
   все статические сущности продолжают работать, старт приложения из-за сохранённой
   формы не падает. При совпадении кода побеждает статическая сущность; поиск
   статического кода не читает live-каталог. Метрики читают каталог, последний раз
   скомпилированный на узле, и сохраняют значение при изменении каталога до новой
   компиляции; алерт `SmartupcmsStudioFormsBroken` (warning, `> 0` дольше 10 мин,
   runbook RB-13). Активация заранее проверяет то же: код статической сущности —
   409 `error.studio.exists`, подписи, перекрывающие bundled-ключи, — 422
   `error.studio.translation_key`, поэтому новая форма не сохраняется сломанной.
   Подпись, перекрытая сохранённым переопределением словаря, пропускается и
   пишется в лог один раз на WARN.
10. Карантин. Строки `studio_forms` неизменяемы (триггер V214), поэтому оператор
    выводит форму из работы отдельной строкой `studio_form_quarantine` (V216):
    `POST /api/v1/studio/quarantine`, `DELETE /api/v1/studio/quarantine/{code}`,
    состояние каталога — `GET /api/v1/studio/catalog`; право `studio.forms.publish`,
    аудит каждой операции. Форма в карантине отвечает 404, её записи и права
    сохраняются (синхронизация каталога прав при старте не делает их deprecated).
    Права сломанной формы и формы в карантине, даже если декларация не
    компилируется, выводятся из сохранённого кода без компиляции: те же пары
    `view/create/update/delete`, что регистрирует компилятор. Сломанная форма в
    карантине не считается сломанной; счётчик `quarantined` (health и метрика) —
    все строки карантина, как в `GET /api/v1/studio/catalog`. Код в пути
    `GET`/`DELETE .../quarantine/{code}`, не похожий на код живой формы, получает
    404 без повтора значения.
11. Кэш каталога. Скомпилированный каталог переиспользуется, пока версия в БД
    (количество и максимальный id обеих таблиц, одно SQL-выражение) не изменилась;
    каждое чтение проверяет версию, поэтому корректность по-прежнему не зависит от
    NOTIFY. Уведомление `studio.catalog` через `smc_cache` уходит с фиксацией
    транзакции (откат его отменяет) и заставляет другие узлы сразу перекомпилировать
    каталог; копия своего узла сбрасывается после фиксации. HTTP-запрос сохраняет
    один snapshot.
12. Точный повтор активации обслуживаемой формы отвечает `200` с тем же телом и без
    `Location`: ничего не создаётся. Новая форма отвечает `201` с `Location`. Оба
    статуса объявлены в API; это единственный обработчик с двумя статусами успеха
    (список исключений `ResponseStatusDeclaredTest` с причиной). Точный повтор формы в
    карантине отвечает 409 `error.studio.quarantined`, сломанной формы — 409
    `error.studio.broken` с причиной, а не «активировано» (изменение 2026-10-17).
13. Совместимость хранимого формата. Golden-образцы simple-form v1 (каждый тип поля и
    опция) обязаны читаться без изменений, сохранять checksum и компилироваться тем же
    способом. Изменение компилятора, DTO или валидатора, ломающее хранимую форму,
    требует пути миграции или новой версии формата, а не правки образцов.
14. Код модуля `studio` и коды модулей платформы зарезервированы: сервер не принимает
    пакет с модулем платформы (кроме `studio` для активации), CLI не доставляет
    статическую сущность ни в модуль платформы, ни в `studio`. Проверка двусторонняя:
    каждый пакет сервера и каждый встроенный манифест модуля либо зарезервирован,
    либо назван бизнес-модулем с причиной (`PlatformModulesReservedTest`).

Исчерпание лимита в 100 форм (create-only, удаления нет) решается состоянием
«архивирована» этапа 1 [ADR-0041](ADR-0041-live-form-evolution.md): архивная форма
не занимает лимит активных форм. Реализовано 2026-10-17 (ADR-0041, «Реализация»):
лимит 100 считает только активные формы, все сохранённые — не более 500; решение 3
(create-only) для ранее активированных определений сохраняется в том смысле, что
строка `studio_forms` остаётся неизменяемой версией 1, а изменения идут новыми
неизменяемыми версиями `studio_form_versions`; ACC-21 из N/A становится проверкой
совместимости версий (`StudioChangeRulesTest`, `StudioFormVersionsHttpTest`).

## Приёмка и эксплуатация

ACC-17: два независимых источника/реестра на общей PostgreSQL, пропущенное
уведомление, реконструкция источников/реестров с новым пулом БД, согласованный
snapshot, сохранение каталога прав, rollback и конкуренция. Локальные тесты
в одном JVM не заменяют drill рестарта отдельных процессов на целевом контуре.
ACC-18: отрицательная матрица чужого ID в CRUD/history/list search/report/export/files;
положительные CRUD/history/export и list search; непредусмотренные FILE/SEARCH закрыты.
ACC-19: существующий editor, отдельное подтверждение активации, ошибки сохраняют
ввод, повтор безопасен, ru/uz/en, keyboard/mobile/a11y.
ACC-21 N/A: изменение опубликованной схемы запрещено.
ACC-20: локальный ограниченный workload и измерения; staging SLO/backup/restore
остаются отдельным release gate, целевая приёмка без стенда не заявляется.

Откат приложения не удаляет декларации/строки. Перед выпуском нужен backup;
после аварии сверяют сохранённые определения, каталог прав и аудит. Runtime
работает DML-only. Полный release CI, публикация и merge не входят в локальный этап.

Версия общего Platform API/SPI — 2.0.0: контракт partition/JSON-поля добавляет
вариант STABLE sealed-типа FieldSource и нарушает прежние exhaustive switch
при пересборке внешнего модуля (ADR-0033). Baseline 1.0.0 сохранён; japicmp
проверяет бинарные сигнатуры, отдельный API policy — изменения sealed-иерархий.
Переход до первого выпуска прямой, без слоя совместимости.

Ссылки и область данных (2026-10-17, ADR-0041, «Этап 1, ветка 2»): решение 3 («нет … ссылок») для живых форм
формата 3 заменено — поддержаны выбор из фиксированных вариантов, ссылки на справочник администратора и на запись
другой живой формы и пользователь; запись видна по области данных формы (все, подразделение, свои). Гарантии
решения 5 сохраняются: значения ссылок лежат в `payload` той же партиции, их проверяет общий runtime правами и
областью цели, DDL в runtime по-прежнему нет; новая колонка `studio_records.org_unit_id` поставлена Flyway (V221).

Раскладка и заголовок записи (2026-10-18, ADR-0041, «Этап 1, ветка 3»): решение 5 («Системные name/code остаются
колонками») для формата 4 уточнено — форма может не иметь системных «Название» и «Код»: запись называется полем,
выбранным администратором, или своим номером в форме (`studio_records.record_number`, V224; `name`/`code` допускают
NULL). Формы форматов 1–3 сохраняют `name`/`code`. Граница `form_id`, проверки runtime и отсутствие DDL в runtime не
меняются.

Формулы и правила (2026-10-18, [ADR-0042](ADR-0042-live-form-formulas.md), формат 5): решение 3 («нет … hooks»,
«без произвольного SQL/скрипта») сохраняется — формула не исполняемый код и не SQL, а выражение фиксированного языка,
проверенное при активации; вычисляемые значения и правила применяет общий runtime на каждом пути записи, значения
хранятся в `payload` той же партиции, DDL в runtime по-прежнему нет.

Документы (2026-10-18, [ADR-0043](ADR-0043-live-form-documents.md), формат 6): решение 3 («нет … ссылок, файлов» и
create-only логика) для живых форм формата 6 дополнено строками документа, номером и статусами с согласованием. Строки
лежат в фиксированных таблицах Flyway `studio_record_lines_1..3`, доступных только через запись своей партиции; номер —
счётчик формы в транзакции; переходы — действия записи общего runtime с правом каждого. DDL в runtime по-прежнему нет.
Файлы живых форм не сделаны.
