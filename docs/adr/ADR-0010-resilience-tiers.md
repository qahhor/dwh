# ADR-0010: Отказоустойчивость — уровни доступности и HA платформенных сервисов

**Статус:** Частично заменено ADR-0014 (2026-09-03)
**Дата:** 2026-08-27
**Закрывает:** слабейшее измерение оценки архитектуры (отказоустойчивость 6/10): нет failover БД, одиночные control plane и Vault
**Зависит от:** ADR-0004, ADR-0007, ADR-0009

> Историческое решение ниже сохраняется для трассируемости. Положения о
> Control Plane, fleet, лицензировании, Nomad, Consul и обязательном Vault
> больше не описывают поддерживаемый runtime.

---

## 1. Контекст

Текущее состояние: отказ узла клиента = простой до ручного восстановления (RTO 4 ч);
Vault — критическая зависимость всего флота (его отказ блокирует деплои, секреты, выпуск
лицензий); control plane одиночный. Это соответствует заявленным 99,5%, но без запаса, и
не даёт ответа первому клиенту, который попросит 99,9%.

Принцип решения: **дифференцировать доступность по цене**, а не строить максимум для всех.
HA — это не свойство архитектуры, это тариф.

## 2. Решения

### 2.1. Платформенные сервисы — кворум из трёх (обязательно, M0)

Nomad server + Consul server + Vault (integrated storage / Raft) — по три экземпляра на
**трёх отдельных небольших узлах** платформы. Это не опция: потеря одиночного Vault означает
стоп деплоев и лицензий всего флота, а стоимость кворума — три VPS малого размера.

- Vault: Raft-кластер, авто-восстановление лидера; процедура unseal — в runbook
  (auto-unseal отложен: ещё одна зависимость ради удобства).
- Клиентские узлы (Nomad clients) от этого не дублируются — см. 2.3.
- Расчёт: платформа переживает отказ любого одного узла платформы без влияния на флот.

### 2.2. Control plane — без HA, с быстрым восстановлением (осознанно)

CP **не** дублируется. Обоснование: экземпляры автономны (grace лицензии 14 дней, объявления
просто не обновляются, heartbeat копится) — недоступность CP на часы не влияет на клиентов.
Строить HA ради нашего же удобства — не окупается.

Вместо этого: **RTO CP ≤ 2 ч** — тот же механизм бэкапов и автопроверки восстановления,
что для экземпляров (ADR-0007 разд. 2.5); job CP при отказе узла перепланируется Nomad'ом на
резервный узел, БД восстанавливается из бэкапа скриптом. Единственная потеря — heartbeat'ы
за окно простоя; лицензии и объявления неизменны.

**Исключение:** алерт «экземпляр молчит» шлёт CP, значит при лежащем CP слепнет и он.
Компенсация: обратный watchdog — vmalert (ADR-0009) проверяет метрику самого CP и поднимает
тревогу, если CP молчит > 10 мин. Наблюдаемость и CP резервируют друг друга крест-накрест.

### 2.3. Доступность экземпляров клиентов — три тарифа

| Тариф | Обещание | Механизм БД | RTO | RPO | Что добавляется |
|---|---|---|---|---|---|
| **Standard** (по умолчанию) | 99,5% | Восстановление из бэкапа **автоматизированным скриптом** (одна команда) | **≤ 1 ч** (было 4) | ≤ 15 мин | Ничего сверх текущего; RTO снижаем автоматизацией restore, а не железом |
| **Standby** (опция) | 99,7% | Потоковая реплика на другом узле, **ручной promote** по runbook | ≤ 15 мин | ~0 (sync опц., async по умолчанию) | +1 узел (или слот на общем standby-узле), +стоимость в тарифе |
| **HA** (опция, по запросу) | 99,9% | **Patroni** (3 узла PostgreSQL, автоматический failover) | ≤ 1 мин | ~0 | +2 узла; вводится отдельным проектом при первом покупателе |

Ключевые правила:
- Приложение (stateless) при отказе узла **перепланируется Nomad'ом автоматически** на
  резервную ёмкость уже в Standard — держим **N+1 узел** в пуле клиентских узлов (ADR-0007).
  Простой Standard-клиента определяется только временем восстановления БД.
- Тариф фиксируется в реестре CP (FR-CP-1) и в Nomad job'е клиента; переход между тарифами —
  без изменения приложения (меняется только топология БД).
- Patroni **не строится в Этапе 1** — проектируется слот под него (шаблон job'а умеет
  standby-группу), реализация — при первом клиенте, купившем HA. Это защита от полугода
  работы «на всякий случай».
- Garage: в Standard — restore из бэкапа вместе с БД; файлы адресуются по SHA, потерь
  согласованности нет.

### 2.4. Обязательные учения (без них HA — декорация)

В приёмку Этапа 1 (M5) добавляются:
- **Учение «отказ клиентского узла»:** гасим узел со Standard-экземпляром → приложение
  переехало само, БД восстановлена скриптом, секундомер ≤ 1 ч.
- **Учение «отказ узла платформы»:** гасим один из трёх узлов кворума → деплой и выпуск
  лицензии продолжают работать.
- **Учение «CP лежит»:** экземпляры работают, vmalert поднял тревогу, CP восстановлен ≤ 2 ч.
Повторение — раз в полгода на проде (game day), результаты — в отчёт эксплуатации.

## 3. Компромиссы

- Standard остаётся с простоем при отказе узла — осознанно: доступность выше 99,5% продаётся,
  а не раздаётся. Митигция — честный SLA в договоре.
- Кворум платформы — +2 небольших узла и дисциплина обновления самих Nomad/Consul/Vault
  (их апгрейд — тоже по кольцам: сначала один узел кворума).
- Крест-накрест мониторинг (CP ↔ vmalert) — две системы должны знать друг о друге; связка
  описана в ADR-0009 разд. 3 и покрывается учением.

## 4. Действия

1. [ ] M0: три узла платформы, Raft-кластеры Nomad/Consul/Vault, N+1 в пуле клиентских узлов.
2. [ ] M0: автоматизированный restore экземпляра «одной командой» (основа тарифа Standard, RTO ≤ 1 ч).
3. [ ] M3: тариф в реестре CP; watchdog CP ↔ vmalert.
4. [ ] M5: три учения из разд. 2.4 в приёмочном чек-листе.
5. [ ] Шаблон job'а: заготовка standby-группы (тариф Standby) — без реализации Patroni.
