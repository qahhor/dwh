# ADR-0028: Код формы — код сущности или области модуля

**Статус:** Принято (2026-10-01)
**Дата:** 2026-10-01
**Зависит от:** ADR-0003 (RBAC), ADR-0006 (модульный монолит, проверка
границ), ADR-0019 (объявление сущности), ADR-0023 (старые формы API на один
релиз), ADR-0026 (опубликованные представления); план 10/10, пункт 4.4

---

## 1. Контекст

Право — пара «форма + действие» (`@RequiresPermission(form, action)`, ключ
`<форма>.<действие>`). До этого решения первый сегмент кода формы называл
группу экранов, а не модуль: формы модуля `md` назывались `iam.users`,
`rbac.roles` и `platform.settings`, а префикс `platform.*` делили пять
модулей — `md` (настройки, навигация, реестр модулей), `ms.notify`
(объявления), `mf` (файлы), `search` и `kwh` (вебхуки). По коду права нельзя
было понять, какой модуль его проверяет и чей ресурс оно открывает; каталог
форм хранил модуль отдельной строкой в `MdFormCatalog`, и он мог разойтись с
кодом.

## 2. Решение

1. **Вид кода.** Код формы — `<область>` или `<область>.<сущность-или-экран>`:
   один или два сегмента `[a-z][a-z0-9_]*`. Действие — один такой же сегмент.
   Три сегмента и заглавные буквы запрещены. Код формы сущности, объявленной
   через `EntityDefinition`, равен коду её области, если сущность в модуле одна
   (`notes`), иначе — `<область>.<сущность>`.
2. **Область называет модуль-владельца.** Область — код бизнес-модуля
   (`analytics`, `audit`, `fnd`, `kauth`, `md`, `mf`, `report`, `search`,
   `upl`) или именованная область из таблицы ниже. Таблица ведётся в одном месте —
   `md.pref.PermissionAreas`; из неё же каталог прав берёт модуль формы
   (`MdFormCatalog.moduleOf`), поэтому модуль в матрице прав больше не
   записывается рядом с названием.

   | Область | Модуль | Почему не код модуля |
   |---|---|---|
   | `tasks` | `ms.task` | код модуля из двух сегментов |
   | `notes` | `ms.note` | то же |
   | `notify` | `ms.notify` | то же |
   | `webhook` | `kwh` | пункт 4.3 переименует модуль `kwh` в `webhook`; область уже носит новое имя, и второй миграции прав не будет |

3. **Контроллер проверяет формы своего модуля.** Обработчик модуля M требует
   форму, область которой принадлежит M. Чужая форма допустима, только если
   владелец публикует её модулю M (`PermissionAreas.PUBLISHED`) — так же, как
   модуль публикует представления для чтения (ADR-0026). Публикация оправдана,
   когда обработчик обслуживает ресурс владельца и отдельное право заставило бы
   администратора выдавать одно и то же дважды:

   | Форма | Кому опубликована | Зачем |
   |---|---|---|
   | `md.profile` | `audit`, `kauth`, `report` | учётная запись самого пользователя: свои сессии, токены и каналы (kauth), свои выгрузки (report), история записей, которые пользователь может открыть (audit дополнительно проверяет право самой записи) |
   | `md.users` | `kauth` | блок «Сессии и безопасность» карточки пользователя — часть администрирования пользователей |
   | `md.settings` | `kauth`, `search` | настройки платформы: список провайдеров входа (kauth), настройки поиска и задания индекса (search) |
   | `tasks.items` | `report` | отчёт по задачам выгружает список задач по тому же праву, по которому его показывают |

   Инфраструктура (`common`, `config`) не модуль: её обработчики (меню
   сущностей, `form-meta`, `query-meta`, сведения о системе) могут требовать
   любую форму, код которой подчиняется правилу.
4. **Старые коды переименованы.** Миграция `V147__permission_codes_by_module.sql`
   переносит формы и всё, что на них ссылается:

   | Было | Стало | Модуль |
   |---|---|---|
   | `iam.users` | `md.users` | md |
   | `iam.profile` | `md.profile` | md |
   | `iam.org_units` | `md.org_units` | md |
   | `rbac.roles` | `md.roles` | md |
   | `rbac.assignments` | `md.assignments` | md |
   | `platform.settings` | `md.settings` | md |
   | `platform.navigation` | `md.navigation` | md |
   | `platform.modules` | `md.modules` | md |
   | `platform.announcements` | `notify.announcements` | ms.notify |
   | `platform.files` | `mf.files` | mf |
   | `platform.search` | `search` | search |
   | `platform.webhooks` | `webhook.subscriptions` | kwh |

   Без изменений: `md.custom_fields`, `audit.log`, `analytics.dashboard`,
   `upl.sources`, `upl.packages`, `tasks.projects`, `tasks.items`,
   `tasks.comments`, `notes`, `notify.inbox`, `notify.preferences`,
   `notify.dead_letter`.

   Для каждой пары «старый → новый» миграция сначала копирует форму и её
   действия (с названиями и признаком устаревания), выдачи ролям
   (`md_role_permissions`), личные права (`md_user_permissions`),
   материализованные эффективные права (`md_effective_permissions`) и привязку
   пунктов меню (`md_navigation_items.required_permission`, ревизия пункта
   растёт), затем удаляет старые строки. Версия прав каждого пользователя
   увеличивается, чтобы клиенты перечитали набор. Изменение данных помечено
   `destructive: approved` (владелец продукта, план 10/10, пункт 4.4).
5. **Старые коды на входе — один релиз.** Старые коды не остаются в каталоге:
   выдать право по старому коду нельзя, и матрица их не показывает. Но запросы,
   которые принимают код формы от клиента, переводят старый код в новый до
   **2026-12-31** (тот же срок, что у старых форм API, ADR-0023):
   `PUT /api/v1/iam/roles/{id}/permissions`, замена личных прав пользователя и
   `requiredPermission` пункта меню. Веб-клиент того же срока
   (`LEGACY_FORM_CODES` в `permission.service.ts`) понимает набор прав,
   загруженный до обновления сервера. После срока обе таблицы удаляются.

## 3. Проверки

- `PermissionCodesTest` (ArchUnit): каждая пара `@RequiresPermission` в
  `main` подчиняется правилу — код правильного вида, область известна, модуль
  контроллера (по `ModuleBoundariesTest.MODULES`) совпадает с владельцем или
  форма ему опубликована; пробы показывают, что `iam.users`,
  `platform.settings`, чужая неопубликованная форма и код из трёх сегментов
  отклоняются. Там же: у каждой области и опубликованной формы есть модуль из
  списка границ, старый код не проходит правило, новый проходит.
- `EntityActionPermissionContractTest`: форма каждого `EntityDefinition`
  принадлежит модулю, названному в его `EntityRights`.
- `PermissionCodesMigrationTest`: база останавливается на V146, получает
  пользователя на каждую роль, роль и личные права на старых кодах и пункты
  меню; после V147 эффективные права каждого пользователя совпадают со
  старыми, переведёнными по таблице, — и в материализованном виде, и после
  пересчёта; ни одна таблица не хранит старый код; таблица миграции и
  `PermissionAreas.LEGACY_FORMS` совпадают.
- `NavigationItemVisibilityIntegrationTest`: пункт меню, созданный со старым
  кодом, сохраняется с новым.

## 4. Последствия

- По коду права видно, какой модуль его проверяет; группировка матрицы прав
  по модулям выводится из кода, а не из отдельной строки.
- Новая форма получает код `<область модуля>.<сущность>`; новая область или
  публикация формы другому модулю — изменение `PermissionAreas` и этого ADR в
  ревью.
- Коды списков реестра (`query-meta/iam.users`), ключи переводов (`iam.*`) и
  пути API (`/api/v1/iam/...`) — отдельные идентификаторы, это решение их не
  меняет: ключи переводов приводит к правилу пункт 4.5, пути — ADR-0023.

### Ограничения (приняты)

- Внешний клиент, который читает `GET /api/v1/auth/me` и сравнивает коды прав
  со старыми строками, увидит новые коды сразу после обновления: ответ не
  может содержать оба набора без удвоения прав в матрице. Поэтому изменение
  оформлено как ломающее (трейлер `Api-Breaking`, раздел Changed в
  CHANGELOG).
- Журнал аудита хранит старые коды в записях до V147: история не
  переписывается.
- Таблица `md_custom_modules` (с колонкой `permissions_json`) не
  использовалась кодом; V147 её не трогает, её удаляет V152 (пункт 4.7).
