# ADR-0007: Стратегия управления флотом — Nomad, миграции, кольца развёртывания

**Статус:** Принято (CEO, 2026-08-27)
**Дата:** 2026-08-27
**Закрывает находки аудита:** O-1 (Compose неадекватен флоту), O-2 (бэкапы), O-3 (канарейка), O-4 (дрейф версий), A-4 (откат миграций)
**Зависит от:** ADR-0004 (экземпляр на клиента)

---

## 1. Контекст

ADR-0004 зафиксировал модель «экземпляр на клиента» при флоте 30–100 экземпляров, но
оставил средством управления Docker Compose. Аудит (AUDIT-01, O-1) показал, что это
несостоятельно: Compose не оркестратор — нет планирования по хостам, восстановления при
отказе узла, обновления без простоя, управления секретами и декларативного состояния.
Оценка ручной эксплуатации: 100 клиентов ≈ 1,5–2,5 FTE постоянно.

Отдельно аудит выявил, что автоприменение миграций при старте (NFR-10) в сочетании с
forward-only Flyway **лишает систему пути отката** — это оценено как самый опасный дефект дизайна.

## 2. Решения

### 2.1. Оркестратор — HashiCorp Nomad (решение CEO)

Nomad вместо Kubernetes и вместо Compose. Обоснование выбора:

| Критерий | Compose+скрипты | **Nomad** | Kubernetes |
|---|---|---|---|
| Потолок по числу экземпляров | ~20–30 | 100+ | 100+ |
| Стоимость внедрения | 8–12 и-дней | **15–20 и-дней** | 25–35 и-дней |
| Порог входа команды | низкий | **средний** | высокий, нужна компетенция |
| Управление секретами | нет | **Vault из коробки** | нужен внешний |
| Канареечное развёртывание | нет | **встроено** | встроено |
| Смешанные нагрузки (batch, периодические задачи) | нет | **да, первоклассно** | да |

Nomad решает ровно нашу задачу — много однотипных стеков на своём железе — без
операционной сложности Kubernetes. Ключевой сопутствующий выигрыш: **связка с Vault**
закрывает управление секретами (аудит SEC-3) и подпись лицензий (A-5) без отдельного решения.

**Состав платформы:** Nomad (оркестрация) + Consul (service discovery, health checks) +
Vault (секреты, подпись лицензий).

### 2.2. Топология: один Nomad job на клиента

```
job "client-<code>"
├── group "app"        → Spring Boot (instance)         [stateless, canary-обновляемая]
├── group "pg-oltp"    → PostgreSQL 18 (OLTP)           [host volume, constraint на узел]
├── group "pg-dwh"     → PostgreSQL 18 (DWH, Этап 2)    [host volume, constraint на узел]
└── group "storage"    → Garage (S3)                    [host volume]
```

**Решение по stateful-нагрузкам.** PostgreSQL и Garage запускаются как Nomad-задачи с
**host volume и жёсткой привязкой к узлу** (`constraint`). Это осознанный компромисс:

- **Даём:** единая модель развёртывания и версионирования, лимиты ресурсов, инвентарь через
  Nomad API, те же инструменты для всех компонентов.
- **Не даём:** автоматический failover БД при отказе узла. Но его не было и в Compose —
  мы ничего не теряем. Автоматический failover (Patroni) — отдельное решение, если появится
  требование доступности выше NFR (99.5%).

Профили ресурсов задаются в `resources`-строфе job'а и соответствуют S/M/L из ТЗ v0.4 разд. 5.
Для крупных клиентов группа `pg-dwh` планируется на **отдельный узел** — логически внутри
контура клиента, физически на своём железе. Nomad делает это констрейнтом, без изменения
архитектуры.

### 2.3. Миграции — отдельный шаг, не старт приложения (закрывает A-4)

**Отменяет NFR-10 в прежней редакции.** Новый порядок:

1. Миграции выполняет **отдельный Nomad batch-job** `migrate-<client>`, запускаемый до
   обновления группы `app`.
2. Приложение при старте **только проверяет** версию схемы и **отказывается стартовать**
   при несовпадении. Мигрировать само оно не может физически.
3. Обновление `app` начинается только после успешного завершения batch-job.

**Правило expand/contract — обязательно.** Каждое изменение схемы разбивается на релизы:

| Релиз | Что делает | Свойство |
|---|---|---|
| N (expand) | Добавляет новое (колонка nullable, новая таблица, новый индекс) | Старый код продолжает работать |
| N (код) | Начинает писать и читать по-новому | Откат приложения возможен: схема совместима с обеими версиями |
| N+1 (contract) | Удаляет старое, когда все экземпляры на новой версии | Выполняется только после подтверждения |

Это возвращает **откат приложения как рабочий механизм**: схема совместима минимум с двумя
соседними версиями кода.

**Защитные меры:**
- Линтер миграций в CI: деструктивные операции (`DROP COLUMN`, `DROP TABLE`, `NOT NULL` на
  заполненной таблице, `ALTER TYPE` с сужением) требуют явной пометки `-- destructive: approved`
  и отдельного ревью.
- Каждая миграция прогоняется в CI на **копии данных крупнейшего клиента** (анонимизированной),
  с замером времени. Миграция дольше 60 с помечается как требующая окна обслуживания.
- Перед `migrate`-job'ом автоматически снимается снапшот БД экземпляра.

### 2.4. Кольца развёртывания (закрывает O-3)

Обновление флота никогда не одномоментное:

| Кольцо | Состав | Выдержка | Критерий продвижения |
|---|---|---|---|
| **R0** | Внутренний стенд | 1 день | Автотесты + ручная проверка сценариев |
| **R1** | 2–3 пилотных клиента (по согласию) | 3 дня | Нет роста ошибок, p95 в пределах SLO, нет обращений |
| **R2** | Остальной флот | — | Продвижение вручную, партиями по ~20% |

Внутри каждого кольца — **canary-развёртывание Nomad**: сначала одна аллокация, проверка
health-check через Consul, автоматический откат (`auto_revert`) при провале. Продвижение
между кольцами — решение человека, не автоматика.

### 2.5. Бэкапы и проверка восстановления (закрывает O-2)

**Отменяет NFR-7 в части «ежеквартально на одном экземпляре выборочно».**

- **Снятие:** периодический Nomad batch-job на экземпляр — ежесуточный базовый бэкап +
  непрерывная архивация WAL. Хранение вне узла экземпляра, **шифрование при записи**
  (ключ в Vault).
- **Проверка (обязательная автоматика):** ночной job поднимает бэкап **случайно выбранного**
  экземпляра во временном окружении, прогоняет smoke-проверки (схема на ожидаемой версии,
  счётчики ключевых таблиц ненулевые, тестовый логин), рапортует результат в control plane.
  Планирование обеспечивает проверку **каждого экземпляра не реже раза в месяц**.
- Проваленная проверка — алерт уровня инцидента, а не строка в отчёте.

### 2.6. Контроль дрейфа версий (закрывает O-4)

Nomad API отдаёт версии запущенных job'ов. Control plane сопоставляет их с текущим релизом:

- Экземпляр отстаёт > 1 minor → предупреждение в дашборде флота.
- Отстаёт > 2 minor → алерт команде эксплуатации, экземпляр попадает в обязательный план
  обновления ближайшего спринта.
- Дашборд показывает распределение флота по версиям — это основной индикатор здоровья
  эксплуатации.

## 3. Компромиссы

- **Nomad — ещё одна платформа в эксплуатации.** Требует обучения команды и содержания
  кластера (серверы Nomad/Consul/Vault). Оправдано с ~15–20 клиентов; до этого выглядит
  избыточным. Но внедрять его позже, имея 30 работающих клиентов, значительно дороже, чем сейчас.
- **Stateful в оркестраторе.** Привязка к узлу означает, что отказ узла = простой клиента до
  ручного вмешательства (RTO 4 ч по NFR). Принимается: это соответствует заявленной
  доступности 99,5%.
- **Кольца замедляют выкатку** — полный прокат по флоту занимает около недели вместо часа.
  Это осознанная плата за то, что дефект не доходит до всех клиентов одновременно.

## 4. Действия

1. [ ] Кластер Nomad + Consul + Vault на нашей инфраструктуре (dev → prod).
2. [ ] Шаблон job-файла клиента с профилями ресурсов S/M/L.
3. [ ] Batch-job миграций + проверка версии схемы при старте приложения.
4. [ ] Линтер миграций и прогон на копии данных в CI.
5. [ ] Job'ы бэкапа и автоматической проверки восстановления.
6. [ ] Интеграция control plane с Nomad API для инвентаря версий.
7. [ ] Runbook: отказ узла, провал миграции, откат релиза.
