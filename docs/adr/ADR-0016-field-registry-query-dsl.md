# ADR-0016: Реестр полей списков, `query-meta` и DSL фильтра

**Статус:** Принято (2026-09-25)
**Дата:** 2026-09-25
**Зависит от:** ADR-0002 (backend stack), ADR-0006 (модульный монолит), ADR-0013 (скоуп данных),
ADR-0015 (перенос UI-кита)

---

## 1. Контекст

dwh — low-code платформа: колонки, фильтры и выборки должны описываться
метаданными на сервере, а экран — строиться по ним. Сейчас каждый список
написан вручную: `JdbcClient` плюс `StringBuilder`, плоские параметры
фильтра, свой формат курсора. Ошибки битого курсора тоже разные: где-то 422,
где-то 400, где-то курсор молча игнорируется. Сортировку с клиента не
принимает ни один список. Таблицы UI-кита (`data-table`, `data-table-filter`)
рассчитаны на протокол Biruni с номерами страниц и потому не переносятся
(ADR-0015). Без серверного контракта перенести их идею нельзя.

Идея — из Biruni: реестр полей формы определяет, что можно показать,
отфильтровать и отсортировать. Реализация своя, под REST с keyset-курсорами.

## 2. Решение

### 2.1. Реестр

Модуль объявляет список бином `QueryList` (`instance.common.query`):

- код списка (`upl.sources`);
- форма и действие права на просмотр;
- `select`, `from` и уникальный ключ строки `idSql`;
- упорядоченный набор полей `QueryField` и сортировка по умолчанию.

Поле `QueryField` описывают:

- `key` — имя поля в DSL и в ответе;
- `labelKey` — ключ словаря для заголовка;
- тип: `text`, `number`, `date`, `instant`, `boolean`, `enum`;
- SQL-выражение над `from`;
- признаки `filterable`, `sortable`, `nullable`, `defaultVisible`;
- для перечисления — значения и префикс ключей словаря.

`QueryListRegistry` собирает все бины и отвергает дубли кодов. Реестр живёт
в `common`: модули зависят от него, он от модулей не зависит (ArchUnit, срезы
без циклов).

Инварианты проверяются при создании описания:

- ключ поля — идентификатор (`^[a-z][a-zA-Z0-9]{0,63}$`);
- сортируемое поле не бывает пустым, иначе keyset-курсор теряет строки на `NULL`;
- сортировка по умолчанию — сортируемое поле;
- значения перечисления заданы только у типа `enum` и у него обязательны.

### 2.2. `GET /api/v1/query-meta/{code}`

Отдаёт поля (без SQL), их типы и допустимые операции, сортировку и размер
страницы по умолчанию, лимиты фильтра. Кто может смотреть список, тот
получает и метаданные.

Неизвестный код и чужой список отвечают одинаково — 404
`QUERY_LIST_NOT_FOUND`: по ответу нельзя перебрать, какие списки есть. Без
входа ответ 401. При обязательной смене пароля ответ 403, как у остальных
защищённых ресурсов.

### 2.3. DSL фильтра

Параметр `filter` — JSON-массив условий, соединённых «и»:

```json
[{"field":"code","op":"starts_with","value":"sales."},
 {"field":"periodicity","op":"in","value":["month","year"]},
 {"field":"lastPublishedVersion","op":"empty"}]
```

Операции зависят от типа поля:

| Тип | Операции |
|---|---|
| text | `eq` `ne` `in` `contains` `starts_with` |
| number | `eq` `ne` `in` `gt` `gte` `lt` `lte` `between` |
| date | `eq` `gt` `gte` `lt` `lte` `between` |
| instant | `gt` `gte` `lt` `lte` `between` |
| boolean | `eq` |
| enum | `eq` `ne` `in` |

Поле с признаком `nullable` дополнительно принимает `empty` и `not_empty`.
Для текста «пусто» — это и `NULL`, и пустая строка.

Значения приводятся к типу поля и попадают в запрос только параметрами.
В SQL идут лишь выражения из реестра. `contains` и `starts_with`
экранируют `%`, `_` и `\`.

Лимиты:

- 20 условий;
- 100 значений в `in`;
- 500 символов в текстовом значении;
- 16 КБ на весь фильтр.

`or` и вложенные группы в первую версию не входят. Когда они понадобятся,
формат расширяется объектом `{"any":[...]}`, не ломая массив «и».

### 2.3а. Свободный поиск `q`

Параметр `q` ищет подстроку без учёта регистра сразу в нескольких текстовых
полях, помеченных в реестре `searchable`, и соединяет их через «или» (для
lookup: «код или название»). DSL фильтра соединяет условия только через
«и», поэтому поиск вынесен в отдельный параметр.

- Поиск складывается с фильтром через «и».
- Значение до 200 символов; `%`, `_` и `\` экранируются так же, как в
  `contains`.
- Поиск входит в отпечаток курсора.
- Искать можно только в текстовых полях. В списке без таких полей `q`
  отвергается кодом `QUERY_SEARCH_INVALID`.
- `query-meta` сообщает `searchable` у каждого поля.

### 2.4. Сортировка и курсор

Параметр `sort` — ключ сортируемого поля; минус означает убывание (`-name`).
Порядок всегда добивается ключом строки: `order by <поле>, <id>` в том же
направлении. Продолжение страницы строится по паре «значение, id».

Курсор хранит значение сортировки, ключ последней строки, итог первой
страницы и отпечаток запроса: SHA-256 от кода списка, сортировки и условий.
Курсор от другого фильтра или сортировки отвергается кодом `INVALID_CURSOR`:
продолжать страницу другим запросом нельзя. Итог считается один раз, на
первой странице.

### 2.5. Ошибки

Все ошибки запроса — 422 `VALIDATION_FAILED`, у каждой свой адрес. Клиент
по нему подсвечивает конкретное условие фильтра.

| Что не так | detail | Адрес и код ошибки |
|---|---|---|
| Фильтр или сортировка | `QUERY_INVALID` | `filter[1].op` → `QUERY_OP_NOT_ALLOWED`, `filter[0].field` → `QUERY_UNKNOWN_FIELD`, `filter[2].value` → `QUERY_VALUE_INVALID`, `filter` → `QUERY_FILTER_INVALID` / `QUERY_FILTER_TOO_LONG`, `sort` → `QUERY_SORT_INVALID` |
| Размер страницы | `INVALID_LIMIT` | `limit` |
| Курсор | `INVALID_CURSOR` | `cursor` |

Ошибки фильтра и сортировки возвращаются все сразу, а не по первой.

### 2.6. Выполнение и скоуп

`QueryListRepository.page(plan, mapper, extra)` выполняет план: страница
`limit + 1` строк и `count(*)` на первой странице. Скоуп данных (ADR-0013)
модуль передаёт предикатом `extra`, и он ложится в тот же SQL. Это не
фильтр после выборки.

Модульные параметры не должны начинаться с `q_`: этот префикс занят
реестром.

### 2.7. Сохранённые представления

Пользователь сохраняет то, что видит в списке, под именем: колонки (порядок,
скрытые, ширина), сортировку и фильтр. Таблица `md_list_views` (V117);
представление принадлежит одному пользователю и одному списку.

API `/api/v1/list-views/{code}`: `GET`, `POST`, `PUT /{id}` (с
`lockVersion`), `DELETE /{id}`.

- Право — от формы профиля, как у собственных настроек. Доступ к самому
  списку проверяется по реестру; чужой список неотличим от несуществующего
  (404).
- Чужие представления не видны и не меняются (404).
- Состояние проверяется по реестру: колонки — только поля списка, ширина —
  пиксели, сортировка и фильтр — то, что принял бы сам список
  (`QueryCompiler`). Ошибки адресованы внутрь состояния
  (`state.columns.order[1]`, `state.filter[0].op`). В базу пишется
  каноническая форма, собранная сервером.
- Название — от 1 до 80 символов, уникально в пределах пользователя и
  списка без учёта регистра. Не больше 20 представлений на список.
  «По умолчанию» может быть только одно (частичный уникальный индекс).
- Сортировка по умолчанию сохраняется как `null`: представление следует за
  списком, если его порядок по умолчанию изменится.

`md_settings` (ключ–значение) не подошла: у представления есть имя, признак
«по умолчанию», версия для оптимистичной блокировки и состояние, которое
сервер обязан проверять.

### 2.8. Массовые действия `POST …/bulk`

Тело — `{action, ids, params}`, ответ — `{action, succeeded, failed,
results: [{id, ok, code, message}]}` (`common.bulk.BulkRunner`).

- Каждая запись меняется той же одиночной операцией сервиса, что и из
  карточки, отдельным вызовом, то есть в своей транзакции. Права, скоуп
  данных, проверки и аудит остаются на одиночной операции; массовое
  действие не обходит ни одну из них.
- Ошибка одной записи не откатывает остальные. У неудачи — код и сообщение
  одиночной операции. Неожиданная ошибка скрывается кодом
  `bulk_item_failed`, причина остаётся в журнале сервера.
- От 1 до 100 записей, повторы схлопываются с сохранением порядка.
  Неизвестное действие — `BULK_ACTION_UNKNOWN`, неверный параметр —
  `BULK_INVALID` с адресом `params.<имя>`. Параметры проверяются до цикла:
  неверный статус не порождает сто одинаковых отказов.
- Право на эндпоинт — то же, что у одиночного изменения.
- Эндпоинт принимает `Idempotency-Key`, как и остальные `POST`: повтор
  запроса после обрыва связи не применит действие дважды.

Первый потребитель — задачи: `POST /api/v1/tasks/bulk`, действия `status`
(`params.statusId`) и `priority` (`params.priority`).

### 2.9. Права на поля

Поле реестра может требовать своё право: `QueryField.requires(form, action)`.
Для того, у кого права нет, поле не существует:

- `query-meta` его не отдаёт — колонки, фильтра и сортировки по нему нет;
- условие фильтра по нему — `QUERY_UNKNOWN_FIELD`, сортировка — `QUERY_SORT_INVALID`,
  как у несуществующего поля: ответ не выдаёт, что поле есть;
- свободный поиск `q` по нему не идёт, иначе по совпадениям его можно было бы
  угадать;
- значение не уходит в ответе: модуль при сборке строки спрашивает
  `QueryPlan.shows(key)` или само поле реестра (`visibleToViewer()`) и оставляет
  его пустым; пустое поле в JSON не пишется.

Сортировка по умолчанию не может требовать права — список должен открываться
любому, кто видит сам список. Первый потребитель — «кто загрузил» в
`upl.packages`: это человек, поэтому поле видно тем, у кого есть
`iam.users view`; карточка загрузки и ответ «применить» следуют тому же
правилу, а шапка карточки без него обходится без «загрузил …».

## 3. Первый потребитель

`GET /api/v1/upl/sources` принимает `filter` и `sort`; поля — код, название,
периодичность, последняя опубликованная версия, наличие черновика. Прежний
контракт сохранён:

- без параметров — сортировка по коду;
- `limit` от 1 до 200, иначе `INVALID_LIMIT`;
- битый курсор — `INVALID_CURSOR`;
- пустой `cursor` означает первую страницу.

Курсоры, выданные до перехода, недействительны, потому что сменился формат.
Клиент получает `INVALID_CURSOR` и начинает список заново.

Второй потребитель — загрузки UPL (`upl.packages`): по умолчанию сначала новые
(`-uploadedAt`). Поля с `defaultVisible: false` (код источника, «период по»,
ошибки, версия анкеты, кто загрузил) — только фильтры, без колонки.

Третий — файлы (`mf.files`). Ключ файла — UUID: курсор хранит ключ строки
текстом (`f.id::text`), числовой ключ по-прежнему связывается числом. Скоуп
данных (ADR-0013) и «только мои» передаются предикатом `extra` в тот же SQL.

## 4. Последствия

- Новые списки описываются реестром вместо ручного `StringBuilder`.
  Существующие переводятся по одному (роадмап волны 3). Свои параметры
  фильтра они держат до перевода.
- Сортировать можно только по полям, помеченным в реестре. Для больших
  таблиц поле сортировки должно быть проиндексировано вместе с ключом.
  Это ответственность того, кто помечает поле сортируемым.
- jOOQ по-прежнему не нужен (ADR-0002): билдер закрывает фильтры гридов
  без новой зависимости.
- Метаданные описывают поля, но не права на колонки. Права на колонки на
  сервере — отдельный пункт (роадмап, п. 19).

## 5. Рассмотренные альтернативы

| Вариант | Почему нет |
|---|---|
| Плоские параметры (`code_starts=…&periodicity=…`) | Нет операций и адресов ошибок; каждый список заново изобретает имена |
| RSQL / FIQL (`code=like=sales*;periodicity=in=(month,year)`) | Компактно, но нужен парсер-зависимость и своё экранирование; JSON клиент собирает и читает без разбора строк |
| Протокол Biruni (`p.column`, `p.filter`, номера страниц) | `COUNT(*)` на каждую страницу и offset; противоречит keyset-курсорам и ADR-0015 |
| jOOQ-DSL | Новая зависимость ради того, что покрывают 400 строк кода |
