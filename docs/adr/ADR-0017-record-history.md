# ADR-0017: Вкладка «История» в карточке записи

**Статус:** Принято (2026-09-25)
**Дата:** 2026-09-25
**Зависит от:** ADR-0006 (модульный монолит), ADR-0013 (скоуп данных),
ADR-0015 (перенос UI-кита, пункт 18 роадмапа)

---

## 1. Контекст

Модули пишут изменения записей в `audit_log` (таблица, первичный ключ,
событие I/U/D, старые и новые значения, автор, веб или API). Прочитать их
может только журнал аудита, а он открывается правом `audit.log view` — это
право администратора безопасности. Человек, который ведёт задачу или
пользователя, не видит, кто и что в ней менял. В Biruni у карточки есть
вкладка истории; идею берём, реализацию пишем свою.

Модули зависят от модуля аудита (пишут в него), поэтому аудит не может
зависеть от модулей: граф модулей должен оставаться без циклов
(`ModularArchitectureTest`).

## 2. Решение

### 2.1. Источник истории

В `instance.common.history` — интерфейс `RecordHistorySource`. Модуль
регистрирует бин на каждый вид записи и сообщает:

- ключ вида в URL (`tasks`, `projects`, `users`);
- таблицу `audit_log.table_name`, под которой пишет изменения;
- право, которым открывается история, — то же, что открывает запись;
- `requireVisible(id)` — бросает not-found, если записи нет или она вне
  скоупа смотрящего (ADR-0013); так история чужой записи не показывается и
  само её существование не раскрывается;
- подписи полей (ключи i18n) и скрытые поля.

Аудит собирает все источники списком бинов и от модулей не зависит.

### 2.2. API

- `GET /api/v1/history` — виды записей, историю которых смотрящий может
  открыть (для UI).
- `GET /api/v1/history/{kind}/{id}?limit=&cursor=` — изменения записи,
  новые сверху, keyset-курсор журнала аудита. Каждое изменение: событие,
  время, автор (имя, логин), веб/API и список полей со старым и новым
  значением. Неизвестный вид, несуществующая или невидимая запись — 404;
  нет права на вид записи — 403.

Эндпоинт помечен базовым правом `iam.profile view` (есть у любого
вошедшего), а право вида проверяет сервис — как `query-meta` в ADR-0016.

### 2.3. Что показывается

- Значения проходят `AuditDataRedactor`, как в журнале аудита.
- Технические поля (`id`, `lockVersion`, `createdAt`/`By`, `modifiedAt`/`By`,
  `companyId`) не показываются.
- Ключи приводятся к camelCase: модули пишут то `project_id`, то
  `projectId`, а подпись поля — одна.
- У изменения (U) показываются только поля, значение которых
  действительно изменилось.

### 2.4. UI

`ui-record-history` — раскрываемая секция карточки: загружается только
при открытии, листает курсором («Показать ещё»), начинает заново при смене
записи, ошибку показывает с повтором. Подключена в карточке задачи и в
карточке пользователя (вкладка «Информация»).

## 3. Последствия

- История видна тем, кто работает с записью, без доступа к журналу аудита.
- Новый вид записи — один бин в своём модуле, без правок аудита.
- **Ограничение: история не полнее аудита.** Сейчас модули пишут
  неполные снимки (например, изменение задачи сохраняет только название и
  приоритет, внешние ключи — числами). Полнота аудита — отдельная работа
  по каждому модулю; UPL в `audit_log` пока не пишет вовсе.
- Имена связанных записей (статус, проект) не подставляются: показываются
  значения, как они сохранены.
