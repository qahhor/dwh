# ADR-0025: Сроки хранения журналов и кэш в кластере

**Статус:** Принято (2026-09-30), уточнено 2026-10-01
**Дата:** 2026-09-30
**Зависит от:** ADR-0020 (именование и миграции); план 10/10, пункт 3.13

---

## 1. Контекст

Журнальные таблицы (события безопасности, попытки входа, коды, закрытые
сессии, журнал и очередь вебхуков, входящие уведомления и их очередь, запуски
фоновых заданий) росли без предела: очищались только ключи идемпотентности,
выгрузки и — через архив — журнал аудита. Справочники (статусы и типы задач,
модули, меню, доп. поля) кэшировались на узле на 10 минут: после правки второй
узел до 10 минут отдавал старое. Словари i18n уже сверяют ревизию языка при
каждом чтении и между узлами согласованы.

## 2. Решение

1. **Срок хранения объявляет модуль.** Бин `RetentionPolicy` (`common.retention`):
   имя, таблица, условие устаревшей строки с `:cutoff`, срок по умолчанию.
   Двенадцать правил в модулях audit, kauth, kwh, ms.notify, fnd (с ADR-0030 — jobs), search:
   к десяти исходным добавлены `failed-jobs` (задания очереди `fnd_job_queue`,
   исчерпавшие попытки, по `failed_at`) и `search-jobs` (завершённые задания
   индекса `search_jobs`; задание, на которое ссылается повтор, и самое новое
   задание остаются — по отсутствию заданий воркер решает, строить ли индекс
   впервые). Срок меняется настройкой `smc.retention.days.<имя>` (в Compose —
   `SMC_RETENTION_<ИМЯ>_DAYS`); 0 — хранить всегда. Строки «в работе» (очередь
   в ожидании, открытая сессия, выполняющееся задание) не удаляются никогда —
   условие отбирает только конечные.
2. **Задание очистки** (`RetentionJob`, ночью): партии по 5000 строк
   `delete … where ctid = any(array(select ctid … limit … for update skip locked))`,
   каждая — отдельный короткий оператор; не больше 200 партий на таблицу за
   проход. Два узла не мешают друг другу. Индексы под условия — V136, V137,
   V139. Срок каждого правила читается внутри его обработки: неверное значение
   одной настройки попадает в журнал и не останавливает остальные таблицы.
   `ctid` уникален только внутри одной таблицы, а у секционированной таблицы
   совпадает в разных секциях: задание отказывается от секционированной
   таблицы (`pg_class.relkind = 'p'`) — при старте приложение не поднимается,
   а перед каждой очисткой таблица проверяется снова. Журнал аудита
   (секционирован) сюда и не входит. Задание и слушатель кэша не создаются в
   профиле `migrate`.
3. **Кэш сообщает кластеру.** `ClusterCacheManager` оборачивает кэши узла:
   чтение и запись локальны; очистка применяется сразу и повторно после
   коммита. Сообщение `NOTIFY smc_cache '<узел> <кэш>'` отправляется внутри
   транзакции на её же соединении: PostgreSQL доставляет его только при
   коммите и отбрасывает при откате, так что откаченная транзакция не
   сообщает ничего. Вне транзакции сообщение уходит сразу на отдельном
   соединении. `CacheInvalidations` на каждом
   узле держит своё соединение с `LISTEN smc_cache` и очищает названный кэш;
   собственные сообщения узел пропускает. После потери соединения узел
   очищает все кэши (мог пропустить сообщение) и слушает снова.
4. **Настройки поиска — тем же каналом.** Узел держит действующие настройки
   поиска в памяти (`SearchPolicyProvider`). Сохранение публикует сообщение
   `searchSettings` (интерфейс `common.cluster.ClusterNotices`) внутри своей
   транзакции; остальные узлы перечитывают настройки сразу. Периодическое
   чтение осталось страховкой: каждые 5 с на узле, чьё чтение не удалось, и раз
   в минуту на каждом — на случай потерянного сообщения.

## 3. Проверки

- `RetentionJobIntegrationTest`: старые строки всех десяти журналов уходят,
  свежие и «в работе» остаются; пять циклов старых строк не увеличивают
  таблицы; повторный проход ничего не удаляет.
- `RetentionJobIntegrationTest` проверяет и новые журналы (`failed-jobs`,
  `search-jobs`) и отказ от секционированной таблицы; `RetentionJobTest` —
  неверную настройку одного журнала.
- `ClusterCacheIntegrationTest`: изменение на одном узле очищает кэш второго
  не позже чем через 2 с после коммита — и через `@CacheEvict` сервиса;
  сообщение из транзакции доходит только после коммита; откат не сообщает
  ничего; эха нет. `CacheInvalidationsTest` — выбор соединения для сообщения.
- `SearchSettingsClusterIntegrationTest`: сохранение настроек поиска на одном
  узле видно второму не позже чем через 2 с; откат не сообщает ничего.

## 4. Последствия

- Каждый узел занимает одно соединение пула под `LISTEN`.
- Журнал загрузок `fnd_load_log` не очищается: это история того, что попало в
  хранилище. Журнал аудита уходит только через проверенный архив.
- Сроки по умолчанию — предположение (год для событий безопасности, месяц для
  попыток входа и отправленной очереди, полгода для входящих, три месяца для
  упавших заданий очереди и заданий индекса); их сдвигают настройкой без
  изменения кода.

### Ограничения (приняты)

- **Секционированные таблицы** правилом срока хранения не очищаются: удаление
  идёт по `ctid`. Для такой таблицы нужен свой механизм (как у журнала аудита —
  отсоединение секций после архива).
- **Гонка инвалидации.** Узел, который прочитал старую строку из базы до
  коммита чужого изменения, а положил её в кэш уже после того, как сообщение
  очистило кэш, держит старое значение до истечения записи — не дольше 10
  минут (`expireAfterWrite` кэшей). Для настроек поиска такой узел
  перечитывает их не позже чем через минуту. Окно — время одного чтения из
  базы; закрывать его версиями записей в кэше не стали.
- **Ограничения частоты — на узле.** `RateLimitService` (и бюджеты поиска)
  считает запросы в памяти узла: за балансировщиком на N узлах клиент может
  сделать до N раз больше настроенного числа запросов в минуту. Общий счётчик
  (в базе или отдельном хранилище) — отдельное решение.
- Если сообщение внутри транзакции не удаётся поставить в очередь, транзакция
  завершается ошибкой: изменение не проходит молча с устаревшими кэшами на
  других узлах.
