# ADR-0020: Именование и типы в схеме базы данных

**Статус:** Принято (2026-09-27)
**Дата:** 2026-09-27
**Зависит от:** ADR-0006 (модульный монолит), руководство по миграциям
([database-migrations.md](../guidelines/database-migrations.md))

---

## 1. Контекст

Миграции V001–V127 писались разными руками, и схема разошлась сама с собой
(подсчёт по файлам на 2026-09-27):

| Что | Как сейчас |
|---|---|
| Имена индексов | суффикс `_idx` — 44, префикс `idx_` — 19, уникальные `_uq`, `_uidx`, без суффикса |
| Время изменения | `modified_at` — 18, `updated_at` — 6 |
| Ключи | `generated always as identity` — 31, `bigserial` — 4, `uuid` — 15 |
| Строки | `text` в большинстве, `varchar(n)` — 17 |
| Ограничения | `<таблица>_(uk\|fk\|ck\|ex)_<суффикс>` в fnd и новых таблицах, автоимена в остальных |

Выпущенные миграции неизменяемы (манифест, план 10/10, пункт 0.5), поэтому
старое расхождение остаётся. Правила ниже обязательны для новых файлов и
проверяются в сборке, так что расхождение больше не растёт.

## 2. Решение

Правила действуют для `db/migration` начиная с **V128** (пункт 1.7 плана 10/10).

| # | Правило | Правильно | Неправильно |
|---|---|---|---|
| 1 | Суррогатный ключ | `id bigint generated always as identity`; `uuid`, когда идентификатор виден снаружи и не должен угадываться | `bigserial`, `serial`, `generated by default as identity` |
| 2 | Строки | `text` и `check` на длину или формат | `varchar(n)`, `char(n)` |
| 3 | Время | `timestamptz` | `timestamp` без зоны |
| 4 | Служебные поля | `created_at`, `modified_at` | `updated_at` |
| 5 | Индекс | `<таблица>_<колонки>_idx` | `idx_<…>`, имя без таблицы |
| 6 | Уникальный индекс | `<таблица>_<колонки>_uq` | `_idx`, `_uidx`, `_key` |
| 7 | Ограничения | первичный ключ `<таблица>_pkey`; `<таблица>_uk_…`, `_fk_…`, `_ck_…`, `_ex_…` | автоимена `…_key`, `…_check`, имена без таблицы |
| 8 | Индекс большой таблицы | `create index concurrently` в отдельном файле; вторая строка шапки может быть `set statement_timeout = '0';` | обычный `create index` — он блокирует запись на всё время построения |

Большие таблицы перечислены в `MigrationLintTest.LARGE_TABLES`:
журналы, очереди, пользователи, задачи, файлы. Новая таблица, которая будет
расти так же, добавляется в список вместе с миграцией, которая её создаёт.
`audit_log` секционирована: `concurrently` к ней не применяется, индекс
строится по партициям отдельной процедурой.

Рекомендуется, но не проверяется: называть ограничения явно (`constraint …`),
а не полагаться на автоимена; именовать таблицу с префиксом своего модуля
(`md_`, `kauth_`, `ms_task_` и т. д.) — это проверяет `ModuleBoundariesTest`
через чужой SQL. Представление для чтения другими модулями называется
`<префикс>_pub_<имя>` и создаётся по правилам ADR-0026.

## 3. Проверка

- `MigrationLintTest` проверяет правила 1–8 на файлах с V128 и на фикстурах
  `migration-fixtures/lint-good` и `lint-bad` (в нарушителе по одному случаю
  каждого правила).
- `MigrationFileRulesTest` теперь видит деструктивные операции внутри блоков
  `DO $$ … $$` (они выполняются сразу, в отличие от тела функции) и
  допускает `statement_timeout = '0'` только в файле с `concurrently`.
- `ReleaseUpgradeIntegrationTest` поднимает базу прошлого релиза
  (`PREVIOUS_RELEASE`, сейчас V123), кладёт в неё данные, обновляет до текущей
  схемы и проверяет `flyway validate`, повторный запуск и сохранность строк. Он
  работает на встроенном PostgreSQL и не пропускается без Docker. При каждом
  релизе `PREVIOUS_RELEASE` переносится на последнюю миграцию выпущенного
  релиза.

## 4. Последствия

- Новая миграция с нарушением валит сборку с указанием правила и ожидаемого
  имени.
- Старые имена не переименовываются: переименование индексов и ограничений
  ради единообразия — это блокировки на проде без пользы. Если таблицу всё
  равно перестраивают, её приводят к правилам в той же миграции.
