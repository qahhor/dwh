# ADR-0045: рассылки отчётов по расписанию

**Статус:** принято 2026-10-19 (этап 2, шаг 2.4 плана конструктора форм и отчётов); реализовано в `main` 2026-10-19.
**Основание:** решения владельца продукта [ADR-0041](ADR-0041-live-form-evolution.md): 2026-10-17, п. 3 — рассылки по
расписанию через существующие каналы доставки (email, Telegram, уведомление в приложении); 2026-10-18, п. 4 — расписание
ежедневно/еженедельно/ежемесячно со временем и часовым поясом, вложение XLSX, ссылка на отчёт, условная отправка (есть
данные или превышен порог).
**Зависит от:** [ADR-0011](ADR-0011-provider-spi.md), [ADR-0018](ADR-0018-async-exports.md),
[ADR-0024](ADR-0024-optimistic-locking.md), [ADR-0025](ADR-0025-retention-and-cluster-cache.md),
[ADR-0030](ADR-0030-fnd-split.md), [ADR-0036](ADR-0036-shared-reports-and-dashboards.md),
[ADR-0044](ADR-0044-report-analytics.md).

## Контекст

Сохранённый отчёт (ADR-0036) исполняется для читателя: его права, область данных и права на поля; параметры (ADR-0044)
читатель заполняет при открытии. Руководителю нужен тот же отчёт каждое утро или первого числа — письмом с файлом, в
Telegram или уведомлением, — без входа в систему за ним. Доставка в продукте уже есть: outbox уведомлений `ms.notify`
с повторами и провайдерами SPI (SMTP, Telegram Bot API), подтверждённые каналы пользователя `kauth`, общая очередь
заданий `jobs` с арендой и расписанием. Кластер — несколько узлов (ADR-0025): один слот расписания не должен уйти
дважды.

| Вариант | Суть | Почему нет / да |
|---|---|---|
| A. Рассылка в модуле `report` поверх общей очереди заданий | Тик планировщика — задание расписания `fnd_job_schedule`, запуск — разовое задание; уникальная строка запуска на слот | **Выбран**: аренда, повторы, выключатель `jobs_enabled` и метрики очереди уже есть; ровно один раз даёт БД |
| B. Отдельный планировщик (Quartz, ShedLock) | Свои таблицы блокировок и cron | Новая зависимость и второй механизм аренды рядом с `jobs` |
| C. Отчёт строится один раз от имени автора и рассылается всем | Один файл на рассылку | Нарушает область данных: получатель увидел бы данные автора |

## Решение

### 1. Рассылка и права

- `report_mailings` (V232): сохранённый отчёт (`view_id` → `md_list_views`, удаление отчёта удаляет рассылки), название,
  каналы (`email`, `telegram`, `in_app`), формат (вложение XLSX и/или ссылка — хотя бы одно), расписание, значения
  параметров (JSON-объект как `?parameters=` читателя), условие, активна или приостановлена, следующая отправка,
  владелец, ревизия. Получатели — `report_mailing_recipients`: только пользователи системы, при сохранении активные, до
  50; свободных внешних адресов нет. Не больше 10 рассылок на отчёт и 1000 всего.
- Права `report.mailings` (V234): `own` — рассылки своих отчётов (роли `chief_admin`, `admin`, `manager`, `user`),
  `manage` — рассылки любого отчёта, который пользователь может открыть (`chief_admin`, `admin`). Отчёт, который
  пользователь не может открыть, — 404, как в каталоге; доступный без права — 403. Изменение и удаление — по ревизии
  (`If-Match`: 428 без неё, 409 при устаревшей), с аудитом (`report_mailings`, I/U/D, получатели в аудите).
- Права проверяются в коде (`MailingAccess`) по отчёту, который называет запрос, а не аннотацией обработчика: модуль
  объявляет пары `report.mailings.own`/`manage` каталогу прав через `common.security.PermissionDeclarations`, иначе
  синхронизация каталога сочла бы их устаревшими и матрица прав не дала бы их выдать. Изменения принимают
  `Idempotency-Key` веб-клиента: повтор отправки воспроизводит ответ, а не шлёт второй раз.
- Каналы — только настроенные в установке (`GET /api/v1/report-mailings/options`): уведомление в приложении всегда,
  email и Telegram — когда провайдер не заглушка `console_*` (или доставка не принуждается, `smc.delivery.enforce=false`
  в разработке, как и для привязки канала).

### 2. Расписание и планировщик

- Расписание — ежедневно, еженедельно (день недели 1–7, ISO) или ежемесячно (число 1–31; число больше длины месяца —
  его последний день) в локальное время `HH:mm` часового пояса базы зон. Слот дня вычисляется в зоне: время, которое
  перевод часов пропускает (02:30 весной), уходит через тот же интервал после перевода (03:30), повторяющееся время —
  при первом наступлении; у каждого дня расписания ровно один слот (`common.schedule.CalendarSchedule`, общий с
  автоматизациями ADR-0046).
- Тик `report.mailing_tick` — задание расписания очереди раз в минуту (V234), берёт его один узел. Он блокирует активные
  рассылки с наступившей `next_run_at` (`for update skip locked`, до 100 за тик), вставляет запуск последнего наступившего
  слота (`report_mailing_runs`, уникальный индекс `(mailing_id, slot) where kind = 'scheduled'`) и ставит разовое
  задание `report.mailing_run`, затем переносит `next_run_at` на первый слот после текущего момента. Два узла, повтор
  тика или гонка с изменением рассылки создают один запуск на слот.
- **После простоя** рассылка отправляется один раз — за последний пропущенный слот, без пачки за все пропущенные.
  Создание, возобновление или смена расписания ставят следующий слот после текущего момента (в прошлое не отправляет);
  приостановка обнуляет `next_run_at`, запуск слота приостановленной рассылки пропускается (`skipped`, `paused`).

### 3. Исполнение от имени получателя

- Запуск обходит получателей, прочитанных из рассылки в момент запуска (проверка — только инициатор). Для каждого:
  пользователь должен быть активен (иначе `inactive`), отчёт исполняется **от имени получателя** —
  `md.service.MdPrincipals.callAs` с его текущими правами, областью данных и правами на поля, на его языке и в часовом поясе
  рассылки (`RequestZone`): готовые периоды параметров (`last_month`, …) считаются в день отправки. Права автора
  рассылки не используются никогда. Отчёт, который получатель больше не может открыть, — `no_access`, ничего не
  отправляется.
- Лимиты — лимиты отчёта (ADR-0036, ADR-0044: группы, ячейки, тайм-аут 5 с); ошибка у одного получателя записывается
  ему (`report_failed`, `parameters`) и не останавливает остальных.
- Результат каждого получателя — `report_mailing_deliveries` (запуск, пользователь, канал, статус `sent`/`queued`/
  `skipped`/`failed`, причина, ключ outbox, число строк), уникально по запуску, пользователю и каналу. Повтор задания
  (сбой узла) пропускает уже записанных получателей. Итог запуска: `done` — без ошибок, `failed` — ни одной отправки и
  есть ошибки, `partial` — между ними; пропуски по условию и без адреса ошибками не считаются.

### 4. Каналы и доставка

- **Email и Telegram** — через outbox уведомлений `ms.notify` (повторы с экспоненциальной паузой, dead letter, метрики
  outbox); ключ идемпотентности детерминирован (`report-mailing:<run>:<user>:<channel>`), поэтому outbox принимает
  доставку один раз. Адрес — **только подтверждённый канал** пользователя (`kauth_user_channels.is_verified`,
  `KauthDeliveryAddresses`): неподтверждённый адрес мог бы отдать отчёт постороннему (то же правило, что у сброса
  пароля); без него канал пропускается с причиной `no_address`. Отключённые пользователем уведомления типа
  `report_mailing` — `opted_out`.
- **Вложение XLSX** — тот же построитель, что у выгрузки сохранённого отчёта (`AggregateExportService.workbook`), из
  того же результата получателя. Письмо outbox несёт одно вложение (V233: `attachment`, `attachment_name`,
  `attachment_type`), worker очищает его, как только письмо отправлено или признано недоставленным, — данные отчёта не
  хранятся дольше доставки. Файл больше `smc.report-mailings.max-attachment-bytes` (5 МБ) не прикладывается: письмо
  говорит об этом и даёт ссылку (`attachment_too_large`).
- **Ссылка** открывает сохранённый отчёт в приложении с параметрами рассылки
  (`/e/<сущность>?mode=report&report=<id>&parameters=<json>`): получатель входит в систему, отчёт строится с его правами.
  Токенов, дающих доступ к данным, в ссылке нет. Абсолютная ссылка в письме и Telegram строится только из
  `smc.public-url`, не из заголовка Host; без него письмо уходит без ссылки.
- **Telegram** — текст и кнопка-ссылка (`sendMessage`, разметка Markdown с экранированием имени); файл в Telegram не
  отправляется (SPI мессенджера — текст и кнопка).
- **Уведомление в приложении** — `ms_notifications` с путём ссылки, сразу (`sent`).
- Тексты письма, Telegram и уведомления — из каталога (`channel.report_mailing.*`, `notify.report_mailing.*`) на языке
  получателя (`MdUserTexts`).

### 5. Условия

На результате каждого получателя: `always`; `has_rows` — у отчёта с группировкой есть группа, у отчёта без групп есть
непустое и ненулевое значение (он всегда отвечает одной строкой); `threshold` — общий итог показателя (позиция показателя
в сохранённом отчёте; у сравнения периодов — текущий период) `gt`/`gte`/`lt`/`lte`/`eq` значения; при итогах в
нескольких валютах достаточно одной. Порог требует общего итога: у отчёта с группировкой без итогов он отклоняется при
сохранении (422 `error.report.mailing_condition_totals`). Невыполненное условие — `skipped`, `condition`.

### 6. Отправить сейчас и проверка

`POST /api/v1/report-mailings/{id}/runs`: `{"scope":"all"}` — всем получателям активной рассылки (приостановленная —
409 `error.report.mailing_paused`); `{"scope":"me"}` — проверка инициатору, в том числе для приостановленной рассылки и
без учёта условия (невыполненное условие отмечается `condition_ignored`). Это законное действие ведущего рассылку, а не
тестовый ход: им же e2e запускает рассылку детерминированно. Не больше 10 отправок и проверок одной рассылки в час
(429 `error.report.mailing_rate_limited`).

### 7. История, метрики, хранение

- История запусков — `GET …/{id}/runs` (страницы `TimePage`) и `GET …/{id}/runs/{runId}` (доставки с состоянием
  outbox: `PENDING`, `SENT`, `DEAD_LETTER`); видна тому, кто ведёт рассылку.
- Метрики: `smc_report_mailing_runs_total{outcome}`, `smc_report_mailing_deliveries_total{channel,status}`. Алерт
  `SmartupcmsReportMailingsFailing` — не меньше трёх `failed` за час 15 минут
  ([RB-14](../runbooks/RB-14-report-mailings.md), promtool-тест `tests/report-mailings.yml`).
- Хранение: завершённые запуски с доставками — 180 дней (`report-mailing-runs`,
  `SMC_RETENTION_REPORT_MAILING_RUNS_DAYS`).

### 8. Веб

Каталог отчётов показывает «Рассылки» у отчёта, который пользователь ведёт; страница `/reports/:id/mailings` — список
рассылок (расписание, каналы, получатели, следующая отправка, последний запуск), диалог создания и изменения (получатели
из списка активных пользователей, «Добавить меня», каналы установки, формат, расписание с часовым поясом, параметры
отчёта — встроенный `smt-report-parameters`, условие), приостановка и возобновление, «Отправить сейчас», «Отправить мне»,
история с доставками, удаление. Тексты ru/uz/en.

## Последствия

- Рассылка не создаёт второго пути прав: отчёт исполняется для каждого получателя тем же оператором, что и при чтении.
- API только расширен: `/api/v1/report-mailings`, `GET /api/v1/report-views/{id}`; outbox умеет одно вложение письма;
  тело письма outbox — текст (`body`), HTML — необязательное `html` (раньше `body` уходил как HTML; вызовов не было).
- Ограничения: получатели — только пользователи (без ролей и подразделений); Telegram — без файла; одна рассылка — не
  больше 50 получателей; расписание с точностью до минуты (тик раз в минуту); подтверждённый email нужен для письма;
  дата «сегодня» для готовых периодов — день фактической отправки (после долгого простоя — день восстановления).
