# ADR-0026: Опубликованные представления для чтения чужих данных

**Статус:** Принято (2026-10-01)
**Дата:** 2026-10-01
**Зависит от:** ADR-0006 (модульный монолит, проверка границ), ADR-0020
(именование и миграции); план 10/10, пункт 1.3

---

## 1. Контекст

`ModuleBoundariesTest` с пункта 1.3 запрещает репозиторию трогать таблицы
другого модуля, но 33 нарушения были заморожены в
`archunit_store/foreign-sql.txt`. Почти все они — чтение: отчёты, аналитика и
поиск соединяют задачи со статусами, проектами и пользователями; аудит, файлы,
комментарии и участники задач показывают имя и логин автора; kauth проверяет,
что пользователь активен и версия его входа не сменилась. Два случая — другого
рода: поиск сам вставлял строки в `audit_log`, файлы читали лимиты хранилища из
таблиц md.

Перевести каждое чтение на вызов сервиса владельца нельзя без потерь: отчёт и
поиск соединяют десятки тысяч строк в одном запросе, вызов сервиса на строку
превращает соединение в N+1. Оставить прямой SQL — значит, что любая правка
таблицы владельца молча ломает чужой запрос, а в чужой запрос попадают колонки,
которые ему не нужны (хеш пароля, секреты).

## 2. Решение

1. **Модуль публикует представления для чтения.** Опубликованное
   представление — часть контракта модуля, как пакет `api`. Имя —
   `<префикс модуля>_pub_<имя>`: `md_pub_users`, `ms_task_pub_tasks`,
   `ms_task_pub_projects`, `ms_task_pub_statuses`, `ms_task_pub_members`,
   `ms_note_pub_notes`, `mf_pub_files` (V141). В представлении только колонки,
   которые нужны читателям, и никогда — пароль, хеш, секрет или токен.
   Представление простое (одна таблица, без агрегатов и `distinct`):
   PostgreSQL подставляет его в запрос читателя и использует индексы базовой
   таблицы, поэтому соединения остаются в SQL, а план тот же, что у запроса к
   таблице.
2. **Читатель другого модуля соединяет представление, а не таблицу.**
   Аналитика, отчёты, поиск, аудит, kauth, файлы и задачи читают так
   пользователей, задачи, проекты, статусы, участников, заметки и файлы.
   Модуль-владелец по-прежнему работает со своими таблицами напрямую.
3. **Запись через представление запрещена.** Каждое представление несёт
   триггер `instead of insert or update or delete`
   (`pub_view_refuse_write()`), который отвечает ошибкой
   `insufficient_privilege`; статическая проверка не пускает
   `insert into`, `update` и `delete from` опубликованного представления ни
   из одного репозитория. Изменение чужих данных идёт через сервис владельца:
   строки аудита заданий поиска пишет `AuditLogService.logEntry(AuditEntry)` —
   с явным актором, а для переключения поколения на соединении доказательства,
   в той же транзакции.
4. **Когда достаточно сервиса.** Если читателю нужно одно значение и вызов
   естественен (малое N), он вызывает сервис владельца: лимиты хранилища
   файлам отдаёт `MdStorageQuotaService` (правило «лимит пользователя, иначе
   наибольший лимит его ролей, иначе 1 ГБ» живёт в md).
5. **Владелец таблицы — модуль, код которого её держит.** `md_sso_providers`
   создана в V017 с префиксом md, но читает и ведёт её только kauth (вход через
   SSO); `ModuleBoundariesTest.ownerOf` относит её к kauth. Переименование
   таблицы ради префикса не делаем (ADR-0020, раздел 4).
6. **Изменение представления — изменение контракта.** Колонку, на которую
   ссылается представление, PostgreSQL не даст удалить или сменить её тип без
   пересоздания представления. Миграция, которая меняет такую колонку,
   пересоздаёт представление в том же файле; удаление опубликованной колонки —
   ломающее изменение для читателей, их переводят в той же ветке.

## 3. Проверки

- `ModuleBoundariesTest.repositoriesTouchOnlyTheirModulesTables` — строгое
  правило без замороженного списка: репозиторий не называет таблицу чужого
  модуля ни после `from`/`join`/`into`/`update`, ни строкой-именем, из
  которой SQL собирается позже; запись в любое опубликованное представление —
  нарушение. Файл `foreign-sql.txt` удалён.
- `ModuleBoundariesTest.everyViewIsPublishedByAModule` — каждое представление
  в миграциях названо `<префикс владельца>_pub_<имя>`; там же пробы правила.
- `PublishedReadViewsTest` — каждое объявленное представление есть в
  мигрированной схеме и других представлений нет; ни одна колонка не названа
  как password/hash/secret/token; вставка в каждое представление
  отклоняется; `EXPLAIN` отчётного соединения задач, статусов, проектов и
  пользователей идёт по `ms_tasks_pkey` без `Subquery Scan`.
- `AnalyticsRepositoryIntegrationTest`, `MdStorageQuotaServiceIntegrationTest`
  и тесты поиска, отчётов, аудита, kauth и задач проверяют запросы на
  представлениях.

## 4. Последствия

- Состав колонок, которые модуль отдаёт наружу, виден в одной миграции, а не
  разбросан по чужим запросам.
- Новый читатель чужих данных добавляет колонку в представление владельца
  отдельной миграцией (`create or replace view` с колонкой в конце) — это
  видно в ревью владельца.
- Представления создаёт роль миграций; приложение и роль резервной копии
  получают права на них теми же default privileges, что и на таблицы.

### Ограничения (приняты)

- Правило проверяет пакеты `repository` и любой класс модуля, выполняющий SQL
  (`JdbcClient`, `JdbcTemplate`, `JdbcOperations`, prepared statement), а с
  2026-10-09 и `config`: связка владеет только `idempotency_keys`, первый
  запуск пишет таблицы md через `MdInstanceService`, страница сведений о
  системе читает организацию через него же. SQL в общих классах `common`
  (например, предикаты скоупа данных `ScopeFilter`) остаётся на базовых
  таблицах: это инфраструктура платформы, а не модуль.
- Представления выполняются с правами владельца (роли миграций), а не
  вызывающего: `security_invoker` требует PostgreSQL 15, а встроенный
  PostgreSQL тестов — 14. Приложение и так читает базовые таблицы, поэтому
  представление не расширяет его права.
- Триггеры базовых таблиц (ревизии поиска, аудит основы) срабатывают как
  прежде: представление только читает.
