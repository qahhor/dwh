# ADR-0024: Обязательная оптимистическая блокировка

**Статус:** Принято (2026-09-30)
**Дата:** 2026-09-30
**Зависит от:** ADR-0021 (модель ошибок), ADR-0023 (единообразный REST);
план 10/10, пункт 3.6

---

## 1. Контекст

Ревизия была у задач (необязательная: без неё сохранение проходило поверх
чужого), у объявлений, представлений списков, языковых пакетов и форматов
UPL. Заметки, проекты, пользователи, роли и их права, доп. поля, оргединицы,
пункты меню, статусы и типы задач, вебхуки сохранялись без неё: из двух
параллельных правок побеждала последняя, и первая пропадала без следа. Веб не
отправлял ревизию и там, где сервер её принимал. Переключатели читали
состояние и писали противоположное: два параллельных запроса давали два
аудита на одно изменение.

## 2. Решение

1. **У записи есть ревизия.** Колонка `revision bigint not null default 1`
   (V135 — десять таблиц, V142 — реестр модулей `md_installed_modules`);
   каждая запись строки увеличивает её на единицу в
   том же `update`, что и меняет строку, — не только сохранение формы, но и
   сброс 2FA, блокировка, анонимизация, смена пароля и поколения входа,
   перестановка статусов и типов задач. Иначе форма, открытая до такой
   записи, сохраняется из той же ревизии и молча её отменяет. Ответ с записью несёт её в теле
   (`revision`) и в заголовке `ETag: "<revision>"` (`Revisioned`,
   `RevisionETagAdvice`); ответ 204 на сохранение несёт новый `ETag`.
2. **Изменение называет ревизию, из которой сделано:** `If-Match: "<revision>"`,
   или `expectedRevision` в теле там, где API её уже принимал (задачи).
   Без неё — **428** `precondition_required`; неверный формат — 422;
   ревизия, которая уже не у записи, — **409** `revision_conflict`
   (`error.common.revision_conflict`, у задач тоже; отдельный код
   `task_revision_conflict` удалён 2026-10-03). Проверка и запись — одно выражение
   `update … where id = :id and revision = :expected returning revision`:
   гонки между чтением и записью нет.
3. **Права роли — часть роли.** `PUT /iam/roles/{id}/permissions` сохраняется
   из ревизии роли и увеличивает её. Так же роли и личные права пользователя
   (`PUT /iam/users/{id}/roles|permissions`) — часть пользователя: `If-Match`
   с ревизией пользователя, ответ несёт новую (`revision` и `ETag`).
   Оргединицы пользователя (`PUT /iam/org-units/users/{id}`) — тоже часть
   пользователя, правило скоупа (`PUT /iam/org-units/roles/{id}/rule`) —
   часть роли: сохраняются из их ревизии и увеличивают её, чтение
   (`GET` тех же путей) отдаёт её в `revision` и `ETag`, ответ 204 — новую в
   `ETag`.
6. **Системные настройки — одна запись.** Каждый ключ — отдельная строка
   `md_settings`, поэтому ревизия набора хранится отдельно: таблица
   `md_settings_revision` (V142, строка `scope = 'system'`; пока строки нет,
   ревизия равна 1, первое сохранение вставляет её с ревизией 2).
   `GET /settings/system` отвечает `{values, revision}` и `ETag`;
   `PATCH /settings/system` требует `If-Match` и увеличивает ревизию одним
   условным `update` до записи ключей: из двух параллельных сохранений из
   одной ревизии второе получает 409, даже если они меняют разные ключи.
   Пустое сохранение ничего не пишет и ревизию не меняет, но из устаревшей
   ревизии тоже получает 409.
7. **Регистрация модуля.** `PUT /modules/{code}` без `If-Match` только
   создаёт модуль; если модуль уже есть — 428. С `If-Match` он заменяет
   регистрацию одним `update … where code = :code and revision = :expected`
   (409 из устаревшей ревизии, 404 — модуля нет); статус и признак системного
   модуля замена не трогает. Переключатель `PUT /modules/{code}/enabled` тоже
   увеличивает ревизию, так что замена из прежней получает 409. Устаревший
   `POST /modules`, заменявший без ревизии, удалён до релиза (ADR-0023, §5).
4. **Переключатель — одна условная запись:**
   `update … set state = :s where id = :id and state <> :s`. Запрос, который
   ничего не изменил, не пишет строку и не пишет аудит; каждая строка аудита
   — настоящий переход (`PUT …/pin`, `…/active`).
5. **Веб** отправляет ревизию загруженной записи (`ApiRequestOptions.ifMatch`)
   во всех формах и в канбане; после сохранения без перечитывания увеличивает
   локальную ревизию на единицу и держит в ней все копии записи (роль в списке
   и выбранная роль). Отказ 409/428 показывается один раз — текстом сервера по
   `messageKey` с кнопкой «Обновить», которая перечитывает запись или список
   (`SaveErrorNotifier`); запрос идёт с `notifyError: false`.

## 3. Проверки

- `RecordRevisionIntegrationTest`: из двух параллельных сохранений из одной
  ревизии ровно одно получает 409; без ревизии — 428, битая — 422; ответ несёт
  новый `ETag`; сто параллельных переключений дают одно состояние и аудит, где
  каждая строка начинается там, где кончилась предыдущая.
- `ChangesNameTheirRevisionTest`: каждый `PUT`/`PATCH` записи принимает
  `If-Match` или ревизию в теле, кроме установщиков состояния (перечислены с
  причиной) и обработчиков, читающих ревизию из тела вручную. Долга нет:
  список `NOT_YET_LOCKED` удалён (V142). Обработчик, который заменяет общую
  запись целиком, — не установщик состояния; имя в списке исключений, которое
  уже называет ревизию в сигнатуре, валит тест.
- `RevisionedUpdatesRaiseRevisionTest`: каждый `update` таблицы из V135,
  `md_installed_modules` и `md_settings_revision` в коде сервера содержит
  `revision = revision + 1`.
- `RecordRevisionIntegrationTest` проверяет и системные настройки (из двух
  параллельных сохранений из одной ревизии ровно одно получает 409),
  оргединицы пользователя, правило скоупа роли и регистрацию модуля.

## 4. Последствия

- Долг пункта закрыт (2026-10-01): системные настройки, оргединицы
  пользователя, правило скоупа роли и регистрация модуля сохраняются из
  ревизии (решения 3, 6, 7). Веб держит ревизию набора настроек на экране
  настроек; панели оргединиц и скоупа берут большую из своей и экрана-хозяина
  и возвращают ему новую. Ответ `GET /settings/system` сменил форму (карта →
  `{values, revision}`): это ломающее изменение того же пункта. Настройки
  поиска (`PUT /search/settings`) сохраняются из `version` в теле
  (409 `error.search.settings_changed`).
- Сохранение оргединиц или правила скоупа увеличивает ревизию пользователя
  или роли: форма профиля или матрица прав, открытые до него, получают 409 и
  перечитывают запись.
- Массовые действия (`POST …/bulk`) меняют много записей сразу и ревизий не
  называют; конфликт одной записи в них — ошибка её элемента.
- Клиент API, который сохранял без ревизии, получает 428: это ломающее
  изменение, объявленное в `CHANGELOG.md` и трейлером `Api-Breaking:`.
