# ADR-0024: Обязательная оптимистическая блокировка

**Статус:** Принято (2026-09-30)
**Дата:** 2026-09-30
**Зависит от:** ADR-0021 (модель ошибок), ADR-0023 (единообразный REST);
план 10/10, пункт 3.6

---

## 1. Контекст

Ревизия была у задач (необязательная: без неё сохранение проходило поверх
чужого), у объявлений, представлений списков, языковых пакетов и форматов
UPL. Заметки, проекты, пользователи, роли и их права, доп. поля, оргединицы,
пункты меню, статусы и типы задач, вебхуки сохранялись без неё: из двух
параллельных правок побеждала последняя, и первая пропадала без следа. Веб не
отправлял ревизию и там, где сервер её принимал. Переключатели читали
состояние и писали противоположное: два параллельных запроса давали два
аудита на одно изменение.

## 2. Решение

1. **У записи есть ревизия.** Колонка `revision bigint not null default 1`
   (V135 — десять таблиц); каждое сохранение увеличивает её на единицу в том
   же `update`, что и меняет запись. Ответ с записью несёт её в теле
   (`revision`) и в заголовке `ETag: "<revision>"` (`Revisioned`,
   `RevisionETagAdvice`); ответ 204 на сохранение несёт новый `ETag`.
2. **Изменение называет ревизию, из которой сделано:** `If-Match: "<revision>"`,
   или `expectedRevision` в теле там, где API её уже принимал (задачи).
   Без неё — **428** `precondition_required`; неверный формат — 422;
   ревизия, которая уже не у записи, — **409** `revision_conflict`
   (`error.common.revision_conflict`; у задач — прежний
   `task_revision_conflict`). Проверка и запись — одно выражение
   `update … where id = :id and revision = :expected returning revision`:
   гонки между чтением и записью нет.
3. **Права роли — часть роли.** `PUT /iam/roles/{id}/permissions` сохраняется
   из ревизии роли и увеличивает её.
4. **Переключатель — одна условная запись:**
   `update … set state = :s where id = :id and state <> :s`. Запрос, который
   ничего не изменил, не пишет строку и не пишет аудит; каждая строка аудита
   — настоящий переход (`PUT …/pin`, `…/active`).
5. **Веб** отправляет ревизию загруженной записи (`ApiRequestOptions.ifMatch`)
   во всех формах и в канбане; после сохранения без перечитывания увеличивает
   локальную ревизию на единицу. На 409 форма показывает текст конфликта по
   `messageKey` и остаётся открытой.

## 3. Проверки

- `RecordRevisionIntegrationTest`: из двух параллельных сохранений из одной
  ревизии ровно одно получает 409; без ревизии — 428, битая — 422; ответ несёт
  новый `ETag`; сто параллельных переключений дают одно состояние и аудит, где
  каждая строка начинается там, где кончилась предыдущая.
- `ChangesNameTheirRevisionTest`: каждый `PUT`/`PATCH` записи принимает
  `If-Match` или ревизию в теле, кроме установщиков состояния (перечислены с
  причиной) и долга `NOT_YET_LOCKED`, который только сокращается.

## 4. Последствия

- Долг пункта: системные настройки (`PATCH /settings/system`), настройки
  поиска (`PUT /search/settings`) — у них нет ревизии; роли и личные права
  пользователя (`PUT /iam/users/{id}/roles|permissions`) — экрану назначений
  нужна ревизия пользователя.
- Массовые действия (`POST …/bulk`) меняют много записей сразу и ревизий не
  называют; конфликт одной записи в них — ошибка её элемента.
- Клиент API, который сохранял без ревизии, получает 428: это ломающее
  изменение, объявленное в `CHANGELOG.md` и трейлером `Api-Breaking:`.
