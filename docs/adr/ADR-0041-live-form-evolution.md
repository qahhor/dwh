# ADR-0041: развитие живых форм — версии схемы в JSONB и выгрузка в код

**Статус:** принято владельцем продукта 2026-10-17 (путь A + C); реализация — этапы
плана универсального конструктора (раздел «Конструктор форм и отчётов» в
[плане 10/10](../plan-10-10.md)). Дополняет [ADR-0038](ADR-0038-live-simple-forms.md),
не отменяет его гарантий (без DDL в runtime, граница `form_id`, права, аудит). Этап 1, ветка 1 (версии,
совместимые изменения, архив), ветка 2 (справочники, ссылки, выбор, пользователь, область данных) и ветка 3
(раскладка, заголовок записи без name/code, перенос записи между подразделениями, каталог отчётов, переход к
записям, порядок и top-N, подписи в XLSX) реализованы; этап 2, шаг 2.1 — формулы, умолчания, условия и правила
(формат 5, [ADR-0042](ADR-0042-live-form-formulas.md)), шаг 2.2 — строки документа, номер, статусы с согласованием
(формат 6, [ADR-0043](ADR-0043-live-form-documents.md)) и шаг 2.3 — аналитика отчётов
([ADR-0044](ADR-0044-report-analytics.md)) — раздел «Реализация».

## Контекст

ADR-0038 сделал живую форму create-only: после активации определение
неизменяемо (триггеры V214), формы нельзя изменить, скрыть или убрать, лимит —
100 форм. Для работы администратора без разработчика это главный блокер:
опечатку в подписи или недостающее поле нельзя исправить без нового кода.
Изучение конструктора (2026-10-17) показало и другие пробелы — ссылки,
справочники, логика, область данных, раскладка, — но все они опираются на
возможность менять форму после публикации.

| Вариант | Суть | Цена |
|---|---|---|
| A. Версии схемы в JSONB | Форма получает версии; разрешены совместимые изменения; данные остаются в `studio_records`, запись помнит версию схемы | Чтение разных версий в списках, отчётах, импорте; правила совместимости |
| B. Таблица на форму через управляемый DDL | Сервер создаёт и меняет таблицы отдельной ролью миграций | Привилегированный online DDL в рабочей БД, блокировки, восстановление; противоречит ADR-0038 |
| C. Выгрузка в код | Стабильная живая форма превращается в объявление `EntityDefinition` через CLI с переносом данных | Нужен инструмент миграции данных и окно переключения |

## Решение

Выбраны **A + C**; вариант B не выбран (может быть пересмотрен отдельным ADR,
если объёмы данных живых форм упрутся в JSONB).

1. **Версии (A).** Определение формы — последовательность неизменяемых версий
   `studio_form_versions` (новая таблица; текущая строка `studio_forms` становится
   версией 1). Активной является одна версия; переключение — CAS по ревизии
   формы (`If-Match`). Старые версии не удаляются и не меняются.
2. **Совместимые изменения**, разрешённые без переноса данных: добавить поле
   (необязательное или с значением по умолчанию), скрыть поле (данные сохраняются),
   изменить подписи ru/uz/en, порядок, раскладку (секции, вкладки), иконку и место
   в меню, сделать поле необязательным, увеличить `maxLength`/`scale`.
   **Несовместимые** (смена типа, удаление данных поля, переименование ключа,
   обязательность без значения по умолчанию) запрещены на этом пути — для них
   есть выгрузка в код (C) или новая форма.
3. **Чтение.** Запись хранит номер версии схемы, по которой сохранена; чтение,
   список, отчёт, экспорт и вебхук проецируют её на активную версию (скрытые поля
   не показываются, новые — пустые или значение по умолчанию). Запись сохраняется
   всегда по активной версии.
4. **Жизненный цикл формы:** активна → архивирована (скрыта из меню, записи
   только для чтения) → восстановлена. Архивная форма не занимает лимит
   активных форм; удаления определения и данных нет.
5. **Выгрузка в код (C).** `cms form eject <studio.code>` создаёт объявление
   `EntityDefinition`, миграцию таблицы и перенос данных из `studio_records`
   (по партиции `form_id`), после чего живая форма архивируется и её код
   резервируется. Выгрузка — выпуск приложения, выполняется разработчиком.
6. **Совместимость хранения.** Формат хранимого определения версионируется;
   «золотой» тест компилирует образцы всех поддерживаемых версий текущим кодом
   (вводится в надёжности живых форм). Изменение формата требует пути миграции.
7. Гарантии ADR-0038 сохраняются: runtime без DDL, граница `form_id` во всех
   путях, права и аудит каждой смены версии, отказ одной формы не роняет runtime.

## Последствия

- Администратор исправляет и развивает форму без выпуска; ошибочные формы
  архивируются, а не копятся.
- Отчёты, импорт и экспорт работают с проекцией версий — сложнее, но в одном месте.
- Производительность ограничена JSONB: для больших объёмов — выгрузка в код.

## Решения владельца продукта 2026-10-17

1. Область данных живой формы выбирает администратор при создании формы: все
   записи, оргединица с подчинёнными или только свои записи (владелец).
2. Внешний BI не планируется: развивается встроенный конструктор отчётов и
   витрины хранилища; внешний BI — только отдельным решением с построчным доступом.
3. Рассылки отчётов по расписанию: email, Telegram и внутренние уведомления
   (существующие каналы доставки).
4. Эталоны этапа 1: форма «Визит торгового представителя» (клиент — ссылка, дата,
   результат — выбор, комментарий, видимость по оргединице), форма «Заявка
   клиента» (клиент, тип заявки — справочник, ответственный — пользователь) и
   отчёт «по регионам» (сводка по справочнику регионов с переходом к записям).

## Решения владельца продукта 2026-10-18

1. **Вебхуки живых форм:** администратор выбирает охват каждой подписки — все записи сущности или только записи в
   области данных автора подписки. Прежде охвата не было (этап 1, ветка 2, «Вебхуки не ограничиваются областью формы»);
   решение действует для всех сущностей с областью данных, а не только для живых форм. Реализация — «Охват подписок на
   вебхуки» ниже.
2. **Область данных живой формы после создания не меняется** — подтверждено; остаётся как реализовано (422
   `error.studio.scope_change`).
3. **Шаг 2.3 включает все четыре части:** сводная таблица (pivot), сравнение периодов, доли и число различных значений,
   параметры отчёта (с наборами данных администратора).
4. **Шаг 2.4 — рассылки отчётов:** расписание ежедневно/еженедельно/ежемесячно (время и часовой пояс), вложение XLSX,
   ссылка на отчёт, условная отправка (только если в отчёте есть данные или превышен порог); каналы — email, Telegram и
   уведомление в приложении (решение 2026-10-17, п. 3).

## Реализация

### Этап 1, ветка 1 — версии, совместимые изменения и архив (2026-10-17, `claude/stage1-form-versions`)

Решения 1–4, 6 и 7 реализованы; выгрузка в код (решение 5) — следующие ветки.

- **Хранение.** Версия 1 — сама неизменяемая строка `studio_forms` (триггер V214
  сохранён, переноса данных нет). Следующие версии — неизменяемые строки
  `studio_form_versions` (V218: `form_id`, `version` 2…100, декларация, checksum,
  автор; UPDATE/DELETE/TRUNCATE закрыты тем же триггером). Изменяемое состояние —
  `studio_form_state` (V219: активная версия, `active`/`archived`, ревизия для
  `If-Match`; строка появляется при первом изменении, удаление запрещено; триггер не
  даёт сослаться на несуществующую версию). Запись хранит версию схемы
  `studio_records.form_version` (V220); её ставит триггер БД при каждой записи —
  активную на момент оператора, поэтому ни один путь записи её не пропускает.
- **Формат 2.** simple-form v2 добавляет полю `hidden` (только `true`) и
  `defaultValue` (фиксированное значение), сущности — `menu` (значок из 10, раздел
  `workspace`/`administration`, порядок 1…999); до 30 полей, из них не скрытых — до
  20. Формат 1 и его checksum не меняются; CLI v2 не принимает. «Золотой» тест
  дополнен образцами v2.
- **Совместимость** (`StudioChangeRules`, те же правила в редакторе): разрешены
  добавление поля (необязательного или с умолчанием), скрытие и обратный показ,
  подписи, порядок, название, пункт меню, снятие обязательности, рост `maxLength` и
  `scale`. Отказ 422 `error.studio.change_incompatible` (`field`, `change`) с
  отдельной ошибкой на каждое изменение: `removed` (удаление или переименование
  ключа), `type`, `required`, `max_length`, `scale`, `default`. Умолчание
  существующего поля не меняется: записи без ключа читали бы другое значение.
  Умолчание проверяется правилами поля до сохранения (`error.md.simple_form_default`).
- **Проекция.** Скрытое поле не компилируется: его нет в форме, списке, экспорте,
  вебхуках; история живой формы показывает только поля, которые форма называет.
  Данные остаются в `payload` (запись JSON-полей сливается). Новое поле в старой
  записи пусто, а при фиксированном умолчании читается как умолчание: выражение
  чтения JSON-свойства подставляет его, пока ключа нет (`->` IS NULL), — одинаково
  для карточки, списка, фильтров, агрегатов отчёта и экспорта. Значение попадает в
  SQL только шестнадцатеричными цифрами. Сигнатуры Platform API не меняются.
- **Жизненный цикл.** Архивная форма обслуживается только для чтения: общий
  `EntityWriteLock` спрашивается перед каждой записью (create, update, delete,
  archive, действие, bulk) — 409 `error.studio.archived`; form-meta не предлагает
  действий, пункта меню нет. Архивная форма не входит в лимит 100 активных; все
  сохранённые формы ограничены 500 (`error.studio.stored_quota`), каталог читает не
  более 501 строки. Восстановление проверяет лимит активных. Карантин независим и
  важнее архива: форма в карантине не обслуживается вовсе; версию для неё выпустить
  можно, для архивной — нет.
- **API** (`studio.forms.publish`, `@NoIdempotency`, ревизия в ETag):
  `GET /api/v1/studio/forms` (страницы `limit` ≤ 100, `cursor`),
  `GET /api/v1/studio/forms/{code}`, `POST .../{code}/versions` (пакет той же формы,
  201 + Location), `POST .../{code}/archive`, `POST .../{code}/restore`. Каждая смена
  — под блокировкой каталога, CAS по ревизии; права (название формы) и аудит
  (`studio_form_versions`, `studio_form_state`) фиксируются той же транзакцией,
  уведомление `studio.catalog` уходит с фиксацией; версия каталога учитывает новые
  таблицы, поэтому корректность от уведомления не зависит.
- **UI.** «Мои формы» (`/settings/form-studio/forms`) и редактор новой версии
  (`/settings/form-studio/forms/{code}/version`) — тот же редактор полей, где у
  сохранённого поля закрыты ключ, тип и умолчание, а удаление заменено скрытием.

Ограничение: форма, к которой версию активировали между проверкой записи и её
оператором, получает в `form_version` новую активную версию; данные остаются
совместимыми, потому что разрешены только совместимые изменения.

### Этап 1, ветка 2 — справочники, ссылки и область данных (2026-10-17, `claude/stage1-references`)

Решения владельца 1 и 4 (без отчёта «по регионам» — он в ветке отчётов).

- **Справочник — отдельная лёгкая структура, а не живая форма.** Изучено: справочники `ENUM` ADR-0032 (4.5) —
  объявленные в коде сущности (`EntityEnums`), вопрос В1 ADR-0032 о справочниках без выпуска оставался открытым.
  Живая форма не подходит: подписи значения нужны на трёх языках (у записи одно `name`), справочник с партицией
  `EntityModel` запрещает (`reference` у общей таблицы), а отключение значения — это архив перечисления, а не записи.
  Поэтому `studio_lists` и `studio_list_items` (V222): постоянный код, подписи ru/uz/en, порядок 1…9999, признак
  `active`; триггеры запрещают DELETE, TRUNCATE и смену кода (значение отключают). Лимиты: 200 справочников, 500
  значений (предел перечисления). API `/api/v1/studio/lists` (`studio.lists.view` — чтение, `studio.lists.manage` —
  ведение, V223, только административным ролям), каждое изменение — `If-Match`, аудит, сброс кэша значений на всех
  узлах сразу и после фиксации.
- **Справочник встроен в перечисления runtime, а не дублирует их.** Новый интерфейс `common.entity.EntityEnumSource`
  (модуль `studio` реализует его как `StudioListEnums`): ссылка поля на справочник — перечисление `studio.list.<код>`.
  Всё, что `ENUM` уже умеет, работает без нового кода: проверка при сохранении (неизвестный код — `option_required`,
  отключённый — `ref_archived`, старое значение сохраняется), `options`/`optionLabels` form-meta, фильтр и подписи
  списка (`EntityEnumResolver` находит перечисления живых списков в каталоге запроса), подписи в XLSX. Подписи
  значений — данные, поэтому выбираются на языке работы (`RequestLanguage`: язык задания экспорта, иначе первый
  `Accept-Language`), кэш — по справочнику и языку.
- **Формат 3** (`simple-form`, только живые формы; CLI его не принимает, как и формат 2): `select` с вариантами
  (1…50, код `[a-z0-9][a-z0-9_-]{0,39}` и подписи; запись хранит код; подписи — словарь формы), `ref` с целью
  `{kind: list|form, code}`, `user` (ссылка на `md.users`), `entity.scope` = `all` | `org_unit` | `owner`. Формат 2 не
  может это выразить, поэтому номер повышен; форматы 1 и 2 и их checksum не меняются, «золотой» тест покрывает все три.
  Поля хранятся в `payload`; Platform API разрешает партиционированной сущности `SELECT`, `ENUM` и `REF` (JSON-свойство
  читает ссылку как `bigint`) — правила только расширены, сигнатуры прежние.
- **Ссылки на формы и пользователей** — обычный `REF` с `target`: значение проверяется существующим механизмом —
  цель видна сохраняющему (право `view` и область данных цели), не в архиве; подписи (`labels`) разрешаются пакетно в
  области зрителя. Для «Пользователя» нужно право `md.users.view`, видны пользователи области зрителя. Сущности
  «клиент» в платформе нет (проверено), поэтому «клиент» эталона — ссылка на живую форму «Клиенты». Цель обязана
  существовать при активации формы и версии (422 `error.studio.target_not_found`); цель, выведенная из работы позже,
  не ломает запрос: новое значение — 422 `ref_not_found` (раньше 500), старое читается без подписи.
- **Область данных формы** — существующий механизм `EntityScope` (ADR-0013, ADR-0032 5.1): `all`, `owner(created_by)`,
  `orgUnit(org_unit_id, created_by)`. `studio_records.org_unit_id` (V221) — новая колонка; форма с `org_unit` получает
  системное поле `orgUnit` (только чтение, по умолчанию основное подразделение автора). Предикат области входит в
  список, карточку, историю, экспорт, отчёты и агрегаты, bulk-действия и проверку ссылок — во все пути чтения и записи
  runtime, как у статических сущностей.
- **Изменение области — несовместимо** (422 `error.studio.scope_change`): расширение покажет записи тем, кто их не
  видел, сужение спрячет записи, сохранённые без подразделения. Нужна новая форма или выгрузка в код. Совместимость
  новых типов: варианты выбора можно добавлять и переименовывать, удалить код — нельзя (`option_removed`); цель
  ссылки не меняется (`target`); смена типа, как и прежде, запрещена.
- **Подписи вместо ключей.** Экспорт XLSX пишет имена ссылок, разрешённые в области выгружающего (`labels` страницы),
  и подписи вариантов и значений справочника на языке задания.
- **Вебхуки не ограничиваются областью формы — сознательное решение** (заменено решением владельца 2026-10-18, п. 1:
  охват подписки выбирает администратор). Подписка — интеграция установки без зрителя
  (ADR-0032, 6.9): её создаёт только держатель `webhook.subscriptions.manage` (администратор), данные без полей с
  правами. Фильтр по автору подписки сломал бы контракт статических сущностей (заметки, заявки) и проверку кита.
  Если понадобится ограничение, это отдельное решение (подписка от имени пользователя с его областью).
- **UI.** «Справочники» (`/settings/form-studio/lists`) рядом с «Мои формы»; в редакторе новой формы (доставка в
  установку) — типы «Выбор из списка», «Ссылка», «Пользователь» и «Видимость записей»; в редакторе версии сохранённые
  варианты и цель закрыты, область показана без изменения. Поле записи выбирает цель существующими контролами
  (`smt-data-select` с поиском и страницами, `select` для вариантов и справочника).

Ограничения ветки: поле подразделения только для чтения (запись нельзя перенести в другое подразделение); множественного
выбора и множественных ссылок нет; отчёт-агрегат XLSX пишет коды групп — подписи групп и каталог
отчётов в ветке отчётов; раскладка (секции, вкладки) и отказ от обязательных `name`/`code` — следующая ветка. Все три
ограничения сняты веткой 3 (кроме множественного выбора).

### Этап 1, ветка 3 — раскладка, заголовок записи и отчёты (2026-10-18, в `main`)

### Охват подписок на вебхуки (2026-10-18, в `main`)

Решение владельца 2026-10-18, п. 1.

- **Охват** `scope` подписки: `creator` — только записи, которые автор подписки может прочитать в момент события
  (активен, держит `view` формы сущности, запись в его области данных — тот же предикат `EntityScopes`, что у списка), или
  `all` — все записи. **По умолчанию `creator`**: узкий охват безопаснее, широкий выбирают явно; существующие подписки
  получили `creator` той же миграцией (клиентов нет). V229 — `kwh_subscriptions.scope` (check `all`/`creator`).
- **Когда проверяется.** При записи события в `kwh_outbox`, в транзакции изменения, один раз на автора
  (`WebhookService.publishEvent(тип, тело, проверка автора)`); тело события строится, только если его кто-то получит.
  Проверка при отправке отвергнута: событие описывает запись на момент изменения, а к отправке запись может измениться
  или исчезнуть. Удаление: перед `delete` runtime публикует `common.entity.EntityRemoving`, слушатель вебхуков запоминает
  в ресурсе транзакции, каким авторам запись была видна, и событие `deleted` получают только их подписки.
- **Автор потерял доступ** (заблокирован, право `view` снято, запись вне области) — событие не ставится в очередь и не
  попадает в журнал доставки; считается в `smc.webhook.events.withheld{reason}` (`out_of_scope`, `creator_access`,
  `not_read_before_deletion`). Подписку не приостанавливаем: приостановка внутри чужой транзакции записала бы в аудит не
  того автора; администратор переводит подписку в `all` или создаёт её заново от активного пользователя. Сверх задания:
  `creator` у сущности без области данных тоже требует активного автора с правом `view` — иначе заблокированный
  администратор продолжал бы выгружать данные.
- **API.** DTO перенесены в `webhook.api.WebhookDtos` (имена схем прежние); `scope` — необязательное поле создания и
  изменения (`PATCH` с `If-Match`, аудит `kwh_subscriptions` пишет `scope` до и после), поле ответа списка и созданной
  подписки; 422 `error.webhook.scope_invalid` для другого значения. `Api-Breaking`: подписка без `scope` больше не
  получает записи вне области автора.
- **UI.** В диалоге создания подписки — выбор «Какие записи отправлять» (карточки с пояснением, клавиатура — стрелки), в
  таблице — колонка охвата.
- **Тесты:** `StudioWebhookScopeHttpTest` (живая форма с областью `org_unit`: запись своего подразделения доходит до
  обеих подписок, чужого — только до `all`, то же для изменения и удаления; автор без права или заблокирован — ничего;
  смена охвата через API с `If-Match` и аудитом), `WebhookServiceLifecycleTest`.

### Этап 2, шаг 2.3 — аналитика отчётов (2026-10-19, в `main`)

Решение владельца 2026-10-18, п. 3: все четыре части. Модель, лимиты и правила — [ADR-0044](ADR-0044-report-analytics.md).

- **Сводная таблица** — `pivot: true` из двух группировок: итоги строк, столбцов и общий (по валюте), до 50 столбцов и
  10 000 ячеек (иначе отказ 422), строки — в порядке отчёта с top-N; подписи справочников, выборов, пользователей и
  ссылок; переход к записям из ячейки и итога, когда список выражает его точно; XLSX — матрица с итогами. Экран —
  таблица с заголовками строк и столбцов (`scope`), прокрутка с клавиатуры, на узком экране — карточки строк.
- **Сравнение периодов** — этот месяц, квартал, год, с начала года или свой период против предыдущего или того же
  периода год назад, в поясе читателя; мера, прежнее значение, изменение и изменение в процентах (0 — пусто); без
  группировок — карточка с изменением.
- **Доли и число различных значений** — доля количества или суммы от итога (в сводной — и от строки, столбца) и
  `count_distinct` поля — точные, на сервере, в группах и итогах.
- **Параметры сохранённого отчёта** — период, выбор, ссылка, пользователь, подразделение, да/нет; обязательность и
  умолчание; значения — суженный фильтр, проверенный компилятором списка; каталог открывает отчёт с формой параметров.
- **Наборы данных администратора** — страница «Наборы данных отчётов» (`/settings/report-datasets`): источник,
  строки документа, поля, постоянный фильтр, вычисляемые показатели; V230 `md_report_datasets`, V231 права
  `md.report_datasets`.
- **Отчёты по строкам документов** — набор по таблице строк: сумма строк по товару и региону, подписи ссылок и
  справочников строк.
- **Тесты** — `QueryAggregateAnalyticsTest`, `StudioReportAnalyticsHttpTest`, `StudioReportDatasetHttpTest`,
  `AggregateWorkbookWriterTest`; e2e `e2e/tests/browser/instance/studio-report-analytics.spec.ts` (сводная «регион ×
  месяц × сумма» с долей, переход из ячейки, XLSX, «этот месяц против прошлого», различные клиенты по регионам,
  отчёт с обязательным периодом и регионом из каталога у продавцов двух подразделений).

Ограничения шага 2.3: группировок две; «прочих» столбцов нет; моменты группируются в UTC; параметры только у
сохранённого отчёта; у наборов по строкам нет перехода к записям; по вычисляемому показателю нет порядка и доли.
