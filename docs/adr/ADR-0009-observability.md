# ADR-0009: Наблюдаемость флота — централизованные логи, метрики, трейсы, алертинг

**Статус:** Частично заменено ADR-0014 (2026-09-03)
**Дата:** 2026-08-27
**Закрывает:** пробел «система логов» (NFR-9 объявлял структурные логи и OTLP, но не определял, куда они попадают, как ищутся и кто получает алерты)
**Зависит от:** ADR-0004 (флот), ADR-0007 (Nomad), ADR-0008 (безопасность)

> Историческое решение ниже сохраняется для трассируемости. Положения о
> Control Plane, fleet, лицензировании, Nomad, Consul и обязательном Vault
> больше не описывают поддерживаемый runtime.

> **Реализация метрик и алертов (2026-10-07, план 10/10, п. 7.3).** Для
> поставки Docker Compose каталог алертов раздела 4 воплощён правилами
> Prometheus (recording и alerting) с юнит-тестами promtool и дашбордами
> Grafana в JSON (`deploy/observability`); сбор, Alertmanager и Grafana
> разворачивает оператор. SLO доступности — утверждённые 99.9 %, пороги
> задержки API — утверждённые владельцем продукта 2026-10-10 p95 ≤ 300 мс и
> p99 ≤ 1 с (`NFR-PERF-02`). У каждого
> алерта есть runbook в `docs/runbooks`. Описание —
> [SLO, метрики и алерты](../ops/slo.md).
>
> **Экспортеры хоста и PostgreSQL (2026-10-10, решение владельца продукта).**
> node_exporter и postgres_exporter раздела 4 поставляются необязательным
> overlay `deploy/observability/docker-compose.observability.yml` (образы
> `prom/node-exporter` и `prometheuscommunity/postgres-exporter` по digest,
> read-only, без capabilities, внутренняя сеть `monitoring`, роль
> мониторинга с `pg_monitor`). Алерты диска хоста (80/90 % раздела 4 и
> прогноз заполнения) и PostgreSQL — `rules/infrastructure.yml`, runbook

## 1. Требования к системе

**Функциональные**
- По любому инциденту у любого из ~100 клиентов: найти логи конкретного экземпляра за период,
  связать HTTP-запрос → лог → SQL по одному `trace_id`, за минуты, не подключаясь к узлу по SSH.
- Дашборды: здоровье флота (по клиентам), здоровье экземпляра (для разборов), SLO из NFR-2.
- Алертинг с маршрутизацией дежурному (канал — Telegram, тот же стек, что и у продукта).

**Нефункциональные**
- Отказ системы наблюдаемости **не влияет** на работу экземпляров (fire-and-forget с локальным буфером).
- Стоимость: укладывается в 1–2 средних узла на весь флот из 100 экземпляров.
- Логи не содержат персональных данных и секретов (см. разд. 5) — это условие того, что
  centralized-логи не становятся второй копией клиентских данных вне контура клиента.
- Хранение: логи 30 дней, метрики 13 месяцев (годовая сезонность для capacity planning),
  трейсы 7 дней с сэмплированием.

## 2. Выбор стека

| Вариант | Оценка | Вердикт |
|---|---|---|
| **Grafana-стек: Alloy → Loki + VictoriaMetrics + Tempo, Grafana** | Лёгкий, каждый компонент масштабируется отдельно, Loki/Tempo хранят в S3 — **у нас уже есть Garage**; индустриальный стандарт, найм и документация — без проблем | **Да** |
| ELK/OpenSearch | Полнотекстовый поиск лучше, но 3–5× дороже по ресурсам; для структурных JSON-логов с label-фильтрацией избыточен | Нет |
| SigNoz (всё-в-одном на ClickHouse) | Компактно, но ещё одна СУБД (ClickHouse) в эксплуатации ради наблюдаемости; меньше зрелость | Нет |
| «Логи в файлах на узлах + grep» | Ничего не стоит сейчас, недееспособно при 10+ клиентах и запрете SSH-туризма | Нет |

**Решение:** Grafana-стек, полностью self-hosted на нашей инфраструктуре:

- **Grafana Alloy** — единый агент сбора (system job Nomad на каждом узле): scrape stdout
  контейнеров → Loki; приём OTLP от приложений (метрики уже Micrometer→OTLP, трейсы) →
  VictoriaMetrics / Tempo. Локальный буфер на диске узла — переживает недоступность центра.
- **Loki** — логи; чанки в Garage (S3), центральный bucket платформы.
- **VictoriaMetrics** (single-node) — метрики; на 100 экземпляров хватает с большим запасом,
  один бинарь, дешевле Mimir.
- **Tempo** — трейсы; хранение в Garage; tail-sampling: 100% ошибок и медленных, 1% остального.
- **Grafana** + **vmalert/Alertmanager** — дашборды и алертинг; маршрутизация в Telegram-канал
  дежурных (переиспользуем компетенцию Telegram-канала из продукта).

Стек живёт на выделенных узлах наблюдаемости (не на узлах клиентов и не в control plane),
разворачивается теми же Nomad job'ами.

## 3. Поток данных

```
узел клиента N                                узлы наблюдаемости (наши)
┌────────────────────────────┐               ┌────────────────────────────────┐
│ app (Spring Boot)          │               │ Loki ──────────┐               │
│  stdout JSON ──┐           │               │ VictoriaMetrics ├── Grafana    │
│  OTLP metrics ─┤           │   push        │ Tempo ─────────┘     │        │
│  OTLP traces ──┼─▶ Alloy ──┼──────────────▶│        ▲             ▼        │
│ pg-oltp logs ──┤ (буфер    │               │     Garage      vmalert/AM     │
│ pg-dwh logs ───┤  на диске)│               │  (чанки Loki,        │        │
│ garage logs ───┘           │               │   блоки Tempo)       ▼        │
└────────────────────────────┘               │              Telegram дежурных │
                                             └────────────────────────────────┘
control plane: показывает бизнес-статусы (heartbeat, версии, лицензии, бэкапы),
Grafana: показывает телеметрию. CP может embed'ить Grafana-панели, но НЕ дублирует их.
```

**Разграничение с control plane (важно, чтобы не строить одно и то же дважды):**
CP отвечает на вопрос «*что с клиентом как с бизнес-объектом*» (жив, какая версия, лицензия,
прошла ли проверка бэкапа). Grafana отвечает «*что происходит внутри*» (логи, латентность,
ресурсы). Heartbeat остаётся в CP — он работает даже если стек наблюдаемости лежит.

## 4. Дисциплина телеметрии

**Логи** — структурный JSON (logstash-encoder), обязательные поля:
`ts, level, logger, msg, client_code, app, module, trace_id, span_id`.
- **Метки Loki** — только низкокардинальные: `client_code, app, level, module`.
  Запрещено в метках: `user_id`, `trace_id`, URL — кардинальность убивает Loki; они ищутся
  по содержимому.
- `trace_id` сквозной: SPA → HTTP-заголовок → MDC → SQL-комментарий (`/*traceparent=...*/`).

**Метрики** — Micrometer: HTTP (латентность по классам операций из NFR-2 — гистограммы),
пул соединений, очередь доставки (глубина, возраст головы, dead-letter), фоновые задачи,
JVM, PostgreSQL (postgres_exporter в составе job'а клиента), Garage, узлы (node_exporter).

**Каталог алертов (минимум M3):**

| Алерт | Условие | Серьёзность |
|---|---|---|
| Экземпляр молчит | нет heartbeat в CP > 10 мин (шлёт CP) | 🔴 инцидент |
| Провал проверки бэкапа | отчёт job'а (ADR-0007 разд. 2.5) | 🔴 инцидент |
| Провал миграции | batch-job завершился ошибкой | 🔴 инцидент |
| Canary откатился | Nomad auto_revert сработал | 🟠 |
| SLO burn-rate | расход бюджета ошибок ×14 за час / ×2 за 6 ч | 🟠/🔴 |
| Очередь доставки | dead-letter растёт или голова старше 15 мин | 🟠 |
| Диск узла | > 80% (предупр.), > 90% (инцидент) | 🟠/🔴 |
| Истечение сертификатов | < 14 дней | 🟠 |
| Vault/Consul/Nomad кворум | потеря узла кворума | 🔴 |

Каждый 🔴-алерт обязан ссылаться на runbook (ADR-0007 O-5).

## 5. Безопасность телеметрии

- **Запрет ПДн и секретов в логах**: маскирующий фильтр в logback (паттерны: password, token,
  Authorization, телефоны, email) + правило в CODE_STYLE «в лог не пишутся значения полей
  пользовательских сущностей, только идентификаторы». Проверка — тестом на маскирование.
- Log-injection закрыт JSON-энкодером (перенос строки не порождает поддельную запись).
- Доступ к Grafana — SSO нашей команды, права по ролям (разработчик видит логи, но не админит).
- Трафик Alloy → центр: mTLS (сертификаты — из Vault).
- Телеметрия — метаданные работы системы; данные клиентов остаются в их экземплярах.

## 6. Что сознательно не делаем

| Не делаем | Причина |
|---|---|
| SaaS-наблюдаемость (Datadog, Grafana Cloud) | Данные и стоимость: 100 экземпляров в SaaS-тарифах дороже двух своих узлов на порядок |
| APM-агенты с байткод-инструментацией | Micrometer + OTel покрывают нужды; меньше магии в JVM |
| 100% трейсинг | Tail-sampling достаточно; 100% — расход впустую |
| Логи ELK с полнотекстом | См. разд. 2 |
| Длинное хранение логов (>30 дней) | Бизнес-события живут в audit_log/security_events БД экземпляра с retention 12 мес — это разные системы с разными задачами |

## 8. Реализация в продукте (2026-10-07, план 10/10, пункты 7.1 и 7.2)

Положения о флоте выше — история; для одного экземпляра действует следующее.

**Логи.** Встроенное structured logging Spring Boot, формат ECS (а не logstash-encoder из разд. 4),
одна JSON-строка на событие в консоли и в файле (`SMC_LOG_FILE`, архив раз в неделю или при 100 МБ —
без изменений). Поля: `@timestamp`, `log.level`, `log.logger`, `process.thread.name`, `service.name`,
`message`, `error.*`, `trace_id`, `span_id` (`traceId`/`spanId` Micrometer Tracing переименованы).
Профиль `dev` печатает в консоль текст. Баннер Spring выключен: в консоли только JSON.

- `client_code` в строке **нет**, заголовок `X-Client-Code` удалён: экземпляр обслуживает одного
  клиента, а значение заголовка задавал вызывающий, то есть подделывал. Метку клиента для Loki ставит
  сборщик (Alloy) по месту развёртывания.
- Маскирование (разд. 5): `LogMaskingJsonMembersCustomizer` обрабатывает каждое поле строки — по имени
  поля (password, secret, token, authorization, cookie, otp, api key, credentials, `code`) и по тексту
  (`key=value`, `"key":"value"`, `Authorization: Bearer`, `Cookie:`, `#token=`, `?code=`). Телефоны и email
  фильтр не распознаёт: запрет из CODE_STYLE, разд. 5, остаётся. Тесты: `LogMaskingTest`,
  `ObservabilityIntegrationTest` (каждая строка консоли и файла — JSON, строки запроса несут его `trace_id`).
- Входящий `traceparent` принимается только строгого вида W3C: версия `00`, 32 и 16 hex-символов в нижнем
  регистре, не нули, 2 hex флагов, один заголовок. Иначе заголовок (с `tracestate`) скрывается и
  начинается новая трасса; значение не возвращается и не пишется. Ответ несёт `traceparent` серверного span.

**Трейсы.** Micrometer Tracing с мостом OpenTelemetry и экспортом OTLP/HTTP (версии — из BOM Spring Boot).
По умолчанию вероятность записи 0 и экспорт выключен (`SMC_TRACING_SAMPLING_PROBABILITY`,
`SMC_TRACING_EXPORT_ENABLED`, `SMC_TRACING_OTLP_ENDPOINT`): идентификаторы трассы создаются и пишутся в
логи, span не записываются. Вместо tail-sampling на экземпляре — вероятностная запись; tail-sampling при
необходимости делает коллектор.

- В записанной трассе каждый оператор JDBC получает клиентский span и комментарий в конце SQL
  `/*traceparent='00-<trace>-<span>-01'*/` (формат sqlcommenter). Библиотеки для этого в Spring Boot нет;
  обёртка источника данных — `config.observability.JdbcTracing`, без новых зависимостей. Вне записанной
  трассы SQL не меняется, чтобы не ломать кэш подготовленных операторов PostgreSQL. В span нет текста SQL
  и параметров.
- Исходящий HTTP вебхуков передаёт `traceparent` получателю. Тест цепочки HTTP → JDBC и комментария —
  `ObservabilityIntegrationTest`.
