# ADR-0048: витрины хранилища как источник отчётов

**Статус:** принято 2026-10-20 (этап 3, шаг 3.3 плана конструктора форм и отчётов); реализовано в `main` 2026-10-20.
**Основание:** план 10/10, раздел «Конструктор форм и отчётов», этап 3 — шаг 3.3 («витрины хранилища как источник
отчётов»).
**Зависит от:** [ADR-0016](ADR-0016-field-registry-query-dsl.md) (`query-meta` и DSL фильтров),
[ADR-0019](ADR-0019-low-code-entity-model.md) (модель сущностей), [ADR-0030](ADR-0030-fnd-split.md) (разделение
`warehouse`, `units` и `jobs`), [ADR-0032](ADR-0032-low-code-platform-v2.md) (платформа сущностей v2 и отчёты),
[ADR-0036](ADR-0036-shared-reports-and-dashboards.md) (общие отчёты, выгрузки и дашборды),
[ADR-0044](ADR-0044-report-analytics.md) (аналитика отчётов и наборы данных),
[ADR-0045](ADR-0045-report-mailings.md) (рассылки отчётов).

## Контекст

Применённые пакеты файлового конвейера (`upl`) записывают исходные строки книги в `raw.rows` второй базы данных
(`pg-dwh`), а учёт загрузок (`fnd_warehouse_loads`) и правила формата (`upl_sources`, `upl_format_versions`) живут в
основной базе. В `raw.rows` лежат как принятые, так и отбракованные при проверке строки, значения хранятся в исходном
виде и в единицах измерения файла (`source_unit`), а при повторной загрузке за тот же период старая загрузка становится
`SUPERSEDED`.

Конструктор отчётов (`EntityReports`, `QueryAggregates`) строит группировки, сводные таблицы, сравнения периодов, доли,
параметры, наборы данных (`ds.*`), виджеты дашбордов, выгрузки в `.xlsx` и рассылки по декларации `EntityDefinition`
в основной базе. Чтобы строить те же аналитические отчёты по данным хранилища без второй реализации конструктора:

| Вариант | Почему нет / да |
|---|---|
| Запрашивать `raw.rows` напрямую из отчёта | В `raw.rows` лежат отбракованные строки и значения до пересчёта единиц измерения и нормализации дат/ключей |
| Копировать нормализованные строки обратно в основную базу (OLTP) | Нарушает разделение OLTP и `pg-dwh` ([ADR-0030](ADR-0030-fnd-split.md)) и раздувает основную базу |
| **Слой витрин `mart.rows` в `pg-dwh` + декларации `mart.<slug>` через `EntityDefinitionSource` + выполнение того же `QueryAggregateRepository` на `pg-dwh`** | **Выбран**: единый язык отчётов, наборов данных, дашбордов, выгрузок и рассылок работает поверх нормализованных строк активных загрузок в `pg-dwh` |

## Решение

### 1. Хранение витрины в `pg-dwh` (`V005__mart_rows.sql`)

- В `pg-dwh` создаётся схема `mart` и таблица `mart.rows (load_id bigint, row_no bigint, source_code text, period_from
  date, period_to date, sheet text, fields jsonb, primary key (load_id, row_no))` с индексами
  `rows_source_period_idx (source_code, period_from, period_to)` и `rows_fields_gin_idx using gin (fields)`.
- В схеме `public` базы `pg-dwh` публикуется представление `public.mart_rows`, чтобы генератор SQL (`QuerySql`,
  допускающий только простые идентификаторы таблиц) обращался к `mart_rows m` без изменения правил экранирования.

### 2. Нормализация и синхронизация витрины (`UplMartBuilder`, `WarehouseMarts`)

- В витрину попадают только строки применённых (`APPLIED`) загрузок, прошедшие проверку текущей версии формата без
  ошибок (`REJECTED` строки отсекаются).
- Значения приводятся к каноническому виду для аналитики:
  - `INTEGER` и `NUMBER` разбираются и при заданных `sourceUnit` / `baseUnit` пересчитываются в базовую единицу через
    `Units.toBase(value, sourceUnit, baseUnit, periodTo)`;
  - `DATE` приводится к ISO `yyyy-MM-dd` (из `yyyy-MM-dd`, `dd.MM.yyyy` или серийного номера даты Excel);
  - `OBJECT_KEY` дополняется ведущими нулями по правилам `keyPadLength` / `keyPadMax` версии формата;
  - `TEXT` и `REF_CODE` очищаются от крайних пробелов.
- При применении пакета (`UplApplyJob`) после фиксации статуса `APPLIED` для пакетов до $50\,000$ строк витрина
  обновляется сразу вне OLTP-транзакции; одновременно из `mart.rows` удаляются строки загрузок источника, перешедших в
  `SUPERSEDED`. Для крупных потоковых загрузок и на случай временной недоступности `pg-dwh` `UplMartBuilder.ensureMaterialized`
  идемпотентно достраивает недостающие активные загрузки из `raw.rows` и очищает заменённые перед выполнением отчёта.
- Сбой чтения или записи `pg-dwh` переводится в `WarehouseUnavailableException` (503).

### 3. Декларации сущностей `mart.<slug>` (`UplMartSources`)

- Каждый файловый источник `upl`, имеющий опубликованную версию (`lastPublishedVersion != null`), публикуется через
  `EntityDefinitionSource` как сущность `mart.<slug>` (`UplMartSources.martCode(sourceCode)` приводит дефисы и сегменты к
  синтаксису кода сущности).
- Сущность привязана к праву формы `upl.sources` (`view`), имеет `EntityScope.all()` и возможность `SAVED_VIEWS`
  (сохранённые отчёты, виджеты дашбордов, выгрузки, рассылки), не добавляет собственных прав в каталог RBAC и не создаёт
  пункт бокового меню.
- Поля витрины (все `readonly`):
  - измерения загрузки `periodFrom` (`period_from`), `periodTo` (`period_to`), `sheetName` (`sheet`);
  - все уникальные колонки листов опубликованной версии формата (`fields->>'<target_field>'`), сопоставленные с типами
    `NUMBER` (`scale = 0` для `INTEGER`), `DATE` и `TEXT`. В названии числового поля с `baseUnit` указывается базовая
    единица измерения (`<Имя колонки> (<baseUnit>)`).
- Строковые поля сущностей `mart.*` помечаются в `query-meta` форматом `dimension` (`QueryAggregates.DIMENSION_FORMAT`),
  чтобы конструктор отчётов и серверный валидатор группировок разрешали группировку по кодам объектов, кодам справочников,
  листам и текстовым измерениям витрины.
- Обычные CRUD-точки записей (`/api/v1/entities/mart.<slug>`) не обслуживаются (`EntityRegistry.records` возвращает
  `Optional.empty()` → `404`).

### 4. Выполнение отчётов и наборов данных поверх витрины (`EntityReportMartRunner`)

- Контракт `EntityReportMartRunner` в `common.entity.report` позволяет модулю `upl` (`UplMartReportRunner`) выполнять
  агрегатные запросы `EntityReports` для сущностей `mart.*` в базе `pg-dwh` без прямой зависимости `common` от
  `warehouse` или `upl`.
- `UplMartReportRunner` проверяет наличие опубликованного источника, синхронизирует активные загрузки в `mart.rows` и
  выполняет `WarehouseMarts.aggregate(entity, query, extraWhere)` с условием `m.source_code = :_mart_source AND
  m.load_id IN (:_mart_loads)` (если у источника ещё нет применённых загрузок — с `1 = 0`).
- Наборы данных администратора (`ds.*`, ADR-0039/0044), построенные поверх `mart.<slug>`, наследуют маршрутизацию в
  `EntityReportMartRunner` вместе со своими фиксированными фильтрами, параметрами и вычисляемыми мерами.

### 5. Веб-интерфейс

- В карточке опубликованного источника (`/upl/sources/:id`) появляется ссылка «Построить отчёт»
  (`[data-testid="upl-open-report"]`), ведущая на `/e/mart.<slug>?mode=report`.
- Экран `/e/mart.<slug>` (`SMTEntityListPageComponent`) определяет префикс `mart.`, сразу открывает конструктор отчёта
  без запроса страницы строк `/api/v1/entities/mart.<slug>`, скрывает переключатель «Список / Отчёт» и отключает
  проваливание из строк и диаграмм отчёта к списку записей.

## Последствия

- Аналитика по загруженным файловым пакетам строится тем же конструктором отчётов (сводные таблицы, итоги, сравнение
  периодов, доли, параметры, сохранённые отчёты, дашборды, `.xlsx`-выгрузки и рассылки), что и по сущностям основной
  базы, но исполняется в `pg-dwh` по проверенным и пересчитанным в базовые единицы данным.
- Ограничения: витрины только для чтения и агрегации (построчный просмотр исходных строк остаётся в карточке пакета
  загрузки); при недоступности `pg-dwh` отчёт по витрине возвращает 503 (`WarehouseUnavailableException`), не затрагивая
  отчёты по основной базе.
