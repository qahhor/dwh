# ADR-0019: Модель low-code — сущность, объявленная метаданными

**Статус:** Предложено (2026-09-26)
**Дата:** 2026-09-26
**Зависит от:** ADR-0002 (backend stack), ADR-0006 (модульный монолит), ADR-0013 (скоуп данных),
ADR-0015 (перенос UI-кита), ADR-0016 (реестр полей и DSL), ADR-0017 (история), ADR-0018 (экспорт)

---

## 1. Контекст

dwh позиционируется как low-code платформа (ADR-0016, решение 2026-09-24).
Проверка кода на 2026-09-26 показывает, что метаданные пока описывают только
списки, и то не все:

| Что | Сейчас | Доказательство |
|---|---|---|
| Списки на реестре `QueryList` | 3 (`mf.files`, `upl.sources`, `upl.packages`) | `MfFileQuery`, `UplSourceQuery`, `UplPackageQuery` |
| Списки с ручным SQL | ~10, среди них пользователи, задачи, аудит, заметки, проекты | `MdUserRepository`, `MsTaskRepository`, `AuditLogRepository`, `MsNoteController` |
| Дополнительные поля | 4 сущности, только в модалке редактирования; не колонки, не фильтры | `md_custom_fields`, `ui-custom-fields.component.ts` |
| Метаданные формы, карточки, раскладки | нет | — |
| Сохранённые виды, экспорт, история, массовые действия | подключаются вручную к 1–3 сущностям каждая | ADR-0016 §2.7–2.8, ADR-0017, ADR-0018 |
| Модуль | строка в `md_installed_modules`, не добавляет ни экранов, ни API | V028 |
| Меню по правам (`FR-MOD-02`) | `required_permission` хранится, но не применяется ни сервером, ни вебом | `NavigationItemService.getActiveItems`, `app-shell.models.ts` |
| Новая сущность (эталон — заметки) | ~20 файлов вручную | `ms/note`, `features/notes`, V028/V030, `MdFormCatalog`, `app.routes.ts` |
| Генератор модуля | `scripts/dev/create-module.ps1` порождает копию кода (миграция, Java, Angular), а не объявление: сгенерированное дальше поддерживается вручную | заголовок скрипта |

Идеи Biruni (только идеи, без кода — ADR-0015): форма и её действия — данные;
сервер отдаёт экрану список разрешённых действий; список объявляется
типизированными полями со ссылками на другие списки; дополнительные поля
(`kdyn`) рисуются одним компонентом по типу; меню — данные. У Biruni правила
проверки не входят в метаданные, а значения дополнительных полей хранятся
текстом — эти два места мы делаем лучше.

## 2. Решение

### 2.1. Сущность как одно объявление

Модуль объявляет сущность бином `EntityDefinition` (`instance.common.entity`):

- код и форма права (`tasks.items`), действия и их права;
- список — существующий `QueryList` (ADR-0016), ставший частью сущности;
- поля формы: ключ, тип, ключ подписи, обязательность, правила проверки
  (длина, диапазон, шаблон, набор значений), ссылка на другой список;
- раскладка карточки: секции, порядок полей, вкладки (история, файлы,
  комментарии) — из того, что сущность поддерживает;
- поддерживаемые возможности: история (ADR-0017), экспорт (ADR-0018),
  массовые действия, сохранённые виды, дополнительные поля.

Из объявления платформа получает остальное: `query-meta`, `form-meta`,
каталог прав с названиями, пункт меню, источник истории, экспортёр. Модуль
пишет только то, что отличает его сущность: SQL выборки и операции сервиса.

### 2.2. `GET /api/v1/form-meta/{code}`

Отдаёт поля формы, раскладку, правила проверки и **разрешённые текущему
пользователю действия** — экран рисует кнопки по ответу, а не по своим
проверкам прав. Неизвестная и чужая сущность — одинаковый 404, как у
`query-meta`. Сервер проверяет запись по тем же правилам, что отдал в
`form-meta`: правило в метаданных не может разойтись с проверкой.

### 2.3. Дополнительные поля — поля реестра

Дополнительное поле сущности становится полем её списка: выражение над
`attributes jsonb`, тип из поля, признаки фильтра и сортировки. Значения
хранятся типизированно в JSON (число — числом), а не текстом, как в Biruni.
Сортируемым дополнительное поле делается только с индексом по выражению.

### 2.4. Ссылки между списками

Тип поля `ref` указывает на код другого `QueryList`: колонка показывает
название, фильтр — выбор из списка через `smt-data-select`, а права и скоуп
данных проверяются по целевому списку. Это идея `refer` из Biruni поверх
нашего REST и keyset.

### 2.5. Интерфейс

Одна форма (`smt-entity-form`) на Signal Forms и контролах кита строится по
`form-meta`; одна карточка — по раскладке. Экран, которому нужно своё,
заменяет отдельную секцию или ячейку, а не пишет форму заново — так же,
как `registryTableConfig` сегодня заменяет ячейки таблицы.

### 2.6. Уровни настройки

1. **Разработчик** объявляет сущность в коде (этот ADR).
2. **Администратор** без выпуска: дополнительные поля, порядок и видимость
   полей в раскладке, меню, сохранённые виды — только то, что не несёт SQL
   и не расширяет права.
3. **Сущности без кода** (администратор создаёт таблицу и экран) — вне этого
   решения. Нужен отдельный ADR: хранение, миграции, скоуп данных и
   безопасность SQL.

### 2.7. Порядок внедрения

Волна 9 роадмапа, каждый пункт — отдельный PR:

1. Меню по правам (`FR-MOD-02`) — дефект, чинится до всего остального.
2. Ручные списки → реестр: пользователи, задачи, журнал аудита, события
   безопасности, заметки, проекты. Это уже решено ADR-0016 §4.
3. Дополнительные поля как поля реестра (§2.3).
4. Ссылки `ref` (§2.4) и группы «или» в DSL (`{"any":[...]}`, ADR-0016 §2.3).
5. `EntityDefinition` и `form-meta` (§2.1–2.2); пилот — заметки.
6. `smt-entity-form` и карточка (§2.5); заметки переписываются на них.
7. Возможности по объявлению: история, экспорт, массовые действия, виды.
8. Меню и названия прав из объявлений; руководство по модулю — чек-лист.

**Критерий успеха:** заметки после п. 6 объявлены одной сущностью — не
больше 5 файлов модуля вместо ~20 сегодня, без изменения API и поведения,
все проверки зелёные.

## 3. Последствия

- Новая сущность — объявление, SQL выборки, сервис и миграция; форма,
  карточка, список, меню и права — из платформы.
- Переходим по одной сущности; старые экраны работают до своего перевода.
- Метаданные — код: проверяются компилятором и тестами, меняются выпуском.
  Администратор меняет только безопасный слой (§2.6, уровень 2).
- `form-meta` — ещё одна точка, где права должны совпадать с сервером;
  тест на каждую сущность сравнивает действия в ответе с `@RequiresPermission`.
- Расхождения ТЗ и кода, найденные при анализе, исправляются отдельно с
  согласия владельца ТЗ: `FR-MOD-01` называет таблицу `md_module_registry`,
  в коде `md_installed_modules`; слова «low-code» в ТЗ нет.

## 4. Рассмотренные альтернативы

| Вариант | Когда подходит | Почему не сейчас |
|---|---|---|
| **A. Метаданные в коде + общий UI** (выбрано) | Команда разработчиков, строгие права и скоуп данных | — |
| B. Определения в БД, редактирует администратор (no-code) | Много однотипных справочников у разных клиентов | SQL и права в данных — риск безопасности; миграции и тесты сложнее. Оставлен уровнем 3 (§2.6) после A |
| C. Как Biruni: логика в БД (PL/SQL), Java — шлюз | Oracle-стек | Противоречит ADR-0002/0014 (Java + PostgreSQL) |
| D. Готовый движок форм (ngx-formly, JSON Forms) | Нет своего кита | Новая зависимость; formly построен на reactive forms, а мы на Signal Forms (ADR-0015); кит уже даёт контролы |
