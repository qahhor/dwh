# ADR-0029: Шифрование секретов в БД

**Статус:** Принято (2026-10-01); пункты 5–6 изменены 2026-10-08
**Дата:** 2026-10-01
**Зависит от:** ADR-0008 (базовая безопасность), ADR-0020 (схема и миграции),
ADR-0024 (оптимистичная блокировка); план 10/10, пункт 4.6

---

## 1. Контекст

Два вида секретов сервер хранит в базе и должен читать обратно, поэтому хеш
им не подходит:

| Колонка | Что это | Кто читает |
|---|---|---|
| `kwh_subscriptions.secret_token` | ключ подписи вебхука (HMAC-SHA256) | `WebhookOutboxWorker` при каждой доставке |
| `md_sso_providers.client_secret` | секрет клиента у провайдера SSO | обмен кода SSO (сейчас выключен, V018) |

Оба лежали открытым текстом. Резервная копия, реплика, выгрузка `pg_dump` или
доступ на чтение к базе отдавали их целиком: с ключом подписи можно подделать
вебхук, с секретом клиента — представиться установкой у провайдера SSO.
Пароли, токены сессий и API-токенов уже хранятся только хешем (Argon2id,
SHA-256) и сюда не относятся.

## 2. Решение

1. **AES-256-GCM средствами JDK**, без новой зависимости:
   `common.crypto.SecretCipher` в `libs/platform-common`. На каждое значение —
   свой случайный 96-битный nonce; тег 128 бит. Контекст `таблица.колонка`
   идёт в associated data: значение, перенесённое в другую колонку, не
   расшифровывается.
2. **Формат хранения:** `v1:` + base64(`nonce | шифротекст | тег`). Префикс
   версии отличает зашифрованное значение от старого открытого и оставляет
   место для смены ключа (`v2:` — следующее поколение ключа).
3. **Ключ — из окружения** `SMC_SECRETS_KEY` (свойство `smc.secrets.key`):
   base64 от 32 байт, `openssl rand -base64 32`; скрипты
   `init-production-env.*` создают его сами. Правила старта
   (`StoredSecrets.fromConfiguration`):
   - профиль `dev` без ключа берёт фиксированный ключ разработки (выводится
     из строки-затравки, в конфигурации его нет);
   - любой другой профиль без ключа, с ключом не той длины или с ключом
     разработки не стартует, сообщение называет переменную и не повторяет
     значение;
   - профиль `migrate` стартует без ключа: миграции секретов не касаются.
4. **Шифрует и расшифровывает репозиторий** — владелец таблицы
   (`WebhookSubscriptionRepository`, `WebhookOutboxRepository`,
   `SsoProviderRepository`). Остальной код видит открытое значение: вебхук
   подписывается прежним ключом, подпись у получателя не меняется.
5. **Открытое значение не принимается** (изменено 2026-10-08). До
   финального релиза установок у клиентов нет (решение владельца продукта
   2026-10-01), поэтому шифровать старые открытые значения при старте не
   нужно: шаг `StoredSecretsSealing` удалён. Колонку с секретом репозиторий
   объявляет через `StoredSecretColumn`; `StoredSecretsCheck`
   (`ApplicationRunner`, все профили, кроме `migrate`) на каждом старте:
   - расшифровывает одно уже зашифрованное значение каждой колонки и
     отказывает в старте, если текущий ключ его не открывает (ключ сменили
     или потеряли);
   - считает значения без префикса `v1:` и отказывает в старте, если они
     есть; сообщение называет таблицу и колонку и число значений, но не сами
     значения.

   Единственные открытые значения в схеме — заглушки `'secret'` у
   демонстрационных провайдеров SSO из V017; миграция V203 их очищает
   (`client_secret = null`), настоящий секрет администратор задаёт через
   приложение. Стенды разработки пересоздаются
   (`scripts/dev/run-local.ps1 down -Volumes`).
6. **Чтение.** `StoredSecrets.open` отдаёт `null` как `null`, а значение без
   префикса и значение с префиксом, которое не расшифровывается, —
   ошибка (`IllegalStateException`, ответ 500, сообщение называет колонку),
   а не тихая подмена.

## 3. Проверка

- `SecretCipherTest`: шифрование и расшифровка, свежий nonce, подмена байта,
  чужой ключ, чужая колонка, битые значения, формат ключа.
- `StoredSecretsTest`: правила ключа для `dev`, `migrate` и остальных
  профилей.
- `StoredSecretsSchemaTest` на базе со всеми миграциями: каждая колонка с
  именем вида `*secret*`, `*token*`, `*password*`, `*api_key*` либо
  зашифрована, либо хеш, либо явно не секрет (список с причинами); после
  миграций и записи через репозиторий в зашифрованных колонках только
  значения с `v1:`, заглушки SSO очищены; открытое значение останавливает
  старт и его чтение, сообщение называет колонку и не содержит значения;
  старт с чужим ключом отказывается.
- `scripts/prod/test-release-config.ps1`: продовый Compose требует
  `SMC_SECRETS_KEY` (`${SMC_SECRETS_KEY:?…}`).

## 4. Последствия

- **Ключ — часть резервной копии.** База, восстановленная без своего ключа,
  теряет ключи подписи вебхуков и секреты SSO: сервер не стартует, пока ключ
  не вернут. Ключ хранится вне хоста, рядом с age-идентичностью бэкапов.
- **Смена ключа** пока не автоматизирована: формат её допускает (`v2:` и
  перешифровка при старте со старым и новым ключом), процедура — отдельная
  задача. До неё ключ меняют только вместе с перевыпуском секретов: новые
  подписки вебхуков и новый секрет клиента SSO.
- **Скользящее обновление.** Узел старой версии читает зашифрованное значение
  как ключ и подписывает вебхук неверно. Продовый Compose запускает один узел
  сервера, поэтому окна нет; несколько узлов обновляют целиком, а не по
  одному.
- Новая колонка с секретом подключается так же: репозиторий шифрует при
  записи, расшифровывает при чтении и объявляет `StoredSecretColumn`; иначе
  `StoredSecretsSchemaTest` падает на неклассифицированной колонке.
