## 4. Дефекты

### Д-1. Дедупликация файлов отдаёт чужую запись и обходит квоту

`MfFileService.upload()` при совпадении SHA-256 возвращает **существующую строку**,
принадлежащую первому загрузившему:

```java
var existingOpt = fileRepository.findBySha256(stored.sha256());
if (existingOpt.isPresent()) {
    storageProvider.delete(DEFAULT_BUCKET, tempKey);
    return existingOpt.get();          // строка другого пользователя
}
```

`mf_files.sha256` объявлен `unique`, второй строки появиться не может, а расход
считается как `sum(size_bytes) where created_by = :userId`.

**Сценарий отказа.** Пользователь A загружает договор и прикрепляет к задаче T1.
Пользователь B загружает тот же файл — получает запись A, его квота не растёт.
B прикрепляет её к своей задаче T2. A удаляет файл у себя в хранилище: проверка
владения проходит (A — владелец), строка удаляется, и `on delete cascade` в
`ms_task_files` и `ms_task_comment_files` **молча сносит вложение и у T2**.
Физический объект тоже удаляется. B не получает ни ошибки, ни предупреждения.

Каскады подтверждены на живой БД:

```
ms_task_comment_files -> mf_files on delete CASCADE
ms_task_files         -> mf_files on delete CASCADE
```

Побочно: B видит `original_name`, заданное пользователем A.

Сейчас дефект не проявился только потому, что все 22 файла в стенде загружены
одной учётной записью.

### Д-2. Защита от удаления физического файла не работает

```java
fileRepository.delete(id);
if (fileRepository.findBySha256(file.sha256()).isEmpty()) {
    storageProvider.delete(file.storageBucket(), file.storageKey());
}
```

Проверка написана так, будто несколько строк могут делить один SHA-256, но
`unique` это запрещает. После удаления единственной строки условие **всегда**
истинно, и файл с диска сносится безусловно. Ветка мёртвая: намерение кода
противоречит схеме.

### Д-3. Гонка при одновременной загрузке одинакового содержимого

Между `findBySha256` и `create` нет блокировки. Два параллельных запроса с
одинаковым содержимым оба не находят дубликат, второй падает на нарушении
`unique` — пользователь получает 500 вместо дедупликации.

### Д-4. Партиции `audit_log` заканчиваются 30 сентября 2026

В живой БД существуют ровно три партиции: `audit_log_2026_08`, `audit_log_2026_09`
и `audit_log_default`. Автосоздания нет — ни воркера, ни `pg_partman`, ни `pg_cron`.

**С 1 октября 2026** все записи аудита пойдут в `audit_log_default`. Это ломает
FR-AUD-2 (retention 12 месяцев с отцеплением партиций): отцепить `default` нельзя.
Хуже того, создать партицию за октябрь задним числом уже не выйдет — PostgreSQL
при `create table ... partition of` сканирует default-партицию и откажет, пока в
ней есть подходящие строки; переносить придётся вручную под `access exclusive`.

Срок — около месяца.

### Д-5. FR-PERM-1 выполнен наполовину

Каталог форм теперь регистрируется из кода при старте — но это **написанный
руками список** в `MdPermissionService`: 5 форм и 21 действие. Остальные 10 форм
по-прежнему приезжают миграциями V002/V003/V009. Аннотации `@RequiresPermission`
читает только интерцептор доступа; никто не сверяет их с каталогом.

Требование ТЗ («регистрируется из кода по `@RequiresPermission`, исчезнувшие
формы помечаются устаревшими») закрыто частично: **пометки устаревших нет
совсем**, расхождение аннотации и списка не обнаруживается.

### Д-7. Аудитор не может сменить собственный пароль

Найдено при закрытии разд. 3. Роль `auditor` имеет на форме `iam.profile`
единственное действие `view`:

```
auditor | iam.profile:view
admin   | iam.profile: manage_channels, manage_tokens, update, view
manager | iam.profile: manage_channels, manage_tokens, update, view
user    | iam.profile: manage_channels, manage_tokens, update, view
```

Смена пароля (`POST /api/v1/iam/users/me/password`) требует `iam.profile:update`.
Значит аудитор **не может сменить пароль, язык и часовой пояс**. Если такую
учётную запись завести с `force_password_change = true`, она блокируется
навсегда: система требует сменить пароль и сама же это запрещает.

Причина — противоречие внутри ТЗ-01 разд. 4.4.1. Строка матрицы даёт аудитору
«✔ всё» на профиль и свои каналы, а правило под матрицей гласит: «auditor не
имеет ни одного мутирующего действия — это его определение». Реализация выбрала
правило, и оно закреплено тестом `auditorHasNoMutatingPermissions`.

Побочно: действие `iam.profile:change_password` регистрируется в каталоге, но не
выдано ни одной роли и не используется ни одним эндпоинтом — мёртвая запись,
которая при этом видна администратору в матрице прав как настраиваемая.

**Требуется решение CEO.** Варианты:

| | Что делаем | Плюс | Минус |
|---|---|---|---|
| а | Аудитор получает `update`, `change_password`, `manage_channels` (без `manage_tokens` — их ТЗ ему не даёт) | Соответствует строке матрицы | Придётся смягчить тест: «без мутаций» станет «без мутаций над данными экземпляра» |
| б | Смена своего пароля выводится из матрицы форм в контур аутентификации, как вход и выход | Устраняет противоречие в корне: смена своего пароля — аутентификация, а не бизнес-форма | Профиль (язык, пояс) аудитору по-прежнему недоступен |
| в | Оставить как есть, запретить `force_password_change` для аудитора | Ничего не меняем | Хрупко: любой сценарий смены пароля упирается в тот же тупик |

Рекомендация: **вариант б** — он снимает противоречие, не размывая определение
роли, и попутно объясняет, почему контур входа уже вынесен из матрицы.

### Д-8. Рабочий пароль стенда закоммичен и запушен (FR-SEC-3)

Найдено при закрытии Д-1: `git add` подхватил чужие незакоммиченные правки
`.env.prod.example`, где плейсхолдеры были заменены настоящим паролем.

Проверка истории показала, что это не единичный случай: в коммите `61bd887`
(29.08.2026 16:49) в `.env.example` плейсхолдеры `DevOnly-ChangeMe-1` и
`CpDevOnly-ChangeMe-1` заменены **действующим паролем администратора стенда**,
и он же прописан значением по умолчанию в `scripts/dev/test-api.ps1`. Оба файла
отслеживаются, коммит входит в `origin/main`.

Устранено на будущее (`2f225d7`): плейсхолдеры возвращены, скрипт e2e без
`ADMIN_PASSWORD` в окружении останавливается с подсказкой вместо подстановки
значения по умолчанию. Локальный `.env` не тронут — он в `.gitignore`.

**Остаётся решить CEO.** Пароль уже в опубликованной истории, поэтому:

1. **Сменить пароль** — обязательно и независимо от всего остального.
2. Вычистка истории (`git filter-repo` + принудительный push) переписывает
   опубликованную ветку. Делать только осознанно.
3. gitleaks в CI это не поймал: его правила рассчитаны на ключи API, а не на
   присваивание пароля в `.env.example`. Стоит добавить собственное правило —
   значение `*_PASSWORD` в отслеживаемом файле, не начинающееся с `CHANGE_ME`
   или `DevOnly`.

### Д-9. Неподдерживаемый HTTP-метод отдаёт 500 вместо 405

`GlobalExceptionHandler` не обрабатывает `HttpRequestMethodNotSupportedException`,
и она проваливается в общий обработчик:

```
POST /api/v1/files  ->  500 {"code":"internal_error"}
```

Правильный ответ — `405 Method Not Allowed`. Тот же класс дефекта, что был у
`HttpMessageNotReadableException` (некорректный JSON отдавал 500 вместо 400):
клиентская ошибка выдаётся за серверную, а в журнал пишется `Unhandled exception`,
маскируя настоящие сбои. Относится к M10, чинится тремя строками в обработчике.

Часть M-требований физически не может быть закрыта без инфраструктуры фазы P,

## 6. Общая оценка

Объём и темп работы высокие, качество отдельных решений хорошее: инварианты
задачника через рекурсивный CTE, идемпотентность с кэшем ответов, ArchUnit,
двухуровневый поиск с откатом. Аудит из декорации стал рабочим механизмом.

Проблема не в коде, а в приёмке. «100% completed with comprehensive verification»
написано при красной сборке, непрогнанном модуле и требованиях, которые не могут
быть выполнены имеющейся инфраструктурой. Это ровно то расхождение отчётности с
фактом, ради устранения которого затевался помодульный пересмотр.

Правило приёмки, которое стоит применять дальше: **веха закрывается только при
зелёном полном прогоне и только по тем требованиям, чья инфраструктура уже
есть**; остальное честно помечается «ждёт фазу P».
