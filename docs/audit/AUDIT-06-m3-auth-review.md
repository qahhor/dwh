## 2. Дефекты

### Д-10. Одноразовый код никуда не отправлялся

`KauthAuthService.login()` при включённой 2FA создавал код в базе и сразу возвращал токен:

```java
otpCodeRepository.create(user.id(), "telegram", codeHash, Instant.now().plusSeconds(300));
return LoginResult.requires2fa(otpToken, user.id());
```

Между созданием и возвратом нет ни одного обращения к провайдеру. Код существовал только
в виде SHA-256 в таблице, то есть **узнать его было неоткуда никому**, включая самого
пользователя. Вход по второму фактору был неработоспособен целиком.

Не всплывало это по двум причинам: 2FA не была включена ни у одной учётной записи, и до
30.08 у экземпляра вообще не было рабочего канала доставки (см. работу по FR-NOTIF-3/4).

Побочно: канал был захардкожен строкой `"telegram"`, тогда как ТЗ требует выбор канала
пользователем.

### Д-11. Токен второго фактора не был связан ни с чем

```java
private Long extractUserIdFromOtpToken(String otpToken) {
    if (otpToken == null || otpToken.isBlank()) { throw ...; }
    return 1L;
}
```

Токен, выданный на первом шаге входа, не проверялся: метод возвращал **захардкоженный
идентификатор 1** — учётную запись администратора, которую создаёт `InstanceBootstrap`.

Последствия, оба плохие:

1. **Настоящий пользователь со включённой 2FA не мог войти никогда** — его код искали
   среди кодов администратора.
2. **Обратное направление опаснее.** Если у администратора существовал активный код
   (то есть у него была включена 2FA и он входил), то любой непустой `otp_token` вместе с
   угаданным шестизначным кодом открывал **сессию администратора**. Три попытки на код,
   но запросить новый первый шаг никто не мешал.

Реализовать вход с 2FA до этой правки было невозможно, поэтому в проде дефект не
проявился бы — он проявился бы ровно в момент, когда 2FA включили.

### Д-12. Каналами связи нельзя было управлять

Таблица `kauth_user_channels` существует с V001, `KauthChannelRepository` написан, право
`iam.profile:manage_channels` числится в матрице — но **эндпоинта не было ни одного**.
Привязать канал было нечем, поэтому и отправлять код было некуда.

Синхронизация каталога форм с кодом (Д-5, 30.08) как раз и пометила это право устаревшим —
механизм сработал ровно на том, ради чего вводился.

## 3. Что сделано

- **V015**: `kauth_otp_codes.otp_token_hash` (уникальный частичный индекс) и `purpose`
  (`login` / `channel_verify`). Коды, выпущенные до миграции, помечены использованными:
  они не привязаны к токену и найти их правильным способом нельзя.
- **Проверка кода ищет его только по хешу выданного токена.** `extractUserIdFromOtpToken`
  удалён; идентификатор пользователя берётся из найденной строки.
- **`KauthOtpSender`**: код действительно уходит в канал — messenger, SMS или почта в
  зависимости от канала. Отправка синхронная: код живёт пять минут, очередь с повторами
  здесь работает против пользователя. Провал доставки — отказ входа, а не «доставим позже»:
  иначе клиент получает токен, которым невозможно воспользоваться.
- **`KauthChannelService` + `KauthChannelController`** (`iam.profile:manage_channels`):
  привязка, подтверждение владения кодом, список, отвязка. Неподтверждённый канал для
  второго фактора не используется — иначе опечатка в адресе означала бы отправку кода
  входа постороннему.
- **Нет подтверждённого канала — вход отклоняется** с `409 otp_channel_missing`, и код
  при этом не выпускается.
- Отправка кода пишется в `security_events` как `OTP_SENT` (канал, без адреса).

## 4. Проверка

- **149 тестов, `BUILD SUCCESS`.** Новый `KauthOtpLoginIntegrationTest` (7 сценариев):
  код доставлен в канал; свой токен и свой код открывают свою сессию; чужой код по своему
  токену не подходит; выдуманный токен отклонён (регрессия на `return 1L`); без
  подтверждённого канала вход отклонён и код не выпущен; канал становится подтверждённым
  только после верного кода.
- **Живой прогон на стенде: 11 из 11.** Сквозной путь: привязка канала → код доставлен →
  подтверждение → включение 2FA → вход возвращает `step=otp` → код доставлен → выдуманный
  токен отклонён (401) → настоящий открыл сессию **того самого** пользователя.
