## 3. Дефекты, найденные этим аудитом (все исправлены)

Живая проверка окупилась немедленно — четыре реальных дефекта:

| # | Дефект | Почему важно | Статус |
|---|---|---|---|
| A | **Control plane мигрировал схему при старте** — R4 применили только к instance | Регресс блокера A-4 на втором приложении: нет пути отката | ✅ паритет: `flyway.enabled=false`, профиль `migrate`, `CpSchemaVersionGate` |
| Б | **`/actuator/prometheus` не существовал** — объявлен в конфиге, registry не подключён | Весь мониторинг был бы фикцией: конфиг обещает метрики, эндпоинт 404 | ✅ registry добавлен, 73 метрики отдаются |
| В | **Контейнер падал при старте**: `LocalStorageProvider` пытался создать `./data/storage` в `/app` под non-root → `AccessDeniedException` | Предметное доказательство блокера C-3: файлы на диске узла ещё и несовместимы с контейнером | ⚠️ обойдено томом `/var/lib/dwh` + `VOLUME`; **настоящее решение — Garage (фаза P)** |
| Г | **`.env.example` попадал под `.gitignore`** (`.env.*`) — шаблон конфигурации не доехал бы до команды | Развёртывание без шаблона = угадывание переменных | ✅ исключение в `.gitignore` |

Дополнительно зафиксировано (не дефект, а расхождение отчётности с фактом):
**control-plane — скелет** (один класс `ControlPlaneApplication` + миграция), тогда
как `stage-1-completion.md` заявлял «управление арендаторами, лицензиями и
heartbeat-мониторингом». Реестр, heartbeat, лицензии и объявления (FR-CP-1…8) —
не реализованы. Это фаза F.

## 4. Оставшиеся блокеры коммерческого запуска

| # | Блокер | Почему блокер | Закрывается |
|---|---|---|---|
| **C-3** | Файлы клиентов на диске узла, не в S3 | Потеря узла = потеря файлов; бэкап их не покрывает | Garage-адаптер `StorageProvider` (код — можно сейчас; хранилище — фаза P) |
| **C-7** | Секреты в `.env`, не в Vault | Нет ротации, нет аудита доступа, лежат в открытом виде на узле | Vault (фаза P, нужен стенд) |
| **C-8** | Нет SSE | FR-NOTIF-2 (must): уведомления не приходят без перезагрузки страницы | Фаза F (инфраструктура не нужна) |
| **C-9** | Нет OpenAPI из кода | FR-API-1 (must); заявлен в DoD CONTRIBUTING | Фаза F |
| **C-10** | Email/SMS — заглушки в лог | Восстановление пароля и OTP по email/SMS не работают | Фаза F (+ договор с провайдером) |
| **C-11** | Нет оркестрации, централизованных логов, автопроверки бэкапов | Эксплуатация 30–100 экземпляров вручную; непроверенный бэкап = отсутствующий | Фаза P (нужен стенд из 4 узлов) |

Дополнительно к NFR-7: текущие бэкапы дают **RPO ≈ 24 часа** вместо заявленных
15 минут (нет WAL-архива) и не шифруются. Это допустимо для пилота при письменном
информировании клиента и недопустимо для SLA.

## 5. Ответ на пункты технического задания аудита

| Запрошено | Статус | Комментарий |
|---|---|---|
| Валидация архитектуры HA/DR | ⚠️ частично | Схема и тарифы доступности спроектированы (ADR-0010), но HA не развёрнут: один узел, failover нет. Требует стенда |
| CI/CD на соответствие production | ✅ | Три обязательных джоба, зелёный прогон; **но** нет автоматической публикации образов в registry и авто-деплоя — добавляется вместе с флотом (фаза P) |
| Управление секретами | ⚠️ частично | Обязательные переменные без умолчаний, `.env` 600, gitleaks в CI. Encryption at rest секретов и ротация — Vault, фаза P |
| Мониторинг/логи/алерты | ⚠️ частично | Метрики реально отдаются (73 шт., изолированный порт), health-пробы работают. Централизованного сбора и алертов нет (фаза P) |
| Элиминация dev-артефактов | ✅ | Выполнено в AUDIT-03 (`test-api.ps1` → `scripts/dev/`, println, `.mvn`, DEMO-seed) + сейчас `.dockerignore` |
| 12-factor | ✅ в основном | Конфиг из окружения, stateless-процесс, логи в stdout, graceful shutdown, dev/prod-паритет через один образ. Отступление: файлы на локальном диске (C-3) |
| Оптимизация Docker-образа | ✅ | Multi-stage, non-root, кэш слоёв, минимум пакетов, JVM по cgroup. 558 МБ — базовый JRE; alpine **сознательно не берём**: `argon2-jvm` тянет native-библиотеки под glibc, риск отказа хеширования паролей в musl |
| Health/liveness/readiness | ✅ | Проверено запуском |
| Backup-стратегия | ⚠️ частично | Автоматический ежесуточный дамп + retention есть; WAL, шифрование, автопроверка — фаза P. Ручная процедура проверки описана |
| **Helm charts** | ❌ не делаем | Противоречит ADR-0007: оркестратор — **Nomad**, не Kubernetes. Helm потребовал бы K8s-кластера, отвергнутого решением CEO. Эквивалент — Nomad job-файлы (`deploy/spike/nomad/`), боевые появятся в фазе P |
| **Ansible playbooks** | ❌ не сейчас | Писать непроверяемый на стенде playbook — создавать иллюзию автоматизации. Разворачивается вместе с Nomad-контуром в фазе P, где его можно прогнать |
| Zero-touch deployment | ❌ не сейчас | Требует registry + оркестратора + секретницы. Сейчас развёртывание скриптовано документально, но не автоматизировано |
| Операционная документация | ✅ | 5 документов + 4 runbook'а + checklist |

## 7. Рекомендации по приоритетам

1. **Стенд из 4 узлов** — единственный настоящий блокер прогресса. Без него
   фаза P не стартует, а без фазы P коммерческий запуск невозможен.
2. Пока стенда нет — **фаза F без инфраструктуры**: Garage-адаптер (готовит C-3),
   SSE (C-8), OpenAPI (C-9). Проверяются Testcontainers, стенд не требуется.
3. **Не выпускать `latest`** — тег версии обязателен (заложено в `.env.example`).
4. Перед первой коммерческой поставкой — внешний пентест (FR-SEC-8) и
   учебная тревога по [rollback.md](../ops/rollback.md) разд. 5.
