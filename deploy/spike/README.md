# Спайк-неделя S-0: гайд (31.08 – 04.09.2026)

**Цель:** подтвердить или опровергнуть связку «Nomad job клиента → batch-миграция Flyway →
canary-обновление с авто-откатом» (ADR-0007). Пятница — go/no-go с CEO (T-003).

**Состав стенда:** 3 малых узла платформы (`p1,p2,p3`) + 1 клиентский (`c1`).
**Версии:** Nomad и Vault — текущие stable (на 2026-08: Nomad 1.10.x, Vault 1.20.x);
PostgreSQL 18, Flyway 11 — образы из ADR-0002.

**Упрощения спайка (осознанные, не для прода):**
- Consul НЕ ставим — service discovery нативный Nomad'а (`provider = "nomad"`).
  Consul — в T-020. На вопрос go/no-go он не влияет.
- ACL Nomad выключены (включаются в T-020).
- Один клиентский узел, один демо-«клиент».
- V3-миграция намеренно нарушает правило линтера (`NOT NULL` на заполненной таблице) —
  так и задумано, это учение.

## День 1 (пн) — T-001: кластер

1. На `p1..p3`: установить nomad + vault (пакеты HashiCorp), развернуть конфиги:
   - `nomad/server.hcl` (поправить IP в `retry_join`)
   - vault: raft-кластер из трёх, `vault operator init` (5 ключей, кворум 3),
     unseal всех узлов, ключи — в физически защищённое место (пока не в сам Vault :)
2. На `c1`: nomad-агент с `nomad/client.hcl` + Docker; создать каталог host volume:
   `mkdir -p /opt/pgdata-demo`.
3. Интеграция Nomad↔Vault — workload identity (JWT): см. `vault/setup.sh`, шаг A.
   Синтаксис сверить с документацией установленных версий — этот механизм менялся.

**Критерий дня:** `scripts/01-check-cluster.sh` зелёный
(3 alive-сервера Nomad, Vault unsealed, тестовый job запускается).

## День 2 (вт) — секреты и первый деплой

1. `vault/setup.sh` шаги B–C: KV v2, секрет `kv/instances/demo/pg`, политика.
2. `scripts/02-deploy-client.sh` — поднимает job `client-demo` (PostgreSQL + приложение-заглушка v1).
3. `scripts/03-migrate.sh 1` — batch-job Flyway до версии схемы 1.
4. Перезапустить app-группу — заглушка стартует (schema-gate пропускает: схема = ожидаемой).

**Критерий дня:** `curl http://<c1>:<port>` отвечает `demo app v1 schema=1`;
пароль PG нигде на диске узла в открытом виде (проверить alloc-каталоги).

## День 3 (ср) — штатное обновление (замер!)

Сценарий «релиз v2»: expand-миграция + canary.

1. `scripts/03-migrate.sh 2` — миграция V2 (expand: nullable-колонка). **Секундомер.**
2. `scripts/04-canary-update.sh 2` — canary v2 рядом с v1, health-check, ручной promote. **Секундомер.**
3. Повторить цикл 2–3 раза до уверенности; записать тайминги в таблицу ниже.

**Критерий дня:** обновление v1→v2 без единой ошибки на клиенте; старый alloc жил, пока canary не стал healthy.

## День 4 (чт) — учения по отказам (главный день спайка)

1. **Ломаная миграция:** `scripts/05-drill-broken.sh` часть 1 —
   миграция V3 падает (NOT NULL на заполненной таблице) → скрипт получает ненулевой код,
   деплой v3 НЕ начинается. Ожидание: БД осталась на версии 2, flyway-история чистая
   (failed-запись — проверить поведение и записать в отчёт: это важно для T-022).
2. **Несовпадение схемы:** часть 2 — принудительный деплой app v3
   (ожидает схему 3, а в БД — 2) → schema-gate валит alloc → deployment unhealthy →
   **auto_revert возвращает v2 сам**. Замер времени до отката.
3. Хаос-мини: `docker kill` контейнера PG → Nomad перезапускает таск, gate защищает app.

**Критерий дня:** оба сценария воспроизводимы скриптом; после каждого система в рабочем
состоянии v2 без ручной починки.
